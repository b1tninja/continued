# Agent interop surfaces: which to support, and the first slice (`continuous acp`)

Last updated: 2026-11-10. Status: research and a first slice built; target 2.6 (Track O). This document sits beside [`agent-interop.md`](./agent-interop.md), which covers sessions that message and start each other. This one covers the protocols between our agent and everything else: which are worth supporting for a local-first fork, in what order, and what the first slice does.

Sources were fetched on 2026-11-10. Anything that came from a secondary source only (blogs, aggregator pages) is in the list of unverified claims at the end and is marked there.

## Decision

1. **Build ACP server mode first** (`continuous acp`). It is the one surface that opens the CLI to editors we do not ship (the U11 requests in [`upstream-signals.md`](./upstream-signals.md): Neovim, Eclipse, Sublime, Visual Studio-class asks), costs one stdio loop over code the CLI already has, and needs no network, account or hosted service. The first slice is built (below).
2. **Keep MCP as the tool and context surface, not an agent surface.** We already consume MCP servers. The agent-relevant additions are elicitation (a server asks the person) and, later, exposing a session as an MCP task-style tool. Do not build MCP sampling: the 2026-07-28 revision deprecates it (see unverified list).
3. **Consume other agents as subagents through ACP-client mode later, not now.** The same protocol runs the other way (we spawn Claude Code, Codex CLI or Gemini CLI as ACP agents and use them as subagents). It is more work than serving (the client owns terminals, file reads and permission UI) and it competes with our own subagent tool; do it only if a user has a concrete need to delegate to a vendor agent.
4. **Do not build A2A.** It is a network protocol for agents that are services (agent cards, HTTP/JSON-RPC/gRPC, authentication between organisations). A local-first fork has no service to describe and no peer to call. Revisit only if Track O's session messaging grows a remote form.
5. **VS Code: stay on the stable APIs.** Chat participant and language-model provider are what we ship (`extensions/vscode/src/ai/`). The Agents-window integration depends on proposed APIs that change between releases; track it, do not build on it for a release.

Why ACP over the alternatives, in one line each: ACP is editor-to-agent over stdio and is what the registry-driven editors speak; A2A is agent-to-agent over HTTP between services; MCP is agent-to-tool; the VS Code APIs are one editor.

## Agent Client Protocol (ACP)

**State.** The protocol is open source (Apache-2.0) under `agentclientprotocol` on GitHub, and its repository states that the current stable protocol version is `1` ([repo](https://github.com/agentclientprotocol/agent-client-protocol), fetched 2026-11-10). Local agents run as subprocesses of the editor and speak JSON-RPC over stdio; remote support over HTTP or WebSocket is described as a work in progress ([introduction](https://agentclientprotocol.com/overview/introduction)). Newer schema items appear in the documentation without a version bump (a `notice` update, `compaction_update`, `usage_update`, session `delete`, `additionalDirectories`, `systemPrompt` capabilities); treat everything beyond the baseline listed below as optional and unstable.

**SDKs.** TypeScript (`@agentclientprotocol/sdk`), Rust (`agent-client-protocol` and the `agent-client-protocol-schema` types crate), Python (`python-sdk`), Kotlin (`acp-kotlin`, JVM) and Java (`java-sdk`) are listed on the repository page. The first slice does not use the TypeScript SDK: the stdio framing is newline-delimited JSON-RPC and the slice needs five methods, so a 150-line peer (`extensions/cli/src/acp/rpc.ts`) avoids a dependency whose release cadence we have not measured. Revisit when the method count grows past what the tests can pin by hand (session loading, terminals).

**Who supports it (clients).** Zed (native, and the originator) and JetBrains IDEs (native; the registry was announced jointly on 2026-01-28 and is built into both) ([Zed blog](https://zed.dev/blog/acp-registry), [JetBrains](https://blog.jetbrains.com/ai/2026/01/acp-agent-registry/), the latter not fetchable here, reached through a search summary). Neovim (CodeCompanion, avante.nvim) and Emacs (agent-shell) through plugins; VS Code only through community extensions (for example `formulahendry/vscode-acp`): no source found says Microsoft ships native support, one July 2026 source suggests otherwise and is unconfirmed. A June 2026 source says Microsoft's experimental Intelligent Terminal has an ACP agent pane. All of this is from search summaries and should be re-checked before it appears in user-facing docs.

**Who supports it (agents).** The Zed registry post lists Claude Code, Codex CLI, GitHub Copilot CLI, OpenCode and Gemini CLI. One secondary source says 50 agents by June 2026 and that Cursor joined the registry in March 2026. Our own roadmap row E5 and the Cline comparison in `upstream-signals.md` (U11) point the same way.

**How a CLI agent becomes an ACP server.** The editor starts the command as a subprocess and writes newline-delimited JSON-RPC 2.0 to its stdin; the agent answers on stdout. stdout is the protocol and nothing else, so everything that would print (logs, a stray `console.log`) must go to stderr. The registry distributes agents by a pull request adding an entry (the post does not say how the command is installed; unverified). Our entry point is `continuous acp`.

**Methods (from the protocol pages, v1).**

| Side           | Baseline                                                                                     | Optional                                                                                                                                                             |
| -------------- | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Agent methods  | `initialize`, `authenticate`, `session/new`, `session/prompt`; notification `session/cancel` | `session/load`, `logout`, `session/set_mode`                                                                                                                         |
| Client methods | `session/request_permission`; notification `session/update`                                  | `fs/read_text_file`, `fs/write_text_file`, `terminal/create`, `terminal/output`, `terminal/release`, `terminal/wait_for_exit`, `terminal/kill`, `elicitation/create` |

- **initialize.** The client sends `protocolVersion` (integer) and `clientCapabilities` (`fs.readTextFile`, `fs.writeTextFile`, `terminal`, and newer ones); the agent answers with its version, `agentCapabilities` (`loadSession`, `promptCapabilities` for image, audio and embedded context, `mcpCapabilities` for http and sse), `agentInfo` and `authMethods`. All capabilities are optional; agents must accept `text` and `resource_link` content regardless.
- **session/new.** `cwd` (must be absolute) and `mcpServers` (stdio mandatory, http and sse only if advertised). Returns `sessionId`.
- **session/prompt.** `sessionId` and a `ContentBlock[]`; result `stopReason` of `end_turn`, `max_tokens`, `max_turn_requests`, `refusal` or `cancelled`. Between request and result the agent streams `session/update` notifications: `agent_message_chunk`, `agent_thought_chunk`, `plan`, `tool_call`, `tool_call_update` and others.
- **Tool calls.** `tool_call` needs `toolCallId` and `title`; optional `kind` (`read`, `edit`, `delete`, `move`, `search`, `execute`, `think`, `fetch`, `switch_mode`, `other`), `status` (`pending`, `in_progress`, `completed`, `failed`), `content` (text, `diff` with `oldText` and `newText`, or `terminal`), `locations` (absolute `path`, optional `line`), `rawInput`, `rawOutput`. `tool_call_update` repeats the id with the changed fields.
- **Permissions.** The agent sends `session/request_permission` with the tool call and `options`, each with `optionId`, `name` and a `kind` of `allow_once`, `allow_always`, `reject_once` or `reject_always`. The reply is `{outcome: "selected", optionId}` or `{outcome: "cancelled"}`; the client must answer pending requests as cancelled when the turn is cancelled.
- **Cancellation.** The client sends `session/cancel`; the agent stops model and tool work and must still answer the original `session/prompt` with `stopReason: "cancelled"`, not an error.
- **Session loading.** Only when `loadSession` is advertised: the client calls `session/load` with `sessionId`, `cwd`, `mcpServers`; the agent replays the conversation as `session/update` notifications and then answers. `session/list` was not found on the pages read (unverified whether it is a stable method).
- **Auth.** `authenticate` against an advertised method; `authMethods` may be empty. For a local-first CLI that reads its own configuration and credentials, empty is correct and keeps secrets out of the editor.
- **File system and terminals.** Client-side: the editor reads and writes text files (so unsaved buffers are seen) and runs terminals. They exist so an agent can use the editor's state instead of the disk; an agent may ignore them and use its own tools.

**What the first slice does and does not map.** Built: `initialize`, `session/new`, `session/prompt`, `session/cancel`, `session/update` (message chunks, tool calls, tool results) and `session/request_permission`. Not built, with the reason: `session/load` (the CLI's session store is a process-wide singleton; replay needs per-session history first), `fs/*` and `terminal/*` (our tools use the disk and a shell directly; mapping them is what makes unsaved buffers visible, and is the largest follow-up), `session/set_mode` (modes are chat, agent and plan in the CLI; the mapping needs a decision on how Plan's file-based plan appears as `plan` updates), `plan` and `agent_thought_chunk` updates (the CLI's callbacks do not expose them separately), image and audio prompts, client-supplied `mcpServers`, `authenticate`. A prompt with content the agent did not advertise is refused as invalid params, not dropped.

**Fail closed.** The CLI's policy engine decides whether a call runs, asks, or is refused; headless runs refuse an ask because nobody can answer. `continuous acp` starts the services non-headless and sets the permission callback, so an ask becomes `session/request_permission`. The reply is an allow only if the client selected exactly the allow option we offered. A cancelled outcome, an error, a malformed reply, a different option id, a closed connection, a cancelled turn and the end of the turn are all a refusal. We offer only `allow_once` and `reject_once`: `allow_always` would be a request to write policy, which belongs in the person's settings, not in an editor popup. A client without a usable permission reply therefore cannot run anything the policy asks about.

## A2A (Agent2Agent)

A2A 1.0 is the first stable specification (Linux Foundation press release on the first anniversary, reported 2026-04-09: 150-plus supporting organisations, available on Bedrock AgentCore and Azure AI Foundry per summaries; later reports place it as a hosted project of the Agentic AI Foundation in August 2026, unconfirmed) ([Linux Foundation](https://linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year)). Objects are agent cards, tasks, messages and artifacts; task states include `INPUT_REQUIRED`; methods are SendMessage, GetTask, ListTasks, CancelTask and SubscribeToTask; a `contextId` groups tasks ([spec](https://a2a-protocol.org/latest/specification/), as recorded in `agent-interop.md` on 2026-11-07). The 150 figure counts supporters, not deployments.

For us it is the wrong shape: it assumes an addressable service with a card and authentication between organisations. Its task states are, however, the vocabulary `agent-interop.md` already adopts for session handles (working, input_required, completed, failed, cancelled), which is as far as it needs to reach us.

## MCP features relevant to agents

Current spec per a secondary source: 2026-07-28 (the cdata.com explainer; the official page `modelcontextprotocol.io/specification/2026-07-28` was not fetched, so this is unverified). Claims to check before relying on them:

- **Elicitation** is the only server-to-client request that stays active; roots and sampling are deprecated, with removal no earlier than the first revision on or after 2027-07-28; servers must use the "multi round-trip" pattern (an `input_required` intermediate result) instead of server-initiated requests.
- **Tasks** (2025-11-25, experimental) let a `tools/call` return a task handle with `tasks/get`, `tasks/result`, `tasks/list`, `tasks/cancel`; the 2026-07-28 revision reportedly moves them into an extension. This is the best fit for "offer a session as a tool to any MCP client" in `agent-interop.md`; do not build until the extension's shape is read from the official page.
- **MCP Apps** (SEP-1865) lets servers ship an interactive HTML view that the host renders in a sandboxed iframe. It is a UI surface for hosts with a webview; the CLI has none, the VS Code and JetBrains GUIs would need to render it. Not a first-slice concern.
- **Structured output** (`structuredContent` plus `outputSchema`) has been in the spec since 2025-06-18 and is already worth using when a tool result feeds another tool.

## VS Code APIs

What the repository ships today is in `extensions/vscode/src/ai/`: a language-model chat provider (`languageModelChatProvider.ts`), an MCP server definition provider (`mcpServerDefinitionProvider.ts`) and agent session registration (`agentSessions.ts`, `agentLoop.ts`). Externally, per search summaries: the Agents window shipped as a preview in VS Code Stable in May 2026; 1.129 added an agent host that runs Copilot, Claude and Codex harnesses outside the main process; the extension hook for the sessions view is the proposed `chatSessionsProvider` API, documented as proposed and subject to change; related proposed types include `chatProvider` and `chatSessionCustomizationProvider`; the Agents window works from the `vscode.lm` provider list, which is why a Claude extension that registers no provider shows only "Auto". The Agent Host Protocol (microsoft.github.io/agent-host-protocol) syncs clients with a host-owned session and does not define messaging between sessions (recorded in `agent-interop.md`). Proposed APIs cannot be published to the Marketplace by extensions that depend on them, so any use is limited to Insiders or sideload; the stable path stays chat participant plus language-model provider.

## SDK conventions: handoffs and subagents

OpenAI Agents SDK: a handoff is a tool (`transfer_to_<agent>`) that moves the conversation; `Agent.as_tool()` runs an agent and returns its result. Claude Code: subagents through a tool, with their own model, tool list and permission mode, resumable by name, with background runs whose permission prompts surface in the parent; cross-session `SendMessage`. Cursor: one-level subagents with `readonly` and background flags. These are recorded with links in `agent-interop.md` (checked 2026-11-07) and were not re-fetched. The convention that matters for design: a subagent is a tool call with a result, not a protocol, which is how our `subagent` tool already works; a handoff changes who talks to the person, which we have no use for in an editor-hosted agent.
