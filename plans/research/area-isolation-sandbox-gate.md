## 1. Summary

- The isolation track is a lot of **pure, tested code and very little wiring**. Three executors exist (local, WSL, per-command container) behind one interface and both terminal tools. The policy-to-sandbox compiler, the escape probes, the egress proxy and the detectors are built. **Nothing is jailed by the sandbox-runtime backend yet** (`@anthropic-ai/sandbox-runtime` is not a dependency of any `package.json`), no executor uses the egress proxy, and no UI claim is generated from probe results. The next real step is W4b (a `sandbox` executor), and everything after it (W4c, W6f, W7h, W8b, W8c) waits on it.
- **SB13 is stale.** The sandbox matrix was run against the 2.14.0 release artifacts on 2026-11-12 (commit a5f42332, `D:\temp\sbx-harness\results-release`): **73 pass, 6 fail, 1 n/a, 2 skip**. The roadmap row still says it was not rerun. Of the six failures, one is a real product bug (a hook with a quoted path on Windows, fixed after the tag by #658), one needs an owner decision (a DNS name the egress test does not allow), and **four are harness assertions that no longer match the product** (see 5.3). A gate that is red for known reasons gets ignored, so SB2's first job is reconciling the matrix, not adding cases.
- **The release gate is entirely manual and entirely outside the repository.** No workflow runs it, `docs/maintaining.md` does not mention it (`grep -i sandbox` finds nothing), and the release job in `.github/workflows/main.yaml` cannot tell whether it was run. Windows Sandbox cannot run on GitHub-hosted runners (a Windows client feature; hosted Windows runners are server images without confirmed nested virtualisation, see 7.1), so the gate must run on the owner's machine and **CI must verify a result file** (commit, artifact hashes, zero unexpected failures) rather than run the matrix. Design in section 5.
- **W17 is a real hazard, not yet reproduced.** `MCPConnection.resolveCommandForPlatform` (`core/context/mcp/MCPConnection.ts:663-684`) turns `npx foo "a b"` into argv `["cmd.exe", "/c", "npx", "foo", "a b"]`. It is the same construction #658 fixed for hooks, where a quoted path reached `cmd.exe` backslash-escaped and did not run. Two failure modes: quoting breakage and, if an argument holds `&`, `|`, `^` or `%`, command injection from an MCP definition. It needs one harness test and a small fix (S).
- **Windows isolation recommendation stays: WSL2 plus sandbox-runtime, container as the second route, Windows Sandbox only for disposable whole-loop runs and for the gate.** Two facts changed since W-D2 and are recorded in 6.4: sandbox-runtime now has an **alpha native Windows backend** (dedicated local user, WFP filter, ACLs; one elevated setup; Schannel tools such as `curl.exe` cannot do HTTPS inside it) and Codex's recommended native Windows sandbox is now "MXC", with the earlier elevated and unelevated modes as fallbacks. Neither changes the build order, but W-D2's "no use of its native Windows backend" needs a re-evaluation date.
- **2.16.0 candidates** (section 8): W17, the SB gate (SB2 reconcile, SB1 script plus CI verifier, SB13 closed), CI27 (a fix is already open as #693), CI29, W4b behind a flag with a Linux and WSL first slice, W8d tests. Not 2.16.0: W5, W6 wiring, W15, W16, native Windows.

## 3. Command execution paths today (what a jail has to wrap)

1. **Terminal tool.** `getCommandExecutor()` picks local, WSL or container from `getTerminalShellPreference()` (editor setting or `CONTINUOUS_TERMINAL_SHELL`). Local on Windows is `powershell.exe -NoLogo -ExecutionPolicy Bypass -Command` (profile runs); elsewhere `$SHELL -l -c`. The environment is `terminalEnvironment()` (host secrets scrubbed) unless the caller passes its own. In a VS Code remote window (`remoteName` set) core hands the command to `ide.runCommand`, so Remote-WSL, SSH and Dev Containers windows already run commands where the window is.
2. **File tools** (read, edit, write, glob, grep, list) run in the host process through the IDE or `fs`. They are **not** routed through the executor; documented under Limits in `terminal-in-container.mdx`.
3. **MCP servers** are spawned by `MCPConnection` on the host (stdio) or reached over HTTP. Not isolated, not routed through the executor.
4. **Hooks** (`extensions/cli/src/hooks/hookRunner.ts`) run `cmd.exe /d /s /c "<cmd>"` on Windows (#658) or `/bin/sh -c`; host-side.
5. **`cn serve` and loops** run entirely on the host.

A jail around (1) is what W2 and W4b deliver; (2), (3), (4) and (5) are what the confused-deputy rule W8d, W14 and W5 are about. The honest claim after W4b is "commands are confined; file tools, MCP and hooks are not", which `notEnforced` in `sandboxPolicy.ts` already records.

## 4. Design for each open row

### 4.1 W17: MCP server launch through `cmd.exe /c`

**Problem (user terms).** On Windows, an MCP server defined as `npx` with an argument that contains a space, a quote or a shell metacharacter either does not start or starts something else. The definition may come from a cloned repository, so the second case is a security issue, bounded by the workspace trust gate (#430) and launch-definition pinning (X1b).

**State.** `WINDOWS_BATCH_COMMANDS = ["npx","uv","uvx","pnpx","dlx","nx","bunx"]` (`MCPConnection.ts:73`). For those, `{command:"cmd.exe", args:["/c", cmd, ...args]}` is passed to `StdioClientTransport` (`:882`), which accepts only `command`, `args`, `env`, `cwd`, `stderr`; Node/libuv quotes each argv element for `CreateProcess`, escaping an inner `"` as `\"`, which `cmd.exe` does not understand. `uv` and `uvx` are real `.exe` files in the usual install, so wrapping them is wrong anyway. Whether the SDK (1.32.2 in `core/package-lock.json`) spawns through `cross-spawn` and therefore already handles `.cmd` shims is **unverified here** (no install); if it does, the wrapper is unnecessary and harmful.

**Design.**

1. Reproduce first. Add `win.mcp.npx-quoted-arg` and `win.mcp.metachar-arg` to the harness: an MCP definition whose command is a `.cmd` shim in a path with a space, arguments `["a b", "x&echo PWNED>c:\\out\\pwn.txt", "100%PATH%"]`, and a stub server that echoes its argv. Assert argv arrives unchanged and no file appears. Expected on the current code: fail.
2. Fix, in order of preference: (a) resolve the command with PATH and PATHEXT and, for a real `.exe`, spawn it directly with no `cmd.exe`; (b) for `.cmd` and `.bat`, build one command line `cmd.exe /d /s /c "<quoted line>"` and spawn with `windowsVerbatimArguments: true` exactly as #658 did for hooks, with each argument quoted by a function that **refuses** (clear error, server not started) an argument containing `%`, `!`, `^`, or a newline, because no quoting is safe against `cmd.exe` batch re-expansion; (c) if the SDK cannot take `windowsVerbatimArguments`, wrap its transport with our own small stdio transport (about 80 lines) or pass through `cross-spawn` if it is what the SDK uses.
3. Put the quoting function and its table-driven test in `core/` with the hook runner's tests reused (both now share the rule: a command line for `cmd.exe` is built once, in one place, tested on every platform).

**Alternatives rejected.** Keep `cmd /c` and escape `\"` to `""` (cmd quoting rules differ for `/c` with and without outer quotes; the hook fix needed `/s`); drop `.cmd` support (npx is the dominant way servers are launched).

**Risks.** Servers that rely on `npx` finding `npx.cmd` through `cmd.exe`'s own search (current directory first) change resolution order. Security reviewers will want the refusal of `%` stated in the docs.

**Test plan.** Unit table of arguments on every platform; harness cases above in the Windows Sandbox; one live case with `npx -y @modelcontextprotocol/server-everything` is possible only with network, so keep it outside the offline matrix.

**Size** S. **Depends on** none. **Acceptance** both harness cases pass on a Windows build; the unit table passes on Linux CI; `%`, `!`, `^` arguments produce a one-line error naming the argument; the hook runner and MCP launch share one helper.

### 4.2 W3b: dev container executor

**Problem.** A project that already has `.devcontainer/devcontainer.json` wants the agent's commands to run in that environment (its toolchain, its user) from the CLI or from VS Code without a Remote window. The detector exists; nothing runs a command.

**Design.** `kind: "devcontainer"`. Per command: `devcontainer exec --workspace-folder <ws> [--config <path>] -- bash -lc 'source <(echo <b64> | base64 -d)'`, reusing `sourceEncodedArgs` (the same reason as WSL: the CLI passes argv through two layers). Lifecycle: **never run `up` on its own**; `devcontainerStatus` extends to three states, `running` (a container with the CLI's `devcontainer.local_folder` label exists, `docker ps --filter label=...`, label name to be confirmed against the CLI source), `not-running` (offer a button that shows the exact `devcontainer up` command and what the lifecycle commands in the file will run; consent is per workspace), `no-cli`. Path mapping: `up` and `read-configuration` give `remoteWorkspaceFolder`; `toHostPath` maps that prefix back to the workspace folder. Properties come only from `read-configuration` plus probes (D5: not a jail by default): a mounted Docker socket, `--privileged`, host networking, `--cap-add` are displayed as risks already by `devcontainer.ts`.

**Open facts to verify before building** (the Microsoft page read 2026-11-12 lists `up`, `exec`, `build` and `read-configuration` but documents no exit-code behaviour): does `exec` return the command's exit code, does it keep stdin open, how does it behave when the container stopped. A 30-minute spike on a machine with Docker answers all three.

**Alternatives rejected.** Reimplementing the spec (features, compose, lifecycle ordering) is large and drifts. Running `docker exec` into the container found by label skips `remoteUser`/`remoteEnv` and the userEnvProbe, giving a different environment from the one the project defined.

**Risks.** Lifecycle commands (`postCreateCommand`) are host-triggered code from the repository: trust prompt required. Windows: bind-mounted workspace performance through Docker Desktop (unmeasured). Podman needs `--docker-path podman`.

**Size** M. **Depends on** W0 gap (`toHostPath`). **Acceptance** a repository with a devcontainer, running, executes `echo $USER && pwd` as the configured `remoteUser` in the remote workspace folder; a stopped container yields a message, not a host run; a mounted socket shows "not jailed".

### 4.3 W4b, W4c, W6f, W7h: the OS-sandbox executor and its evidence

**Problem.** Today every command runs with the person's full account. People will give more autonomy only if what a command can touch is contained and the product says so only when measured.

**Design (follows W-D2).**

- **Architecture.** A `sandbox` executor on Linux, WSL2 and macOS only. `wrapWithSandbox` returns a shell string and is async while `CommandExecutor.spawn` is synchronous, so the interface gains `prepare(): Promise<void>` called once per session (it starts srt's proxies and writes the config) and `spawn` stays synchronous over the prepared state. On Windows hosts the executor lives **inside WSL**: the executor is `wsl.exe -d <distro> -- node <helper.js> ...` where a bundled single-file helper imports the pinned sandbox-runtime and runs the base64-sourced command; this needs `node` in the distribution (detect it as the other detectors do; if absent, say how to install, never install).
- **Config.** The compiled plan from `compileSandboxConfig` (W8a): writes to the workspace and a private temp directory; `denyRead` for `~/.ssh`, cloud credential folders, our own config; `denyWrite` for `.git/hooks`, `.git/config`, shell start-up files, hook and settings files; network `none` by default with the allowlist and the model host as options. `precreate` files are created only if absent.
- **Path mapping.** Same paths as the host on Linux and macOS (no mapping). On Windows hosts the workspace should be in the Linux file system for speed; a `D:\ws` workspace appears as `/mnt/d/ws` and the plan marks the Windows drive as a conflict (already in the compiler: "a Windows drive on WSL2"), so the first Windows slice requires the workspace in the distro or accepts `weakened`.
- **Credentials.** Environment is scrubbed by `terminalEnvironment()` before srt; the model key never enters because approach A keeps the loop on the host.
- **Performance.** srt wraps each command (bubblewrap start is milliseconds on Linux; macOS Seatbelt similar; WSL adds the `wsl.exe` round trip, measured in the W1 work). Budget: under 100 ms added on Linux, to be measured in W4c.
- **Evidence (W4c, W7h).** Run the 22 escape probes through the executor on each platform, store the table keyed by `{backend, srt version, config hash, kernel, distro}`, and have `continuous sandbox status` and the badge read **only that table**. A probe set older than the srt version or the config hash is `unverified`. The spike already measured: writes outside the workspace denied, `.git/hooks`, `.git/config` and `.bashrc` denied, no capabilities, seccomp on; not held: `/mnt/c` readable, host environment variables, files created later. The network half has not been run (`socat` needs `libssl` in that distribution).
- **W6f.** Point srt's `parentProxy` at `egressProxy` so the registry presets, address checks and pinning sit in front, and the model reverse proxy for W5 later sits there as well.

**Alternatives rejected.** Hand-written `bwrap` argv (we would own the Seatbelt profiles and seccomp filters); Landlock only (cannot do the network namespace and has kernel-version gaps, unverified here); containers for every command on Linux (works today as W2, but heavier and the image must have the toolchain).

**Risks and escape paths.** srt is beta and its API may change: pin exact, keep our own interface. Files created after start are unprotected (symlink to a protected path); user-namespace restrictions (Ubuntu 24.04's AppArmor setting, nested containers) make the executor `installed-but-unusable`, which must fail closed. Anything that talks to a host service on a unix socket (Docker, ssh-agent) must be denied: the srt docs say Docker is incompatible with its sandbox, so "commands cannot use docker" is a user-visible cost to state. `/mnt/c` and Windows interop from WSL are outside the jail unless the distribution's `wsl.conf` disables them; see 4.4.

**Dependencies.** W-D2, W8a (built), W10 for the status shape, W7h for the claim.

**Test plan.** Unit: config compile (done). Integration on Linux CI: bubblewrap and socat are installable on `ubuntu-latest`; run the probes in a `sandbox-probes` job and compare to the expected table (this is a place where CI **can** assert the property, unlike Windows Sandbox). WSL: harness on the owner's machine. macOS: the macOS runner in `main.yaml` already exists (`darwin_runner`).

**Size** W4b M-L, W4c M, W6f S-M, W7h S. **Acceptance** `continuous sandbox status` on a Linux CI runner reports `contained` only after the probes ran in the same run; writing outside the workspace fails with a message naming the jail; the executor is off by default; a missing bubblewrap yields a message with the install command and no host run.

### 4.4 A dedicated WSL distribution as a cheaper Windows isolation step (new)

**Problem.** WSL as built is a convenience: the user's distro automounts `C:`/`D:` under `/mnt`, can launch Windows executables (`[interop] enabled=true`, `appendWindowsPath=true` are the defaults per the Microsoft `wsl.conf` page read 2026-11-12), and the probe run found five violated properties. Windows users without Docker have no jail at all until W4b lands and even then need `node` and bubblewrap in a distro they may use for other things.

**Design.** Offer, never silently do, `wsl --import continuous-jail <dir> <rootfs.tar.gz>` from a pinned Ubuntu rootfs, with a `wsl.conf` of `[automount] enabled=false`, `[interop] enabled=false appendWindowsPath=false`, `[user] default=<non-root>`, `[boot] systemd=false`. The workspace is bind-mounted by a per-session `mount --bind` from `\\wsl.localhost\...` or, better, the workspace is cloned into the distro's file system by the Loop's worktree helper. Combined with W4b inside it, this removes `/mnt/c` and interop from the jail.

**Honest limits.** All WSL2 distributions share one utility VM and its kernel; a distro boundary is a mount-namespace boundary, not a VM boundary (shared `/mnt/wsl`, `wsl.exe -d other` is reachable if interop is on). It is a reduction, and the probes must say so. Whether Microsoft documents WSL distros as a security boundary is **unverified**; assume not.

**Size** M, optional, after W4b. **Recommendation.** Record as a candidate (new row W19), not 2.16.0.

### 4.5 W5: whole-process jail for `cn serve` and loops

**Design.** Approach B of `isolation.md`: the loop driver, file tools, hooks and MCP stdio run in a container (or inside the sandbox executor on WSL2) and the IDE talks to `cn serve`. The model key stays on the host: a **host-side reverse proxy** adds the key and a per-run token authenticates the jailed process; the jailed process gets `HTTPS_PROXY` and a base URL pointing at it. On Linux the proxy is reached over a bind-mounted unix socket or a user-defined `--internal` network with the proxy as the only member that has a route out; on Docker Desktop for Windows `host.docker.internal` reaches the host but nothing stops the container from reaching other host ports, so the allowlist is **not enforceable** there without a sidecar proxy container; WSL2 with srt's namespace is the enforceable Windows path. The existing proxy (#469) is ready for either.

**Risks.** The key never enters, but a jailed process can ask the proxy for any model call the token allows (a cost and data path), so the gateway needs budgets (Track T) and a path allowlist (`/v1/messages` and the like). MCP servers launched inside the jail see no host credentials, which breaks servers that rely on them (state it). **Size** L. **Dependencies** W4b, W6f, W7h. **Defer** after 2.16.0.

### 4.6 W6 wiring (network policy into executors)

`egressProxy` and `egressPolicy` are pure code with tests; no executor uses them. First consumer is W6f (srt `parentProxy`). For the container executor, expose `network: none | proxy` and implement `proxy` only where it is enforceable (Linux with an `--internal` network and a proxy sidecar; not on Docker Desktop). Until then the container setting stays `none` and the docs say so. **Size** S (W6f) then M (container sidecar), **depends** W4b.

### 4.7 W7: escape tests per backend and generated claims

Extend `runEscapeProbes.ts` to a `--backend sandbox|devcontainer|windows-sandbox` set, write the result to a per-machine cache `~/.continuous/sandbox-probes.json` with the key in 4.3, and wire `describeSandboxPlan` and the badge to it. Windows Sandbox backend needs PowerShell probes (a short list: write outside the share, read host paths not mapped, host loopback and LAN reach, mapped-folder write persistence); these can run inside the gate's sandbox as an extra matrix family, with no new executor. **Size** M. **Acceptance** a regression in a probe flips the badge text in a unit test with a canned result file; no string in the UI claims "contained" without a table row.

### 4.8 W8b, W8c, W8d, W13, W14: policy integration

- **W8d** is the gate for everything automatic. Finish with the test the row names: a command in the jail creates a symlink inside the workspace to `~/.continuous/config.yaml`; the host edit tool, given that path, resolves and refuses. Built in part (#586, #588); the remaining work is the "link created during the run" case (record the real path at decision time and compare at open time, W14) and host-side writes to hooks and config.
- **W14** open-time recheck. On POSIX: open with `O_NOFOLLOW` for the leaf and compare `fs.realpath` of the parent before and after, write to a temp file in the same directory and `rename`. On Windows Node has no `O_NOFOLLOW`; use `fs.open` then `fs.realpath.native` of the opened path and `lstat` for reparse points, and refuse junctions and symlinks at the target. This narrows the window, it does not close it (Node cannot do `openat`); the sandbox is the real boundary. Cited advisories in `agent-security.md` (CVE-2026-88968 and others) are the evidence. **Size** M.
- **W8b** (Permissions page shows per rule who enforces it) is GUI work on top of `describeSandboxPlan`; S-M once W7h exists; until then show "policy only".
- **W8c** stays gated: B28 (path analyser) and W8d first. Do not build before; the roadmap note that 54 of 152 dangerous cases skipped a prompt without it is the reason.
- **W13** is solved by the same two things (B28 plus W8) and needs no separate work.

### 4.9 W15 job object and W16 AppContainer

- **W15.** Node has no job-object API; options are a native addon (supply-chain and prebuilds burden), a helper executable (a new signed binary), or PowerShell `Add-Type` P/Invoke in a helper process (about 300 ms start-up and the kind of pattern antivirus products flag). The current `taskkill /T /F` kills descendants of a living parent; it misses processes whose parent already exited. **Recommendation: measure the miss first** (a harness case: a command that spawns a detached grandchild, cancel, count survivors), and build only if survivors are real. Size S to measure, M to build. Defer.
- **W16.** The cheapest honest way to answer "does node, git and tsc run under an AppContainer or restricted token" is to **run sandbox-runtime's Windows alpha inside the disposable Windows Sandbox**: the guest account is an administrator, so its one-time elevated `windows-install` can be tested without touching the host. Needs networking enabled for that one session, which the repository runner supports (`--network on`). Treat it as an SB12 extension and a research note; record node/git/tsc results and the Schannel finding. Size S, research only.

### 4.10 W10 platform awareness: finish it

Add `core/util/backendStatus.ts` with one union `{ backend, state: "unsupported-platform" | "not-installed" | "installed-but-unusable" | "ready", hint?, detail? }` and adapters over the four existing detectors plus devcontainer; `continuous sandbox status` prints them all; the VS Code settings page lists only backends whose state is not `unsupported-platform`. ### 5.2 Design

**Principle: test the bytes that will ship, produce a result file that names them, and make the release job refuse without it.**

1. **Inputs are the release workflow's artifacts.** Run `main.yaml` by `workflow_dispatch` on the candidate commit with `publish_build=false` (it already builds `cli-tgz` and the platform VSIX artifacts), then `gh run download <run-id> -n cli-tgz -n win32-x64-vsix`. The gate script records `sha256` of each. (Today the harness rebuilds from a worktree; that tests the source, not the artifact, and a build difference ships unseen.)
2. **One entry point in the repository: `tools/sandbox/gate.ps1 -RunId <id> [-Out dir]`** (move the harness to `tools/sandbox/`, with `runner/`, `oauth/`, `summarize.mjs`; downloads of `node.zip` and `vscode.zip` are fetched into a git-ignored cache with pinned versions and SHA-256 listed in `tools/sandbox/pins.json`). It: takes a lock (a file, plus `wsb list` empty), checks the preconditions the repository code already knows (`windowsSandboxStatus()`, VPN check from `windowsSandboxRun.ts`), downloads and verifies artifacts, builds the config with `buildSandboxConfig` (reuse, do not keep two XML builders), starts, logs on, runs, collects, **stops the sandbox in a `finally`**.
3. **Result file: `gate-result.json`** with `{ schema, commit, tag, workflow_run_id, artifacts: [{name, sha256}], harness: {version, tests_total}, host: {os_build, wsb_version}, started, finished, results: [{id, status, detail}], summary: {pass, fail, na, skip}, waivers: [ids] }`, plus `SUMMARY.md` and a trimmed screenshot set.
4. **Waivers are data, not judgement.** `tools/sandbox/expected.json` lists test ids allowed to be `fail`, `skip` or `na` with a ticket, a reason and an expiry date; a `na` is allowed only where the harness's marker detection says the feature is absent from the build **and** the id is listed. The gate exits non-zero on any other non-pass. This is what makes SB1's "pass or a recorded not-applicable" mechanical. (`-ExpectFeatures` already turns an absent feature into a failure on candidates; keep it.)
5. **Where the result lives.** Commit `release-gates/<tag>.json` to the release PR (a small file; the owner's machine produced it, the PR carries it, review sees the summary), and upload `gate-result.json`, `SUMMARY.md` and a zip of screenshots to the GitHub release as assets in the manual `gh release create` step (CI28 records that step is manual).
6. **CI verifies, never runs.** A new `gate-verify` job in `main.yaml`, `needs: [build, cli]`, `release` and `publish-marketplace` both `needs` it. It reads `release-gates/<tag>.json` from the tagged commit and fails unless: `commit == github.sha`, every artifact hash equals the hash of the artifact this run built (`sha256sum`; reproducibility of the build matters here, so if builds are not byte-reproducible the verifier compares the hashes of the **downloaded gate artifacts from the same run id**, which means the gate must be run on the exact workflow run that will publish, via `republish_run_id`, see below), `summary.fail == 0` after waivers, `finished` is after the commit time and within 14 days, and no waiver has expired. This turns SB1 from a rule into a check the owner cannot forget, while an honest owner-produced file remains a trust assumption (a person can fabricate it; it is a safety net against forgetting and against stale results, not against a hostile maintainer; state this in `docs/maintaining.md`).
7. **Sequence that fits the existing process.** The release workflow already supports `republish_run_id` (publish an earlier run's VSIX). So: (a) dispatch `main.yaml` on the candidate with `publish_build=false`; (b) run `gate.ps1 -RunId <that run>`; (c) commit `release-gates/<tag>.json`; (d) tag; the tagged run republishes with `republish_run_id` equal to the gated run, so the bytes published are the bytes tested. This removes the byte-reproducibility problem entirely. Needs a small change to the release job so it can take the gated run's artifacts; that is part of CI28.
8. **What runs in CI on every PR or nightly without a VM.** The matrix runner already supports host mode (`SBX_ALLOW_NET=1 node runner/run.mjs --only cli --skip-vscode`, per its README). Run that subset on `windows-latest` in `post-merge-check.yml` (nightly or on `extensions/cli/**`, `core/context/mcp/**`, `core/util/shell.ts` changes): it catches W17-style Windows quoting regressions, serve guards, CRLF edits and permission lint cases in minutes, but it is **not** a clean machine (the runner has Git, long-path defaults, a real profile, network), so it is a smoke test and not the gate. Linux and macOS jobs run the escape probes for W4c (4.3).

### 5.4 Clean-machine fidelity

What a Windows Sandbox gives: a pristine Windows 11 guest per start, a non-ASCII profile can be synthesised (the harness uses `Zoë Müller\My Tools`), no Git for Windows (a known limit: it cannot start in the sandbox; the product's behaviour without git is tested implicitly), no network by default in our config. State these limits in the gate output.

### 5.5 Logon, desktop, screenshots (SB12 specifics)

- **Logon.** `wsb exec -r ExistingLogin` needs an active session, which `wsb connect` creates (Microsoft's CLI page, read 2026-11-12: "An active user session is required ... a remote desktop connection should be established ... using the connect command"); `-r System` works without it but has no desktop, so no VS Code and no screenshots. The harness's solution (hidden `wsb connect` then poll) works; its defects are the viewer being a child of the starting process, and `Show-Sandbox` stealing focus. Fixes: start the viewer with `Start-Process -WindowStyle Minimized` in a detached `cmd /c start`, remove the focus loops from the gate path (keep an explicit `-Show` switch for human sessions), and wait for logon by polling `ready.txt` with a hard timeout and one retry that stops and restarts the sandbox. **Experiment E1** (30 minutes, one sandbox): does `<LogonCommand>` in the `.wsb` run when started by `wsb start --config` with no client connected? The configuration page lists it; whether the user logs on without a connected client is **unverified**. If it does, bootstrapping needs no `exec` at all and the logon race disappears.
- **Screenshots.** The two mechanisms exist: guest `CopyFromScreen` of the virtual screen (reliable, 4 MB PNG each) and host `PrintWindow` of the `WindowsSandboxRemoteSession` window (`hostshot.ps1`, captures only that window; works while the window is not minimized). Reduce volume: capture on **test boundaries and failures**, not every 5 s; save as JPEG quality 70 at 1280 px wide (about 100 KB); keep a rolling buffer of the last 10 per test and write it only when the test fails. Per-window capture with `PrintWindow` inside the guest (Code.exe window handle) is better for the VS Code case than the whole desktop; `PrintWindow` with the `PW_RENDERFULLCONTENT` flag (value 2, as `hostshot.ps1` already passes) is needed for Chromium-based windows. Result: roughly 10 to 30 MB per run instead of 1.4 GB.
- **One at a time.** The lock plus `wsb list` check; on a stale sandbox (previous crash) `gate.ps1` stops it only when its id is in the lock file this tool wrote, never a sandbox the owner started.
- **Staging crash.** `New-Item -ItemType HardLink` fails for the large zips in `ui-session.ps1`; map the pinned download cache folder read-only directly instead of hard-linking into a stage (mapped folders are snapshots, and a read-only cache folder needs no copy).

### 5.6 One runner or two

`extensions/cli/scripts/sandboxRun.ts` (SYSTEM, `wsb exec`, one command, result protocol, always stops the sandbox, VPN refusal) and the harness (`ExistingLogin`, desktop, full matrix) overlap in config building, VPN handling and cleanup. Make `tools/sandbox/gate.ps1` a thin PowerShell wrapper that calls a Node module reusing `core/util/windowsSandboxRun.ts` (`buildSandboxConfig`, `detectVpn`, `parseSandboxIds`, `pollResult`) and `windowsSandboxStatus`. That removes duplicated untested PowerShell logic and puts the parts that can be unit-tested under vitest. The interactive-desktop path stays PowerShell because it needs `wsb connect` and window APIs.

### 5.7 Matrix additions (SB2) and the cases the gate cannot see

Add: `win.mcp.*` (W17), `win.terminal.wsl-absent` (the setting is ignored or fails closed with the hint when no distro exists: the guest has no WSL), `win.terminal.container-absent` (message with install hint, no host run), `win.job.orphan` (W15 measurement), `cli.firstrun.*` per the decision in 5.3, a CRLF multi-line edit through **both** the CLI Edit tool and the extension (SB2 asks for it; the CLI case passes already), `cli.serve.*` as today, and `sandbox.status` (`continuous sandbox status --json` parses and says no `contained` anywhere). For `oauth.dyn.listener-unreachable-off-loopback`: enable networking for that single test only (separate sandbox start) or add a second virtual adapter; both are heavier than the value, so keep it a recorded `skip` with an expiry and cover it with a unit test of the bind address (already done in #634).

Cases that stay manual and should be on a written checklist the owner ticks in the release PR: the visual check of the chat, Loop controls, settings and permissions pages with screenshots from the guest (the gate captures them; a human looks); a real sign-in with a real provider; Windows Home and enterprise policy machines; macOS and Linux VSIX smoke (a Linux CI job can cover the CLI tarball and the VSIX unpack).

### 5.8 Alternative: a Hyper-V VM with a checkpoint

Windows Sandbox is free, always clean and has no licence work, but is limited by one instance at a time, no process output (`wsb exec` returns no I/O: the CLI page says so), start-up of about 3 s plus logon of tens of seconds, the connect-window quirks above, and no way to pre-install anything (so Node and VS Code are unpacked each run, about 1 s and 3 s measured). A Hyper-V VM (Pro or Enterprise) reverted from a checkpoint gives a real logged-on desktop in seconds, PowerShell Direct (`Invoke-Command -VMName`) with real stdout, multiple VMs, pre-installed Git and VS Code, and a persistent UI session. Costs: a Windows image (evaluation images need re-arming; a licence is the owner's call), 30 to 40 GB of disk, drift when the base image is updated, and a second thing that is not "clean machine" unless the checkpoint is rebuilt for each release. **Recommendation:** keep Windows Sandbox for the gate; add the VM only for the interactive UI-session use of SB12 if the owner wants instant sessions. Not required for 2.16.0.

## 6. External research

All fetched 2026-11-12. "Unverified" marks claims the sources do not state.

### 6.1 Windows Sandbox and `wsb`

- CLI page ([learn.microsoft.com/.../windows-sandbox-cli](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-cli), page dated 2025-01): Windows 11 24H2 onward (`WSB_MIN_BUILD = 26100` in our detector); commands `start`, `list`, `exec`, `stop`, `share`, `connect`, `ip`; `--raw` gives JSON. `exec -r <ExistingLogin|System>` is required; "there is no support for process I/O", so output must travel through a shared folder; `ExistingLogin` needs a connected session. `share` takes `-w/--allow-write`. `start --config` takes the XML as a string.
- Configuration page ([learn.microsoft.com/.../windows-sandbox-configure-using-wsb-file](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file), updated 2026-03): elements `VGpu`, `Networking` (`Enable|Disable|Default`), `MappedFolders` (host folder must exist or the sandbox fails to start; writable changes **persist after the sandbox is disposed**), `LogonCommand`, `AudioInput`, `VideoInput`, `ProtectedClient`, `PrinterRedirection`, `ClipboardRedirection`, `MemoryInMB` (minimum 2048). Default networking is on and uses the Hyper-V default switch, so an untrusted app can reach the internal network; default memory cap 4 GB. **`ProtectedClient` runs the sandbox inside an AppContainer isolation environment** (credential, device, file, network, process and window isolation) and "may restrict copy and paste". Worth adding to the gate's config as an option to see whether our tests still pass (it is a hardening of the viewer, not of the guest).
- Not stated by the docs and therefore unverified: start-up time, the single-instance limit (known from our own testing and `isolation.md`), behaviour of `LogonCommand` under `wsb start` with no client.

### 6.2 Claude Code sandboxing

[code.claude.com/docs/en/sandboxing](https://code.claude.com/docs/en/sandboxing): Seatbelt on macOS; bubblewrap on Linux and **WSL2** (needs `bubblewrap` and `socat`; separate network namespace with no route out; optional seccomp filter blocks unix domain sockets); **WSL1 and native Windows unsupported**. Traffic leaves through a host proxy that checks hostnames against `allowedDomains` and `deniedDomains` (allowlist starts empty; the proxy refuses hostnames that resolve only to local or link-local addresses; TLS is not inspected by default; tools that ignore proxy variables, such as plain `ssh`, and non-TCP traffic cannot connect). Writes allowed to the working directory, a per-user temp directory and added directories; reads allowed across most of the machine **including `~/.ssh`** unless denied; protected paths denied for writes even inside the workspace (settings, `.mcp.json`, hooks, shell start-up files, `.gitconfig`, `.git/hooks`). Escape hatch: `dangerouslyDisableSandbox` retries unsandboxed, governed by permission mode; `allowUnsandboxedCommands: false` with `failIfUnavailable: true` is the strict mode. **Outside the sandbox:** built-in file tools, web tools, hooks, local MCP servers, status line and LSP servers. `docker` is incompatible; rootless Podman and Chromium need user namespaces the sandbox blocks by default; Ubuntu AppArmor can block bubblewrap. This matches our `notEnforced` list and the W-D2 shape. Take two things: a strict mode that refuses to run unsandboxed (our "fail closed", and a setting equivalent to `failIfUnavailable`), and the `dangerouslyDisableSandbox`-style retry **must not exist silently** in ours: a command that fails inside the jail asks, with the jail's denial named.

- `@anthropic-ai/sandbox-runtime` ([github.com/anthropic-experimental/sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime)): Apache-2.0, "beta research preview", APIs may change; `SandboxManager.initialize`, `wrapWithSandbox`, violation attribution, per-command allow lists keyed by an id that must carry 128 bits of randomness (the id is the only binding: a process that presents another live command's id gets its allows). **Windows is alpha**: a dedicated `srt-sandbox` local user, a WFP egress filter, a write-restricted token and NTFS ACEs, one elevated `windows-install`; tools using Schannel (`curl.exe`, `Invoke-WebRequest`, .NET `HttpClient`, `winget`) cannot do HTTPS inside it; traffic carried by a system service on a process's behalf is not filtered; kept write grants on project directories can be read by other sandboxed sessions. Linux: root callers need `CAP_SETFCAP`; Ubuntu 24.04 may need the AppArmor user-namespace restriction lifted; nested sandboxes (Chromium, rootless podman) fail unless `allowNestedUserNamespaces`.

### 6.3 Codex

[learn.chatgpt.com/docs/windows/windows-sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox) (redirect from developers.openai.com/codex/windows): native Windows sandbox modes in order of preference **MXC** (native process isolation, no administrator setup, no extra accounts or firewall rules, rolling out with Windows 11 24H2 and 25H2 builds; capability details unverified), **elevated** (dedicated lower-privilege sandbox users, filesystem permission boundaries, firewall rules, local policy changes, private desktop; needs an administrator-approved setup; error 1385 on managed machines; a warning when folders are writable by Everyone) and **unelevated** (restricted token derived from the current user, ACLs only, no denied read paths, weaker network isolation). Diagnostics in `CODEX_HOME/.sandbox/sandbox.log`; enterprise switches `allowed_sandbox_implementations` and `windows.allow_mxc`. It still recommends WSL for Linux-native tooling. Reading: even the vendor with the largest Windows investment has a three-tier fallback with real failure modes on managed machines. That supports "do not build native Windows isolation" and "watch MXC" (new row W18).

### 6.4 WSL interop pitfalls

[learn.microsoft.com/windows/wsl/wsl-config](https://learn.microsoft.com/en-us/windows/wsl/wsl-config) (updated 2026-10-16): `[automount] enabled` (default true, drives under `/mnt`), `[interop] enabled` and `appendWindowsPath` (both default true, so Linux processes can start Windows `.exe` and see the Windows PATH), `[boot] systemd` (default false, WSL2 only), `.wslconfig` `[wsl2]` options `memory` (default 50 percent of host), `networkingMode` (`nat`, `mirrored`, `consomme`, `none`), `firewall` (true lets Windows Firewall and Hyper-V rules filter WSL traffic), `vmIdleTimeout` (60 s), `[general] instanceIdleTimeout` (15 s). Changes need `wsl --shutdown` and about 8 seconds. Pitfalls relevant to us: the default distro may be Docker Desktop's own (our detector already drops it); a command line over about 32,000 characters fails (our encoder fails over about 24,000 before encoding); `wsl.exe` re-parses its arguments (the reason for base64); `/mnt/c` I/O is slow and unprotected; the VM goes idle and the next command pays a start. `networkingMode=none` and `firewall` are the supported ways to cut a distro off the network, but they are global to WSL2, not per distro.

### 6.5 Dev containers

[code.visualstudio.com/docs/devcontainers/devcontainer-cli](https://code.visualstudio.com/docs/devcontainers/devcontainer-cli): `devcontainer up --workspace-folder` prints JSON with `outcome`, `containerId`, `remoteUser`, `remoteWorkspaceFolder`; `exec`, `build`, `read-configuration`; installed from npm (`@devcontainers/cli`, needs Node 14 or later and a C/C++ toolchain for a dependency) or from the VS Code command. The page does not document exit codes or `--remote-env`/`--id-label`. Dev containers are environments, not jails (D5).

### 6.6 gVisor, Firecracker, Kata

Blog sources ([Northflank](https://northflank.com/blog/firecracker-vs-gvisor), [Fly.io](https://fly.io/learn/firecracker-vs-gvisor.md), others; vendor and blog material, benchmark numbers conflict and are not used here): microVMs (Firecracker, Kata) give a separate kernel and a hardware boundary; gVisor intercepts syscalls in a user-space kernel (`runsc`) and is a drop-in Docker runtime with lower memory overhead but a larger syscall-compatibility surface. Relevance: **gVisor is a runtime flag for the container executor on Linux** (`--runtime=runsc`) and is worth listing as an optional hardening, not a dependency; Firecracker is a server-side technology (needs KVM) and has no role on a developer's Windows laptop, where Windows Sandbox and WSL2 are already microVM-class. A 2026 report that Docker shipped "Docker Sandboxes" with microVM isolation is a single secondary source and is **unverified**. Not recommended work for 2.16.0 or 2.17.0.

### 6.7 Hosted CI cannot run Windows Sandbox

Search 2026-11-12 found no GitHub documentation that hosted Windows runners support nested virtualisation, and community threads state they do not (a runner-images discussion lists larger runners as a later exception, unverified for Windows Sandbox). Windows Sandbox is a Windows client feature (our detector lists the client editions that ship it); hosted `windows-latest` is a server image (unverified whether the optional feature can be enabled there; the edition regex in `windowsSandboxStatus.ts` includes `ServerRdsh`, Windows Enterprise multi-session, but not Server). A self-hosted runner on the owner's machine would work technically but on a public repository exposes the machine to code from pull requests; do not do it for PR events. If the owner wants CI-driven gates later: a dedicated self-hosted runner that accepts only `workflow_dispatch` from `main` by maintainers. Not recommended now.

## 7. Risks across the track (short)

1. **Words outrun evidence.** The compiler and probes are careful, but any UI string written by hand claiming containment before W7h would break D4. Guard: a vitest that greps the GUI strings for "contained" and requires an import from the probe table.

5. **Confused deputy through host file tools** remains the largest gap after W4b; W8d and W14 stay before any auto-approval, as the roadmap says.

Added 2026-11-12 after the first version of this report merged (#711). Release naming below: **2.17.0** is the next release after the one being cut now, **2.18.0** the one after. The first version of this report called the release being cut "2.16.0"; read its candidate lists as the next release's.

### 11.1 Findings that were unverified, now researched

**Does `LogonCommand` run under `wsb start` with no client connected? Probably not.** The LOLBAS entry for `wsb.exe` ([lolbas-project.github.io/lolbas/OtherMSBinaries/Wsb](https://lolbas-project.github.io/lolbas/OtherMSBinaries/Wsb/), fetched 2026-11-12, a third-party security reference and not Microsoft) says `<LogonCommand>` "only fires once `WDAGUtilityAccount` actually logs in", which needs an RDP session from `wsb connect`, and that `wsb start` alone does not start `WindowsSandboxRemoteSession.exe`. Microsoft's pages do not say either way. The harness's own finding agrees: a started sandbox has no logged-on user and `-r ExistingLogin` fails until `wsb connect`. Experiment E1 is therefore demoted: do not expect it to remove `wsb connect`. A smaller use remains: with `wsb connect` started minimised, `LogonCommand` can launch `bootstrap.ps1` at logon, which removes the loop that calls `wsb exec` repeatedly until the session is ready (unproven; one sandbox run, 30 minutes).

**Can part of the matrix run with no session at all? Probably.** `wsb exec -r System` runs without a logged-on user (Microsoft's CLI page; the repository's `sandboxRun.ts` uses it). It has no desktop and no profile. The CLI half of the matrix (`cli.*`, `feat.*`, `oauth.dyn.*`) needs neither, and the harness already builds a synthetic non-ASCII profile through environment variables. Experiment E2: run the CLI half as System and keep `wsb connect` for the VS Code half only. The CLI half then also runs from a scheduled or remote session.

**What does `ProtectedClient` do?** Microsoft: enabled, it runs the sandbox in "AppContainer Isolation" with "Credential, Device, File, Network, Process, and Window isolation", and it "may restrict the user's ability to copy/paste files in and out" (configuration page, updated 2026-03). The page does not say whether the AppContainer wraps the guest, the RDP client process or both (search summaries say it hardens the RDP session). **Still unverified** whether it affects `wsb exec`, mapped-folder writes or screenshots. Experiment E3: one gate run with `<ProtectedClient>Enable</ProtectedClient>`, adopted only if every case and both screenshot paths work. Clipboard is already disabled in our config, so the documented cost is nil.

**sandbox-runtime's Windows backend.** From the README (fetched 2026-11-12, second half of the page): setup is `npx @anthropic-ai/sandbox-runtime windows-install`, which creates a WFP filter set, a local account `srt-sandbox` and a group `sandbox-runtime-users` behind one UAC prompt; the profile read grant can take minutes and blocks other sessions; `windows-uninstall` reverses it and leaves `%ProgramData%\sandbox-runtime`. `windows.backend` is `srt-win` (default) or **`mxc`** (experimental; needs `@microsoft/mxc-sdk`, Node 24 or later and a Windows build with the BaseContainer tier; Git Bash does not start; sandboxed programs can open desktop windows; `%TEMP%` is per-command scratch). Its listed caveats: the profile grant is machine-wide; commands can read `.npmrc`, pip config, `NuGet.Config`, `.gitconfig`, `gradle.properties` and Maven `settings.xml`; the network fence does not cover DNS through the system resolver, SMB or WSL traffic; Schannel clients (.NET, PowerShell's default) do not work; `proxyAuthToken` is visible in a command line. The first part of the README labels the Windows backend alpha. This confirms W-D2: an installed local account, machine-wide grants and a readable-credentials list are not what a default-on feature can ship. W16 stays a research run inside the disposable Windows Sandbox, now with a concrete checklist (the `mxc` backend, Git Bash, Schannel tools).

**Merge queue availability (SB9 says "unavailable on a user-owned repository").** GitHub's managing-a-merge-queue page (fetched 2026-11-12) does not state availability; it says a queue is enabled with "Require merge queue" under branch protection or rulesets and cannot be used with wildcard branch patterns. A same-day search returned GitHub's wording: queues are available in public repositories **owned by an organization** and in private Enterprise Cloud repositories (repeated by the 2023 general-availability announcement). The user-owned exclusion is an inference from that wording, consistent with the existing SB9 note, and the `b1tninja-labs` organisation would qualify if the repository moved (CI14). The gate does not depend on a queue: it verifies at release time, not at merge.

**Hosted Windows runners and Windows Sandbox.** Still no evidence that standard hosted Windows runners support nested virtualisation; unchanged from section 6.7.

**New risk.** LOLBAS lists `wsb.exe start --config` with an inline `LogonCommand`, `wsb share --allow-write` and `wsb exec -r System` as detection indicators for abuse, and `WindowsSandboxServer.exe` running without `WindowsSandboxRemoteSession.exe` as "highest-signal for headless abuse". The gate's no-viewer System-mode runs (E2) look like that to an endpoint product on a managed machine. The gate is therefore an owner-machine tool; SB17 records it.
