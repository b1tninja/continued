## Summary

The product has seven surfaces that share `core/` and diverge above it:

| Surface               | Entry                                                   | Who drives a turn                                                                             |
| --------------------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| VS Code               | `extensions/vscode` + `gui/`                            | redux thunks in the webview (`gui/src/redux/thunks/streamNormalInput.ts`)                     |
| CLI TUI               | `continuous`                                            | `cli/stream/streamChatResponse.ts`, services started `headless: false`                        |
| CLI headless          | `continuous -p`                                         | the same driver, `headless: true`                                                             |
| serve                 | `continuous serve` (hidden command, `cli/index.ts:292`) | the same driver, `headless: true` (`cli/commands/serve.ts:123` **V**)                         |
| ACP                   | `continuous acp`                                        | the same driver, `headless: false` (`cli/acp/backend.ts:38` **V**)                            |
| JetBrains             | `extensions/intellij` + `gui/` in JCEF + core binary    | the same webview thunks as VS Code, behind a Kotlin message gate                              |
| Subagents and workers | IDE: in-webview loops. CLI: in-process or a forked `cn` | `gui/src/util/subagents/runSubagent.ts`, `cli/subagent/executor.ts`, `cli/loop/loopWorker.ts` |

Four findings matter most.

1. **The same tool call gets a different answer depending on the surface, and the difference is not written down anywhere.** A shell command the IDE would ask about (tools: Cautious) is allowed in `-p`, in `serve` and in a CLI Loop worker (list defaults `Bash: allow`, `*: allow`), asked in the TUI and over ACP, and decided in the webview on both IDEs. When the rule engine throws, the IDE refuses and the CLI at default settings lets the list default decide.
2. **There are two complete agents in the tree.** The IDE agent is the webview thunks plus core tools; the CLI agent is its own driver, its own 20-tool registry, its own system-prompt builder, its own MCP service and its own Loop driver. They share pure functions (`core/tools/permissions/*`, `core/util/loopMode.ts`, `core/llm/prompts/turns.ts`), and everything around those functions is written twice. Counting the IDE subagent and the IDE Loop worker, the request loop exists four times.
3. **In the IDE the webview is the only gate.** Core's `tools/call` runs what it is sent and records it as approved (`core/core.ts:2231-2233` **V**). That is acceptable in VS Code, where the extension guards panel messages. In JetBrains the panel gate is thinner, and the messages that load the person's permission levels are not routed at all.
4. **JetBrains is not a supportable surface today.** 20 webview-to-core message types are rejected, 13 core-to-IDE requests are never answered (two of them would hang `create_new_file` and checkpoint restore), the plugin is upstream-branded and reads `~/.continue`, and no release has ever carried a JetBrains asset. Recommendation, pending owner: park it (section 5).

The proposed rows are track **PAR** (unused on `origin/main` and in every open pull request title and body searched), section 7.

### 4.1 Shared conformance suite

- **Scenario file** (`conformance/scenarios/*.yaml`): a fixture workspace, config and `permissions.yaml`, a scripted model (a list of replies with tool calls), and the person's scripted answers.
- **Expected output**, per surface: canonical tool ids offered, each call's decision (allow, ask, deny, hold, refuse), who decided and the source, audit rows, prompt segment hashes, final stop reason.
- **Declared differences**: one file, `conformance/differences.yaml`, lists each cell where a surface may differ from the reference, with the reason and the row that would remove it. A difference not in the file fails. This document's section 2 is the first draft of that file.
- **Drivers**:
  - CLI: the scripted model already exists for e2e (`cli/e2e/headless-mock-llm.test.ts`, `headless-dynamic-responses.test.ts`); headless, serve (HTTP), ACP (stdio with the scripted backend of `cli/acp/agent.test.ts`) and the worker entry are four launch modes of one driver.
  - IDE-core: the gui test store (`gui/src/util/test/mockStore.ts`, `render.tsx`) with core in-process instead of a mocked messenger. Whether core can be hosted in the gui vitest environment without the binary is **unverified**; the fallback is the binary over IPC, which is also how JetBrains talks to it.
- **First scenarios**: read a file; a shell command with no rule; a protected path; plan-mode edit; an MCP tool from two servers with one name; the engine throws; a subagent that needs an ask; cancel during a command.

### 4.2 Message-protocol diff test for JetBrains

It needs no Gradle and runs in the core job. An allow-list file names the messages deliberately not routed. Today it would report 20 missing, 7 stale and 13 unanswered IDE requests (section 5.1).

### 5.5 Recommendation (pending owner)

**Park now, and make ACP the JetBrains route.** Reasons:

1. No usage signal, and the README already disclaims it.
2. The plugin cannot be called safe as it is: the person's levels do not load (D5), and the panel gate is thin (D4).

Parking is reversible: nothing is deleted, and the diff test keeps a count of what a restart would cost.
