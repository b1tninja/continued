## 4. A golden corpus for command analysis and lint

What exists (verified by file names and heads): `corpus/verdicts.ts` (about 550 lines: shell, command, expected `reads | writes | unsure`), `corpus/verdictReport.ts` generating `plans/command-analysis-report.md` and checked by the build, `corpus/denyVariants.ts` (spellings of denied commands with advisory ids), `corpus/falsePositives.vitest.ts`, `corpus/knownGaps.vitest.ts`, `corpus/powershellOracle.vitest.ts` (Windows only: PowerShell's own parser as the oracle), `corpus/envVerdicts.ts`, `corpus/askProtectionsCorpus.vitest.ts`, `corpus/deputyCorpus.vitest.ts`, `injectionCorpus.ts`.

What to add, in order of value:

1. **One row schema, three expectations.** Each row: `id`, `shell`, `command`, `source` (`synthetic | advisory:<id> | real-sanitised | constructed`), and an `expect` object with any of `graph` (understood or the reason; programs and words), `verdict`, `effects`, `paths`, `hosts`, `lint` (codes that must fire and codes that must not), `decision` per level. One file per concern keeps diffs readable; a rows-must-have-an-id test and a "no new row without an expectation" test keep it honest.
2. **A syntax oracle per shell, run in CI on a runner that has the shell.** `bash -n` and `zsh -n` for POSIX, PowerShell's `Parser.ParseInput` for PowerShell (already used on Windows), nothing for cmd. A row whose graph says "understood" while the oracle reports a syntax error is a failure. This is the parser-differential test the GuardFall and CVE-2025-66032 class needs (section 6).
3. **An expansion oracle (proposed, not built).** For rows the graph claims to understand, run the command in a real shell with every program name resolved to a stub that prints its argv as JSON, in a temp directory with a fixed file set, and compare the argv to the graph's words. It catches quote-removal, `$IFS`, brace and glob, ANSI-C quoting and tilde differences, which is where the two readers have disagreed before (the environment-prefix case in `command-analysis.md` "Measured by P0"). Cost: a stub directory and a runner that is Linux or macOS for POSIX and Windows for PowerShell. Never run it on a row that is not marked safe to execute, and run it in the sandbox runner (Track SB), not on the developer's machine, because a mistaken row would execute.
4. **A held-out real-command set that is never committed.** ROADMAP B31c and B51 already describe this (counts only, the commands never committed). Keep the counts as the CI assertion (understood rate, YOLO ask rate under 20%, floor false allow 0) and the commands on the owner's machine or in the audit trail's "add to my cases" export (B66), masked.
5. **Real-world sources that can be committed.** Public advisories (extend B81: the confirmed rows of `research/agent-security.md` section 5, each with its id, constructed payloads labelled), the ShellCheck wiki's example per code for R5 (BSD or GPL licence not checked, so only cite codes and write own examples), and the bypass classes of section 6. Do not commit commands harvested from other people's traces.
6. **Property tests.** Already in the plan (`command-analysis.md` "How we will know it works"): appending `; <anything>` to a `reads` command never leaves it `reads` unless the tail is; an unquoted `>`, `$(` or backtick never yields `reads`. Add: permuting wrapper order and path or `.exe` spellings never loosens a deny.

For lint specifically: each rule needs a "fires" row, a near-miss "does not fire" row, and, for R1, a rate from the real set. R1's rule from `command-lint.md` (demote any rule over 5% false positives) is the acceptance.

### 5.1 Reviewer gate (B4, B12a, B46 to B54, B83)

Problem in user terms: Auto mode stays behind the experimental flag until a number says the reviewer is safe. The number does not exist yet because there are two eval sets and no agreed bar.

Design. B12a: write an importer from `auto/evaluation/cases.ts` (207 cases) into the `reviewEvalDataset.ts` format as `reviewer-full.json`, keep `reviewer-starter.json` as the quick set, and make `qualityBar.ts` the only gate; turn `runEval` into a wrapper that calls the new runner or delete it with its callers. Acceptance: one command `continuous reviewer eval --set full` and one pass/fail line that cites the bar. B47 (Clopper-Pearson upper bound beside every zero) is S and should ship with B12a, because "0 of 14" is already being quoted. B53 and B83: run in this order, each reporting the union of floor false allows: Haiku 4.5 `--repeat 3` (about USD 0.48), then Nova 2 Lite with `promptV3` and `tightenAllow` on (about USD 0.7). B46 (owner relabel review) blocks trusting any #553 number; it is a document task for the owner, 20 rows listed in the ROADMAP.

Alternatives rejected: raising the bar after seeing numbers (the point of a bar), a third dataset format.

Risks: spend is small but the result is a screening number; below ten repeats it is labelled as such (#517 convention). Overfitting the prompt to the 80 cases: B51 held-out sample first.

Dependencies: B12a before B13, B16 reports, B10's "result of the eval gate" line. Test plan: dataset round-trip test (207 in, 207 out, labels equal), a bar-threshold test with a fabricated result. Size: B12a S to M; B47 S; B83 measurement S plus spend; B48 to B51 S each, not before B12a. Acceptance: the Permissions page can show "checked on this model: pass or fail, guidance version".

### 5.4 Path analyser and what the shell cannot be told (B28, B31b, B31c, B76 to B80, H6)

**B28 (M, security).** Problem in user terms: with a sandbox on, commands that cannot escape are allowed without asking, but nothing tells the skip what the command touches. Per ROADMAP the skip "must never skip" until `touchedPaths` exists, so today the feature is inert.

Design: `commandPaths(graph, spec) -> {reads, writes, deletes, unresolved}` in a new `commandPaths.ts` next to `commandSpecs.ts`. Inputs are the understood command graph, `commandSpecs.ts` operand kinds (which P5 does not yet type for paths; add `operands: "path"` to the 15 or so programs that matter first: `rm`, `mv`, `cp`, `mkdir`, `touch`, `tee`, `sed -i`, `dd of=`, redirect targets, `Remove-Item`, `Set-Content`, `Out-File`, `New-Item`), the cwd and the workspace roots (`workspaceRoots.ts`). Output paths are resolved with `realPath.ts` (symlinks, junctions, 8.3, `\\?\`). Anything with an expansion, a glob, a `cd` into an unresolved place, an unknown program, or an unknown flag is `unresolved`, and `sandboxAutoApproval` treats `unresolved` as "do not skip". Alternative rejected: running the command in a dry-run mode (`--dry-run` is per program and a lie for most). Alternative rejected: deriving paths from the text scan in `protectedCall.ts` (that is the five-readers problem). Risks: a literal path that is a symlink created earlier in the same compound command (`ln -s / x && rm -rf x/...`): handle by treating any command that creates a link, `mklink`, `New-Item -ItemType SymbolicLink|Junction`, or `cd` after a write in the same command as unresolved for later segments. Windows: case-insensitivity, `%VAR%` in cmd is unresolved by definition, PowerShell `$env:` and `Join-Path` already have a resolver in `runtimeWriteTarget.ts` (reuse, do not rewrite). Test plan: table per program (path operand rows), property test (a literal in-workspace write resolves; anything with a metacharacter does not), and the deputy corpus extended. Acceptance (from ROADMAP): the 54 uncontained dangerous skips drop with the ask rules; the skip never fires without `touchedPaths`. Depends on P5's operand types and `W8c`.

**B31b/B31c (S each).** B31b is an owner-confirmed list of temp roots in user config (`terminal.tempRoots`), shown on the Permissions page, never inferred from the environment alone; `runtimeWriteTarget.ts` takes it as an extra proof. B31c is the standing replay with counts only; it needs the 1,013-command set, which is local, so the CI part is a skip-if-absent test and the owner runs it before a release.

**H6 (S to M, security).** `node -e`, `node -`, `python -c`, `perl -e`, `ruby -e`, `pwsh -Command` with file-writing APIs, and base64-decoded payloads are currently opaque to the classifier (candidates expand them only for deny and ask matching). Design: treat an interpreter with an inline script flag as `exec` (so it is never `reads`) and, when the script is a literal, run a small API scan for write calls (`fs.writeFile`, `open(..., 'w')`, `Set-Content`) to move it from unsure to `writes` with unresolved path; a base64 pipeline into a decoder into a shell is already covered by `no-fetch-and-run` only when fetch is involved, so add `decode | sh` as its own ask. Alternative rejected: parsing JavaScript or Python (a new parser per language; the ROADMAP's own position is that text gating is defence in depth). Risk: false positives on `node -e "console.log(1)"`; keep it unsure, not writes, unless a write API is seen. Tests: add rows to `verdicts.ts` for each interpreter and shell. The `.continuous/plans/*` protection during an item run is ok via `CONFIG_DIRS`; verify in the loop test, not here.

**B76 to B80.** B76 (flip the `readPolicy` default to workspace-only) needs the toolchain testing the ROADMAP names (build tools, package managers and language servers read outside the workspace); I would not flip a default for 2.16.0 without a measured count of asks per 100 reads. ## 8. Risks that cut across the tracks

- **Command text is read before the shell expands it.** Every rule in these tracks is defence in depth below a sandbox (Track W, SB). Nothing here should be described to a user as a boundary; the ROADMAP's "confined" wording rule applies.
- **Windows and PowerShell.** PowerShell 5.1 has no `&&`; `.` is dot-sourcing; backtick escapes; curly quotes are quote characters; aliases shadow GNU names; parameter abbreviation. cmd expands `%VAR%` before parsing and searches the current directory first. The corpus must run on a Windows runner (the PowerShell oracle already does), and any new rule needs a PowerShell and a cmd row.
- **False positives.** A new ask or lint stop costs a click or a round trip; measure asks per 100 calls and the 5% rule before promoting anything from warn to error.
- **Backwards compatibility.** B18's Automatic refusal and B76's default flip change behaviour for unattended runs; release notes must say so; no config key changes unless R2 and B31b add keys (both user-only).
- **Parser disagreement.** The tree-sitter second reader catches differences but is not bash; every new construct an owner wants to allow needs the expansion oracle row first.
- **Trust.** Every new setting here is classed (B21) as loosening, tightening or neutral and written only through the editor; R2 and B31b are loosening-class when they turn something off.
