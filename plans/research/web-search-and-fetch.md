# Web search, web fetch and web content: research and design (2026-11-11)

Status: research and design only, read from `origin/main` at `152451827`. Nothing was run: no model call, no GPU, no search request was sent to any backend, and no code was changed. Web sources were fetched on **2026-11-11** with WebFetch or WebSearch; every URL below carries that date unless another is given. Sources are marked P (primary: vendor documentation, terms, registry metadata, specification) or S (secondary: blog, aggregator, search-engine summary). A recommendation never rests on an S source alone. Anything dated before 2026-05-11 is flagged "old" (more than six months). Not legal advice: the Brave terms reading in section 3 is a summary of text, and the owner should have the storage clause read by someone qualified before a Brave default ships.

Scope: the built-in `search_web` tool, the `@web` provider, `fetch_url_content`, `@url`, `@docs` and the docs crawlers, and what the replacement for the upstream search proxy should be. The privacy report (PR #622, `plans/research/privacy-egress-licensing.md`, findings F1 and F2) established that `search_web` and `@web` post the query to an upstream-operated Cloud Run proxy together with an embedded key, the machine id, the OS and the extension version, and that the docs crawler can do the same for a site with `useLocalCrawling: false`. At the time of writing no pull request from a branch `egressfix` exists in `b1tninja/continuous` (`gh pr list` shows none, and `git fetch origin egressfix` fails), so the compatibility target below is the stated intent ("`search_web` becomes configured-or-hidden") and not a diff. The owner should reconcile section 7 with that pull request when it lands.

Three facts drive most of this. First, `search_web` is `allowedWithoutPermission` and is in every tool list (`core/tools/definitions/searchWeb.ts:28`, `core/tools/index.ts:34`), so today the model can send any string to a third party with no prompt and no scan. Second, the fork already has the hard parts of a safe fetch (resolve once, pin the address, guard redirects, ask on private targets, an outbound secret profile, a spotlight helper) but several are not wired where the data flows. Third, the field's strongest cheap control is not a filter but a rule about where a URL may come from.

## 2. What the code does today

All paths are under the repository root; line numbers are from `origin/main` at `152451827`.

### 2.1 `fetch_url_content`

- **Definition** (`core/tools/definitions/fetchUrlContent.ts`): `readonly: true`, `isInstant: true`, `defaultToolPolicy: "allowedWithPermission"` (line 30). `preprocessArgs` (33 to 44) resolves the host once and records `nonPublic` and `resolvedAddresses`. `evaluateToolCallPolicy` (47 to 56) lifts any policy except `disabled` to ask when `isPrivateFetchTarget` says so. The permission engine repeats this as the `private-url` protection (`core/tools/permissions/evaluate.ts:384`), which Hands-off and allow rules cannot loosen; only YOLO reaches past it.
- **Implementation** (`core/tools/implementations/fetchUrlContent.ts`): calls `getUrlContextItems(url, extras.fetch, { guardRedirects: true })` (12), truncates each item to 20 000 characters (7, 20 to 29) and appends a "Truncation warning" item that tells the model to "fetch specific sections", although the tool has no parameter for that. Spotlighting is applied only when `experimental.spotlightUntrusted` or `CONTINUOUS_SPOTLIGHT_UNTRUSTED=1` is set (40 to 48).
- **Retrieval and conversion** (`core/context/providers/URLContextProvider.ts`): `resp.text()` reads the whole body (63); `new JSDOM(html)` with no URL (65); `Readability.parse()` (66 to 68); `NodeHtmlMarkdown.translate` (69). If `Readability` returns nothing the content is the empty string (68). Nothing reads the `Content-Type`, the `Content-Length` or any size. There is no deadline except the connect timeout in `packages/fetch/src/fetch.ts:196`. The result carries the page title as the item name and the URL as the description (76 to 87); links are not extracted; relative links cannot be resolved because JSDOM has no base URL.
- **Redirects** (`URLContextProvider.ts:92` to `123`): up to five, one at a time with `redirect: "manual"`, the address of each hop resolved and pinned (`pinnedLookup`), a hop from a public host to a non-public one refused, a non-http(s) redirect target refused. An approved private start URL may stay private.
- **Address classification** (`core/util/networkAddress.ts`): IPv4 loopback, RFC 1918, CGNAT, link-local (so the metadata address), multicast and reserved (`a >= 224`) at 28 to 41; IPv6 with embedded IPv4 (mapped, compatible, NAT64, 6to4) at 88 to 110; names ending `.localhost`, `.local`, `.internal`, `.home.arpa` at 113; one resolution per host cached ten minutes (139, 158 to 173); a name that fails to resolve is "public" (170); `fetchwithRequestOptions` rewrites `localhost` to `127.0.0.1` (`packages/fetch/src/fetch.ts:101`).
- **Ask-unknown-host** (`core/tools/permissions/askProtections.ts:140`): acts only when the person's own config has a non-empty `trustedDomains` (142); a fetch to any other host asks. With no list the rule does nothing.
- **Secret scan on URLs:** none. The outbound profile of `core/util/secretScan` is used in production only by the auto-reviewer's shadow path (`core/tools/permissions/auto/shadow.ts:107`); the audit masker uses the at-rest profile (`core/tools/permissions/audit/mask.ts:186`) and already masks `secret-query` values in URLs (176).
- **Transport:** `extras.fetch` is `fetchwithRequestOptions(url, init, config.requestOptions)` (`core/core.ts:2204`). It honours proxy, `noProxy`, CA bundle, system CA store, client certificate and `verifySsl`. The address pin applies only on the direct path (`packages/fetch/src/fetch.ts:114` to `123`); behind a proxy the proxy resolves the name.

### 2.2 `search_web` and `@web`

- `core/tools/definitions/searchWeb.ts`: policy `allowedWithoutPermission` (28), no `preprocessArgs`, description tells the model to "use sparingly".
- `core/tools/index.ts:34` pushes the tool unconditionally; `core/tools/searchWebGating.vitest.ts` pins that.
- `core/tools/implementations/searchWeb.ts:10` calls `fetchSearchResults(query, 5, extras.fetch)`; each result is cut to 8 000 characters (5) with a truncation item; no spotlight, no scan.
- `core/context/providers/WebContextProvider.ts`: `TRIAL_PROXY_URL` (9), POST of `{ query, n }` with `getHeaders()` (16 to 25), which adds the embedded key, version, OS and machine id (`core/continueServer/stubs/headers.ts`). The `@web` provider sends `extras.fullInput`, the person's whole chat message and not only the typed query (52).
- The response shape is whatever the proxy returns: `ContextItem[]` (name, description, content). That is the only contract the replacement must keep for `@web`.

### 2.3 `@url`

`URLContextProvider.getContextItems` calls `getUrlContextItems(query, extras.fetch)` with no options (27): no redirect guard, a favicon fetch with the global `fetch` (`core/util/fetchFavicon.ts:7`, `37`). The URL is typed by the person, so the missing guard is a smaller concern than for the tool, but a typed URL can redirect to the metadata address.

### 2.4 Docs crawling and `@docs`

- `DocsCrawler.crawl` (`core/indexing/docs/crawlers/DocsCrawler.ts:43`): GitHub hosts go to `GitHubCrawler`; with `useLocalCrawling: false` the page URL goes to the upstream `/crawl` endpoint with the same identifying headers (`DefaultCrawler.ts:4` to `26`); otherwise `CheerioCrawler` (global `fetch` at line 94, same-hostname link filter, up to 50 pages per batch, depth 4, 1 000 pages), with the optional Chromium crawler behind `experimental.useChromiumForDocsCrawling`.
- `CheerioCrawler` reads each body whole, has no deadline and no size cap, ignores `robots.txt` (it lists the file only in an ignore-suffix list), follows redirects to any host (default `fetch`), and does not use `requestOptions`.
- Crawled pages are chunked and embedded with the configured embeddings model. They come back through `@docs` as context items with no spotlight. An injection planted on a docs site is therefore stored in the person's index and replayed on every retrieval ("stored injection"). I found no spotlight or notice wiring for `@docs` (`spotlightItems` is called only from `fetchUrlContent.ts`).

Do not switch on a benchmark from the vendors' READMEs.

### 4.2 JavaScript-rendered pages, PDFs, size, links, citations, cache

- **JavaScript rendering: out of scope for the fetch tool.** A headless browser adds a download of hundreds of megabytes, a process that executes attacker script, a much larger SSRF and credential surface (cookies, storage, WebSocket, service workers), and a cost the tool list cannot show. The fork already has an opt-in Chromium crawler for docs indexing (`ChromiumCrawler.ts`, one-time download behind consent); that is the right place for it. Anthropic's own fetch tool does not render JavaScript either and points to a separate browser-use client tool (P, web-fetch page).
- **PDFs:** worth adding later with `unpdf` or `pdfjs-dist` (size cap, page cap, text only). Many specifications and papers are PDFs; today they fail or return noise.
- **Size and truncation:** the field's pattern is a small default with an offset. The MCP fetch server pages with `start_index` and `max_length` 5 000; Anthropic's tool has `max_content_tokens`. Our 20 000-character cut with a message that tells the model to ask for a section it cannot request is a defect, not a policy (G5).
- **Links:** return a short list of the page's outbound links (absolute, deduplicated, same-page anchors removed, at most 20) after the text, and mark them as untrusted too. Needed for documentation browsing; also the data the URL provenance rule (section 7.5) needs.
- **Citations:** carry the URL, title and retrieval time in a fixed header line so the model can cite; nothing in the fork needs the vendors' structured citation blocks.
- **Cache:** a per-session in-memory map keyed by canonical URL with a 15-minute lifetime, as in Claude Code's WebFetch (its tool description states a 15-minute cache, P, this session's tool schema). Search results must be **in memory only and never written to disk or the index**, because of the Brave storage clause; the same rule is the safe default for every backend.

## 5. Security review

Threat frame: the "lethal trifecta" (Simon Willison, 2025-06-16, **old**: https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/): private data, exposure to untrusted content, and a way to communicate outward in one agent. A coding agent has all three by default, and `fetch_url_content` and `search_web` are the outward channel: the URL path and query, or the search query, are bytes the model chooses and a server the attacker may own receives them. Meta's "Agents Rule of Two" (2025-10-31, old; summarised in `plans/prompt-injection.md` section 2) says to hold at most two of the three in one session. The fork's existing answers are the private-URL ask, the injection notice and (optional) spotlight; the table lists what is missing.

### 5.2 What is already right

The classification is done once per host and the connection is pinned to the checked addresses (`networkAddress.ts:226`, `URLContextProvider.ts:92` to `106`), which is the control Gemini CLI documents and the MCP fetch server says it lacks. IPv4-mapped, NAT64 and 6to4 forms are handled by value (`networkAddress.ts:88` to `110`), and the WHATWG URL parser turns decimal, octal and hexadecimal IPv4 spellings into dotted form before our code sees the host, so `http://2130706433/` arrives as `127.0.0.1` (parser behaviour; to be confirmed by test T3, which I did not run). Redirect hops are re-classified. The private-URL ask cannot be loosened by an allow rule. Credentials are not sent across origins by `createWebFetch` (`packages/fetch/src/webFetch.ts:7`, which lists the credential headers it drops); node-fetch has no cookie jar, so cookies are not replayed.

## 6. Privacy of the query itself

A search query is outbound data. Queries written by a model from a conversation about someone's repository contain identifiers, file paths, error text with hostnames, and occasionally a pasted token. Backends differ in who sees it and for how long (section 3), and for the hosted ones the retention period is mostly unstated: Brave states none, Tavily and Kagi were not read, Exa and Brave offer zero retention only to Enterprise buyers (P, section 3.1).

Proposal (a gate on the search tool, never on the backend):

1. **Scan with the outbound profile** (`scanText(query, "outbound")`, `core/util/secretScan/scan.ts`): only high-confidence structural rules run, so a finding means a credential-shaped string. Verdict: **refuse** with a one-line reason; the model can rewrite the query. Redaction is the second choice: it changes what the model asked and hides that from it.
2. **Ask, do not refuse, for context-leaking shapes:** an absolute path inside a workspace folder or the home directory, a query over 256 characters, more than one line, or an internal hostname (`classifyHost` says non-public). The card says what it would send.
3. **First use per backend per session shows one consent card:** "Search sends your query to `search.example.org` (Brave). Queries are not private from that service." Allow for the session is a button.
4. **Log what was sent.** One audit line per search: backend id, host, masked query (`mask.ts` at-rest profile), result count, bytes. A person can read it with `continuous audit`. No query text on disk unmasked.
5. **Keys:** from the secret store only (section 7.2); the Tavily remote URL form with the key in the query string is refused by the config validator.
6. **No result persistence:** results live in the tool result only; nothing is written to the index or a cache file (Brave §3(b)(i)).

## 7. Design

### 7.1 Provider interface

```ts
// core/tools/webSearch/provider.ts (proposal; no file is created by this report)
export interface WebSearchQuery {
  query: string; // already scanned
  maxResults: number; // 1..10, default 5
  recency?: "day" | "week" | "month" | "year";
  allowedDomains?: string[]; // from the person's trustedDomains when set
}
export interface WebSearchHit {
  title: string;
  url: string; // canonical, tracking parameters removed
  snippet: string; // at most 300 characters
  publishedAt?: string;
}
export interface WebSearchProvider {
  readonly id: "searxng" | "brave" | "tavily" | "exa" | "mcp";
  /** Host the query goes to, for the consent card and the audit line. */
  readonly destination: string;
  search(q: WebSearchQuery, signal: AbortSignal): Promise<WebSearchHit[]>;
  /** One request that proves the key and the endpoint; never sends user text. */
  test(signal: AbortSignal): Promise<{ ok: boolean; detail: string }>;
}
```

An MCP-backed provider is an adapter over a named MCP tool (`mcp.server: brave`, `mcp.tool: brave_web_search`) that maps its result into `WebSearchHit`. It exists so a person with a working Brave MCP does not configure it twice; it gets the same scan, consent card and log, because the gate lives in our tool and not in the provider.

### 7.2 Configuration and visibility

Read only from the person's own user config (the rule `trustedDomains` already follows: never a workspace file or an assistant):

```yaml
# ~/.continuous/config.yaml
webSearch:
  provider: searxng # absent: the tool is not offered to the model
  searxng:
    url: http://localhost:8080
  # brave:
  #   apiKey: ${{ secrets.BRAVE_API_KEY }}
  # tavily:
  #   apiKey: ${{ secrets.TAVILY_API_KEY }}
  # mcp:
  #   server: brave
  #   tool: brave_web_search
  maxResults: 5
  privacy:
    onSecret: refuse # refuse | redact
    askOnPaths: true
```

Default: **no `webSearch` block, no tool**. `core/tools/index.ts:34` becomes conditional on a configured provider, `searchWebGating.vitest.ts` is inverted ("absent unless configured"), `@web` is registered only with a provider, `DefaultCrawler.ts` and the proxy constants are deleted. A workspace config or an MCP server may not set or change `webSearch`.

A `continuous test-connection --search` mode (the existing command is `extensions/cli/src/commands/testConnection.ts`; it already reads keys from named environment variables, never prints them, and records host names only): it calls `provider.test()` with a fixed harmless query, prints `ok` or the failure class (DNS, TLS, 401, 403 "JSON format not enabled" for SearXNG, 429), and, for SearXNG, whether `format=json` is allowed. The settings page gets the same button.

### 7.4 Result format (compact and cache-friendly)

```
web_search results for "<query>" via brave (5)
1. <title> | <host/path> | <snippet, at most 200 characters>
2. ...
```

Plain text, numbered, no timestamps, no request ids, tracking parameters removed, a stable order, and the same spotlight wrapper as fetch around the whole block (title and snippet are attacker text). Result text goes into the conversation once and is never rewritten, so it does not disturb the prompt-cache prefix. The tool description is short and static (the tool list is part of every request's cached prefix, Track Z). Rough cost: five results of about 250 characters is about 300 tokens (estimate at four characters per token, not measured); the fetch cap of 20 000 characters is about 5 000 tokens (estimate); Anthropic's own figures are 2 500 tokens for a 10 kB page and 25 000 for 100 kB.

### 7.6 Provider-native search tools

Expose them per model and only where the provider supports them, never by default:

- A model entry gets `webSearch: native` (off unless set). It is offered only when the provider family is on a known list (Anthropic API, OpenAI Responses, Gemini, xAI Responses) and not for an Anthropic model reached through a route that the vendor page does not list (Bedrock is unlisted; the setting is refused there with the reason, until tested).
- The first use per session shows the consent line "Web search runs at <provider> and sends your query and context there". The query goes to that provider anyway with the rest of the conversation, which is why consent is one line and not a hurdle; what changes is the provider also contacts third-party sites for you.
- **These calls are invisible to our policy engine**: no scan, no provenance rule, no private-URL ask, no audit line from us (the provider runs the search). Reduce the exposure with the vendor's own controls: `max_uses`, `allowed_domains` filled from the person's `trustedDomains`, and the basic Anthropic tool version because dynamic filtering is not ZDR-eligible. Log the `server_tool_use` query from the response into the audit trail after the fact.
- Adapter work: Anthropic results carry `encrypted_content` and `encrypted_index` that must be echoed back unmodified (P), so the provider adapter must preserve server-tool blocks verbatim in history; ageing or masking (Track V) must not rewrite them.
- Display rules: Anthropic and OpenAI require citations to be shown; Gemini requires the search-suggestion snippet. The chat already renders links; confirm before enabling.
- Cost is shown in the cost counter as a separate line (Anthropic $10 per 1 000, Gemini $14 per 1 000 after 5 000 free, xAI $5 per 1 000 unverified).
