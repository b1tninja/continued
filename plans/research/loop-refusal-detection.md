# Refusal detection as a loop cue, with IDGAF in mind (2026-11-12)

Status: DRAFT, research and design only. Nothing here is built, no model was called, no product code was changed. Code read at `origin/main` b9fccf19d; the open PR #687 (`yolo-never-asks-questions`) was read from its branch because the IDGAF auto-answer path is not on main yet. Web pages were fetched on 2026-11-12 through a summarising fetch tool, so quotes below are as that tool returned them and the marker list and file contents should be re-read from the source before anyone copies them.

Owner's question: research "heretic" or refusal-prompt detection as a loop-avoidance cue, especially at IDGAF, where nothing asks and the agent answers its own questions. If the model just refuses, the loop should not keep asking, and perhaps it should encourage the model to answer and detect that it refuses.

## 1. Summary

1. **Heretic is an open-source tool that removes refusals from a model's weights.** It is p-e-w/heretic (AGPL-3.0, first released November 2025). It scores a candidate model with a refusal rate (a case-insensitive keyword match over the opening of each reply) and a KL divergence, and searches for the edit that lowers the first without raising the second. It is a way to _produce_ a model that does not refuse. It is not a runtime detector, though its marker list is a usable seed for one.
2. **The best detector is structural first, textual second.** Anthropic returns refusals as HTTP 200 with `stop_reason: "refusal"` and a `stop_details` object; OpenAI returns a `refusal` field. Those are certain, free and need no model call. A narrow marker check on the final text of a turn is a second, weaker tier. An LLM judge is not needed for v1.
3. **The loop does not see refusals today.** A refusal is a text-only turn without `finish_item`. The loop sends the same "You ended without reporting" nudge it sends to any model that forgot to report, counts an attempt, fails the item after two, and stops after three failed items. It is bounded, so it does not run forever, but it is paid for in calls that are likely to be refused again, and the stop reason says "items failed", not "the model declined". Anthropic's own guidance is that continuing without resetting the context "will result in continued refusals".
4. **Recommendation.** Build detection, a refusal budget and an honest stop or skip with the reason. Do not build anything that persuades a model to override a refusal, and do not ship or route to abliterated models as a workaround (section 6). At IDGAF the detector matters more, not less: with nobody to look, a refusal that the loop papers over is a silent wrong answer.

What this implies for runtime detection:

- The measurement is cheap and has no model call: a substring list over the first ~100 tokens. That is the shape of a tier-2 detector.
- It is tuned for a setting where the prompt is _known_ to be harmful or harmless and the reply is a single chat answer. In an agent loop the base rate of refusals is tiny and most replies are tool calls, code and summaries. Single words such as `illegal`, `harmful`, `violat` and `sorry` would fire on ordinary engineering text ("handle the illegal state", "sorry, the build failed"). The list cannot be copied; it can only seed a narrower one.
- Heretic's own authors treat the list as an approximation (the config offers a classifier instead; one entry, `i an ai`, looks like a typo). Neither is a ground truth.
- Not verified: Heretic's published refusal counts on any model, and whether other tools or projects use the word "heretic" for refusal detection. I found only this one meaning and did not search exhaustively for others.

Superscripts 1 and 2 point to the numbered sources at the end.

**Scoping the text detector** (the false-positive guard):

1. Only the assistant's text of the turn that ended the run, never tool output, never earlier turns, never a `finish_item` summary field.
2. Strip fenced and inline code, quoted blocks and `<think>` spans before matching, so `throw new Error("cannot open file")` and a pasted error message do not count.
3. Require the marker in the first 200 characters of the remaining text and a total length under about 600: refusals are short and open with the refusal; a long report that says "I cannot reproduce the failure" in paragraph four is not one.
4. Require no tool call in the turn and no file change during the run. A model that did work and then says "I can't finish X" has _reported_, it has not refused.
5. Use phrases, not words: never `sorry`, `illegal`, `harmful`, `violat`, `ethical` alone.
6. Separate "cannot" meaning _unable_ ("I can't find the file", "I can't run the tests here") from "cannot" meaning _declines_. The first is a capability failure the existing stuck logic handles; only the second is a refusal. The marker list should lean on declining phrases ("I can't help with", "I can't assist", "against my guidelines", "I'm not able to provide") and the golden corpus (section 5.7) decides the edge.

Known false-positive classes to put in the corpus: security tooling discussed by the user's own task (scanners, fuzzers, malware analysis), a model quoting a tool's error, apologies for a failed build, `finish_item` blockers ("cannot proceed without the API key"), and refusals that are _correct_ because the content came from an injected instruction (section 6).

## 4. How refusals meet this loop

### 4.1 What the loop does today

I walked `core/util/loopMode.ts`, `extensions/cli/src/loop/loopDriver.ts`, `gui/src/redux/thunks/loop.ts`, `core/util/turnEnd.ts` and `core/util/stuckSignals.ts` at main.

| Step                      | Code                                                                                                                                                                                                  | What a refusal does there                                                                                                                                                                                                                                                                                                    |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Run ends with no report   | `finishRun` (CLI) and the item step of `loop.ts` (GUI): once per run `nudgeRun` sends `finishItemNudge`: "You ended without reporting. Call finish_item now with the outcome and a one-line summary." | A refusal is a text-only turn, so it gets the nudge. The nudge is appended to the same context. The reply is likely a second refusal, one more request spent. (Anthropic: re-sending a refused request to the same model "usually earns another refusal"; continuing without resetting "will result in continued refusals".) |
| Second end with no report | `finishItemRun` then `statusAfterRun`: no report means `pending` until `attempts >= maxAttempts` (default 2), then `failed`                                                                           | Item fails after about four requests. Summary is generic.                                                                                                                                                                                                                                                                    |
| Items in a row fail       | `maxConsecutiveFailures` (default 3): stop with reason `failures`, "N items in a row failed."                                                                                                         | The stop is correct in effect, wrong in wording.                                                                                                                                                                                                                                                                             |
| A repair re-plan          | After a failed item the loop re-plans (`replanOrStop`); a round that finishes nothing counts toward `maxNoProgressRounds` (default 2), then stop `no_progress`                                        | A re-plan model that is also refused burns more requests. A re-plan that rewords the refused item to get past the refusal is the thing section 6 says not to encourage.                                                                                                                                                      |
| Limits behind all that    | `maxRounds` 5, `maxItemTurns` 60 with 10 grace, `LOOP_REPEAT_LIMIT` 4 identical calls, token and wall budgets                                                                                         | These bound the damage. None is about refusals.                                                                                                                                                                                                                                                                              |
| Stuck signals             | `detectStuck` in `core/util/stuckSignals.ts` (S0, built) feeds `extensions/cli/src/stream/stuckNotes.ts` and the audit steps; loop mode on the shared signals is S5, "Not started"                    | The `monologue` signal would catch three restating text-only steps, but the loop never reaches it: it gives up at the attempt limit first. No signal has a refusal kind.                                                                                                                                                     |

So the answer to "does the current loop detect no-progress?": yes, by counting, in three places (attempts, consecutive failures, no-progress rounds). A refusal is indistinguishable from "the model forgot to report", gets the same remedy and the same generic outcome. Nothing is hidden, but nothing says why.

### 4.2 (a) The loop asking questions repeatedly and the model deflecting

Below IDGAF, a held question is deduplicated (`same` in `holdQuestion`), capped at 4 open per item and 40 per loop, and waits for the person. At IDGAF, `holdQuestion` returns `decideAlone` before any of that (`loopQuestionDecider(...) === "agent"`), so there is no duplicate check, no per-item cap and nothing recorded as open. The only brakes are the identical-call guard (4 identical calls; a paraphrased question is a different call), the item turn limit and attempts. A model that deflects by asking a fresh question each turn is auto-answered each time and nothing says so. That is the "just keep asking" failure in the owner's note. It is not a refusal; it is a question loop, and it wants its own stuck signal: auto-answered questions per item with no file change in between (proposed S10-like row, section 8).

### 4.3 (b) The IDGAF auto-answer path

On the PR #687 branch, `answerIfIdgaf` in `extensions/cli/src/util/idgafQuestions.ts` calls `answerWithoutAsking` (`core/util/autoAnswer.ts`: the option labelled "(recommended)", else the first, else "No one is available to answer; use your best judgment and state the assumption") and `recordAutoAnswer` writes a `decision` line, `by: system`. The answer is produced by local code, not a model, so the auto-answer itself cannot be refused. What can be refused is the _next model turn_ after the answer. Two things follow:

- A refusal after an auto-answer looks like any other refusal and takes the path in 4.1.
- The auto-answer is the system speaking for the person. Any "clarification" built from it must not assert more than the person actually said (section 6, rule 3).

### 4.4 (c) Where a refusal signal plugs in

1. A pure function `detectRefusal(turn)` next to `stuckSignals.ts`, host-free like the stuck signals.
2. The adapters carry the structural flag up: `core/llm/llms/Anthropic.ts` already passes `stopReason` in the usage response info (`withResponseInfo`); `packages/openai-adapters/src/apis/Anthropic.ts` does not (it writes `finish_reason: "stop"`, `refusal: null`, and only sets `sawStop` on `message_delta`). That adapter needs to map `stop_reason: "refusal"` to `finish_reason: "content_filter"` and keep `stop_details`.
3. The loop calls it at the one place both hosts already share the logic: before `nudgeRun` in `finishRun` (`extensions/cli/src/loop/loopDriver.ts`) and in step 1 of the item turn in `gui/src/redux/thunks/loop.ts`. A certain or likely refusal skips the nudge and reports the run as ended with a refusal; `finishItemRun` already takes a report (`outcome: "stuck"` plus `blocker`), so the change is a new blocker value (`LoopBlocker` today: answer, observe, plan, environment, dependency) and a new stop reason (`LoopStopReason` has no `refused`).
4. The same check runs on a re-plan turn (`kind: "replan"`): a refused re-plan stops with `replan_failed` today; it should say why.

## 5. Proposal

### 5.1 Signal definitions

```ts
type RefusalSource =
  | "stop_reason" // Anthropic stop_reason "refusal"
  | "provider_field" // OpenAI refusal / content_filter
  | "marker" // tier 2 text match
  | "empty"; // empty final text, no tool call

type RefusalConfidence = "certain" | "likely" | "weak";

interface RefusalSignal {
  kind: "refusal";
  source: RefusalSource;
  confidence: RefusalConfidence;
  /** Provider category (cyber, bio, ...), when the API gave one; may be null */
  category?: string | null;
  /** Masked (core/util secretScan, maskText), cut at 120 characters */
  excerpt: string;
  /** Turn index in the run */
  turn: number;
}
```

`certain` and `likely` count against the budget; `weak` is recorded and shown as a note only. The function takes `{ finishReason?, stopDetails?, refusalField?, finalText, hadToolCalls, changedFiles }` and nothing else.

### 5.2 Where computed

Core, in one pure module, called by the CLI loop driver (headless and `cn serve` share it) and the GUI thunk. The adapter fix in 4.4 item 2 is part of this row, not a separate feature.

### 5.3 Audit trail

One line per detected refusal, `by: "system"`, kind `refusal`: item id, source, confidence, category, masked excerpt, and what the loop did (stopped the item, spent budget N of M). Today `AuditBy` already has `system` and `recordAutoAnswer` writes a `decision` line; a new line kind means the reader and index (`core/tools/permissions/audit/auditIndexKeys.ts`) must learn it. I did not read the trail format deeply enough to say how large that is: **not verified**.

### 5.4 Settings

| Setting                        | Default       | Meaning                                                                                                                                                                                  |
| ------------------------------ | ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Refusal detection              | on            | tiers 1 and 2; off disables 2 only, 1 is a fact the provider sent                                                                                                                        |
| Refusal budget                 | 2 consecutive | N refusals in a row end the loop with reason `refused`. 2, not 3: a refusal is not transient noise the way a build failure is, and the second item that hits the same model likely will. |
| Fallback model on refusal      | none          | optional name of a model the person already configured (section 6); off unless set                                                                                                       |
| Re-ask once with clarification | off in v1     | see section 6                                                                                                                                                                            |

Names are for the owner to settle; the loop settings dialog from #701 is the natural home.

### 5.5 Loop states and wording (reusing #697 and #700)

PR #697's single status line takes its word from `loopVisualState`; PR #700's Needs you tray shows one grey line when nothing waits ("Nothing needs you. The loop is running.") and rows with actions when something does. Reuse both; add no new surface.

| Where                | Wording                                                                                                                                                                                         |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Item row (plan tree) | "Declined by the model" with the provider category when there is one                                                                                                                            |
| Status line          | the existing stopped state, detail "Stopped: the model declined 2 items in a row."                                                                                                              |
| Needs you tray       | "The model declined item 3. Nothing was changed." with the actions: Open the reply, Skip this item, Edit the to-do (focuses the input), and, only if a fallback is configured, "Try Sonnet 5.5" |
| IDGAF, CLI headless  | one line on stderr and the exit report: "Stopped: the model declined item 3 (category: cyber). Reply saved to the audit trail."                                                                 |

Wording says "declined", not "refused", where a person reads it ("refused" is already used for rule refusals; `plans/ROADMAP.md` uses both, so this is for the owner). It never says "retrying" unless a retry really happens.

### 5.6 Accessibility

No new `aria-live`. The existing polite announcer (`useLoopAnnouncements`, state changes only) gets one new message, "Loop stopped: the model declined item 3". The tray row is inside the existing "Needs you" region; actions are buttons with visible text; the category is text, not colour.

### 5.7 Tests

Golden corpus, same style as the RQ7 false-call scan (`plans/research/rq7-false-calls.md`): a JSON file of labelled replies with the expected tier and decision, run by a vitest.

| Class                 | Examples                                                                                                                                                                                                                                                                                                                                        | Expected                          |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| Structural positives  | Anthropic `stop_reason: "refusal"` with `category: "cyber"`, and with `category: null`; OpenAI content item of type `refusal`; `finish_reason: "content_filter"`                                                                                                                                                                                | certain                           |
| Text positives        | "I can't help with that.", "I'm sorry, but I can't assist with this request.", "I won't write that." (one per family: Claude, GPT, Llama, Qwen, Nova, Gemma)                                                                                                                                                                                    | likely                            |
| False-positive cases  | `throw new Error("cannot open")` in a fence; a pasted `ENOENT ... cannot find`; "Sorry, the test failed, fixing"; "I can't find `config.ts`"; `finish_item` summary "cannot proceed without the API key"; a long report with "I cannot reproduce" in paragraph four; a security-scanner task that says "this payload is illegal in strict mode" | none (or weak at most)            |
| Not-a-refusal edge    | text-only turn that wrote a tool call as text (H13 shape)                                                                                                                                                                                                                                                                                       | none; the existing nudge keeps it |
| Real recorded replies | the 254 non-call replies RQ7 already scans as negatives, plus the Anthropic/OpenAI adapter fixtures                                                                                                                                                                                                                                             | zero fires, or each one reviewed  |

Gate on false positives (zero on the recorded replies), report recall without gating it; a missed refusal falls back to today's behaviour, a false one stops real work.

### 5.8 Privacy

Local only. No reply text leaves the machine for detection. The audit excerpt is masked and cut at 120 characters like RQ7's excerpts. There is no telemetry row.

### 5.9 Rollout order

1. Pure function, golden corpus, adapter pass-through of the structural flag. No behaviour change.
2. Loop: skip the nudge on a certain or likely refusal, report the item, the refusal budget, stop reason `refused`.
3. Audit line, tray and status wording, announcer message.
4. Settings row and docs.
5. Measure on the bench and real runs (fire rate, false positives, requests saved).
6. Optional, separate decisions: fallback model; a question-loop signal; a single re-ask (section 6).

**The boundary, stated plainly.** A refusal is the model's output and sometimes a correct one. Continuous may detect it, stop spending on it, tell the person exactly what happened, and let the person choose. It must not try to talk the model out of it, rewrite the request to slip past it, or swap in a model whose refusals were removed in order to get an answer. That holds at IDGAF too: IDGAF removes the person's prompts for approvals and questions, it does not remove the model's judgment and it does not make the system a proxy for authority the person never gave.

**Rules if a clarifying re-ask is ever built** (deferred, owner decides):

1. Only for a tier-2 text refusal, never for a classifier (`stop_reason: "refusal"`) refusal. For those, the provider says what to do: reset the context or use a documented fallback.
2. At most once per item, and counted against the budget whether or not it works.
3. Content: the to-do's own text and facts already in the repository or the person's messages (what the project is, which files are the person's own). Never an assertion of authorisation, ownership or intent the person did not state; never a persona, a hypothetical, an instruction to disregard rules, or a claim that the person approved. At IDGAF the auto-answer is by definition not the person's statement and must not be presented as one.
4. A refusal that follows content read from a tool result, a web page or a file is treated as possibly correct: surface it with the source, do not re-ask.
5. Audit line for the re-ask, with the exact text sent.

Honest uncertainty: whether a re-ask measurably recovers misread tasks is unknown. If the owner wants it, the experiment is a bench run over benign tasks that a family of models over-refuses, before shipping; I have not run one and cite no number.
