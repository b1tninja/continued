The repository was read at `origin/main` 0d4fe36f3. Every URL was fetched on 2026-11-11 unless the text says otherwise. ## 0. Summary and ranked recommendations

1. **Hooks: we are ahead on safety and behind on compatibility.** Fail-closed defaults, a project hook that cannot approve, and a script-content fingerprint are better than Claude Code's documented defaults. But the same setting is spelled `onFailure` there and `onError` here with opposite defaults, we accept 17 event names and fire 7, and Claude Code now has 31 events, an `if` filter and an exec form (`args`) for commands. A hook file written for one tool is read differently by the other today. Section 2.
2. **Cheapest compatibility step**: accept `onFailure` as a synonym, add `args`, wire `Stop`, `SessionStart`, `SessionEnd`, `PreCompact`, `Notification` and `PermissionRequest` (row D4, with the dialect additions below). Effort small to medium, risk low.
3. **Upstream backlog**: of 60 triaged open issues, the largest cluster is requests for other editors (ACP already answers part of it), then chat layout in narrow sidebars, terminal output in remote hosts, and the edit tool overwriting files. Only a handful are cheap and unfixed here. Section 3.
4. **Planning**: the design in `task-planning.md` already matches what the field converges on (list as state outside the transcript, plan as a file, new context carries the plan). The gap is the plan **file lifecycle**: nothing resumes a plan from disk by itself, and the ROADMAP Track F table disagrees with the plan's own status line. Section 4.
5. **Code intelligence**: the evidence supports a grep-first agent with language-server tools, plus a structural repo map, and does not support shipping a dense vector index as the default. Our bundled embedding model (all-MiniLM-L6-v2) is the weakest option for code: trained on natural-language pairs and cut at 256 word pieces. Recommendation: keep L0 to L3 as written, make embeddings opt-in per machine class, and test one code embedding model on the 5090 before choosing. Section 5.

The Agent SDK uses the same JSON and the same precedence (`deny` over `defer` over `ask` over `allow`), adds `onFailure: "block"` per matcher, and says a callback that times out on `PreToolUse` blocks the call. The reference page and the SDK page disagree about whether a command-hook timeout blocks `PreToolUse`; we block, which is the safe reading of that disagreement. Claude Code also warns that `if` is best effort and that hooks that start background processes must redirect their output or the call is held (a 10-second wait, then "stdio went quiet"), the same hazard `hooks-wiring.md` records for our runner (U2).

### 2.3 Trust and security model

| Tool          | Project hooks                                                                                                                                                                                             | Managed only                               |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| Claude Code   | follow workspace trust; the docs say to review `.claude/settings.json` changes like code; `allowedHttpHookUrls` and `httpHookAllowedEnvVars` limit HTTP hooks; `if` is best effort                        | `allowManagedHooksOnly`, `disableAllHooks` |
| Codex         | non-managed hooks must be reviewed and are trusted by a hash of the exact definition; a changed bundled script needs re-review; `/hooks` UI; `--dangerously-bypass-hook-trust`                            | `allow_managed_hooks_only`                 |
| Gemini CLI    | not on the page read                                                                                                                                                                                      | not on the page read                       |
| Cline plugins | one worker thread per plugin, described as "crash isolation, not a security boundary"; 3 s hook timeout; five consecutive failures disable a plugin                                                       | none                                       |
| Here          | trust by project path plus a fingerprint of the definitions; PR #541 adds the sha256 of a workspace script the command runs; a project hook's `allow` is ignored; no environment variable can grant trust | none (open decision in `hooks-wiring.md`)  |

Findings:

1. **Where we are ahead.** Claude Code's documented default lets a failed or timed-out `PreToolUse` hook through unless `onFailure` is set; ours blocks. Claude Code has no rule that a project hook cannot approve; ours has one (D3a). Only Codex also hashes the exact definition, and only we hash the script a command runs (best effort; Codex re-reviews changed bundled plugin scripts).
2. **Where we are behind.** No managed-only mode, no HTTP URL allowlist, no output cap on `additionalContext` (a hook can fill the request), no `if` filter. Codex and Claude Code both ship a managed-only switch, which is what an organisation needs to make `onError` defaults enforceable (`hooks-wiring.md` asks the same question).
3. **The part both vendors say out loud.** Codex: tool hooks are "a guardrail, not a complete enforcement boundary" and some paths bypass them; Claude Code: use the permission system for hard enforcement. Our D4 docs page should say the same, and say which of our tool paths do not call the hooks (the CLI's search and glob tools, MCP tools, the IDE path until D5).
4. **Compatibility cost.** A shared file means `onFailure` is ignored here (the hook blocks anyway) and `onError` is ignored there (the hook continues anyway), so the same file fails closed in one tool and open in the other. Exit 2 plus stderr is portable across all four tools; the JSON `hookSpecificOutput` is portable between Claude Code, Codex and the Agent SDK.

### 2.4 Proposed dialect

Target the Claude Code settings shape and JSON, because Codex and the Agent SDK converge on it.

- Accept every Claude Code event name; log once and ignore those we never fire.
- Accept `onFailure: "block" or "continue"` as a synonym for `onError`. When both are present, `onError` wins. Keep our default of blocking, and document that a Claude Code file without `onFailure` will block here when it fails.
- Add input fields scripts read: `prompt_id`, `agent_id` and `agent_type` (subagent hooks), `model` (Codex) and `timestamp` (Gemini). All cost nothing to add.
- Add the `args` exec form for command hooks. It removes shell quoting and the Windows `cmd.exe` problem that `hooks-wiring.md` describes.
- Add an `if` filter using our own permission rule syntax, documented as best effort.
- Wire `Stop` with the `stop_hook_active` guard and a cap on consecutive continuations, then `SessionStart`, `SessionEnd`, `PreCompact`, `Notification`, `PermissionRequest`.
- Cap `additionalContext` (Claude Code 10,000 characters, Codex about 2,500 tokens); spill the rest to a file under the session directory.
- Environment: `CLAUDE_PROJECT_DIR` next to a native `CONTINUOUS_PROJECT_DIR`, on the scrubbed environment already used for agent commands.
- Managed-only: a `managedHooksOnly` setting honoured only from the user-level or an administrator-only path (owner decision, already open).

Not proposed: `mcp_tool` handlers, the model-request and model-switch events, `PostToolBatch`, `MessageDisplay`. None has a user request behind it.

### 4.2 What shape of artifact works

- **Checklist** (Roo, Gemini, Claude Code tasks): cheap, per-turn, good for keeping place. It fails when it lives only in the transcript; the fix everyone converges on is state outside the transcript, re-supplied each request. We built that.
- **Spec files** (Kiro): three documents with an approval gate between them. Good for large features and for review by people, costly for small changes; Kiro itself offers a one-pass Quick Spec to skip the gates, which is evidence that the gated flow is too heavy as a default.
- **Plan file** (Claude Code, Cline `/deep-planning`, Cursor): one markdown document the person can edit, then a build step. This is the middle shape and what P4 built.
- **Two models** (Aider, Cline per-mode models): a planning model and an editing model improve weaker editors; the gain is largest when the planner is a reasoning model. Our per-mode models are Track M.
- **Isolated subtasks** (Roo): the cleanest context control, at the price of a summary being all that returns. This is F6, blocked on E1.

Our shape (list as session state, plan as a file, steps seeding the list, new session carrying the plan) is the union of the first, third and fifth. Nothing in the pages read argues for adding a Kiro-style three-document flow as default.

### 4.3 Gaps in our plan work

1. **ROADMAP and plan disagree.** Track F lists F0 to F6 as scope with no state; `task-planning.md` records P1, P3, part of P2 and P4 as built. A reader should not need two files to learn this.
2. **Resumption is by hand.** A plan file written by Plan mode is read back "the next time the plan is loaded" but there is no command or startup path that offers it: `cn` with a `.continue/plans/` file in the workspace says nothing. Claude Code and Kiro both show their plan or task state on re-entry (Kiro in its task view; Claude Code's plan is re-injected after compaction per our earlier reading).
3. **Verification step missing.** Kiro's tasks and Roo's `preventCompletionWithOpenTodos` both attach completion to checks; ours is the opt-in block in F5 and nothing runs tests on a step.
4. **Headless.** Plan mode "writes the file and stops" in headless mode, which is right, but a `--plan-file` input to build from an existing file in `cn -p` is not described.

### 4.4 Minimal design for Track F, what remains

No new type. Three small additions to the built design:

- **`cn plan` surface**: `cn plan list` shows `.continue/plans/*.md` with the step counts read from the file; `cn plan build <file>` seeds the list and starts a turn (the same as the Build button). The chat shows a one-line notice at start if a plan file in the workspace has open steps and no list is loaded.
- **Step verification field**: an optional `check` string on a plan step (a command from the allow policy). The completion of a step with a `check` runs it through the normal permission path and records pass or fail in the item's `note`. Off unless the step has a `check`.
- **One reconciliation edit** to the ROADMAP: add a state column to Track F restating F0 to F4 from `task-planning.md`.

Not proposed: a three-file spec flow, a goal object, auto-spawned subtasks before E1 is done.

The plain reading: for the 5090 users a 0.6B code-capable model (Qwen3-Embedding-0.6B, Apache-2.0) is a few hundred megabytes and embeds a repository in minutes; a 7B model is possible but is a second large model resident beside the chat model. For CPU-only users the choices are MiniLM (cheap, weak on code) or no embeddings at all. No benchmark in these sources compares them on our task, so none of the above ranks them for us; the experiment below does.

### 5.4 Recommendation

1. **Default for everyone**: grep, read, `code_navigation` where a language server exists, and `view_repo_map` ranked by reference count. This is L0 to L3 as already planned; do not move embeddings ahead of L2 and L3.
2. **FTS and symbol tables without any embedding model** (L0) so CPU-only users get an index at all. This is the largest practical gain for them: today a fresh install indexes nothing.
3. **Embeddings are opt-in, per machine class**: on a machine with a capable GPU offer a Qwen3-Embedding-0.6B model through the user's own local server (llama-server or Ollama are already supported providers), not bundled; on CPU-only machines leave MiniLM as an explicit choice with the 256-piece limit stated in the setting's description. Never silently build vectors on a laptop.
4. **Guidance and a benchmark before any retriever** (L4): the turbopuffer-style finding in `codebase-index.md`, that the bottleneck is the model's policy for when to call the tool, applies to whatever is built. A retriever without turn-text guidance and a bench scenario will sit unused like today's index.
5. **Do not adopt jina-code-embeddings** as a default or bundle it: CC-BY-NC-4.0 on the model page.
