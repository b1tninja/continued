# Research: benchmarks, tool-call styles, command analysis and loop reliability

Status: DRAFT 1, written 2026-11-11. Docs only. Nothing here was run: no model calls, no GPU, no change to `plans/ROADMAP.md` or the command corpus. Rows and corpus cases below are proposals with TBD ids.

Sources are cited inline with the fetch date. Every URL was read (or searched) on **2026-11-11** unless a different date is given. "Search snippet" means the claim came from a web-search summary and the page itself was not opened; treat those as unverified. Anything published before 2026-05-11 is flagged **(older than 6 months)**.

Tracks covered: I (benchmark), M (which model does what), Q (tool-call styles), R (command lint), P (command analysis), S (stuck detection), T (loop budgets), Y (loop reliability), N (parallel waves).

## 1. Summary

1. **What we have is already a good fit for the question we ask.** `bench/` scores "valid tool call + exact-string edit + stay in policy" mechanically on a three-file seed; none of the public benchmarks measures that cell directly. The public ones are useful as priors for which models to try, not as our scorecard (section 2).
2. **SWE-bench Verified is no longer a safe headline.** OpenAI stopped reporting it on 2026-02-23 citing flawed tests and contamination. Prefer Pro (public set, 731 tasks) or a private set. For us neither runs on one 5090 in a useful time (section 2.2).
3. **The cheapest predictor of our failure mode is BFCL-style AST scoring plus the Aider polyglot "well-formed edit" rate**, not resolve rates. Both are what our `bench/` already approximates; add a paired, clustered statistic on top (section 2.4).
4. **Parser bugs in servers are still frequent and family-specific.** vLLM's Qwen3-Coder parser strips all leading and trailing whitespace of string arguments in v0.24.0 to v0.25.1 and `main` (open issue filed 2026-07-15), which silently breaks exact-string edits. Ollama's qwen3-coder parser drops a bare `<function=` call and turns malformed XML into a lost turn. llama.cpp's grammar and PEG parser disagree on value boundaries for Qwen3.6 XML. gpt-oss's Harmony parsers misread restarted headers in vLLM, SGLang and llama.cpp. Our recovery dialects (Q5, Q12, Q20) are still earning their keep, and Q9's "server did not parse a right call" bucket has public evidence (section 3).
5. **Add a whitespace-fidelity probe.** A one-call probe whose argument has leading indentation and a trailing newline would catch the vLLM strip bug on any served Qwen. Cheap, local, no model spend beyond one request.
6. **The R17 recommendation (persistent PowerShell `ParseInput` helper) is sound on the numbers and right to be deferred.** Public advisories show script-block and alias gaps in other agents; our shipped alias-table fix (#569) closes the cheaper half. Keep R24 as the trigger and keep shadow mode first (section 4.4).
7. **Our stuck detector is better calibrated in method than anything published, but the evidence is one session.** No other tool publishes a false-positive rate. The S3 experiment as pre-registered is sound; the missing piece is a second and third labelled corpus (section 5).
8. **Budgets: we have more dimensions than most (item, loop, share) but no CLI flags (T3) and no wall-clock hard stop outside loops.** Peers expose a dollar cap and a turn cap as flags; this is the cheapest gap to close (section 5.3).

### 2.2 Cost on a single 5090 or on Bedrock

- **Anything with Docker per task and 100+ step trajectories is out of reach on one 5090 at useful speed.** At about 20 tokens a second (the lab's own planning assumption, `bench/lab/README.md`), a 100-step trajectory of 30k tokens of output is tens of minutes per task; 89 tasks of Terminal-Bench is a day or more for a 27B-30B model and the model also fails often, so runs hit step limits.
- **Per-task cost at the frontier is $0.76 to $0.88 on Terminal-Bench** (Vals.ai snippet), so about $70 for one run of one model on Bedrock-class pricing, before the three runs per cell our own plan wants. Our account has Claude 5.5-generation and Fable at 0 TPM (workspace memory), so the frontier column is unreachable on Bedrock today.
- **Aider polyglot is the only public suite that is inexpensive enough to run locally** and has a format-validity column. Two caveats: the exercises are single-file and Exercism is public; and its edit formats (diff, whole) differ from our exact-string `edit` tool, so the "well formed" rate does not transfer one to one.
- **BFCL non-agentic categories are cheap** (single-turn AST, no environment). They measure whether the first call is right, which is axis (a). They say nothing about multi-step edits.

### 2.3 Which subset predicts "valid tool call + exact-string edit"

Nothing public predicts it well on its own. Ranked by usefulness for us:

1. Our own `bench/` Tier 1 and the capture battery (live-tool-call-findings), because they use our tool list and our edit tool.
2. BFCL V4 non-live and live AST categories as an external check on (a), published per model, free to read.
3. Aider polyglot's well-formed percent as an external check on (b).
4. tau2-bench's pass^k as the template for how to report reliability: a model that is right 80% of the time per trial is right all four times about 41% of the time, which is what a 20-step loop experiences.

### 2.4 Statistics for small-n comparisons

Our plan runs 3 to 10 per cell, and 8 for the Bedrock cells of Q42. At that size the choices matter more than the model.

Two rules for the existing plan: record temperature and seed per run (tau2 uses temperature 0 and four trials, per a secondary source, but a temperature-0 run of a local server is not deterministic under batching), and never compare cells with different n without the interval.

Readings:

- Most of the _drops_ are not the model writing the wrong thing; they are server parsers that are stricter than the model's drift (missing wrapper, duplicate close tag, extra whitespace). This is the answer Q10 wanted, from outside: **at least for Qwen XML on Ollama and llama.cpp, the model's form is often right enough for a lenient parser, and the server's strict parse loses the turn.** Our recovery is a lenient second parser, the shape the Ollama issue (#18563) itself proposes.
- The vLLM whitespace strip is the most dangerous because it is silent. Unlike a dropped call, the edit tool sees a call and fails to match; the agent retries with a different `old_string`.
- Version churn is high (a "fixed in" claim from a month ago may be stale). Strata's pinned version matters more than the doc.

### 4.4 Evaluating the "persistent PowerShell ParseInput helper" recommendation (R17)

Where it is recorded: ROADMAP R4, R17 to R25 and `plans/command-shell-dialects.md` section 7 (`ParseInput` appears in those; the spike itself is in a session scratchpad, not in the repo, so I could not re-read its numbers).

What the roadmap says it measured: start 311 to 343 ms, then p50 about 3 ms and about 91 MB; understands 99% of 1,013 real commands where the text scanner understands 30% and tree-sitter-powershell 97.7%.

My assessment:

| Question                                   | Answer                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Is it technically sound?                   | Yes. `Parser.ParseInput` is the same parser PowerShell uses, so aliases are not resolved by it (it gives `CommandAst` with the written name) but script blocks, sub-expressions, backtick escapes and `-EncodedCommand` operands are all structurally visible. That is exactly the class of the public Cursor and OpenClaw findings                                                                                                                                    |
| Is a persistent process the right shape?   | Per-call start is 170 ms (Claude Code issue, cited in `command-shell-dialects.md`) to 340 ms (spike); a persistent helper reduces it to milliseconds. Cost: 91 MB resident, an IPC channel, a lifecycle (idle exit, deadline, circuit breaker as in R17), and **a Windows-only code path that has to fail closed when the helper is down**                                                                                                                             |
| Does it change verdicts or only add facts? | Only facts, behind ask-only rules (R20), and shadow mode first. This keeps the failure mode "ask more", not "allow more"                                                                                                                                                                                                                                                                                                                                               |
| Is deferral reasonable?                    | Yes, on the roadmap's own logic: #569 fixed the alias table (153 aliases from `Get-Alias` on 5.1); the count that decides is R24 and has no data yet                                                                                                                                                                                                                                                                                                                   |
| What would change my mind?                 | (1) A single published bypass that our text scanner also misses; C9, C11 and C15 above are the candidates, and each is a 5-minute test against the current scanner. (2) R24 showing alias or definition misses above the owner's bar. (3) A real PowerShell host on every Windows install: Windows PowerShell 5.1 ships with Windows, so no extra install is needed; macOS and Linux users have no `pwsh` unless installed, so the helper helps only part of the fleet |
| Risk of building it                        | Medium: a long-lived child process in the extension host; Windows Sandbox and locked-down machines (AppLocker, Constrained Language Mode) can break it; the parse itself does not execute code, but starting `powershell.exe` runs the user's profile unless `-NoProfile` is passed (the spike used it). Owner decision                                                                                                                                                |

Recommendation: do not build now; run the cheap test (C9, C11, C12, C14, C15 against the current scanner, in the existing corpus differential run P0) and let the result be R24's first data point.
