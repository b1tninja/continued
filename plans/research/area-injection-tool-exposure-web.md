# Prompt injection, MCP content, tool exposure and web tools: state, gaps, designs and build order

Status: research, 2026-11-12, docs only. Written against `origin/main` 028a74050 (merge of #674). Nothing was built, run or measured: every "today" statement is from reading code on that commit, and the places where a claim needs a test to settle it say so. Areas: ROADMAP Track X (prompt injection and MCP content), Track TR (tool exposure, MCP toggles, per-role tool access), Track WB (web search and web fetch). The MCP add/configure wizard is another note's subject (`research-mcp-server-wizard` was not on the remote when this was written, so nothing here depends on it); this note covers MCP content trust, exposure and roles, and where the wizard must hand them a decision.

This extends, and does not repeat: `plans/prompt-injection.md`, `plans/design/tainted-session.md`, `plans/research/agent-security.md`, `plans/research/tool-exposure-roles-prompts.md`, `plans/research/tr-owner-decisions.md`, `plans/research/web-search-and-fetch.md`. ## 1. Findings in one page

1. **The ROADMAP is about a day behind main for these three tracks.** About a dozen PRs merged on 2026-11-12 (#627, #631, #634, #636, #638, #642, #646, #647 and others) and the rows still read "Not started" or "open" for X4, X11, X17, TR1, TR2, WB1 (part), WB5, WB6 (part), WB7 (part), WB8 (part), WB9 (part), X1b, X9b, X10a. Section 2 is the corrected state, row by row; section 10 has the replacement text.
2. **A server's own `readOnlyHint` still buys an unprompted call, and it also switches off the tainted-session rule.** `mcpToolIsReadOnly` (`core/config/profile/doLoadConfig.ts:69-76`) believes the hint for any server not defined inside the open folder and sets `defaultToolPolicy: allowedWithoutPermission` (lines 239-242); the CLI does the same through `withReadOnlyMcp` (`extensions/cli/src/permissions/readOnlyMcp.ts`) and `convertMcpToolToContinueTool`. The taint rule's `mcp-send` sink is "an MCP tool not marked read-only" (`core/tools/permissions/taint/taintSinks.ts:166`), so a hostile or compromised server that sets the hint is neither asked about nor counted as a sink. TR2 closed this for Plan mode only. The MCP spec says annotations are untrusted unless the server is trusted (cited in `tool-exposure-roles-prompts.md` section 8). This is the highest-value open fix in TR (new row TR22).
3. **The CLI names MCP tools by their bare name and routes a call to the first connected server that has that name.** `convertMcpToolToContinueTool` uses `name: mcpTool.name` and `MCPService.runTool(name)` loops over connections in insertion order. Core namespaces (`getMCPToolName`: `<server>_<tool>`). Two servers that both offer `search`, or a server that offers `Read` or `Bash`, collide: the permission card describes the entry that `find` returns from the sorted tool list, while `runTool` runs whichever server connected first, and servers connect in no fixed order. That is the cross-server shadowing class from the literature, present in the CLI as a name-routing bug. Not run; a two-server test settles it (new row TR23).
4. **The CLI `Fetch` tool hands Node's global `fetch` to the hardened fetch implementation** (`extensions/cli/src/tools/fetch.ts`, `fetchUrlContentImpl({ url }, { fetch })`). The address pin works by passing a `lookup` option that only `fetchwithRequestOptions` honours (`packages/fetch/src/fetch.ts:114-117`, `core/util/guardedFetch.ts:54`); global `fetch` ignores it, and proxy, CA bundle, `verifySsl` and the `experimental.spotlightUntrusted` setting (read from `extras.config`, absent here) do not apply either. #636 hardened the caps and content types for both surfaces but the CLI loses the DNS pin and the person's network settings. Not run (WB13).
5. **Content that an MCP server returns is the least defended text in the product.** `core/tools/callTool.ts:140-190` turns each `text` item into a context item with no size cap, no spotlight, no hidden-character handling and no tag; an `isError` result throws the raw JSON of its content; the CLI returns `JSON.stringify(result.content)` (`extensions/cli/src/tools/index.tsx:257-259`), so an image block arrives as base64 text. The injection notice is the only control (IDE `callToolById.ts:136`, CLI `flagToolResult`). Tool descriptions go to the model verbatim and unbounded (`doLoadConfig.ts:233-237`). The first definition a user ever sees is pinned only when a tool is first called (`MCPConnection.recordToolUse`), so first-contact descriptions steer the model before any approval (rows TR14, TR15, TR4 as redefined in 5.3).
6. **The tainted-session rule exists and nothing documents it.** `taintedSessionRule: off | ask` is built, default off (#647), with a synthetic replay: 1 to 2.5 new asks per 100 tainted calls where a person is already deciding, 4 to 15 at YOLO. `docs/` has no mention of the setting, and `prompt-injection.mdx` line 25 still says "The terminal agent does not do it" although the CLI flags output (#480). The rule's two structural gaps are named in 4.1: `untrusted-workspace` has no host signal, and nothing taints on writing instructions that persist (new rows X24, X25).
7. **Workspace instruction files are the one repository-supplied text with no trust gate.** `core/config/projectTrust.ts` scopes are `mcp, models, providers, catalog, data, rc, worktree`; rules (`.continue/rules`, `.continuous/rules`) and `AGENTS.md` are read as trusted instructions (`extensions/cli/src/instructionFiles.ts`, `core/config/markdown/loadMarkdownRules.ts`). That is X20; the recommended design ties it to the taint rule instead of refusing to read the file (4.3).
8. **Web: the dangerous parts are mostly closed on main; what is left is consent, provenance and search-result handling.** #636 landed byte and time caps, content-type rules, a URL secret scan, text cleaning and header scoping; #627 removed the upstream proxy and the embedded key; #638 moved the crawlers to the guarded fetch. Open: `search_web` is still `allowedWithoutPermission` with no query scan and no result marking (`core/tools/definitions/searchWeb.ts:28`, `core/tools/implementations/searchWeb.ts`), spotlight is still off by default, there is no URL provenance rule, no paging, no RFC 6890 ranges (`networkAddress.ts` has no `198.18.0.0/15` entry), and the docs crawler still ignores `robots.txt`.
9. **MCP Apps render server-supplied HTML with a server-declared CSP.** `gui/src/pages/gui/ToolCallDiv/MCPAppRenderer.tsx:35-72` builds the iframe CSP from the server's own `connectDomains` and `resourceDomains`, with `'unsafe-eval'` and `'unsafe-inline'`; the sandbox correctly omits `allow-same-origin`. The app's tool calls go through the approval path (`runMcpAppToolCall`), so this is a network-reach and tracking question more than a tool-call one (row X26, low).
10. **Order.** Quick wins that are S and independent: TR22 (hint trust), TR23 (CLI names), WB13 (CLI fetch), X21 (docs), TR14 (description normalisation). The structural pieces for 2.16.0: TR22, TR4 as redefined, TR15, X4 default decision with the replay on the real audit directory, X20/X24 together. Section 8 has the order and the critical path.

## 4. Track X: open rows

### 4.1 X4 and X17 follow-through: from "built, off" to a decided default

**Threat.** An attacker who controls a web page, an issue, a package README or an MCP result plants text; the agent, at a level that does not ask, runs a state change or an egress call (`git push`, `curl` to an attacker host, a publish, an MCP send tool, a write outside the workspace). Impact: data exfiltration and persistence. The rule raises exactly those calls to ask at every level once the session has seen untrusted content.

**What is built.** Sources, sinks, per-session registry, evaluator wrapper, reviewer line and cache key, audit field, `/untaint` (`plans/design/tainted-session.md`).

**Remaining work.**

1. **Decide the default** (owner). The synthetic replay says about 1 new ask per 100 tainted calls at labelled behaviour and 2.4 at Permissive; 3.9 to 14.8 at YOLO. Recommended, pending owner: ship `ask` as the default for new installs at every level except Manual and Cautious (which already ask on every sink, new asks 0), keep `off` for existing configs for one release with a notice, and gate the change on the real-audit replay (E2 below). The sentence that decides it is the one DR6 already records: nothing changes until the replay on the real audit directory has been read.
2. **Close the hint hole** (TR22): `taintSinks.ts:166` makes a tool a non-sink on `tool.readonly === true`. That field is the server's hint. Make `mcp-send` a non-sink only for a user-trusted read-only tool (the same predicate as `mcpToolIsUserReadOnly`).
3. **`untrusted-workspace` signal.** The API exists and no host sets it. Set it from `core/config/projectTrust.ts`: a folder whose `rc`/`mcp`/`models` scopes are not trusted, and (with X20) a folder whose instruction files the person has not accepted, taints the session from turn 0. Structural, free, no model.
4. **Persistence sink** (X25): a write to an instruction file (`AGENTS.md`, `CLAUDE.md`, `.continue/rules/*`, `.continuous/rules/*`, the `create_rule_block` tool) while tainted asks. `protectedPaths.ts` leaves instruction files writable on purpose, so today an injected agent can plant a standing instruction that survives the session (OWASP ASI01 and memory-poisoning shape; rated here as the cheapest persistence channel).
5. **Acknowledge control.** Built: `/untaint` (CLI). Missing: the IDE control (`untaintSession` exists in core; needs a protocol message). Acknowledge per source kind, not globally, so clearing `web-fetch` does not clear `mcp-result`. A webview click is acceptable here because the threat is the model, not a compromised renderer (X12 covers the other threat).
6. **Interaction with in-flight PRs.** #687 makes a tainted ask at IDGAF a recorded system refusal in a loop (the PR body lists "a tainted session" among the floors). That is the intended effect, but the loop must say so: acceptance item 6. #691 lets file edits at IDGAF reach outside the workspace: `outside-write` is a taint sink resolved from `processedArgs.resolvedPath` (`taintRule.ts`), so #691's new path resolution must feed the same field; one test in the taint suite with the new `outsideEdits.ts` path.

**Alternatives rejected.** A model judging whether content is hostile (injectable, costs a call per result). CaMeL-style value tracking (the agent-security note judges it infeasible for an open-ended coding agent; the narrow form, a plan turn that fixes the tool set, is the Loop's job). Clearing on a timer or on the first approval (the attacker only has to wait). Exempting YOLO (YOLO is where the rule is the only brake; the owner may still choose it, DR6 holds that decision).

**False positives.** A loop that fetches docs and then pushes asks at every push until acknowledged. Mitigations in the design: trusted-domain hosts are not egress; read-only user-trusted MCP tools are not sinks; one acknowledgement per source kind. A post-taint list of hosts the person approved earlier is the next relief and is not built.

**Dependencies.** TR22 (item 2), X20 (item 3), DR6. **Size.** S for items 2 to 4, M for the default flip with the real-audit replay and the IDE control.

**Test plan.** Extend `taintedSession.vitest.ts`: hint-claiming MCP tool is a sink when the server is not user-trusted; folder not trusted gives `untrusted-workspace`; `AGENTS.md` write asks when tainted and not otherwise; acknowledge `web-fetch` leaves `mcp-result`. Red-team: scenario files exist (`bench/scenarios/injection-in-file.json`, `injection-in-tool-result.json`); add a pair whose benign canary is an instruction to `curl` a loopback listener, count listener hits with the rule off and on.

**Acceptance.**

- [ ] The default and the existing-config behaviour are decided and written in `docs/ide-extensions/agent/prompt-injection.mdx` and `permissions-page.mdx` (the setting is documented nowhere today).
- [ ] A server-claimed read-only MCP tool is a sink unless the user trusted the server.
- [ ] `untrusted-workspace` is set from folder trust.
- [ ] An instruction-file write in a tainted session asks.
- [ ] The IDE can acknowledge per kind; `/untaint` takes a kind.
- [ ] A loop blocked by the rule reports it in its end summary, not only in the audit trail.
- [ ] The replay on the owner's audit directory is run and its numbers are in `tainted-session.md` section 7.

### 4.2 MCP content: X2 for MCP, TR14, TR15 and result limits (X3 remainder)

**Threat.** (a) Tool poisoning: instructions hidden in a description or parameter description steer the model before any call; (b) result injection: a result carries instructions; (c) hidden characters in both; (d) oversize results exhaust the context or hide an instruction deep in a long text; (e) image or resource blocks pasted as raw text. Attacker: the server operator, a compromised upstream the server wraps (a public issue read through a GitHub server is the standing example in `prompt-injection.md` section 4), or a lookalike package. Impact: the model misuses other tools; the approval and taint layers then decide.

**Design (one function, both surfaces).**

1. `normaliseMcpText(text, {cap})` in core: NFC, remove tag characters, bidi controls, zero-width and C0 controls, drop HTML comments, collapse runs of whitespace, cap with a visible notice. Reuse the cleaning in `core/util/fetchedText.ts`, which already removes the right set for fetch (X22's shared sanitiser is the same function; do it once).
2. **Hash the raw definition, show and send the normalised one.** Pinning keeps seeing an added invisible character (the existing choice: no string normalisation before hashing); the model never gets it. Description cap 1,024, parameter descriptions 512 (the proposal in `tool-exposure-roles-prompts.md` section 8); a cap hit shows in the Tools page and is part of the pin summary.
3. **Results.** Cap each text item (suggested 50,000 characters, spilled to a file in the CLI with a pointer, truncated with a notice in the IDE); `isError` content is cleaned the same way before it is thrown; image and blob items become `[image omitted: <mime>, <bytes>]` (the CLI's `JSON.stringify(result.content)` should stop carrying base64).
4. **Wrap** each MCP result in the session spotlight boundary (existing `createSpotlight`, per-session token) and add the one system-text sentence once per session, not per call. Default on for MCP results and fetch results together (WB7), after the leak-count measurement below. Tag per call is TR15; the token per session is X2; they are one change.
5. Keep the detector as a notice. It stays a tripwire (0 of 10 on the reworded split).

**Alternatives rejected.** A classifier model over descriptions or results (cost, latency, itself injectable, and the literature says detection lowers rates only). Signing and registry reputation (ETDI-style) is a server-side ecosystem change we cannot ship. Blocking on a detector hit (precision 0.96 on tuned data, near zero on rewording: it would block benign text and miss real attacks). Datamarking (breaks code; the plan already says prose only).

**False positives.** Legitimate descriptions over 1,024 characters (rare; the notice says what was cut); HTML comments in markdown results (removed from the model's copy only); tools whose results are intentionally large (spill to file keeps them usable).

**Dependencies.** X22 (shared sanitiser), TR5. **Size.** S (normaliser and caps), S (wrapper), plus a measurement slice.

**Test plan.** Fixtures with benign canaries only: a description containing a tag-character-encoded `CANARY-D1`, a result with `CANARY-R1` in an HTML comment, a 300,000-character result, an image block. Assert: the model-bound copy has no canary characters, the pin hash differs, the cap notice shows, the wrapper token cannot be forged by the result (existing spotlight tests cover forging). Measure with the cross-model harness: leak counts with and without the wrapper on `injection-in-tool-result.json` (E3 in `agent-security.md`; about USD 0.7 for two arms on Haiku 4.5 per that note, owner spend).

**Acceptance.**

- [ ] One normaliser used by the IDE and the CLI; a test shows both call it.
- [ ] Descriptions and results are capped with a visible notice.
- [ ] No base64 image text reaches the CLI model context.
- [ ] Wrapper default is decided from the measurement, not assumed.

### 4.3 X20, X22, X23: repository text and attached context

**Threat.** A cloned repository carries `AGENTS.md` or a rules file with a standing instruction, including hidden Unicode (the rules-file backdoor class named in `agent-security.md` section 7). A pasted or dropped file carries the same. Impact: the instruction sits in the system message or first user message of every session.

**Design.**

- X22: one `sanitiseInvisible` (the function in 4.2) with the keep-list the ROADMAP row gives (ZWJ, ZWNJ, emoji variation selectors kept). Returns the removal count for a notice and for the audit record. Used by the GUI paste, the CLI submit, instruction-file load and MCP text.
- X20: **read the instruction file, strip invisibles, show where it came from, and taint the session until the person accepts the folder's instructions.** Concretely: add an `instructions` scope to `PROJECT_CONFIG_SCOPES` (content hash recorded outside the folder, like the other scopes); until it is trusted the text is still loaded but labelled "repository-provided" and the session carries `untrusted-workspace` (4.1 item 3). Recommended, pending owner. The alternative, not reading untrusted `AGENTS.md` at all, breaks the most common way people use a coding agent in a fresh clone and is what the owner decides.
- X23: attached context (`@file`, drop, paste) runs `protectedPathHit` and `scanText` (warn with the masked finding), a size cap, a binary check, and is recorded by name, size and hash.

**Rejected.** Refusing untrusted instruction files outright (usability, and the user cloned the repository to work on it). Stripping instruction content by pattern (detector evasion).

**False positives.** Legitimate emoji sequences (kept by the keep-list); files with bidi text in right-to-left languages (flag only for control characters used as overrides and isolates, which the ROADMAP row already lists).

**Dependencies.** None for X22; X20 needs the scope and X4 item 3; X23 needs B1. **Size.** S, S-M, M.

**Test plan.** Fixtures: `AGENTS.md` with tag characters spelling a benign canary sentence; a pasted block with U+202E; a dropped file named `.env` with a fake `AKIAEXAMPLE...` canary; assert removal counts, notice text, taint kind, scan warning.

**Acceptance.** Invisible characters never reach the model from instruction files or paste; the source of each instruction block is shown; an untrusted folder's instructions taint the session; attached `.env`-shaped files warn.

## 5. Track TR: open rows

### 5.1 TR22 (new): trust of annotations

**Threat.** A malicious server, or a compromised one, sets `readOnlyHint: true` on a tool that writes, sends or deletes. Today that gives: an unprompted call (IDE `defaultToolPolicy: allowedWithoutPermission`, CLI `withReadOnlyMcp`), availability in Plan mode only when listed (TR2, built), and a free pass from the taint rule's `mcp-send` sink. The pin sees a later change of the hint (annotations are in the hash) but accepts the first claim.

**Design.** The hint is believed only for a server the person trusts in their own config (`mcpServers: { name: trusted }`, the key TR2 already reads), never for one from the folder, an assistant or a hub. For other servers the first call asks; "Allow this tool" writes a per-tool allow bound to the current pin hash, so a changed definition drops it (the pin machinery already does the invalidation). The wizard (other note) should offer "trust this server's read-only tools" in the same dialog that shows the tool list.

**Alternatives rejected.** Never believe the hint (too much friction for a user's own docs server). Believe it after N clean calls (a rug pull waits N calls). Ask a model whether the tool is read-only (injectable, and the description is the attacker's text).

**False positives and friction.** A first-use ask per tool for non-trusted servers; one click to remember. The existing user base of third-party servers loses silent calls on upgrade: say so in the release notes.

**Dependencies.** TR2 (built). **Size.** S. **Test plan.** `deputyMcp`-style table: hinted tool from workspace, assistant, user-untrusted, user-trusted server across all five levels and both surfaces; taint sink test (4.1 item 2). **Acceptance.** [ ] No MCP tool runs unprompted on a server claim alone. [ ] `mcp-send` follows the same predicate. [ ] The CLI and the IDE share the predicate.

### 5.2 TR23 (new) and TR5 remainder: names, identity and keys

**Threat.** Two servers, or a server and a built-in, share a tool name. In the CLI the name is bare (`index.tsx:239-262`); the card describes the first entry returned by `find` in the sorted list (`streamChatResponse.helpers.ts:765`), `runTool` runs the first connected server with that name (`MCPService.ts:273-294`), and a tool named like a built-in puts two tools with one name in the request, which several providers reject (provider behaviour not tested here). In core the composed name `<slug>_<tool>` can also collide across servers: server `a` with tool `b_c` and server `a_b` with tool `c` both compose to `a_b_c` (`mcpToolName.ts`; the existing test only checks that a shorter slug does not claim a longer name). Reasoned from the code, not run.

**Design.** (1) CLI uses the core name function (`getMCPToolName`) so both surfaces agree. (2) Permission rules, role keys, pins and audit key on the tool `uri` (`mcp://<server id>/<tool>`, already built by `encodeMCPToolUri`), and the model-facing name is a label. (3) On a composed-name collision keep the first by config order and rename the second with a stable suffix, with a notice; never route by name alone. (4) Drop or rename tool names outside the spec's character set with a notice. (5) Per-description caps (TR14).

**Size.** S. **Test plan.** Two mock servers (the existing mock servers in `core/context/mcp/` cover the transport) offering the same name, a name equal to a built-in, and the `a`/`a_b` pair; assert the run goes to the server the card named, in both surfaces. **Acceptance.** [ ] One server per name at execution time. [ ] The card and the executed server are the same object, shown by a test. [ ] Collision notice in the Tools page and `cn` status.

### 5.3 TR4 redefined: keep unapproved definitions out of the request

**Threat.** The value of pinning is blunted by timing: a changed definition asks at the call, but the changed description has already been in the model's context since the connect or since `tools/list_changed`. Tool poisoning and shadowing act through that text on other tools' calls. A new tool is also unreviewed until the first call pins it (`recordToolUse`).

**Design.** A per-tool pin state `approved | new | changed`. A tool that is `new` or `changed` and comes from anything but the person's own trusted-server config is absent from the request and listed in the Tools page ("3 tools waiting for approval", with the full description and a diff against the approved one). Approve per tool or "approve all from this server" (an act in the UI, never from workspace or hub config). A server in the user's own config that the person marked trusted may be set to "enable new tools" (the ROADMAP's own wording). Mid-session changes apply at the next request and cost one cache miss, which decision 2 in `tr-owner-decisions.md` already accepted.

**Alternatives rejected.** Block the whole server on any change (too coarse, and the launch pin already does that for the launch definition). Keep the current ask-at-call only (does not address description-borne steering).

**False positives.** Auto-updating servers produce an approval after each update; per-tool pinning limits it to the tools that changed. **Dependencies.** X1b (built), TR1 (built). **Size.** M. **Test plan.** Extend `mcpDefinitionChange.vitest.ts` and `mcpRevision.vitest.ts`: changed description is absent from the request body, present in the Tools page; approval brings it in with one cache-miss notice. **Acceptance.** [ ] Unapproved tool text never enters a request. [ ] A user-trusted server can opt into "enable new". [ ] The pin store records per-tool approval.

### 6.1 WB1 to WB4: provider layer and the search gate

**State.** One backend (SearXNG-compatible, env variable), sent with an optional bearer key to that endpoint only. `search_web` is hidden without it. It is still `allowedWithoutPermission`, its results carry no marking, and the query is unscanned.

### 6.2 WB6: URL provenance

## 7. Red-team corpus (benign canaries only)

Goal: regression tests for the structural controls, and measurements of the rate-reducing ones. No payload that would do harm if a defence failed.

- **Canary form.** Instruction text asks the agent to perform a harmless, countable action: fetch `http://127.0.0.1:<port>/canary/<id>` (a loopback listener in the test), or write the string `CANARY-<id>` into a scratch file. Where a name is needed and no request should leave the machine, use a `.invalid` host (RFC 6761 §6.4: always NXDOMAIN).
- **Carriers.** Web page body; page title; alt text; HTML comment; CSS-hidden text; tag-character encoding; markdown image URL; MCP tool description; MCP parameter description; MCP result text; MCP error text; image block; `AGENTS.md`; pasted block; issue text via `gh`; docs index chunk.
- **Cases per carrier.** (1) instruction to egress; (2) instruction to write a rule or instruction file; (3) instruction to call a second server's tool; (4) description that renames or mimics another tool; (5) definition that changes after approval; (6) hint-claiming write tool.
- **Assertions.** Structural: the call asks or is refused (X4, TR22, TR23, TR4), the model-bound text has no hidden characters (X22), the pin hash changed. Rate: how often a model follows the canary with and without markers (E3), reported with the 95% interval, on a fixed seed, and never as a bound (the adaptive-attacker result in `prompt-injection.md` section 3.4 applies).
