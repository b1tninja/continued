# Telling the agent about its shell on Windows, and when to use WSL

Research and design report, 2026-11-12. Code read on `origin/main` at `ee644eb15` (which has #759, `plans/research/shell-awareness.md`), with the open pull requests #756 to #758 (shell context), #763 (environment fact detectors) and #765 (the IDE tool sentence for Windows) read as diffs. `plans/ROADMAP.md` is not edited: section 10 holds the exact row text. Releases use even minors: 2.16.0 is being cut, so "2.18.0 candidate" means the release after it.

This report builds on `shell-awareness.md` and does not repeat it. That report settled who reads a command (the outer shell, spawned or unknown, and the interpreters inside it). This one asks what goes wrong when a model writes a command for the wrong shell on Windows, what to tell the model so it writes the right one, what to say when it does not, and whether a person should be able to send commands to WSL instead.

Convention: "measured" means run on the review machine in a scratch directory outside the repository, with benign commands only (`echo`, `cd`, `pwd`, temporary files, `node -e`, `--version`). "Verified by reading" names the file and line. "Primary" means a vendor's own documentation or source, read on the date given. "Unverified" means from memory, a search snippet or a secondary source.

## 1. Summary

1. **The cheapest failures are the commonest, and they are certain.** On Windows PowerShell 5.1, `&&`, `||`, a heredoc, a trailing `&`, `[ -d . ]` and backticks inside a double-quoted string are parse errors, and when PowerShell cannot parse a command, none of it runs (measured, section 3). The fix for each one can be stated exactly. The existing command lint (`core/tools/permissions/commandLint.ts`, CL001 to CL045) already finds most of them before the command runs, but it reports `&&` only as a warning, with a quote check that a nested quote defeats, and it runs after the person has approved the command (section 6).
2. **The expensive failures are the silent ones.** These commands run and report success while doing the wrong thing. Measured on 5.1:
   - `echo $FOO` prints an empty string.
   - `where node` is `Where-Object` and prints nothing.
   - `echo *.txt` prints `*.txt`.
   - `rm -rf d1; echo done` exits 0 after a parameter error.
   - `node -e "process.exit(3)"` comes back as exit code 1 (the real code is lost), and with `; echo DONE` after it, as 0.
   - `echo hello > f.txt` writes UTF-16LE with a BOM.
   - `Write-Output 'café ✓'` reaches the tool as `caf\x82 \xfb`, which the IDE tool decodes as GBK into mojibake.
   - A JSON argument to a native program loses its inner quotes (`'{"a":1}'` arrives as `{a:1}`).
3. **Three commands hang until the timeout, because the shell is waiting for input nobody can type.** These are `curl -s --version` (the `curl` alias is `Invoke-WebRequest`, which prompts for its missing `-Uri`), `Read-Host`, and `Remove-Item` on a folder with files in it (a confirmation prompt). They hang because the product starts PowerShell without `-NonInteractive` and leaves its standard input open. With either fixed, all three fail at once with a clear message (measured, section 3.6). This is a one-line product fix (EV24).
4. **What the model is told is thin or wrong.**
   - The IDE tool says "optimized for win32 and x64 and shell powershell.exe" (`core/tools/definitions/runTerminalCommand.ts:27`), fixed once at module load.
   - It says the same when the person chose WSL or a container, and when the window is remote (verified by reading). #765 improves the Windows sentence but keeps it static.
   - The CLI's sentence is right per mode (`extensions/cli/src/tools/runTerminalCommand.ts:85-99`).

   Section 5 proposes one short paragraph per shell (about 90 to 130 tokens for PowerShell 5.1), derived from the measured catalogue and computed from the executor, never from `os.platform()`.

5. **Do not rewrite commands.** VS Code's Copilot agent rewrites `&&` to `;` for PowerShell (primary, section 8). The rewrite changes what the command means: after `;`, the next step runs even when the previous one failed. The design here keeps the lint's rule: reject before running, with the exact fix in the message, and never change the text after it was approved.
6. **WSL is already a machine-level choice** (`continuous.terminal.shell: wsl`, `CONTINUOUS_TERMINAL_SHELL`, W1 in `plans/isolation.md`). The questions left open are three. Should the product suggest WSL when the model keeps writing bash? Should a "prefer WSL for POSIX commands" mode exist? What does forcing WSL change?
   - **Recommended, pending owner:** keep the default on PowerShell. Offer WSL with one notice per session, after repeated bash-isms, and only when a distribution is installed. Do not build per-command routing in 2.18.0.
   - When WSL is on, tell the model the facts that differ, measured in section 7:
     - Windows environment variables are not passed (WSLENV).
     - `/mnt/c` is about 90 times slower for a file walk than the Linux file system.
     - A script with CRLF line endings fails.
     - Windows programs need `.exe`.
     - The distribution has its own `python3` and `node`.
7. **No published evidence separates model families** on this mistake (section 8). Issues show the same mistake from Claude, Gemini and Cursor's agents, despite instructions. One text for every model, with the corrective lint, is the evidence-backed position. Per-family variants should wait for the benchmark row EV37.

## 2. Machine and method

Review machine: Windows 11 Pro build 26300, Windows PowerShell 5.1.26100.9711, `cmd.exe` 10.0.26300, Git for Windows bash 5.3.9 (MSYS2), WSL 2 with Arch Linux (default) and `docker-desktop`, Node 25.9.0. Console code page 437 (`[Console]::OutputEncoding` IBM437, `$OutputEncoding` us-ascii), culture en-US. **`pwsh` is not installed** (not on PATH, no `C:\Program Files\PowerShell`); its column comes from Microsoft's documentation and is marked so. No PowerShell profile exists, so the product's "profile runs first" made no difference here.

A Node harness spawned each probe the way the product does:

| Shell          | Invocation (the product's, where it has one)                                                                                                     |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| PowerShell 5.1 | `powershell.exe -NoLogo -ExecutionPolicy Bypass -Command <cmd>` (`core/util/shell.ts` `resolveShell`), standard input an open pipe as in `spawn` |
| cmd            | `cmd.exe /d /s /c "<cmd>"`, as hooks run (`extensions/cli/src/hooks/hookRunner.ts:118-123`)                                                      |
| Git Bash       | `C:\Program Files\Git\bin\bash.exe -lc <cmd>` (the product never spawns it; shown because models write for it)                                   |
| WSL            | `wsl.exe -d archlinux -- bash -lc 'source <(echo <base64> \| base64 -d)'` (`wslArgs`, `sourceEncodedArgs`)                                       |
| PowerShell 7   | Not run; from documentation                                                                                                                      |

The environment was the machine and user `Path` from the registry, the way an editor started from the Start menu sees it. That `Path` holds `C:\Program Files\Git\cmd` (so `git`) but **not** Git's `usr\bin` (so no `grep`, `sed`, `head`). A second run put `usr\bin` first, the way an editor launched from a Git Bash prompt inherits it. In the clean run, `grep --version` fails. With `usr\bin` first, it prints `grep (GNU grep) 3.0`. So whether Unix tools exist under PowerShell depends on how the editor was started, and the text of the command cannot tell. Each probe ran in a new empty folder. Usernames and host names are redacted to `<user>`.

Documented for 5.1 (§8 F2): "`Out-File` and the redirection operators `>` and `>>` create UTF-16LE"; "`Set-Content` and `Add-Content` use `Default` encoding" (ANSI); "`Get-Content` ... uses the `Default` ANSI encoding" when there is no BOM. A file the model writes with `>` is therefore unreadable to `git diff`, to a test fixture loader, or to the model's own next `grep`. The tool description already says to write files with the edit tools (`runTerminalCommand.ts:33`). The guidance below adds the reason.

## 4. The ten failure modes that matter most

Ranked by how often models write the mistake, from the issues in section 8 and the lint's existing rules, weighted by how much it costs when the shell accepts it silently.

| #   | Failure                                                                                                                                       | Shells affected                                 | What happens                                                                  | Caught today                                                    |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- | ----------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 1   | `&&` / `\|\|` chains                                                                                                                          | PS 5.1 (parse error); cmd `;` the reverse       | Nothing runs                                                                  | CL040, warn only, crude quote check, after approval             |
| 2   | Exit status lost: `-Command` returns 1 for any native failure; `; echo` hides it; `$?` is a boolean; `2>&1` makes `$?` false                  | PS 5.1                                          | The model believes a failed step passed, or the reverse                       | No (`withRealExitCode` exists, unused by the terminal tools)    |

## 5. What to tell the model

### 5.1 Principles

- **Compute the sentence from the executor that will run the command**, not from `os.platform()`. `getCommandExecutor().describe()` already exists, and the CLI uses it. The IDE tool's constant is wrong in WSL mode, in container mode and in a remote window (EV21).
- **Say what to do, not only what not to do.** Every "no" carries its replacement. Issues show models ignoring a bare "do not use &&" (Gemini #21997: "despite instructions not to", §8). A replacement they can copy holds up better (unverified; EV37 measures it).
- **Spend tokens only on mistakes that fail silently or are frequent.** A parse error is caught by the lint for free, so it gets few words in the prompt and an exact hint at run time.
- **The text goes in the tool description**, which is cached with the tool list. Do not repeat it per turn. One shell per session, so the text is stable (see #764 on cache stability).

### 5.2 Text per shell (proposed)

Windows PowerShell 5.1 (default on Windows; about 125 tokens):

> Commands run in Windows PowerShell 5.1 (powershell.exe), not bash. No `&&` or `||`: use `a; if ($?) { b }`. No heredocs, `export` or `VAR=x cmd`: use `$env:VAR='x'; cmd`. Use `2>$null`, not `2>/dev/null`. `curl`, `ls`, `rm`, `where` are PowerShell aliases: call `curl.exe`, `where.exe`, `Remove-Item -Recurse -Force`; grep/sed/head may be missing (use `Select-String`, `Select-Object -First`). Quote an exe path as `& "C:\path\x.exe"`. Paths are `C:\...` or `C:/...`, never `/c/` or `/mnt/c/`. Nothing can answer a prompt: pass `-Force` or `-Confirm:$false`. `>` writes UTF-16: write files with the edit tool. After a native program, `$LASTEXITCODE` holds its exit code.

PowerShell 7 (`pwsh`, if SH8 ever chooses it; about 60 tokens):

> Commands run in PowerShell 7 (pwsh). `&&` and `||` work. Otherwise PowerShell syntax: `$env:VAR='x'`, no heredocs (use the edit tool), `2>$null`. `ls`/`rm` are aliases of Get-ChildItem/Remove-Item; call `curl.exe` explicitly. Paths are `C:\...`. Nothing can answer a prompt: pass `-Force`.

cmd (only hooks run here today; for hook documentation, SH9):

> Hook commands run in cmd.exe: chain with `&&` or `&` (`;` is not a separator), `%VAR%` for variables, double quotes only (single quotes do not quote), no Unix tools.

Bash in WSL (the CLI's sentence, extended; about 80 tokens):

> Commands run in bash inside WSL (archlinux), starting in the workspace folder; Windows drives are `/mnt/c/...` (slow for large trees). Use bash syntax and Linux paths. The distribution has its own tools (`python3`, `node`, `git`), not Windows'; a Windows program needs `.exe` (`cmd.exe /c`, `node.exe`). Environment variables from Windows are not passed. Files with CRLF line endings break bash scripts.

Git Bash (never spawned by the product; included only if an "external shell" mode is ever added):

> Commands run in Git Bash (MSYS2 bash on Windows): bash syntax, paths `/c/Users/...` or `C:/...`; arguments that look like paths are converted for Windows programs (`/b` becomes `B:/`; write `//b` or set `MSYS_NO_PATHCONV=1`).

The PowerShell 5.1 text changes in one respect when the session probe (EV22) finds Git's `usr\bin` on PATH: "grep/sed/head may be missing" becomes "grep, sed and head are Git for Windows' copies". The probe runs once per session (`Get-Command` for a fixed list), not once per command, as `shell-awareness.md` §6 decided.

### 5.3 Per model family

No published comparison was found (§8 F14). The issues show Claude (anthropics/claude-code #45831, #64254), Gemini (gemini-cli #21997, #27097) and Cursor's agent all writing `&&` for PowerShell 5.1, so no family is safe to leave out. **Recommended, pending owner:** one text for all families now. Measure first-attempt correctness per family with and without the text (EV37) before adding variants. The one variant that might pay is for small local models, where 125 tokens is a measurable share of the context. Those get the first two sentences only (EV37 decides).

## 6. Corrective feedback: the shell-hint layer

### 6.1 What exists

`commandLintGate` (`commandLint.ts:455`) runs inside both terminal tools before the command is spawned (`core/tools/implementations/runTerminalCommand.ts:149-156` and `:180`, `extensions/cli/src/tools/runTerminalCommand.ts:107-113`). An `error` finding always stops the call. A `warn` stops it once, and the same text sent again runs. The message is returned in place of a result: "The command was not run: ...". Under PowerShell it has CL001 (heredoc), CL002 (`export`), CL003 (`VAR=x cmd`), CL040 (`&&`, warn), CL041 (`/dev/null`), CL042 and CL043 (other dialect, with advice). The detector (`detectShell.ts`) is evidence, never a source of truth (`shell-awareness.md` §6).

Three things are wrong with it as a hint layer:

1. **It runs after the approval.** The gate is inside the tool implementation, so the person is asked to approve a command that is certain not to run, and then the model sends a corrected one that needs a second approval (verified by reading: the policy path, `core.ts` and the card, does not call `lintCommand`; only the rule tester does, `testToolCall.ts:693`).
2. **`&&` under 5.1 is a warning, with a quote test that misses nesting.** It is a certain parse error outside quotes and here-strings. The test `/['"][^'"]*(?:&&|\|\|)[^'"]*['"]/` excuses any command in which some quoted text contains `&&`, even when another `&&` is outside quotes (`echo "a && b" && echo c`).
3. **It says nothing after a run.** Silent failures (section 4 rows 2, 3, 5, 8) are visible only in the output: "is not recognized as the name of a cmdlet", "A parameter cannot be found that matches parameter name", "Cannot find path 'D:\c\...'", "missing mandatory parameters".

### 6.2 Design

**(a) After a run: a hint appended to the result**, never replacing it. Hints are matched on the shell kind, the command's first word and the error text. Each is one line beginning `Shell hint:`. At most two per result, and none when the exit code is 0 and stderr is empty.

| Signal (PowerShell 5.1)                                                                  | Hint                                                                                           |
| ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| "The term 'X' is not recognized" where X is a Unix tool                                  | The PowerShell for X (the lint's table), or "Git's usr\bin is not on PATH here"                |
| "A parameter cannot be found that matches parameter name 'la'" after `ls`, `rm`, `cp`    | "`ls` is Get-ChildItem here: use `Get-ChildItem -Force`" (and so on)                           |
| "Cannot find path 'D:\c\" or 'D:\mnt\'                                                   | "PowerShell paths are `C:\...`; `/c/` and `/mnt/c/` are bash forms"                            |
| A native program's exit code is not 0 but the line exits 0 (needs EV23's real exit code) | "Step N exited with code K; `;` does not stop on failure: use `if ($?) { ... }`"               |
| "missing mandatory parameters" after the `curl` or `wget` alias                          | "`curl` is Invoke-WebRequest here: call `curl.exe`"                                            |
| The command timed out while the last output line ends in `:` or a `[Y] Yes` prompt       | "The command was waiting for input; pass `-Force` or `-Confirm:$false`" (moot once EV24 lands) |

**(b) Before a run: reject with the fix, never rewrite.** Certain parse errors stop the call before approval (EV26). The card does not ask for a command that cannot run. The model gets the lint message with the corrected form shown as text:

```text
The command was not run: Windows PowerShell 5.1 cannot parse it.
- SH-PS001 (column 12): `&&` is not a statement separator in Windows PowerShell 5.1.
  Instead: cd app; if ($?) { npm test }
Fix it and call again.
```

The suggestion is shown, not run. The model sends it back as a new tool call, which is approved as written. Rewriting silently was rejected for three reasons. It changes meaning (`;` runs the next step after a failure, which is why Copilot's rewrite is wrong in general). The approval would cover text the person did not see. And the audit record would hold a command nobody wrote. A rewrite offered as a button on the card ("Run as `a; if ($?) { b }`") is possible later. The person would then be approving the rewritten text, so it is the same rule.

**(c) Suggest WSL to the person, not to the model.** When WSL is `ready` (`wslStatus`) and the session has had three or more certain bash-isms rejected, show the person one notice per session: "The model keeps writing bash. Commands can run in WSL (archlinux) instead. [Use WSL] [Keep PowerShell]". Telling the model "wrap it in `wsl -- bash -c`" was rejected. That command runs a different toolchain without the host's environment. Allow rules never cover a launcher (`shell-awareness.md` §6 rule 5), so every such command asks. And the card would say "Runs through: bash in WSL" for a choice the person never made.

**(d) Auto-route only when the person opted in, and decide before the approval.** A "prefer WSL for POSIX commands" mode would classify each command and pick the executor before the policy runs. The card would show "Shell: bash in WSL" (SH4), and the rules would be evaluated under bash. Routing after approval is never allowed. **Recommended, pending owner: do not build this for 2.18.0** (EV33). It makes consecutive commands run in two environments with different `PATH`, environment and tools, which is the "different results" failure of row 10 made worse. "Force WSL" (the existing setting) is predictable; "prefer" is not.

### 6.3 Detection rules (the pure detector, EV27)

The detector takes the command text and the interpreter family and version (from `executionShell` and #756's `classifyInterpreter`). It returns `{rule, severity, span, message, suggestion}`.

- **Tokenize, do not regex the whole text.** Skip single-quoted and double-quoted strings, here-strings (`@'`...`'@` and `@"`...`"@`), `#` comments and `<# #>` blocks. The PowerShell escape is the backtick. `&&` inside `bash -c '...'`, `cmd /c "..."` or `wsl ...` belongs to the inner interpreter: the classifier gives the inner text, and the detector does not read it with PowerShell rules.
- **Version gate.** `&&`, `||` and `??` are 5.1-only findings. Under `pwsh` 7 they are valid. Under an unknown PowerShell version (a remote terminal reporting `pwsh`: VS Code's `TerminalState.shell` uses `pwsh` for both versions, §8 F10), they are a warning, not an error.
- **Certain (error) under 5.1:** `&&` and `||` outside strings; `<<WORD` heredoc; a trailing `&` outside strings; `[ ` as the first token followed by `-d`/`-f`/`-z`/`-n`; a backtick before the closing double quote.
- **Certain under PowerShell (any version):** `export NAME=` at statement start; `NAME=value cmd` at statement start; `2>/dev/null` and `>/dev/null`.
- **Likely (warn):** `$NAME` where NAME is all capitals and not a PowerShell automatic variable (`$HOME`, `$PWD`, `$PID` and so on are excused); `$(...)` that contains a Unix tool name; `source`; `set -e`, `set -o`; a quoted exe path at statement start without `&`; `where` without `.exe`; a JSON-looking single-quoted argument to a native program (`'{"`).
- **False positives to pin in the corpus:** `&&` inside quotes, in a here-string, in a comment, in `cmd /c "a && b"` or `bash -c 'a && b'`, in a URL query (`'https://x?a=1&&b=2'`, quoted), and under pwsh 7 and bash; `$HOME` and `$env:X`; `mkdir -p` (works in 5.1); `cp -r` (works); `cat file` (works).

### 6.4 How it composes

- **With the shell context (SH rows).** The detector needs the outer shell's family and version. Its input is `executionShell()`, and #756's `interpretersOfCommand` tells it which spans another interpreter reads. With an unknown outer shell (a remote window), no certain finding is raised. The interpreter is unknown, so `&&` may be right.
- **With the lint.** The detector becomes the lint's PowerShell half (CL001 to CL003 and CL040 to CL041 move onto it). It is not a second gate. The lint keeps its "warn stops once" rule.
- **With approvals.** Certain findings are computed in the policy step, before the card. A certain-to-fail command is answered to the model without asking the person (EV26). Warnings still go to the card, shown as a line: "This looks like bash; it runs in PowerShell 5.1".
- **With hooks.** A `PreToolUse` hook sees the command the model wrote, and a hook that rewrites the command (if hooks ever may) is subject to the same rule: the card shows the rewritten text. The hint text is not hook-visible state.
- **With the audit.** Each rejection records the rule ids, so the rate of bash-isms per model and per shell can be counted. That count is the evidence the per-family question (5.3) lacks.

## 7. WSL: prefer, force, and what changes

### 7.1 Settings and UX

- **Keep the setting machine-scoped**, as it is (`continuous.terminal.shell`, `"scope": "machine"`, `extensions/vscode/package.json:160-174`). A workspace must not be able to move commands out of the person's chosen shell. A per-workspace "this repository lives in WSL" preference is better answered by opening the folder with Remote WSL, where the existing remote path applies.
- **Values:** `default` | `wsl` | `container` today. Add nothing in 2.18.0. `prefer-wsl` stays an owner question (EV33).
- **First run on Windows:** no question. Most people never see a bash-ism problem once the lint and the prompt text are right, and a first-run question about shells is noise. The notice of 6.2(c) asks at the moment it is relevant.
- **Status chip:** "Shell: PowerShell 5.1", "Shell: bash in WSL (archlinux)" or "Shell: remote terminal (not known)" in the chat footer and on the card when it is not the default (SH4 carries the label). Clicking it opens the setting.
- **Settings page text:** one paragraph naming what changes (7.2). It must not call WSL a sandbox (7.3).

### 7.3 Sandbox and permissions

WSL is not a jail. The Windows drives are mounted read-write. Interop runs Windows programs as the Windows user. Microsoft: "Have the same Windows administrative rights as the calling process" (§8 F5). The existing setting text says so ("It is not isolation by itself"), and that stays. When WSL is the executor:

- The policy reads the command as bash (`resolveShell` kind `bash`), and the rules and vouching follow.
- A Windows path in a deny rule (`C:\Users\...\secrets`) does not match `/mnt/c/Users/.../secrets` today. The path guards should normalise `/mnt/<x>/` to `<X>:\` when the executor is WSL (EV32; unverified whether #744's path guards already do this).
- `cmd.exe /c` and `powershell.exe` from inside WSL are launchers. The classifier already names them (#756), and they are never vouched.

What the field shows: everyone tells the model the shell. Two vendors (Gemini, Codex) and Claude Code's PowerShell tool moved to `pwsh` when present, because instructions alone did not stop `&&`. The design here is the same as theirs in what the model is told and differs in two places: it rejects with an exact fix instead of rewriting, and it stays on 5.1 until the owner decides SH8.

## 11. Open questions for the owner

1. **The default shell on Windows stays Windows PowerShell 5.1.** Recommended, pending owner: yes for 2.18.0, with EV21, EV23 to EV26. Revisit `pwsh` (SH8, EV40) after EV37 shows whether the text and the lint suffice.
2. **Certain lint findings answered before the card (EV26).** Recommended, pending owner: yes. A person should never approve a command that cannot parse.

4. **The WSL suggestion goes to the person, once per session, after three certain bash-isms (EV29).** Recommended, pending owner: yes; three is a guess to tune from the audit counts.
5. **`prefer-wsl` per-command routing (EV33).** Recommended, pending owner: not in 2.18.0.
6. **WSL stays a machine-scoped setting, with no first-run question.** Recommended, pending owner: yes.
7. **`-NonInteractive` (EV24).** Recommended, pending owner: yes. A script that wanted a prompt has no one to answer it anyway.
8. **UTF-8 output (EV25)** changes the bytes a profile or script that set its own code page sees. Recommended, pending owner: yes, set it before the command, so a command can still set its own.
