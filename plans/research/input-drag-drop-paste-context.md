# Chat input: paste, drag and drop, rich clipboard and @ context

Research report, 2026-11-12. Evidence is read from `origin/main` at `ecc11d03e` (the worktree for this report) and from primary sources cited by URL. Nothing here is built. The rows that come out of it are `UX20` to `UX32`, `X22` and `X23` in [`../ROADMAP.md`](../ROADMAP.md).

Where a claim comes from reading source but has not been run on a real host, it says "predicted". Phase 0 (UX21) exists to turn every prediction into a measured row.

## 1. Summary and recommendation

1. Keep text as text. The editor schema has no mark nodes, so pasted formatting is already dropped, but three leaks remain: a remote `<img>` in pasted HTML becomes an image node, hidden Unicode passes through untouched, and nothing says so. Make plain text a guaranteed property of the paste path, not a side effect of the schema (UX22, X22).
2. Ctrl+V and Cmd+V paste plain text. Ctrl+Shift+V is **dead in the VS Code webview today** (predicted from VS Code source, section 4): fix it to mean plain text, which is the platform convention.
3. "Paste as Markdown" is an explicit action, never a default. Reach it from a right-click item, a command-palette entry and one keyboard shortcut. Recommended shortcut: Ctrl+Alt+V / Cmd+Alt+V (not claimed by the VS Code default keymap, not claimed by JetBrains). Setting `input.pasteMode: plain | markdown`, default `plain` (UX28).
4. Convert in the webview only, with `turndown` plus its GFM plugin over a sanitised inert DOM, and use the `vscode-editor-data` clipboard entry to fence code with its language.
5. Images: keep the existing paste and picker path, fix its defects (MIME typo that rejects SVG by accident, upscaling, silent drops, no `onerror`), cap count and size, show a chip with size and estimated tokens, and say plainly when the model has no vision (UX23 to UX25).
6. Drag and drop: build a drop handler that turns VS Code Explorer drags (`ResourceURLs`, `text/uri-list`) and OS file drags into context items, with an overlay that tells VS Code users to hold Shift. Keyboard users keep the existing "Add context (@)" button, which satisfies WCAG 2.5.7 (UX26, UX27).
7. Treat a dropped, pasted or @-added file as an explicit person action but not as an exemption from the credential rules: run `protectedPathHit` and `scanText` on it (X23). Today neither runs on any context path.
8. Do the CLI cleanup that costs nothing: stop spawning `powershell`, `osascript` and `xclip` once a second to look for an image, strip hidden Unicode on submit as Claude Code does, and cap `@` file reads (UX31).

## 3. Plain text by default (research question 2)

What happens now: formatting is dropped because the schema cannot hold it; remote `<img>` and hidden characters are not. A rich clipboard from a browser, Word, Slack or an editor with syntax highlighting arrives as `text/html` plus `text/plain`; ProseMirror prefers the HTML and parses it into paragraphs of text, with `<pre>` blocks flattened to paragraphs and with the line structure decided by the HTML, not the plain text. The text the person sees may differ from `text/plain`, which is the fidelity people expect from "paste plain text".

Mechanisms ProseMirror gives us (<https://prosemirror.net/docs/ref/#view.EditorProps>): `transformPastedHTML` runs on the HTML string before parsing; `clipboardTextParser` parses plain text into a slice; `transformPasted` runs on the slice for pastes and drops; `handlePaste` can take over; `handleDOMEvents` handlers run before ProseMirror's own and must call `preventDefault` themselves if they return true.

Recommended guarantee, in one plugin:

1. Take the paste over in `handlePaste` (or the existing `handleDOMEvents.paste`): when the clipboard has no image file, call `event.preventDefault()` and run the editor's own plain path with `view.pasteText(sanitisedTextPlain, event)`. Do **not** make `transformPastedHTML` return an empty string and expect a fallback: `parseFromClipboard` has already chosen the HTML branch by then (`clipboard.ts:47,67-69`), so an empty string pastes nothing. When `text/plain` is absent (some sources put only HTML on the clipboard), fall back to the text content of the sanitised HTML.
2. A `transformPasted` step walks the slice and removes any `image` node that has a non-`data:` `src` (covers drops of HTML too).
3. The plain text goes through one shared sanitiser (X22): remove tag characters (U+E0000 to U+E007F), bidi embeddings and overrides (U+202A to U+202E, U+2066 to U+2069), zero-width space and word joiner, BOM and C0 controls. **Keep** ZWJ (U+200D), ZWNJ (U+200C) and variation selectors where they sit inside emoji sequences or Persian and Indic text: `stripInvisible` at `core/util/fetchedText.ts:80-90` removes U+200B to U+200F, which includes the two joiners, so it needs a variant, not a straight reuse. Claude Code documents the same distinction: it removes tag characters, bidirectional controls and zero-width spaces on Enter and keeps the joiners and emoji selectors, and holds the send for a second Enter with a notice (<https://code.claude.com/docs/en/interactive-mode.md>, "Invisible characters in prompts").
4. Show a one-line notice when something was removed ("Removed 3 invisible characters"), and count the removals in the audit record without content.
5. Do not scan or rewrite the plain text for secrets at paste time (a person pasting a key into their own prompt is common). Mask it in displays and logs (X15's rule), and let X23 decide what happens on send. This keeps the "text remains text" rule.

How this relates to the existing security work: WB7 neutralises images and strips invisible characters in fetched text; X20 does the same for instruction files; X22 is the paste edge of the same helper. The permission layer's prompt-injection hint (`core/tools/permissions/injection.ts`) only looks at tool output, so a person pasting a hostile page (HTML hidden spans, white-on-white text) is covered only by the schema's removal of styling plus step 3: the hidden span text still arrives as text, which is correct for a plain-text paste (the person can see it in the input before sending, which is the point of showing everything).

## 5. Paste as Markdown (research question 4)

Where it runs: the webview only. There is no network and nothing leaves the machine; the conversion is a pure function from `text/html` and `vscode-editor-data` to a string. The CLI cannot do it, because a terminal paste is text only (no rich clipboard through bracketed paste).

Library choice (npm registry, 2026-11-12):

| Library                     | Licence | Unpacked size | Notes                                                                                                                                                                                                                                                          |
| --------------------------- | ------- | ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `turndown` 7.2.5            | MIT     | 193 KB        | One dependency, `@mixmark-io/domino`, which its `browser` field excludes so the browser build uses the real DOM. The reference HTML to Markdown converter; rules are replaceable (<https://raw.githubusercontent.com/mixmark-io/turndown/master/package.json>) |
| `turndown-plugin-gfm` 1.0.2 | MIT     | 24 KB         | Tables, strikethrough, task lists                                                                                                                                                                                                                              |
| `node-html-markdown` 2.0.0  | MIT     | 113 KB        | Already a dependency of `core` (`core/package.json:85`) and used for fetched pages (`URLContextProvider.ts:3`). One dependency, `node-html-parser`. No `browser` field, so bundling for the webview must be checked                                            |
| `rehype-remark` 10.0.1      | MIT     | 23 KB         | A `unified` pipeline (hast to mdast, then `remark-stringify`). Pulls the whole ecosystem; `gui` already has `react-markdown`, `remark-math`, `rehype-*` for rendering, so the parts are in the bundle already                                                  |

Unpacked sizes are not bundle sizes and were not measured; UX28 must measure the minified, gzipped delta in the webview bundle (a budget of tens of KB is the guess to test). Recommendation: **`turndown` plus the GFM plugin**, because the webview already has a real DOM, the converter walks that DOM, and its rule hooks make the drop list below easy. `node-html-markdown` is the alternative if sharing the code path with `@url` matters more than bundle size.

Sanitising before converting (and none of it needs a network):

1. Parse with `DOMParser` into a detached document, never into the live page. `gui` already depends on `dompurify` (`gui/package.json:41`); use it with an allow-list (headings, paragraphs, lists, tables, `pre`, `code`, `a`, `blockquote`, `em`, `strong`, `br`, `hr`) so scripts, styles, `iframe`, `object`, `svg`, forms and event attributes are gone before the converter sees them.
2. Drop every `img` (no `data:` payloads, no tracking pixels), replacing it with `[image: alt]` as WB7 does. Pasting an image is the separate image path.
3. Drop elements hidden by `hidden`, `display:none`, `visibility:hidden`, `aria-hidden`, zero-size or off-screen styles, and text coloured like its background where detectable. Pasting hidden text is the prompt-injection case; the plain-text path shows everything, and the Markdown path must not turn invisible HTML into visible-looking Markdown that the person never saw. Where detection is unsure, keep the text and let the person see it.
4. Links: keep `[text](url)`; show the URL when the text differs from it; resolve nothing, fetch nothing. Do not rewrite tracking parameters (a surprise edit of a URL the person copied is worse than a long URL); do strip `javascript:` and `data:` hrefs.
5. Run the shared invisible-character step from section 3 over the result, and cap the result (for example 200,000 characters, then paste the plain text with a notice).
6. Never let the converter output HTML. Markdown made from sanitised HTML cannot carry raw tags: configure the converter to escape rather than pass through.

Editor code: VS Code puts a `vscode-editor-data` entry on the clipboard when text is copied from an editor, and the paste side reads it with `clipboardData.getData('vscode-editor-data')`, requires `version === 1`, and gets fields including `mode`, `isFromEmptySelection` and `multicursorText` (`src/vs/editor/browser/controller/editContext/clipboardUtils.ts` lines 137-166 and the type around 106-110; <https://github.com/microsoft/vscode/blob/main/src/vs/editor/browser/controller/editContext/clipboardUtils.ts>). When present, "Paste as Markdown" should emit a fenced block with `mode` as the info string, using the plain text as the content, instead of converting the syntax-highlighted HTML (which is a pile of coloured spans). When it is absent and the HTML is a single `pre` or `code` block, emit a fence without a language. Parse the JSON defensively and treat `mode` as untrusted text (letters, digits, `+`, `-`, `.`, `#` only, at most 32 characters). This entry is VS Code specific: it does not exist for text copied in JetBrains or other apps, so the language is a bonus, not a contract.

Fence length: choose a fence longer than any run of backticks in the content, or the content can close the fence and the rest reads as Markdown outside it.

## 6. Rich clipboard (research question 5)

Facts from the platform:

- A `paste` event carries `clipboardData` and fires only on a person's paste action; it needs no permission. MDN: the handler "can access the clipboard contents by calling `getData()` on the event's `clipboardData` property", and a handler that wants different content must cancel the default and insert it itself (<https://developer.mozilla.org/en-US/docs/Web/API/Element/paste_event>). Synthetic `paste` events "will not affect the document's contents" on the same page, which is also why tests need a purpose-built editor harness, not just dispatching an event.
- The async `navigator.clipboard.read()` needs a secure context and a permission policy, rejects with `NotAllowedError`, and returns text, HTML and PNG as the types browsers commonly support; Chromium sanitises HTML on read unless `unsanitized` is passed (<https://developer.mozilla.org/en-US/docs/Web/API/Clipboard/read>). VS Code grants `clipboard-read` and `clipboard-write` to the webview iframe (`allow` attribute in `pre/index.html`), but the paste event is the route that needs nothing extra. Use the event, never the async API, except for the web build's existing fallback.
- A `File` from a paste or drop has no absolute path in the web platform. Electron removed `File.path` and offers `webUtils.getPathForFile(file)` in the main-world renderer (<https://www.electronjs.org/docs/latest/api/web-utils>), which is not reachable from a VS Code webview (an iframe with no Node). So a file dropped from the OS yields bytes and a name, not a location. For an OS file the honest item is an **inline snapshot** (name, size, a content hash, the text) labelled as such; a reference needs a path, which only an IDE-originated drag supplies.
- Chromium keeps only the first URI in `text/uri-list` in some drags (VS Code works around it with its own `application/vnd.code.uri-list`, `src/vs/base/browser/dnd.ts:77-81`, citing Chromium bug 239745).

## 7. Drag and drop (research question 6)

### 7.1 What VS Code does with a drag over a webview

Read from source, `microsoft/vscode` main:

- The webview page listens for `dragenter`, `dragover`, `drag` and `drop` on `window` (`pre/index.html` lines 964-967). `dragenter` returns early when the event is already handled or **Shift is held**; for a drag whose items are all files it posts `drag-start` to the workbench; `drop` only calls `preventDefault()` (`handleInnerDragStartEvent`, 832-846; `handleInnerDropEvent`, 870-872).
- The workbench answers `drag-start` by setting the webview element's `pointer-events: none` (`webviewElement.ts:337-339`, `_startBlockingIframeDragEvents` at 608-612), so the drop lands on VS Code's own drop targets instead of the page. `WebviewWindowDragMonitor` (`webviewWindowDragMonitor.ts`) applies the same on `drag` and `dragover` **unless Shift is held**, where it restores pointer events (`if (event.shiftKey) onDragEnd(); else onDragStart();`).
- Consequence: **a drag from outside the page reaches our `onDrop` only when the person holds Shift**. This is what the existing overlay text "Hold ⇧ to drop image" means (`DragOverlay.tsx:37`), and what Cline's docs say for VS Code: "hold Shift while dragging files into the chat input" (<https://docs.cline.bot/features/at-mentions/overview>). The overlay should name the real requirement per host and not mention only images.
- What an Explorer drag carries (`src/vs/workbench/browser/dnd.ts:325-340,440-455`; `src/vs/base/browser/dnd.ts:54-82`; `src/vs/platform/dnd/browser/dnd.ts:32-40`): `ResourceURLs` (a JSON array of URIs, **files only, not folders**), `DownloadURL` (first file, `file:` only), `CodeEditors` (JSON), `CodeFiles`, `text/uri-list` (**the first entry only**), `application/vnd.code.uri-list` (all entries), and for other sources `application/vnd.code.symbols`, `application/vnd.code.diagnostics`, `application/vnd.code.chat-reference`. Editor tabs set `CodeEditors` plus the two URI lists. Whether these custom types survive the cross-frame hop into our iframe's `drop` event is **not verified**: Phase 0 prints `dataTransfer.types` and the values for each source.
- MDN: drag data can be read only in `drop` and `dragstart`; during `dragover` only the list of types is visible, so the overlay can decide from types, not values (<https://developer.mozilla.org/en-US/docs/Web/API/HTML_Drag_and_Drop_API/Drag_operations>).
- Folder drag: `ResourceURLs` excludes directories. A folder would arrive only through `text/uri-list` (first entry) or `application/vnd.code.uri-list`, and the page cannot tell a folder from a file by URI alone; it would have to ask the host (`ide.getFileStats` or the existing `@folder` provider). Phase 0 measures it.

### 7.3 UX and accessibility

- Overlay: "Drop to add context" with the host hint ("hold Shift" in VS Code). Show it only when `dataTransfer.types` includes something we handle, and always say why when we do not ("This model does not read images").
- WCAG 2.2 SC 2.5.7 Dragging Movements, level AA: "All functionality that uses a dragging movement for operation can be achieved by a single pointer without dragging" (<https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html>). Drag and drop here is a convenience, and the single-pointer alternative exists in the toolbar: the "Add context (@)" item and the image picker (`AttachMenu.tsx:42-94`, UX2). The criterion is met only if that item stays reachable and complete: it must cover files, folders and images, not only `@` text. Add keyboard-complete "Add file...", which opens the host's file picker, if the `@file` list is judged too slow for a path the person already has.
- Announce adds and refusals in a polite live region (UX18's mechanism), with a removable chip per item (items in the editor are atoms: Backspace removes one).
- Screenshot harness: add `drop-overlay`, `chips` and `refused` views to `bench/screenshots` (`axe.mjs`, `axe-baseline.json`, `harness/`) and run `axe-core` over them.

### 7.4 Permissions, secrets and size

- Dropping or pasting is an explicit act by the person, so the Context use area does not need to ask for a file the person chose. It must still refuse or warn for what the project already protects: `~/.ssh/*`, `.env`, cloud credential files and the global config folder (`protectedPathHit(raw, kinds)` at `core/tools/permissions/protected.ts:156` returns `secret` or `config` hits), and a path outside the workspace gets a one-line "outside the workspace" note. Proposed policy, X23: a `secret` hit on a drop or an `@file` shows a confirmation naming the file and the reason (not a silent block, since the person chose it; not a silent allow, since a dropped file is often dragged by mistake); a `config` hit asks; an outside-workspace path notes. Whether an owner setting may turn the confirmation off is decision D6.
- Run `scanText` (`core/util/secretScan/scan.ts:199`) over inline snapshots and over file content read for a mention, and warn with the masked finding ("looks like an AWS key in line 12") before send. Mask the display with the shared masker; do not rewrite the content without the person's say.
- Size caps: per file and per message, shown in the chip. Binary files refused by sniffing (NUL bytes) with a message.
- Audit: record attachments by name, size and SHA-256 and the sanitiser's removal count, never the content (the audit file already avoids content; X10's canary suite covers it).

## 9. Privacy and security (research question 8)

- **What leaves the machine:** image bytes and file text go to the configured model provider, in the request, and nowhere else. Nothing uploads on paste or drop. Paste as Markdown and sanitising run locally. A URL mention fetches the page (to the host that URL names) through the guarded fetch, and only when the person adds it. Say so in the chip tooltips.
- **EXIF and metadata:** see section 6; canvas re-encode strips it in the GUI, `sharp` strips it by default in the CLI, and the CLI's no-`sharp` fallback does not.
- **Clipboard permission:** the paste event needs none; the async API needs a secure context and permission policy (MDN above). Use the event.
- **Hidden-text injection:** sections 3 and 5. HTML hidden spans and white-on-white become visible text in a plain paste; zero-width, bidi and tag characters are removed with a notice; hidden HTML is dropped in the Markdown path.
- **Remote image URLs in pasted HTML:** removed (section 2.1).
- **Logs:** attachments recorded by name, size, hash; never content, never the base64 string. The session store keeps images in memory and on disk (V0 row: images are held in Redux); externalising them is V2.
- **Display:** pasted secrets are masked in displays and logs by the existing masker; the text itself is not rewritten.
