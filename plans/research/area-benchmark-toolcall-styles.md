## 4. Design shared by every run: from result to default

### 4.1 The verdict row

Every experiment ends in one record, written outside the repository (MR8's schema is the container) and proposed by pull request (MR13 `propose`), never applied by a tool:

```
question_id, arm_a, arm_b, metric, bar, n_a, n_b, k_a, k_b, interval_a, interval_b,
test (exact McNemar | Fisher | SPRT | bootstrap), p_or_bound, verdict (win | tie | loss | screening),
model_id, provider, engine+version+parser (I34), template sha, quant, sampling,
product sha, bench sha, scenario-set hash (held-out twin flag), date, cost_usd, run_ids
```

A default changes only on `verdict = win` with every field present. `screening` (under about 10 per arm, per RQ10) may not change a default. The preset table's `measured` mark (Q21) generalises to a `verified:` reference to a verdict row, with the same drift script that already lists stale `readOn` dates (Q21) flagging a verdict older than the model, server or template it rests on.

### 4.2 Scoring

Keep the existing per-run record (`model-benchmark.md` section 5). Add, in `bench/score.mjs`:

- **pass^k beside pass@1** for loops and multi-step scenarios: a model right 80 percent per run is right three times running 51 percent of the time; this is the number a 20-item loop experiences (the tau-bench reporting idea, `benchmarks-toolcalls-loops.md` section 2.3) (I33).
- **Paired comparison** by (scenario, seed, run index) with exact McNemar for binary outcomes and a paired bootstrap for medians (turns, tokens, cost), reusing `bench/lab/lib/compare.mjs` logic rather than a third copy (I33).
- **Effective n**: temperature 0 repeats are not independent samples of the prompt distribution. `bench/lab/lib/stats.mjs` has the clustered effective n; the scorer should print it beside raw n (MR32 does this for the lab).
- **A bar per metric set before the run**, in the run's plan file, with the stopping rule: SPRT for one arm against a bar and Wilson-bound looks for two arms (RQ10, #624). Peeking without a rule is the cheapest way to manufacture a win.

### 4.3 Overfitting guard

The scenario set is small and public (24 files). Three guards, in order of cost:

1. **Held-out twin** (MR11): for each scenario that decides a default, a differently worded twin with different seed files, frozen and hashed, run only at verdict time. A win that does not hold on the twin is `tie`.
2. **Two seeds, two sizes** on edit scenarios (small file and a 400-line file), because the exact-string failure depends on file shape.
3. **Never tune a prompt on the verdict set.** Prompt iteration runs on the Strata or Qwen3-Coder local slice; verdicts come from a fresh draw.

### 4.4 Reproducibility

Record: product commit, bench commit, `LAB_CONTRACT_VERSION`, model id as sent, provider, region or profile, engine name and version and tool-parser setting (I34), template sha (`/props`, `/api/show`, MR18), sampling actually sent (MR31), settings (`--profile`, `--dialect`, `--tail`, `--effort`), seed bundle hash. Reply bodies stay in the run folder outside the repository; only the verdict row travels. Hosted models drift; a verdict row has a date and is stale after the vendor's next model-id change (MR12's canary is the later cure, not 2.16.0).

### 4.5 Cost governance

Dry run by default (the runner already has `--dry-run`); every paid run lists models, scenarios, repetitions and an estimated ceiling first and waits for the owner's word. The budget stop (`killed: tokens`, I3 and I16) is the second line. MR8 and MR9 (schema and governor) formally gate paid or remote runs and are not built [roadmap]; until they are, "the owner's word per run" is the governor, and section 6 is written so each plan fits in one approval.

### 5.3 Tool-call styles (Track Q)

**Q2 names, Q3 edit format, Q6 profile (the core experiment; M + S + S).**

- Problem: our names and edit shape are one set for every family; vendor documents confirm wire format but not trained-in names (`tool-call-styles.md`, "What is not"), and Diff-XYZ's Qwen2.5-Coder result is the prior, not the answer.
- Design, 2 x 3 factorial, one factor at a time on the first pass:
  - Factor N (names): `ours` (CLI: `Read`, `Write`, `Edit`, `Bash`, `Grep`), `qwen-code` (`edit` with `old_string`/`new_string`, `write_file`, `run_shell_command`), `cline` (`replace_in_file`, `write_to_file`, `execute_command`) [names from `tool-call-styles.md`, unverified against each tool's source].
  - Factor E (edit): `exact` with the shipped matcher (#482), `search-replace` (one block per edit, applied through the same matcher), `whole` file write.
  - Scenarios: `agent-acts`, `loop-fix-forward`, and two new seeded edit scenarios that fail on whitespace and on repeated lines (the two classes `edit-formats.md` lists). Metrics: invalid-call rate, `not found` rate per edit, retries per edit, leaks (`classifyToolReply`), completion, input tokens. Pre-registered bar: an arm must beat control by at least 0.2 absolute on edit-failure rate with the Wilson bounds not overlapping at n of 30 or more, else `tie` (RQ10: 0.3 needs about 20 to 50 per arm; 0.2 needs 40 to 100, so for 0.2 use a sequential design).
  - Models: Qwen3-Coder 30B (Bedrock, cheap), Strata Qwen3.8 Flash (free), Nova 2 Lite (the other family our logs show failing), then gpt-oss-120b if an OpenAI-family tool profile is considered (Q8).
  - Outcome feeds Q6: a family gets a profile only where the verdict row says win and the held-out twin agrees.
