# What we tell the model about its environment: current state and peers

Research report, 2026-11-13. Code read on `origin/main` at `ee644eb15` (which includes the merged shell-awareness research, #759). `plans/ROADMAP.md` is not edited: section 8 holds the exact row text. Releases use even minors: 2.16.0 is being cut, so "2.18.0 candidate" means the release after it.

Convention: "verified by reading" names a file. "Measured" means run on the review machine (Windows 11, Windows PowerShell 5.1.26100.9711, no `pwsh` installed). "Peer source" names a URL and the date it was read. "Unverified" means from memory or a source that could not be fetched. This report does not redo `plans/research/shell-awareness.md`; it uses its facts (which interpreter runs a command, how the policy reads it) and asks a different question: what does the model itself read about where it is running.

## 1. Summary: the ten findings that matter

1. **The IDE agent, plan and chat system prompts say nothing about the environment.** `core/llm/defaultSystemMessages.ts` has no OS, shell, working directory or date. The only environment text the IDE model sees is one sentence inside the terminal tool's description (finding 2). The CLI has an `<env>` block; the IDE has no equivalent. The two surfaces share the turn text (`core/llm/prompts/turns.ts`) but not an environment preamble.
2. **The IDE terminal tool's shell sentence is the weakest we ship.** `core/tools/definitions/runTerminalCommand.ts:27` says "Choose terminal commands and scripts optimized for win32 and x64 and shell powershell.exe." It does not say Windows PowerShell 5.1, does not say `&&` is a parse error there (measured, section 2.4), and does not mention WSL or containers. The CLI's own tool says all of that (`extensions/cli/src/tools/runTerminalCommand.ts:75-104`, `describeShell`), added because models "wrote `a && b` on Windows ... and lost several calls per run" (its comment). The fix exists in one surface and not the other.
3. **The IDE sentence can contradict what actually runs.** It is built once at import time from `os.platform()` and `process.env.SHELL`. When the person sets `terminalShell: wsl` (or a container), `resolveShell()` runs bash in WSL, while the description still says `powershell.exe`. A setting changed mid-session never reaches the description (module constant). Verified by reading (`core/util/shell.ts:196-240`).
4. **In a remote window nobody knows the shell.** The tool types the command into the editor's terminal on the other machine (shell-awareness section 2). The model is told the extension host's `os.platform()`, which is right for the OS and silent about the terminal's shell. Fixing the policy side is SH2; the prompt side has no row yet (EV8).
5. **The CLI says `Platform: win32` and nothing else in its `<env>` block.** `extensions/cli/src/systemMessage.ts:44-50`. That is Node's identifier, not an OS name, and it carries no version, no architecture, no shell, no path style. The shell guidance lives only in the Bash tool description. Subagents and the loop reuse the same preamble and tool, so they inherit both the strength and the gap.
6. **Cache behaviour is already well designed and should be kept.** Volatile facts (date, git status) were moved out of the system message into the first user message (`environmentContext.ts`, golden `env.date+git`, stability "session"). The stable facts (cwd, platform, shell sentence) sit in system and tools. Any v2 field must be stable for the session or go in that first-user block. Two real exposures remain: the git status is uncapped (fixed in draft #750) and the tool description embeds `process.cwd()` in the tools region, the very start of the prefix, so two folders never share a cached prefix (acceptable, but a choice).
7. **A runtime backstop already exists and is the right second layer.** `core/tools/permissions/commandLint.ts:318-327` refuses `&&` and `||` under PowerShell with "Windows PowerShell 5.1 reports a syntax error" plus a fix, in both the IDE and the CLI path. The prompt warning prevents the wasted call; the lint catches what slips through. Neither replaces the other, and the lint text is the best-worded Windows guidance we have.
8. **Peers split three ways.** Claude Code does not publish its prompt, but documents a PowerShell tool that auto-selects `pwsh` 7 with a fallback to 5.1 and tells the model "PowerShell is the primary shell" (section 3). Codex renders shell and, on Windows PowerShell, a probed shell version in an `<environment_context>` user-message block. Gemini CLI, Roo and Aider put only a platform name (and in Aider's case a `COMSPEC`/`SHELL` value) in. Nobody in the set we could read tells the model the `&&` rule in the environment block; the guidance, where it exists, is in the tool description.
9. **Windows 5.1 has more traps than `&&`, and we state none of the others.** Measured on this machine: `;` runs the next command after a failure (`exit=1` came back after "after" printed); `>` writes UTF-16LE with a byte-order mark (`255 254 104 0`); `curl` is an alias (`CommandType = Alias`). Each is a recurring source of silent wrong output rather than a visible error, which is worse than the `&&` parse error.
10. **We do not say what a WSL preference means for paths.** With `terminalShell: wsl` the shell sees `/mnt/c/...` while the file tools take Windows paths. The CLI sentence mentions `/mnt/c` for the drive; nothing tells the model that a path from a tool result must be translated before it goes into a command, or that `powershell.exe` is still reachable from inside WSL. This is the owner's "WSL preferred or forced" question, and today there is only one mode, with no wording for the other.

### 2.2 Cache impact

The segment manifest (`core/llm/promptSegments.ts`) classes every segment as static, session, turn or request and requires non-decreasing stability inside a region. What the environment fields are today:

`extensions/cli/src/promptSegmentGolden.json` pins only hashes: `preamble` is `86df2e5027c5` in every scenario, so any new character in the `<env>` block changes the `preamble` hash and every cached CLI prefix once, on every provider that caches. `gui/src/redux/util/segmentGolden.json` and the two `requestGolden.json` files pin the IDE; the IDE scenarios use a stand-in terminal tool (`segmentScenarios.ts`: "The real terminal tool describes the host OS and shell, so a fixed stand-in keeps the goldens the same on every platform"), which means a change to the real IDE terminal description changes no golden and no test sees it. That is a coverage gap (EV17).

Draft #750 ("one prompt-byte bundle") already changes the CLI `environmentContext.ts` (the git status cap), `multiEdit`, `searchTools` and the four goldens. A v2 change to the preamble should land in the same release as #750's goldens, or after them, so the cache goes cold once.

### 2.3 Windows, WSL, and the recent shell-awareness work

Status of the work in `plans/research/shell-awareness.md` (read 2026-11-13): the research is merged (#759). `core/tools/permissions/shellContext.ts` exists on the draft branch of #756 (and not on `main`: `git ls-tree` on `main` finds no such file); #757 (card line), #758 (`executionShell(remoteName)`) and #744 are drafts. What the set shows:

- **Everybody names the platform; only some name the shell.** Claude Code, Codex, Roo and Aider do; Gemini does not (platform only).
- **Where the dialect is stated, it is next to the tool, not in the environment block.** Our CLI does the same, and the choice is sound: the shell sentence is read when the model decides to call the tool.
- **Codex's version probe is the technique worth copying for `pwsh`.** It costs one process per shell path per process, is time-boxed, and is skipped unless the shell is PowerShell. We do not need it while the product only spawns 5.1 (known, not probed); we will if SH8 chooses `pwsh` or if a remote terminal's shell is probed (SH2).
- **Claude Code's answer to "which shell" is two tools, not one shell with a note.** The model is given a `PowerShell` tool and a `Bash` tool and each takes its own syntax. That sidesteps the "one command text, unknown dialect" problem our policy work (SH1) has to solve by classification. It is a design option for the owner (question 6), not a text fix.
- **Privacy:** Roo puts the home directory and the absolute workspace path (both contain the user name on Windows and macOS) in the system prompt. We send the working directory (CLI) and nothing else personal; v2 must not add a home directory, user name or host name (section 5).

What is cheap (an afternoon each, no owner decision beyond wording): F2 and F3 by sharing one `describeShell` between the IDE and the CLI (the function is pure given `platform`, `shell` and the preference), F4's OS name, F6's sentence, F7 (drop the cwd from one place), F11 (local date), F12 (a test that builds the real description).

Risks:

- **Cache.** Any change to the CLI preamble or a tool description changes the `preamble` or `tools.builtin@*` hash and cools every cached prefix once. Bundle with #750. Never put a per-request or per-turn value in the system or tools region: v2 puts only session-constant text there.
- **Setting changes mid-session.** A `terminalShell` change must rebuild the tool list at the next session boundary, not per request. Emitting the text from a function called per request would make the tools hash depend on a setting that can flip, which is a cache event of the kind the manifest calls `tool-list-event`.
- **Privacy.** The working directory carries a user name on most machines (`C:\Users\<name>\...`) and is already sent. Do not add the home directory, user name, host name, domain or the list of environment variables. Prefer the workspace-relative form in the reviewer. A `redactCwd` switch is a possible owner decision (question 8).
- **Token cost.** The proposed Windows block is about 120 tokens, once, in the cached prefix; the other platforms about 40. Against the measured cost of a wasted call (a tool round trip, a refused or failed command, often a retry) it pays for itself after one avoided failure per session.
- **Wrong text is worse than none.** A sentence that says "PowerShell 5.1" in a remote window, or when WSL is preferred, makes the model confident and wrong (F3). Every variant below is chosen from the same function the executor uses, or it says "not known".

## 5. Environment block v2

### 5.1 Principles

1. One function owns the text and takes the same input as the executor (`resolveShell()` or SH1's `executionShell(remoteName)`): the platform, the shell kind, the version if known, where it runs (host, WSL, container, remote terminal) and how it was learned (spawned or not known). The prompt never states a shell the policy reads differently.
2. Stable facts go in system (or tools); session facts go in the first user message; nothing is per request. Same classes as the manifest.
3. State the dialect once, next to the tool, and put identity (OS, arch, shell, path style) in the environment block, so the two cannot drift and neither is repeated.
4. Say what the model cannot see: if the shell is not known, say that and tell it to write portable commands.
5. Short, imperative, no apology. No home directory, user name or host name.

### 5.2 Fields

### 5.3 Wording by variant

Each variant is the tool-description sentence; the `<env>` lines are the Host and Commands-run-in fields above. Unverified claims are marked and must be measured on a runner that has the shell before the text ships (EV14).

**Windows PowerShell 5.1 (default on Windows; always today):**

> Runs in Windows PowerShell 5.1 (powershell.exe), a new process for every command, started in the working directory: no state carries over. Write PowerShell, not bash. Chain with `;` or a newline, never `&&` or `||` (syntax errors in 5.1). `;` does not stop after a failure: test `$?` or `$LASTEXITCODE`. `>` writes UTF-16: use `Out-File -Encoding utf8` or the edit tools. `curl` and `wget` are aliases of Invoke-WebRequest: call `curl.exe` for the program. Use `$env:NAME` for variables; quote paths that contain spaces.

(About 115 tokens.) The `&&` clause alone is the part already shipped by the CLI.

**PowerShell 7 (`pwsh`; when SH8 chooses it, or the person set it):**

> Runs in PowerShell 7 (pwsh), a new process for every command. `&&` and `||` work. `;` runs the next command even after a failure. Output is UTF-8 without a byte-order mark by default (unverified here; no `pwsh` on the review machine). Use `$env:NAME` for variables.

**cmd (only when a person configures it; not offered today):**

> Runs in cmd.exe. Chain with `&&` or `&`; `;` is not a separator. Variables are `%NAME%`; escape with `^`; only double quotes quote.

**Git Bash (never spawned by us; appears only as `bash -c` inside a command):** no variant for the tool. If it is ever chosen: "Runs in bash from Git for Windows on Windows: bash syntax, Windows programs on PATH, paths as `/c/Users/...`; text files may have CRLF line endings."

**WSL, preferred (a Windows host where the person set `terminalShell: wsl`; Windows tools remain reachable):**

> Runs in bash (login shell) inside WSL (distro), started in the workspace folder. Use bash syntax and Linux paths: the Windows folder `C:\a\b` is `/mnt/c/a/b` here. File tools take Windows paths; translate a path before putting it in a command. `powershell.exe` and other Windows programs can be called from here when needed.

**WSL, forced (a policy of the person or the organization: no PowerShell fallback):** the same text without the last sentence, and: "There is no PowerShell in this tool."

"Preferred" versus "forced" is the same executor today (one preference); the distinction is whether the last sentence is true, so it follows from whether a fallback exists (question 5).

**macOS (zsh or `$SHELL`):**

> Runs in zsh as a login shell on macOS, a new process for every command. The userland is BSD: `sed -i ''` needs the empty suffix and some GNU flags are missing.

**Linux (bash, dash or other):**

> Runs in bash as a login shell on Linux, a new process for every command. (For `sh` or `dash`: "sh is dash here: no bash-only syntax.")

**Container:**

> Runs in bash inside a container (image), started in the workspace folder, which is the only thing mounted. Use bash syntax and Linux paths.

**Remote terminal (the shell is not known):**

> The command is typed into the editor's terminal on the remote host, whose shell is not known. Write one simple command at a time using syntax common to bash and PowerShell, and do not chain with `&&`, `;` or `||` unless the output says which shell it is.

**fish, nushell, ksh (`$SHELL`):** name the shell and add "Commands here are not checked against this shell's syntax; keep them simple." (F14.)

### 5.4 Per-model-family variants

| Profile                                               | Environment text                                                                                                                                                           |

| `full` (Claude, GPT, Gemini families and the default) | The 5.2 `<env>` lines and the 5.3 sentence                                                                                                                                 |
| `short` (Qwen and other small models)                 | The `<env>` lines and only the first two clauses of the sentence: shell name and the chaining rule (about 35 tokens). Small models follow one short rule better than seven |

| Setting                                                  | Host line                | Commands-run-in line        | Tool sentence               |

### 5.7 Second layer

Keep the lint (`commandLint.ts`) as the backstop and keep its messages in step with the block: when the lint refuses `&&`, it says what to write; the prompt says it first. Do not attempt a "model wrote `&&`, rewrite it" repair: a rewriter that changes a command after approval is the failure DS7 exists to prevent.

## 6. Open questions for the owner

Each is "recommended, pending owner".

1. **Add an environment block to the IDE system prompts (F1)?** Recommended, pending owner: yes, the same `<env>` lines as the CLI, from the same function, in the system message (stable) with date and status excluded until the IDE has a first-user block.

4. **Platform name versus `process.platform`.** Recommended, pending owner: a name and version (`Windows 11`, `macOS 15`) plus the Node identifier in parentheses; no build number below the major.
5. **WSL preferred versus forced (the owner's question).** Recommended, pending owner: one setting, `terminalShell: wsl`, with the "PowerShell is still reachable" sentence true only when a Windows host is present; "forced" becomes a managed-policy flag (`terminalShell.fallback: none`) in a later release, not a prompt choice.
