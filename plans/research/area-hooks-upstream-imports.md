## 2. Track D: what remains, per open row

Hook execution is arbitrary code. Every row below assumes the rules already built and shipped: project hooks load only after trust by definition hash plus script hash (`hookTrust.ts`, `hookScripts.ts`); a project hook cannot approve (`allow` ignored); failure blocks on `PreToolUse`, `PermissionRequest` and `UserPromptSubmit`; `--trust-project-hooks` is a flag, never an environment variable; project and HTTP hook input is masked; the environment is scrubbed. New work must not weaken any of these, and each new row below says what it adds to the trust surface.

### D4a (new split of D4): finish the docs page

Problem: the page for hooks is called "Project Hooks and Trust" and sits under the IDE extension agent section, while the hooks are CLI-only; nobody looking for "hooks" finds a reference, and two sentences are wrong (section 1.1).

Design: move or add `docs/cli/hooks.mdx` as the reference (settings file shape, the six file locations, event table with input and output fields, exit-code table, `onError` and `onFailure`, trust, managed only, masking, what is not covered) and leave `hooks-trust.mdx` as the trust chapter, or fold it in. The page must say that hooks are a guardrail and not a boundary (Codex and Claude Code both say so), name the paths that never reach them (the IDE until D5; the CLI's `Bash` calls made by a hook itself; `SessionEnd` on a signal), and correct the MCP sentence after a one-test check. Docs style per the `docs-style` skill. Check the build first: CI29 records that an MDX autolink broke the docs deploy; use markdown links only.

Size S (half a day). Acceptance: page builds (`npm run build` in `docs` or the CI docs check); table of events matches `HOOK_EVENT_NAMES`; every claim about behaviour has a test name beside it in the PR; the MCP sentence is verified with a test that a `mcp__server__tool` call fires `PreToolUse`.

### D4b: obey `Stop` (and say what a hook may do)

Problem: "run the tests before the agent says it is done" is the most common hook people bring from Claude Code, Codex (`Stop` block starts a continuation) and Cursor (`stop` returns `followup_message`, `loop_limit` default 5). Today a `Stop` hook that blocks is logged and ignored (`lifecycleHooks.ts runStopHooks`).

Design:

- `runStopHooks(lastAssistantMessage)` returns `{ continue: true, reason }` when a hook blocks (exit 2, or JSON `decision: "block"` with `reason`) and the continuation budget for this user turn is not used up.
- The caller (`commands/chat.ts`, `serve.helpers.ts`, `useChat.stream.helpers.ts`) adds the reason as a synthetic user message marked `source: "hook"` and runs another turn. `stop_hook_active: true` is set on the input for the continuation turn so a script can tell (the field exists already).
- Cap: `hooks.stopContinuationLimit`, default 3 (the proposed number in the previous research; Cursor's default is 5, recommended 3, pending owner). After the cap the turn ends with a notice naming the hook. The counter resets on the next real user prompt. A hook failure (timeout, crash) never continues.
- Only a user-level hook may continue a turn without a notice; a project hook that continues shows a one-line note ("a project hook kept the agent working: <reason first 200 characters>"), because a repository hook that keeps a headless run going is a cost and loop risk. Loop mode and `--max-turns`, `--max-budget-usd`, `--max-duration` (`cc1e3d79`) still apply and win.
- Alternatives rejected: unlimited continuation with a stuck detector (Track S does not run in plain chat); making `Stop` hooks asynchronous (cannot decide).

Risks: runaway cost (mitigated by the cap and the existing run limits); a hook that always blocks makes headless runs fail to finish (cap, then exit with the notice and a non-zero code only if the owner wants it, recommended: exit 0 with the notice).

Test plan: a hook that blocks twice then allows ends after three turns; a hook that always blocks stops at the cap; `stop_hook_active` is true on the second input; a crash does not continue; a project hook continuation shows the note; `--max-turns` wins over the continuation. Size M (2 to 3 days, three call sites plus the TUI). Owner decision: the cap (section 8, question 1).

### D4c: `SessionStart` context and `PreCompact` blocking

`SessionStart` plain stdout or `additionalContext` is where people inject "git status" or a ticket summary. Design: collect the capped context and put it into the first request as a system-reminder-style block after the system message (it must not change the system prompt prefix, to keep the cache stable: Track C rules, `plans/prompt-caching.md`). A project hook's context is masked-input only and is shown to the user as "N characters from a project hook" before the first turn. `PreCompact` block: honour only the manual trigger (a user typing the compaction command) and ignore a block on automatic compaction with a notice, because a blocked automatic compaction ends in a context overflow. Size S each. Defer `PreCompact` blocking unless asked; `SessionStart` context is the one with demand.

### D7: `args` exec form and the `if` filter

Problem: a shell command line is a quoting problem on every platform, and on Windows a cmd.exe problem (#658 fixed the verbatim pass-through but the shell form still means `cmd.exe` metacharacter rules apply to the user's own text). Claude Code now has `args` (spawned directly, no shell; on Windows needs a real executable, `.cmd` and `.bat` need shell form) and `if` (one permission-rule pattern, best effort; evaluated only on tool events).

Design:

- `CommandHookHandler.args?: string[]`. When present, `spawn(command, args, { shell: false })` with placeholder substitution of `${CLAUDE_PROJECT_DIR}` and `${CONTINUOUS_PROJECT_DIR}` as plain strings. Add `CONTINUOUS_PROJECT_DIR` to the environment beside the two existing names (PV10 renames).
- The trust fingerprint must include `args` (it must change when any argument changes) and the script-hash scanner (`hookScripts.ts`) must read the first arguments for `node x.js` style invocations, as it does for the shell form.
- On Windows refuse `.cmd`/`.bat` in exec form with the message "use the shell form or run node on the script", rather than reproducing Node's CVE-2024-27980 behaviour (Node refuses to spawn `.bat` and `.cmd` without a shell; unverified against the Node version we ship, check before documenting).
- `if`: accept the field, evaluate it with our own permission-rule matcher (`core/tools/permissions`, the `Tool(pattern)` syntax already used in `permissions.yaml` and `toolPermissions`), only on the five tool events; on any other event ignore it with a one-time log. Document as best effort and not a security control. A rule that does not parse makes the hook run (fail towards running, because `if` narrows and a hook that does not run on a call it should have guarded is the dangerous direction; recommended, pending owner).
- Alternative rejected: a new tiny argument language of our own. The Claude Code shape is the one files are written in.

Risks: exec form removes `sh` features people rely on (pipes, `&&`); documented. `if` evaluated against our tool names: a Claude Code file's `Bash(git *)` matches our `Bash` tool name only if the tool-name alias table is used (`core/subagents/tools.ts` maps Claude Code's tool names). Size S (1 to 2 days). Test plan: exec form with spaces and quotes in an argument on Windows and POSIX (a fixture that echoes `argv` as JSON), fingerprint changes with `args`, `.cmd` refused, `if` match and mismatch and a bad rule.

### D8: the remaining input fields and spill to a file

Add `prompt_id` (one per user prompt, already a notion in the stream code; check), `model`, `timestamp` (ISO 8601, Gemini CLI has it), and `agent_id`/`agent_type` on every event fired inside a subagent run. All cost nothing and let one script serve Claude Code, Codex and Gemini files. For the cap: instead of truncating with a notice, write the full text to a file under the session directory (`<globalDir>/hook-context/<session>/<n>.txt`, mode 0600) and put the first 2,000 characters and the path in the context; the model can read the rest with the read tool. Spill is only for user-level hooks; for project hooks keep truncation (a project must not cause a file write the user did not expect). Size S.

### D9: administrator path for managed-only

The user-level switch is built; what an organisation needs is a file a developer cannot edit. Claude Code reads managed settings from a system directory, Codex from `requirements.toml` (`managed_dir`), Cursor from `/etc/cursor/hooks.json` (Linux and WSL), `C:\ProgramData\Cursor\hooks.json` and the macOS Application Support path. Proposal: read `managed-settings.json` from `/etc/continuous/` (Linux, WSL), `/Library/Application Support/Continuous/` (macOS) and `%ProgramData%\Continuous\` (Windows), only when the directory is not writable by the current user (`fs.access` with `W_OK` fails, and on POSIX the owner is root); honour `hooks`, `managedHooksOnly`, `disableAllHooks`. It is also where B19 (policy locked by an administrator) would read. Needs the owner decision first (section 8, question 3), and B19. Size M. Not for 2.16.0.

### D10 (new): an unparseable hook settings file must not fail open

Problem in user terms: a person's `~/.claude/settings.json` has a trailing comma (Claude Code says settings files are strict JSON, so this is easy to do when editing by hand); `cn` logs a warning at the warn level and runs with no hooks. The guard hook that blocked `rm -rf` is gone and nothing on screen says so. The same shape as upstream 13461 for `permissions.yaml`.

Design:

- `loadSettingsFile` distinguishes "absent" from "present but unparseable". For a **user-level** file that is present and unparseable: in the TUI show a one-time banner with the path and the parse error position; in headless and `serve` mode refuse to start with exit code 2 and the message (the decision in `hooks-wiring.md`, never built); `--ignore-broken-settings` for a deliberate override. For a **project-level** file: treat as untrusted-and-broken: do not run, show the notice in `continuous hooks list` and in the startup notice, because a repository cannot be allowed to stop the user's own policy by shipping a broken file.
- A file that parses but has an `hooks` key of the wrong type, or an unknown event name, loads the valid part and warns for the rest (Claude Code does the same: "Settings Warning").
- Apply the same rule to `permissions.yaml` (E10) with one shared helper, `readPolicyFile(path)` returning `{ status: "absent" | "ok" | "broken", value, error }`, so the two loaders cannot drift.
- Rejected: block every tool call when a policy file is broken (too blunt for the TUI where a person can fix the file; correct for headless).

Size S (1 day). Test plan: broken user file refuses headless start and shows the TUI banner; broken project file does not run and does not disable user hooks; broken `permissions.yaml` in headless refuses start; absent file is silent; the exit code and message are stable (a test asserts the text).

### D11: real `prompt` and `agent` handlers

Today both fail closed. Claude Code has both (prompt: single turn, JSON result, 30 s; agent: a subagent with tools, 60 s, "experimental"), Cursor has `prompt` returning `{ ok, reason }`, Codex parses and skips both. A `prompt` handler is a model call on every matching event, so cost and egress apply (PV track: the input is conversation content and must be masked before it goes to a model other than the session's). Recommended: build `prompt` only, on the cheap role model, behind a per-hook `model` and the cost counter, with the same masking as http hooks; leave `agent` failing closed. Size M. Defer: no user request is recorded, and it adds a model-egress path.

### D12: HTTP hook URL allowlist

Claude Code has `allowedHttpHookUrls` and `httpHookAllowedEnvVars`. Ours masks input and sends through the shared fetch (PL22) but has no allowlist, so a project hook (after trust) can post masked conversation content to any URL. Recommended: user-level `allowedHttpHookUrls` (list of origin prefixes), default empty meaning "ask once per URL origin at trust time", enforced after the trust fingerprint. Size S. Pair with D9.

### D5: hooks in the IDE

Problem: hooks do nothing in the VS Code and JetBrains extensions, which is where most users are. The agent tool loop in the IDE is split: `gui/src/redux/thunks/evaluateToolPolicies.ts` decides policy in the webview, `callToolById.ts` calls core `tools/call`, and core executes (`core/core.ts:2039`).

Design (recommended): move the engine, not the settings loader, into `core/hooks/` (types, runner, config loader, trust store) with the CLI importing it, because the CLI already imports `core/util/secretScan`. Expose two core messages, `hooks/preToolUse` (input: tool call; output: `{ blocked, reason, updatedInput, decision }`) and `hooks/event` (fire-and-forget lifecycle). The webview calls `hooks/preToolUse` in `evaluateToolPolicies` before the policy decision (so a hook `deny` or `ask` composes with the policy as D3 defines: deny beats ask beats allow; project hook `allow` ignored) and `hooks/event` for `Stop`, `UserPromptSubmit`, `SessionStart`. Trust: an IDE dialog listing the commands, reusing `trusted-hooks.json`, and a "Hooks" row in the planned Trusted list (B20). Alternative rejected: run the CLI hook module inside the VS Code extension host only (JetBrains gets nothing; two copies of trust code). Another rejected: leave hooks CLI-only and say so (acceptable short term; the docs page must say it).

Risks: the core binary is built with `@yao-pkg/pkg`; `child_process` hook execution from core in the IDE must use the same terminal environment scrub (`terminalEnvironment()` lives in the CLI tree; it must move with the runner). Windows quoting must be exercised in the extension host, not only in Node tests. Size L (6 to 10 days: move, protocol on three message lists including `MessageTypes.kt`, trust UI, tests). Not for 2.16.0 unless the owner puts hooks first.

### Not proposed (with reasons)

`mcp_tool` handlers, model-request and model-switch events, `PostToolBatch`, `MessageDisplay`, `FileChanged`, `CwdChanged`: no request is recorded; each adds an execution path. Cursor's `beforeShellExecution` and `beforeReadFile` style events: our matcher on tool name covers them. `async` hooks that rewake the agent: no decision from an async hook is allowed in any of the four tools, so there is nothing to port.

### 5.5 Wizard, conflicts and the dry-run

Follow the plan's four steps (pick a tool, pick items, review, result) and add:

- **Dry run is the review screen.** It is a diff against the user's real files: for `config.yaml`, a unified diff of what the in-place YAML edit would produce (the importer already edits in place and writes a `.bak`); for rule files, the file list with a preview of the first 20 lines; for secrets, names and "reads X from your environment today". A "Copy as text" button writes the same diff to the clipboard so it can be attached to a bug report without secrets.
- **Conflict handling**: a server or model whose name matches an existing entry is shown as "already exists" with three choices: skip (default), import under a suffixed name (`name-claude`), replace (never the default, and shows a diff of the changed fields). Matching is by name ignoring case for servers (the #193 behaviour) and by connection endpoint for providers (the existing "another connection to that endpoint already exists" rule in `providerSetup.ts`).
- **Idempotence**: importing twice changes nothing the second time; the result screen says "nothing new".
- **Provenance**: each imported entry carries a comment line in `config.yaml` (`# imported from Claude Code .mcp.json, 2026-11-12`) so a later reader knows where it came from; comments survive the in-place edit.
- **Undo**: the `.bak` is named in the result screen; `continuous config restore` is not proposed (not needed for 2.16.0).
- **CLI parity**: `continuous import <tool> [--dry-run] [--yes] [--items servers,models]` using the same core adapters; headless without `--yes` prints the dry run and exits 0; with `--yes` still refuses allow rules and hooks (they need the interactive trust prompt).
- **Remote workspaces**: detection runs where core runs; a message says so when nothing is found.

### 10.1 What was marked unverified, now traced or fetched

**MCP tools and hooks in the CLI (traced, by reading).** The sentence in `hooks-trust.mdx` is half right.

- Every call, MCP included, reaches `runPreToolUseHooks(call)` (`stream/streamChatResponse.helpers.ts:923`) and `runPostToolUseHooks` (`:1024`); `executeToolCall` runs after the hook. So MCP tools **do** fire the tool hooks, and so do `Search` and `List`.
- But the name the hook sees is the server's raw tool name. `convertMcpToolToContinueTool` (`tools/index.tsx:239-262`) sets `name: mcpTool.name` and keeps the server in a separate `mcpServer` field; `firePreToolUse(call.name, ...)` passes only `call.name` (`toolHooks.ts:32`, `fireHook.ts:79-81`), and the hook input types have no server field (`types.ts:151-175`). The permission code uses `mcp__<server>__<tool>` (`permissions/coreRules.ts:97-105`); the hook code does not.
- Consequence: a matcher written for Claude Code or Gemini CLI (`mcp__github__.*`, `mcp_github_.*`) or for Cursor (`MCP:<tool>`) never matches an MCP call here, so a guard hook for an MCP server silently does not run; and two servers that expose a tool of the same name are indistinguishable to a hook. There is no test of an MCP call through the hook path (`stream/toolHooks.test.ts` has none). This is a fail-open gap of the same kind as D10. New row D13.
- The docs sentence should say: "MCP and search tools do call tool hooks; hook input names an MCP tool by its server's own tool name until D13."
