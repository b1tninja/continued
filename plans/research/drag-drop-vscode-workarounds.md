# Drag and drop into the chat on VS Code 1.140 and later: status and workarounds

Research report, 2026-11-13. Docs only; nothing here is built. It follows [`input-drag-drop-paste-context.md`](input-drag-drop-paste-context.md) (UX20 to UX32) and draft PR #800 (branch `chat-drag-drop-context`, UX21 from sources, UX26, UX27), which found that Explorer and editor-tab drops no longer reach extension webviews. The rows that come out of it are `UX67` to `UX72` (section 9); they are proposed here and not yet in [`../ROADMAP.md`](../ROADMAP.md).

The owner's question: people want to drop files into the chat from (1) the VS Code Explorer, (2) open editor tabs and (3) Windows File Explorer, from another window or folder. Our chat input lives in a webview **view** in the sidebar (`continuous.continueGUIView`, `extensions/vscode/package.json`), and "Open in new window" (`continuous.openInNewWindow`, `extensions/vscode/src/commands.ts:764`) puts the same page in a webview **panel** in the editor area.

Labels: "source" means read from the code at the commit or URL given; "reported" means a third party says so in the linked issue; "predicted" or "unverified" means neither we nor a cited source has run it. Section 6 is a probe that turns the predictions into measurements in five minutes.

## 1. Summary and recommendation

1. **The regression is open, with no fix merged and no setting or flag that restores the old behaviour.** microsoft/vscode#339036 is open, labelled `regression`, assigned to the Electron owner, and was moved from the 1.142.0 milestone to "On Deck" on 2026-10-12. The community fix, microsoft/vscode#344153, is open, unreviewed by a maintainer and unmerged. VS Code main (1.147.0, Electron 43.8.9) has no change to the drag code, so Insiders is not fixed (source, 2026-11-13). No ETA.
2. **The cause is a Chromium security check that Electron turned back on.** Since Electron 43.7.0, a drag that starts in a top-level page is refused by any cross-site frame of the same page; VS Code webviews are cross-site iframes. Drags from **another window or another app** are not covered by the check, which is why OS file drops still arrive.
3. **What accepts Explorer and tab drops today:** native workbench UI only. For an extension that means a **tree view** with a `TreeDragAndDropController` (gets `text/uri-list`, and OS files as `files` with a real `uri` on desktop) and a **text editor** through `DocumentDropEditProvider`. Webview views, webview panels and custom editors (all iframes) do not.
4. **Recommendation, in order:**
   1. Ship the routes that never depend on drag and drop: an **"Add to Continuous chat"** item on the Explorer (multi-select), the editor tab and the editor context menus, plus **"Add active file"** and **"Add open editors"** commands. The extension already has half of this: `continuous.selectFilesAsContext` on `explorer/context`, but it reads every selected file in full with no size cap and no credential check, and walks folders recursively (section 2.4). Fix it and extend it (UX68).
   2. Treat a pasted list of absolute paths (VS Code's **Copy Path**, Shift+Alt+C) as an offer to add those files (UX69).
   3. Add a small **native drop zone**, a tree view in the Continuous container, which takes Explorer, tab and OS drops without Shift on every VS Code version and gives OS files their real path (UX70). Measure it first (UX67).
   4. Keep PR #800's webview drop handler: it works today for OS files with Shift and starts working for the Explorer and tabs the day VS Code ships a fix. Add text snapshot chips for OS files that are not images (UX71), as Kilo Code did.
   5. Say plainly in the drop overlay and the docs that VS Code 1.140 and later do not deliver Explorer and tab drops to extension webviews, and name the context menu instead (UX72). Track #339036.
5. **Do not** patch `workbench.desktop.main.js`, add a Chromium site-isolation switch, or move the chat into an editor tab to get around this: section 7 says why.

### 2.2 Which check, in which version

The analysis comment on #339036 (2026-10-05) traces the break to VS Code PR #336697 (commit `0d9ade07b60`), which moved Electron from 43.6.0 (VS Code 1.139.0) to 43.7.3 (VS Code 1.140.0) and so picked up Electron #53750.

The check is `WebContentsViewDragSecurityInfo::IsValidDragTarget` in Chromium, `content/browser/web_contents/web_contents_view_drag_security_info.cc` ([source](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/content/browser/web_contents/web_contents_view_drag_security_info.cc), read 2026-11-13). It is the browser half of crbug.com/59081 and it reads, in order:

1. If the drag was **not** initiated by this top-level view (`did_initiate_` false: "the drag started outside of the browser or from a different top-level WebContents"), allow it.
2. If source and target are different pages (different `WebContents`, or a guest frame tree), allow it.
3. Otherwise allow only when source and target share a `SiteInstanceGroup`.

Electron's old `webview_cross_drag.patch` made the function return `true` always; #53669 narrowed that to guests (Electron `<webview>` tags) and let rule 3 apply again. VS Code's extension webviews are **cross-site `<iframe>` elements** (`vscode-webview://{uuid}`), not `<webview>` guests (`webviewElement.ts`, cited in the #339036 analysis), so an Explorer drag (source: the workbench page) onto a webview (target: a cross-site frame in the same page) fails rule 3 and is refused before the page sees `dragenter`. Electron #53669's own test table shows exactly this: "page to a cross-site `<iframe>` in the same page ... refused: the frame never sees `dragenter`, `dragend` reports `none`".

Consequences that follow from the rules (source, not measured):

- The Shift gesture is irrelevant to this check. Shift only controls VS Code's own `pointer-events: none` blocking (`webviewWindowDragMonitor.ts`, unchanged since 2024-08-30 per its commit history), which is a second, older gate.
- Webview **views** (sidebar), webview **panels** (editor tabs) and **custom editors** are all the same iframe and all affected. The first comment on #339036 (2026-10-01, Windows) reports both the sidebar and the editor-tab placement failing.
- **OS file drops are allowed** by rule 1 and still arrive (reported on 1.145.2 in the #339036 comment of 2026-11-11).
- **Drags from an extension's own tree view** into its own webview fail too (same page): reported with a 1.139.0 to 1.145.2 table in the same comment.
- The native chat (Copilot Chat's view) is workbench DOM, not an iframe, so it still accepts drops ("Dragging into the built-in chat still works", #339036 comment of 2026-10-05).
- **Hypothesis, unverified:** a webview in an **auxiliary window** (a webview panel moved with "Move Editor into New Window") is a different top-level `WebContents`, so a drag from the main window's Explorer should pass rule 1 or 2. Probe row 15 tests it. If it holds, it is a workaround for power users, not a product design.

### 2.3 Settings and switches

None found that restores the old behaviour:

- **Settings:** neither `webviewWindowDragMonitor.ts` nor `pre/index.html` reads a configuration value (source, VS Code main, 2026-11-13). There is no `workbench.*` or `window.*` setting for webview drops; `editor.dropIntoEditor.enabled` applies to text editors only.
- **`argv.json`:** VS Code only passes an allow-list of keys to Electron: `disable-hardware-acceleration`, `force-color-profile`, `disable-lcd-text`, `proxy-bypass-list`, `remote-debugging-port`, plus `force-renderer-accessibility` and `password-store` on Linux (`SUPPORTED_ELECTRON_SWITCHES` in `src/mainImpl.ts`, VS Code main, 2026-11-13). Nothing about drag and drop.
- **Electron or Chromium switch:** the check has no switch; it is unconditional code in the browser process. A site-isolation switch (for example `--disable-site-isolation-trials` on the command line) might put the webview frame in the same `SiteInstanceGroup` and pass rule 3: **unverified, and rejected** because it weakens isolation for every webview in the window, including untrusted extension content, and `argv.json` would not accept it anyway.
- **Patching the workbench bundle:** a #339036 comment (2026-10-08, macOS, 1.141.0) reports that neutralising the drag blocking in `workbench.desktop.main.js` makes drops work. Rejected: VS Code reports a modified installation as corrupt, an update overwrites it, and it is not something to tell users to do.
- **Downgrading** to VS Code 1.139.0 restores it (reported, several comments), at the cost of every later fix. Not a recommendation.

The lesson: the tools whose chat is native workbench UI (Copilot Chat, and the forks) are not hit; every extension with a webview chat is. No extension API lets a webview opt out of the check.

**Is there an API that would let us be "native"?** Only by not being a webview. `vscode.chat.createChatParticipant` (stable) makes us a participant inside VS Code's own chat, which then does the drop for us and hands us `references`; the proposed `vscode.proposed.chatContextProvider.d.ts` (`registerChatWorkspaceContextProvider`, `registerChatAttachContextProvider`, `registerChatTabContextProvider`) feeds context **into** that native chat. Both mean giving up our own UI for the chat, which is out of scope for a drag-and-drop fix. `registerWebviewViewProvider`'s options are `webviewOptions.retainContextWhenHidden` only; `WebviewOptions` has `enableScripts`, `enableForms`, `enableCommandUris`, `localResourceRoots` and `portMapping`. Nothing about drops (stable `vscode.d.ts`, VS Code main, 2026-11-13). The proposed API directory has no drop proposal for webviews (file list of `src/vscode-dts`, 2026-11-13).

Three findings from our own code while checking the menus:

1. **We already have an Explorer menu item.** `continuous.selectFilesAsContext` ("Select Files as Context") is on `explorer/context` (`package.json:672-677`) and handles multi-select (`commands.ts:451-485`).

## 5. OS drops into a webview (research question c)

What the page gets from Windows File Explorer, macOS Finder or a Linux file manager (source and reports; probe rows 6 to 8 and 12 measure it):

- **Delivery:** yes on 1.140+ (rule 1 in section 2.2), **but only with Shift**. Without Shift, VS Code's preload posts `drag-start` when every item is a file (`pre/index.html` `handleInnerDragStartEvent`, lines 832-846), the workbench sets `pointer-events: none` on the iframe, and the drop goes to the workbench, which opens the file in an editor. Calling `preventDefault()` in our `dragenter` skips that post, but the forwarded `drag` message still carries `shiftKey` to the monitor (#346855's reading of the same code). Probe row 12 tests both.
- **Types:** `Files` only; `text/uri-list` empty (Kilo #14822's recording on VS Code 1.107; #339036 comment on 1.145.2).
- **`File` objects:** `name`, `size`, `type` (from the extension, often empty), `lastModified`, and the bytes through `arrayBuffer()`, `text()` or `stream()`. **No path:** Electron removed the non-standard `File.path` in 32.0 in favour of `webUtils.getPathForFile` (Electron `docs/breaking-changes.md`, "Removed: `File.path`"), and `webUtils` is a preload API that an extension webview cannot reach.
- **Folders:** `DataTransferItem.webkitGetAsEntry()` returns a `FileSystemDirectoryEntry` whose `createReader().readEntries()` lists children in batches; it has to be called synchronously inside the `drop` handler. Predicted to work in the webview (it is plain Chromium), unverified; probe row 7. `getAsFileSystemHandle()` (File System Access API) needs a secure context; whether `vscode-webview://` counts is unverified, and the probe logs `isSecureContext` and the handle.
- **Size:** the web platform sets no limit on a dropped `File`; the bytes are read lazily from disk. The limit is ours: memory in the webview and the message size to the extension host. Read a 4 KB head first to classify, then read whole only under a cap. Probe row 8 logs the head read time on a large file.
- **Remote windows:** the OS file is on the local machine and the workspace is on the remote. A snapshot (bytes in the message) works; a reference cannot.

Security of reading a file the person dragged from outside the workspace:

- **Consent:** a deliberate drag of one named file onto the chat is an explicit gesture for **that file's content to be added to this message**. It is not consent to read its folder, to remember the location, or to read it again later. A folder drop is consent to see a list, not to inline every file: show the list with sizes and let the person pick, with caps.
- **Credentials:** the same rules as PR #800 for workspace files, applied to the name (`securityPatternHit`) and, since we have the bytes, to the content (`scanText`, `core/util/secretScan/scan.ts`) **before** the chip is created. Default: refuse with the reason, as PR #800 does for names (decision D6 of the earlier note); the confirm variant belongs to X23.
- **Binary:** a NUL byte in the first 8 KB, or invalid UTF-8, marks the file as binary; images go to the image path, everything else is refused with the reason ("binary files are not added"). Kilo uses the same NUL rule.
- **Caps:** at most 256 KB per text snapshot (Kilo's figure) and a total per message; the chip shows name, size, an estimated token count and a short hash, so the person sees exactly what goes out.
- **Hidden characters:** the dropped text goes through the same sanitiser as paste (X22).
- **Logging:** the audit record gets name, size and hash, never content or a path (there is none).
- **Re-identification, optional:** a dropped OS file that is really inside the workspace (the person dragged it from Windows Explorer in the project folder) can be matched by name, size and modification time against `workspace.findFiles` results and turned into a normal `@file` reference. Heuristic: two files can match; offer it, never assume it.

## 6. Probe: turning the predictions into measurements

A throwaway extension, outside the repository: **`D:\temp\dnd-probe`** (`package.json`, `extension.js`, `README.md`; no dependencies, no build). It registers:

1. a **webview view** ("Webview view drop target") in its own activity bar container, logging `dragenter`, `dragover` (throttled), `dragleave`, `drop`, `paste`, `pointerover` and `pointerenter`, with `types`, every `getData` value, every `File` (name, size, type, `path` present or not, NUL in the first 4 KB, read time), `webkitGetAsEntry` listings for folders and `getAsFileSystemHandle` results; a checkbox turns `preventDefault()` on `dragenter` on and off;
2. a **tree view** with a `TreeDragAndDropController` accepting `text/uri-list`, `files`, `application/vnd.code.uri-list`, `resourceurls`, `codeeditors`, `text/plain` and the Explorer's tree type, logging every entry (`asString`, `asFile().uri`, size, NUL);
3. a **webview panel** in the editor area (command "DnD Probe: Open webview panel (editor area)") with the same page as 1;
4. "DnD Probe: Add to probe" on `explorer/context`, `editor/title/context` and `editor/context` (and Ctrl+Alt+Shift+A), logging the arguments VS Code passes; "Add all open tabs" (`tabGroups`); "Read clipboard text" (`env.clipboard.readText`).

Everything goes to the "DnD Probe" output channel and to `D:\temp\dnd-probe\logs\probe.jsonl`, one JSON object per line with the VS Code version, platform and remote name.

Load it:

```
code --extensionDevelopmentPath=D:\temp\dnd-probe D:\some\scratch-folder
```

Use a scratch folder with a few files and one subfolder. `code-insiders` for Insiders; a portable 1.139.0 zip gives the "before" column.

## 8. Recommendation

Do 1, 2 and the version-aware message from 6 in the patch release (2.16.1): they are small, need no new surface, work on every VS Code version and remote, and the menu rework removes an uncapped whole-file read with no credential check that ships today. Run the probe (UX67) before committing to 3, because the drop zone is the only real drag-and-drop answer for the Explorer and tabs while #339036 is open, and its tab and OS-path behaviour are predictions. Then 3 and 4 in 2.18.0. Merge PR #800 as it is (it is correct and becomes fully useful once VS Code is fixed), with the overlay text from UX72. Re-check #339036 and #344153 at each release; when a fixed VS Code ships, the drop zone can be hidden behind a setting rather than removed, for people who stay on older versions.

Owner decisions:

- **D1:** the menu label ("Add to Continuous chat" or "Add as context") and whether "Select Files as Context" is renamed or replaced.
- **D2:** a default keybinding for "Add active file" and "Add open editors", or palette only. Our existing bindings (section 4 of the earlier note) and VS Code's defaults leave few free chords; palette only is the safe default.
- **D3:** whether the tree drop zone is visible by default or appears only on VS Code 1.140 and later.
- **D4:** whether dropping an OS file from outside the workspace is allowed at all (snapshot with the checks above) or refused as PR #800 does today.
