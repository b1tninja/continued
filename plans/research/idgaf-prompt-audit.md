# IDGAF prompt and refusal audit (2.16.2)

Owner report: "YOLO/IDGAF mode is still prompting in some scenarios asking the user to Accept." The owner later set the spec: in IDGAF the permission layer must neither ask nor deny a tool call. What a rule or guard would have done is recorded instead, without blocking. Each site below was found by reading the code at `62277ea78`. Hotfix #825 and its follow-up PR change it.

"IDGAF" in this document means the level of the call's own area (Context use, Tool use or File edits) is `idgaf`. The IDGAF preset sets all five areas to IDGAF. `cn --auto` raises the three tool areas to IDGAF.

## The decision point

- **Core:** `idgafRunsEverything` in `core/tools/permissions/evaluate.ts` is the only place IDGAF overrides a decision. Every rule and guard decides first, exactly as at any other level. If the call's area is at IDGAF, the call then runs. The decision keeps `idgafOverride` (what would have happened), and the reason gains `Below IDGAF this call would have been refused/asked: …`. A call that IDGAF settled earlier gets the same record from `objectionUnderIdgaf`. A future Custom policy that enforces chosen guards at IDGAF belongs at this point.
- **CLI:** `runsAtIdgaf` and `liftAtIdgaf` in `extensions/cli/src/permissions/coreRules.ts` do the same for the CLI's own `allow/ask/exclude` lists, which run before core. They apply in two places: the approval path (`decideToolApproval`) and the tools offered to the model (`getRequestTools`).
- **Not counted as an objection:** a tool's own setting asking with no rule behind it, such as the catch-all `*: ask`. At IDGAF that would be every call.

## Recording

Every call IDGAF ran past an objection is written to the existing audit trail. The decision line carries `level: "idgaf"` and a masked `wouldHave: { policy, source, rule, reason }`. The audit index counts these lines under one key, and the Permissions page's audit overview shows the 30-day count. `cn` prints one stderr line at the end of a run and adds `numIdgafObjections` to the stream-json `result` event. Recording failures never block a call, and the model is never told.

## Owner decisions

1. **PreToolUse hooks.** A hook the user wrote still runs at IDGAF. Its `ask` prompts in the TUI and is refused headless. Proposal: keep running hooks (they are the user's own code), but at IDGAF treat a hook's `ask` as allow, recorded as an objection, and keep a hook's explicit block.
2. **Technical stops stay.** These include unknown tools, invalid arguments, missing files, provider errors and the user's `--max-*` limits.
3. **Plan mode stays a separate mode.** That includes the CLI's blocking "Build this plan?" (row 23). Proposal: at Questions IDGAF, end the turn with the plan saved instead of blocking, to match the GUI's non-blocking card.
4. **Workspace config trust (row 30).** It is not suppressed by IDGAF, because accepting it would load a repository's hooks and config.
5. **CLI IDGAF is per process.** Should `--resume` restore the level a session was saved at?
6. **A tool the person switched off stays off at IDGAF (row 18).**

## Follow-ups (by priority)

- **F1. Remote terminal (row 32).** Send the command with a newline once the policy has allowed it (an `execute` option on `TerminalOptions`). Also stop telling the model "Command executed" for text that was only typed.
- **F2. CLI "Build this plan?" at Questions IDGAF (row 23).** See decision 3.
- **F3. Held approvals refused on switching to IDGAF (row 27).** Grant them instead of refusing, to match the new spec.
- **F4. `ApplyManager` early returns (row 36).** Send a closed or error apply state so the edit tool call ends.
- **F5. Config-updated toast (row 33).** Do not await it before reloading.
- **F6. MCP elicitation level (row 28).** It is read from the last `tools/evaluatePolicy`. Push it on level change instead.
- **F7. CLI Permissive for tools core cannot name (Subagent).** Permissive still asks there. Only IDGAF was in scope here.
