# Custom policies and "IDGAF + guards": a concept review (2026-11-13)

Status: DRAFT, review of a product concept before it is built. Docs only: no product code changed, no model called. Code read at `origin/main` 62277ea. Web pages fetched on 2026-11-13; a claim I could not confirm on the vendor's own page is marked **unverified**. The IDGAF "never ask, never deny" hotfix the owner described is not on `main` or on a pushed branch, so where this note says what the hotfix must touch it is reading the current code, not the hotfix.

## 1. Verdict

The concept is worth building, but not as described. Four corrections matter most:

1. **"IDGAF + guards" is not a separate mode.** Once a guard can ask or deny, the policy no longer means "never asks, never refuses", which is the whole promise of the IDGAF label. With record-only guards it is still IDGAF, plus annotations. With any guard that asks or denies, it is a custom policy that allows by default and enforces a named set of checks. The engine can already almost express that: Permissive levels plus `builtin:` switches plus `floor:` deny rules (section 4). Build **one** custom-policy model. "Based on X" records where it started and has no effect on behaviour, and the IDGAF name and red chip stay reserved for the record-only case.
2. **The fallback ("when a stricter preset would have objected") does the same job as the guards.** With Approve, the policy is IDGAF. With Ask, it is Hands-off. With Deny, it is Hands-off with Claude Code's `dontAsk` disposition. What the setting really controls is how an objection is resolved, and the same choice (record, ask, deny) is needed for every guard and for every unattended run. Make it one setting, applied everywhere, and limit the reference preset to deterministic presets.
3. **Half the example guards cannot be enforced at the tool layer.** File-tool path guards, fetch-tool host guards, the tainted-session sink rule, policy-file locks and spend caps work at the tool layer. Command denylists, terminal network or path limits, "destructive command" detection, typosquat detection and prompt-injection detection only catch accidents. Every peer that tried to make command lists a boundary found them bypassable, and most now ship OS sandboxing (section 6). Label the second group **best-effort** in the UI, and do not claim containment until W8 (sandbox) lands.
4. **Prompt-injection detection must not decide the taint.** The taint must come from where the content came from: a fetch, an MCP result, an outside read, issue text. That is what `plans/design/tainted-session.md` already builds. A detector hit can annotate the record and add weight to the decision. A detector cannot be the trigger, because adaptive attacks get past published detectors more than 90% of the time (section 5.3).

## 2. The concept, restated precisely

The owner's description, corrected against the code:

- **Areas are not "files, terminal, MCP, fetch".** They are Context use, Tool use, File edits, Plan edits and Questions (`core/tools/permissions/policy.ts:11-19`). Terminal, MCP and web are all in Tool use. A terminal command that the parser vouches as read-only moves to Context use (`policy.ts:513-515`), an MCP tool with `readonly` moves to Context (`policy.ts:519`), and web tools are never Context because they can send data out (`policy.ts:479-480`).
- **Levels:** Manual, Cautious, Automatic, Permissive, IDGAF (`policy.ts:22-31`). **Presets** set the five levels: Careful, Accept edits, Hands off, Reviewer, IDGAF (`policy.ts:225-276`). A combination that matches no preset already shows as "Custom" (`plans/policy-areas.md:312`, `presetOf` at `policy.ts:282`).
- **IDGAF is session-only.** It is never written to `permissions.yaml`, and a saved `idgaf` is read back as the area's default (`core/tools/permissions/settingsFile.ts:24-25, 85-93`; the CLI's `savePolicyFile` "never IDGAF", `extensions/cli/src/permissions/policyLevels.ts:85-91`). A saved custom policy "based on IDGAF" runs into this invariant (decision D2).
- **What still refuses at IDGAF today, which the hotfix must change:** `noAskAtIdgaf` turns any remaining ask into a refusal when Questions is IDGAF (`evaluate.ts:195-229`); `lockPolicyFiles` and the locked floor rule `protect-policy-files` (`evaluate.ts:282`, `policy.ts:180-191`); `lockRuntimeWrites` asks on runtime-built write targets (`evaluate.ts:231-260`); the tainted-session rule, when switched on, applies "at every level including YOLO" (`plans/design/tainted-session.md` §5); and the person's own `floor:` deny rules "bind at every level, IDGAF included" (`approval.ts:34-35`, `settingsFile.ts:28-29`). `floor:` is already "IDGAF + deny guards". The hotfix has to drop it, keep it, or turn it into guards (D3).

The concept, stated precisely:

> A **policy** is: five area levels; a set of **checks** (the built-in rules, the person's own deny/ask/allow lists, and opt-in guards), each with an **action** of `off | record | ask | deny`; one **objection disposition** for whatever no check settles (`approve | ask | deny`, optionally measured against a deterministic reference preset); and an **unattended rule** for an `ask` that nobody can answer. A **preset** is a named, read-only policy. **Custom** is any other policy, labelled with the preset it started from. **IDGAF** is the one policy whose every check is `record` or `off` and whose disposition is `approve`: it never asks and never refuses. Recording is the only thing its checks do.

## 3. Coherence

### 3.1 Is "IDGAF + guards" meaningful?

| Guard actions in use            | What it really is                                                      | Label                                                     |
| ------------------------------- | ---------------------------------------------------------------------- | --------------------------------------------------------- |
| none, or only `record`          | IDGAF, with "would have objected" entries in the audit trail           | IDGAF                                                     |
| any `ask` or `deny`             | Allow by default, these named checks enforced                          | Custom (from IDGAF) · N guards                            |
| disposition `ask` vs Hands off  | Hands off, with the guard list replacing the built-ins that are on     | Custom (from Hands off)                                   |
| disposition `deny` vs Hands off | Hands off, and every objection refused (Claude Code's `dontAsk` shape) | Custom (from Hands off) · objections refused, never asked |

So it does collapse into a custom preset. The useful difference from "Permissive with some built-ins switched off" is only the starting point: an IDGAF-based policy starts with **every** check at `off` and turns them on one at a time (allow by default), while Permissive starts with every built-in on. That is a wizard default, not a separate engine mode.

### 3.2 Precedence (proposed; one rule, most restrictive wins)

Every matching check is evaluated, not only the first. The verdict is the strictest action among the matches, `deny > ask > record > allow`. Ties go to the earlier row below, so the explanation names one deciding check and lists the others.

| #   | Check                                                                                               | Can be loosened by | Notes                                                                                                                                                                                                           |
| --- | --------------------------------------------------------------------------------------------------- | ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0   | Tool absent: switched off, `exclude`, Plan role, organisation ceiling                               | nothing            | Not a denial by IDGAF. The tool is not offered at all, which is how `exclude` already works (`extensions/cli/src/permissions/README.md:21-23`)                                                                  |
| 1   | Guard at `deny` (incl. migrated `floor:` rules and, when any guard is on, the policy-file lock: D4) | nothing            | An allow rule cannot carve out an exception, as with Claude Code's deny-first rule                                                                                                                              |
| 2   | Person's deny list                                                                                  | nothing            | In an IDGAF-based custom, the deny list is simply a guard ("Never run these")                                                                                                                                   |
| 3   | Guard at `ask`, protected path, ask list                                                            | nothing below      | Becomes `deny` or `hold` when unattended (3.3)                                                                                                                                                                  |
| 4   | Workspace (repository) file                                                                         | -                  | May add rows 1 to 3 only; may never loosen (`trust.ts:1-26` already drops loosening keys)                                                                                                                       |
| 5   | Allow list                                                                                          | -                  | Only settles calls nothing above matched                                                                                                                                                                        |
| 6   | Reference-preset objection, then the disposition                                                    | -                  | Evaluate the reference preset's levels with the **same** rules. If it would ask or deny, apply the disposition. Per-category overrides pick a different disposition by check class, never a different reference |
| 7   | Area level default                                                                                  | -                  | IDGAF: approve                                                                                                                                                                                                  |
| -   | `record` matches at any row                                                                         | -                  | Never change the verdict. Every one is written to the audit record (`wouldHave: [{check, action, reason}]`)                                                                                                     |

The engine today is first-match in a fixed order (`decide.ts:164-243`), and that order is close to the table above. The changes needed are collecting every match for the record, adding the `guard` source, and running row 6 as a second pass of the same evaluator. The test panel can reuse `testToolCall.ts` for that pass (`testToolCall.ts:47-52`).

### 3.3 An `ask` that nobody can answer

The code already does the right thing. A loop holds the call as a question, a headless run refuses it (`extensions/cli/src/stream/streamChatResponse.helpers.ts:385-397, 410-417`), and when the check itself fails the call goes to `ask`, so it fails closed (`:280-285`). Claude Code's `-p` does the same: a call that needs approval is denied unless something approved it ([permission modes](https://code.claude.com/docs/en/permission-modes)). Recommendation: an unattended `ask` is **hold** in a loop that has an inbox and **deny** otherwise. It is **never approve**: a person who wants approval picks `record`. The wizard's review page says "Ask means Deny when nobody can answer" next to every `ask`. When Questions is IDGAF, an `ask` guard therefore refuses, because `noAskAtIdgaf` (`evaluate.ts:207-229`) does exactly that. This must stay true after the hotfix for guards the person set to `ask`, even though built-in floors stop refusing.

### 3.4 Determinism and explainability

- Deterministic if and only if the reference preset is deterministic. Reviewer/Automatic calls a model (`approval.ts:23-24`). Disallow it as a reference (D6), or mark the policy "model-decided" and never replay it as exact.
- Every verdict carries: the deciding check id, its action, the file it came from (already done for rules: `decide.ts:21-46`), every `record` match, and for row 6 the reference preset's own reason. For an unattended `ask`, the reason also says "nobody could answer, so refused" (already done: `:396`).
- The audit `setting` record already logs level, preset, floor and built-in changes (`audit/trail.ts:225-240`). A custom policy must log its whole definition hash with each decision, so a past decision can be explained against the policy that made it.

### 5.2 Denylists vs allowlists

A command denylist enumerates bad strings, and every bad command has unboundedly many spellings. Backslash showed four classes of bypass against Cursor's auto-run denylist (base64, subshells, scripts, quoting), and Cursor deprecated the denylist in 1.3 ([Backslash, 2025-07-21](https://www.backslash.security/blog/cursor-ai-security-flaw-autorun-denylist); vendor response as reported there). Claude Code's own docs call argument-constraining Bash patterns "fragile", and say a deny rule "doesn't match the same program by path or inside `sh -c`, so pair it with the sandbox network allowlist when the restriction must hold" ([permissions](https://code.claude.com/docs/en/permissions)). VS Code calls terminal auto-approve "a best-effort convenience, not a security boundary", and a `false` rule there "requires approval. It does not block the command" ([approvals](https://code.visualstudio.com/docs/agents/approvals)). This repository's own floor text already says it ("a sandbox that denies writes to these folders is what holds for certain", `policy.ts:189`). An allowlist fails closed, so it is the right shape for an unattended run. A denylist is still worth having, but only to stop a model's honest mistakes.

### 5.3 Prompt-injection detection

- Adaptive attacks bypassed 12 published defences with success rates above 90% for most, where the papers had reported near zero ([Nasr, Carlini, Tramèr et al., "The Attacker Moves Second", arXiv 2510.09023](https://arxiv.org/abs/2510.09023)).
- Willison: "we still don't know how to 100% reliably prevent this", and a 95% detection rate is "very much a failing grade" in security. After untrusted input the agent "must be constrained so that it is impossible for that input to trigger any consequential actions" ([The lethal trifecta, 2025-06-16](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)).
- Design-pattern and CaMeL work moves the guarantee from detection to capability limits ([arXiv 2506.08837](https://arxiv.org/abs/2506.08837); [CaMeL, arXiv 2503.18813](https://arxiv.org/abs/2503.18813): 77% of AgentDojo tasks with provable security vs 84% undefended, as recorded in `plans/research/agent-security.md:35`).
- Claude Code's auto mode runs a server-side probe on tool results **and** strips tool results from the classifier's input. It still says auto mode "does not guarantee safety", and that bypassPermissions "offers no protection against prompt injection" ([permission modes](https://code.claude.com/docs/en/permission-modes)).
- False positives: the repo's own detector says "ordinary text can match by accident" (`injection.ts:7-8`). On a security page or in a test fixture it will fire regularly.

So the detector is sold as "flags text that looks addressed to the agent". It may raise a pending sink to `ask` **in addition to** provenance taint, never instead of it. A detector-driven taint with no provenance taint behind it gives a false sense of safety in exactly the mode where nothing else is checking.

### 5.4 The taint/sink model is the right core

The lethal trifecta needs private data, untrusted content and a way to communicate out; Meta's Rule of Two allows at most two of those without a person ([Meta, practical agent security](https://ai.meta.com/blog/practical-ai-agent-security/), as cited in `tainted-session.md` §1). The built rule taints on provenance and raises sinks to `ask`. The concept's "secret read then network send" is a **second label**, private data, not a replacement. Recommended guard: `egress-after-untrusted` (exists) plus `egress-after-secret-read` (new, set by a protected-secret read or a `credential-read` sink). Each gets its own action. CaMeL-style data-flow tracking stays out of scope, as the design already judges it infeasible for an open-ended coding agent.

### 5.5 False sense of safety in a mode named IDGAF

The risk is a red "IDGAF" chip with a few guards ticked, read as "IDGAF but safe". Mitigations:

- Rename the label as soon as any guard blocks (3.1).
- The review page shows every guard's enforcement class from 5.1 next to it.
- Show a standing line, "Terminal commands, scripts and MCP servers are not contained. No sandbox is active.", until W8 reports a verified containment. `srtStatus.ts` already refuses to say "contained" (`containment` is `"not-verified"`, `srtStatus.ts:17-21`).
- Codex and Claude Code both say full-bypass modes are for isolated environments only ([Codex approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security); [Claude Code permissions](https://code.claude.com/docs/en/permissions)).

### 5.6 "Test this policy" limits

Replaying the audit trail through `testToolCall` is cheap and deterministic. It can only be as good as the record, and the record has three limits:

- Args are masked and clipped to 2,000 characters (`record.ts:15`), so a long command or a call whose secret was masked replays as a different call.
- File and link state at the time of the call is gone, so the real-path checks re-resolve against today's disk.
- The taint fact is recorded only when the rule was on.

The panel must show "replayed from a masked record" and count the calls it could not replay exactly, rather than presenting a clean diff.

Every product that ran command lists as a boundary (Cursor, Copilot, Claude Code) now ships an OS sandbox and documents the lists as best-effort. Cursor removed its denylist outright.

## 7. Recommendation

### 7.1 What to build

- **One policy model** in `permissions.yaml`: `levels`, `checks: {<id>: off|record|ask|deny}`, `disposition: {action: approve|ask|deny, reference?: careful|acceptEdits|handsOff, byClass?: {...}}`, `unattended: hold|deny`, plus the existing lists. `builtin:` becomes `checks:` (on → that rule's current action, off → `off`), and `floor:` becomes `checks` entries at `deny`. Migrate without loosening anything (as `migrateApproval` does, `policy.ts:427-450`).
- **Wizard**: start from a preset → per-area levels → checks, grouped by the enforcement classes of 5.1 with their labels → lists → disposition → review (YAML diff, precedence summary, "Ask means Deny when nobody can answer") → test against recent calls → save.
- **Label**: preset name if it matches exactly. Otherwise "Custom (from X)", with a count of checks that ask or deny. "IDGAF" only for the record-only policy.
- **Read/write split**: do not add areas. Context vs File edits already splits read from write for files. Within Tool use, add per-kind checks (terminal, MCP, web) and keep using `classifyReadOnly` and trusted `readOnlyHint` to move reads into Context. Web is never a read (`policy.ts:479`).

### 7.4 Do not build, do not claim

- Do not claim "network only to listed hosts", "no writes outside the workspace" or "secrets protected" for terminal commands, scripts or MCP servers until a verified sandbox is active. Say "file tools only" or "best-effort".
- Do not sell the injection detector as protection, and do not let it be the only taint trigger.
- Do not build a typosquat detector or claim one. Ask on dependencies new to the lockfile.
- Do not offer "approve" as the answer to an unattended `ask`.
- Do not use the Reviewer preset as a fallback reference, and do not present replay of model-decided policies as exact.
- Do not let a workspace file turn a check off or lower its action (`trust.ts` rule).
- Do not build a second evaluator for the wizard or the test panel. `testToolCall` is the one.
- Do not add new areas for terminal, MCP and web. Use checks.
- Do not call `record` entries "blocked", "protected" or "caught" anywhere in the UI. They are "would have objected".
