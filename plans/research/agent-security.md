## 2. Prompt-injection defences: the literature and what maps to us

`plans/prompt-injection.md` (2026-11-10) listed several figures as "unverified, from search summaries". This pass re-fetched what it could.

Verified in this pass:

- The lethal trifecta (private data, untrusted content, external communication) is Willison's, 2025-06-16: https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/ (fetched 2026-11-11). His mitigation for users is to avoid having all three; for developers, constrain the agent once untrusted input has entered. He calls a 95% guardrail detection rate a failing grade in web security.
- "Design Patterns for Securing LLM Agents against Prompt Injections", arXiv 2506.08837, v3 27 June 2025: patterns that limit what an agent can do after reading untrusted input, ten case studies including software-engineering agents; the authors argue detection improvements stay heuristic and brittle. https://arxiv.org/abs/2506.08837 (via search listing 2026-11-11; the six pattern names were not re-read, see section 9).

Also verified this pass (abstract pages, fetched 2026-11-11): CaMeL, "Defeating Prompt Injections by Design", arXiv 2503.18813, v1 2025-03-24, v2 2025-06-24: 77% of tasks solved with provable security against 84% undefended on AgentDojo (https://arxiv.org/abs/2503.18813). "The Attacker Moves Second", arXiv 2510.09023, 2025-10-10, Nasr, Carlini, Tramer and others: 12 recent defenses, adaptive attacks above 90% success on most of them, which had reported near zero (https://arxiv.org/abs/2510.09023). Spotlighting, arXiv 2403.14720, 2024-03-20: attack success from above 50% to below 2% in the authors GPT-family experiments (https://arxiv.org/abs/2403.14720). Meta Agents Rule of Two, 2025-10-31: no more than two of untrustworthy input, access to sensitive systems or data, ability to change state or communicate externally per session; if all three are needed, no autonomous run, supervise (https://ai.meta.com/blog/practical-ai-agent-security/). LlamaFirewall, arXiv 2505.03574 (via search summary of the paper tables): AgentDojo attack success 17.63% with no guardrail, 7.53% with PromptGuard 2 alone, 2.89% with AlignmentCheck alone, 1.75% combined, utility 47.7% to 42.7%; the authors note the benchmark covers a narrow class of attack (https://arxiv.org/pdf/2505.03574). Still carried from `prompt-injection.md` and not re-verified: FIDES, AgentDojo and InjecAgent numbers, the Anthropic and Google vendor posts.

Finding: the field's consistent conclusion is that detection lowers rates and constraint of effects is what holds. Our engine already constrains effects at the call boundary; the one missing structural piece is the taint rule (X4). It is the single change that converts the three-trifecta property from "hoped" to "asked".

## 3. MCP security

### Spec

Fetched from https://modelcontextprotocol.io/specification/draft/basic/authorization and https://modelcontextprotocol.io/specification/draft/basic/security_best_practices on 2026-11-11 (the "draft" spec; the security page says session handling changed from protocol version 2025-11-25):

- Authorization is optional. Clients using HTTP transport SHOULD follow it; stdio SHOULD NOT and takes credentials from the environment.
- Servers MUST implement RFC 9728 protected resource metadata; clients MUST use it to find the authorization server, and MUST support both RFC 8414 and OpenID Connect discovery.
- Client registration order: Client ID Metadata Documents (SHOULD), pre-registration, Dynamic Client Registration (RFC 7591, now MAY and deprecated for back-compat).
- Clients MUST send the RFC 8707 `resource` parameter in authorization and token requests; MUST record the issuer before redirecting and validate `iss` (RFC 9207) before sending a code to a token endpoint; PKCE is required; access tokens MUST NOT be in the query string; clients MUST NOT send tokens to a server other than ones issued by that server's authorization server; servers MUST NOT accept or pass through tokens not issued to them.
- Security page: SSRF during metadata discovery (clients SHOULD block private, loopback and link-local ranges, pin DNS between check and use, validate redirect hops); authorization URL validation (clients MUST allow only http and https, MUST NOT open URLs through a shell); local-server consent (MUST show the exact command, untruncated, before one-click install; SHOULD sandbox).

RFC checks through `rfclib` (all current, no verified errata, 2026-11-09 corpus): RFC 9728 (Proposed Standard, 2025-04) section 3.3 says the `resource` value MUST be identical to the URL the client used to make the request, else the data MUST NOT be used; section 7.7 says clients SHOULD block internal address ranges. RFC 8414 (2018), RFC 7591 (2015), RFC 8707 (2020), RFC 9700 BCP 240 (2025-01): section 2.1.1 says public clients MUST use PKCE and S256 is the only method that does not expose the verifier.

## 6. Sandboxing on Windows for a VS Code extension and CLI

Facts verified 2026-11-11: Claude Code does not sandbox on native Windows; it runs commands unsandboxed there, and with `failIfUnavailable` it exits at startup; WSL2 uses bubblewrap, WSL1 is unsupported (https://code.claude.com/docs/en/sandboxing). The Codex Windows claim is not verified (docs fetch failed, section 4).

| Mechanism                                | Filesystem                              | Network              | Process                                             | Notes for us                                                                                                             |
| ---------------------------------------- | --------------------------------------- | -------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| WSL2 plus bubblewrap (`sandbox-runtime`) | write scope enforced; `/mnt/c` readable | namespace plus proxy | PID namespace, seccomp                              | our decision W-D2; spike measured write scope held, `/mnt/c` readable, host env leaks, network half not run              |
| Docker, Podman                           | mount plan                              | none by default      | container                                           | built (W2); workspace mount is writable by design                                                                        |
| Dev container                            | as container; socket and mounts vary    | varies               | container                                           | detection only (W3)                                                                                                      |
| Windows Sandbox (`wsb`)                  | disposable VM, mapped folders           | optional             | full VM                                             | measured 2.2 to 4.0 s a cycle (`windows-sandbox-runner.md`); Pro and Enterprise only; suits loop runs, not per command   |
| Job objects                              | none                                    | none                 | kill-on-close, memory and process limits, UI limits | resource limits and tree kill, not a security boundary alone                                                             |
| Restricted token, integrity level        | ACL based, deny-only SIDs               | none                 | process                                             | needs ACLs applied to the workspace; a native sandbox project in its own right                                           |
| AppContainer, LPAC                       | capability based, per-package ACL       | capability gated     | process                                             | strongest native option, but classic Win32 tools and Node child processes often fail; size as research (W9 asked for it) |

Codex native Windows (https://learn.chatgpt.com/docs/windows/windows-sandbox.md, fetched 2026-11-11, reached through a redirect from `developers.openai.com`): an elevated mode that runs commands as dedicated lower-privilege sandbox users with a dedicated offline-user firewall rule, filesystem permission boundaries and denied read paths, needing an administrator-approved setup (local users and groups, firewall rules, logon rights; it can fail with error 1385 on managed machines); and an unelevated mode with a restricted token derived from the current user, ACL boundaries only, environment-level offline controls and no denied read paths. The page labels both "legacy fallback", so a newer default exists that was not read. The engineering post https://openai.com/index/building-codex-windows-sandbox/ returned 403. Gemini CLI uses `icacls` Low integrity with labels that persist on files. AppContainer (https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation, updated 2025-07) isolates files and registry, network by capability, processes, windows and device access; the page says nothing about compatibility with arbitrary Win32 console tools, so that cost is unmeasured here.

Feasibility for us, in order of cost: (1) route Windows users to WSL2 plus `sandbox-runtime` (built decision W-D2, same as Claude Code), cost S to M each, needs bubblewrap and socat inside the distro; (2) container executor, built; (3) Windows Sandbox for whole loop runs, measured 2.2 to 4.0 s per cycle, Pro and Enterprise only; (4) a native restricted-token sandbox with ACLs, the Codex route: it needs administrator setup for the strong form, ACL changes that persist on the user files, and a per-release maintenance burden, so it is a project of its own (L to XL) and not recommended before WSL2 and containers are wired; (5) AppContainer or LPAC: unmeasured, risk of breaking Node, git and compilers, research only. Job objects add kill-on-close and limits to any of these and cost little (S).

## 8. Residual risks, ranked

1. Prompt injection plus an allowed network or write effect (no X4). Severity high, likelihood high: every agent in section 4 was hit by the same shape.
2. Command-analyser per-program flag gaps (section 5 table, untested). High, medium: unknown until E1.
3. `cn serve` and local IPC guards (X11). High, medium: three comparable advisories in 2026.
4. Reading a repo-supplied git config or executable (`git status` runs `core.fsmonitor`). Medium to high, medium: no row covers the read side.
5. Reviewer on weak models (Nova 2 Lite floor false allows, run-to-run flipping, B53 unrun). Medium, medium: gated by the eval and by the deterministic floor.
6. No OS isolation wired at all (W4b to W8c unbuilt); every guarantee is analyser-level. High, certain, but the analyser is the designed answer for now.
7. Native Windows has no sandbox option short of WSL2, a container or Windows Sandbox; the field has the same gap.
8. TOCTOU between decision and write for file tools (CVE-2026-88968, CVE-2026-103435): our deputy rule resolves at decision time only.
9. Standing instruction files (AGENTS.md) are trusted.

## 9. What we do against the field

- Stronger than the field: deterministic command grammar with a narrow read-only allowlist (`sed` only as a print range, every exec-flag of the section 5 programs rejected including abbreviations, git vouched only after reading the repository and user config for `core.fsmonitor`, hooks and filters), a locked policy floor, MCP launch pins, user-only allow rules, a reviewer that never sees tool output, and a measured reviewer gate. Several advisories in section 4 (the `sort`, `rg`, `git ls-remote`, `sed e`, `xargs`, `$IFS` and `@P` cases) correspond to code comments and rejects already in `readOnlyCommand.ts` and `command.ts`; this suggests the 2025 advisories were absorbed, though no test in this pass proves each one.
- Equal to the field: no sandbox on native Windows (Claude Code is the same), prompt injection is a notice and not a gate.
- Weaker than the field: no OS sandbox wired anywhere (Claude Code, Codex and Gemini CLI ship one), no managed policy layer (B19), no taint rule (X4), `cn serve` guards unbuilt (X11), no TOCTOU recheck at file open, no stated stance on hidden Unicode in instruction files.
