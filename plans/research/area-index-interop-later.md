## 3. Track L: open rows in depth

### 3.1 L0 and L10: build what needs no embedding model

- Problem (user terms): a fresh install builds nothing, so `@codebase` and the `codebase` tool return nothing useful; a person with an Ollama embed model gets everything, a person without gets nothing, and the setting text does not say why.
- Design: split `getIndexesToBuild` into "always" (chunk, fullTextSearch, codeSnippets) and "needs embed" (embeddings). Run the first group whenever `disableIndexing` is false, in a dependency-sorted order (chunk before FTS before snippets; chunk before embeddings), encoded as a static `dependsOn` map instead of provider order. Embeddings only when `selectedModelByRole.embed` is set; the bundled MiniLM never builds vectors unless chosen (L10 text). Remove the dead `continueServerClient` guard; pass `undefined` when no remote server is configured. Privacy: everything stays under `~/.continuous/index/`; the only network use is a user-configured embed provider. Windows: keep the existing URI-to-path handling; the index key is the workspace URI plus branch, not a drive-letter path.
- Alternatives rejected: build lazily on first `search_codebase` call (surprising latency in a tool call, no progress UI); build only on an explicit command (that is the status quo that nobody uses).
- Risks: CPU and disk on large monorepos for people who never asked for an index (mitigation: the default for the new always-on build is a decision, Q1; cap files and bytes using the existing ignore rules, show progress in the existing indexing status).
- Dependencies: none. Test plan: unit tests with a fake `IDE` for (a) `codebase`-only config, (b) no providers, (c) embed model set, asserting which `artifactId`s are built and in which order; an integration run on the repo itself; a regression test that FTS rows exist for each chunked file.
- Size: S (L0) plus XS (L10). Acceptance: with no embed model and the default config, `search`-style retrieval over FTS returns rows after the first index; the order test fails if FTS precedes chunk; the README known-problems section is refreshed; the setting text names MiniLM's 256 word-piece cut.

### 3.2 L1: correctness subset first, timing fixture second

- Problem: wrong or empty retrieval (the `"NONE"` tag), leaks across branches, slow per-file lookups, and a directory containing `%` or `_` matching other paths.
- Design: (1) Replace the `NONE` fallback by "no branch filter" with a logged warning, or by the last known branch for that directory. (2) Escape `%`, `_` and the escape character in SQLite `LIKE` with an `ESCAPE '\'` clause; reuse the quoting approach of `lanceFilter.ts`. (3) Honour `directory` in `FullTextSearchCodebaseIndex.retrieve`. (4) Add the tag filter to `getPathsAndSignatures`. (5) `CREATE INDEX IF NOT EXISTS` on `chunks(cacheKey, path)` and `lance_db_cache(cacheKey)` (idempotent migration, run once at open). (6) Fix the `(d+)` regex to `(\d+)`. (7) Queue edits made while indexing is paused. (8) Leave "one copy of each vector" to L12, because removing the JSON copy needs the `addTag` path read first.
- Alternatives rejected: a new schema version with full re-index (loses users' existing indexes for a perf fix).
- Risks: a migration that runs `CREATE INDEX` on a multi-GB table at startup blocks the first query on Windows disks; run it inside the indexing job, not at open.
- Test plan: unit tests per fix (a path with `%` in a fake tree; a slow branch lookup stub; FTS with `directory`); the timing fixture (5,000-file repository, build seconds, disk size, per-query latency before and after) recorded as a table in `codebase-index.md`; that fixture is the M-sized part and can slip to 2.17.
- Size: S for items 1 to 7, M with the fixture. Acceptance: each of the seven fixes has a failing-then-passing test; no query returns another branch's signatures; the timing table exists.

### 3.3 L2: finish `code_navigation`

- Problem: the agent cannot ask "what type is this", "who implements it", "who calls it", and is never told when to prefer the tool over grep.
- Design: add operations `hover`, `implementations`, `callers`, `callees`, `signature`. Protocol: new `IDE` methods in `core/protocol/ide.ts` and `core/index.d.ts`, VS Code implementation through `vscode.executeHoverProvider`, `executeImplementationProvider`, `vscode.prepareCallHierarchy` with `provideIncomingCalls`/`provideOutgoingCalls`, `executeSignatureHelpProvider`; stubs return empty so the tool degrades to "fall back to grep_search". Keep one tool with an `operation` enum (the file's own comment: each definition is resent every request; Track Z counts this). Turn text: one sentence per tool in the act and plan turns (`core/llm/prompts/turns.ts`), which must be added to the prompt-caching accounting, not appended silently.
- Alternatives rejected: six tools (tool-list cost); an LSP client in core (VS Code already runs the servers).
- Risks: call hierarchy is expensive on large repositories (cap results and depth 1); results vary by installed language extension (already stated in the tool text).
- Dependencies: none; unblocks L4, L5, L6. Test plan: unit tests with a fake IDE for each operation's formatting and cap; a snapshot test for the tool definition token count (L2 must not grow the tool list by more than a stated budget); one manual check in VS Code on this repository.
- Size: M. Acceptance: five operations registered in VS Code, each returns bounded output, empty-result text tells the model to fall back; prompt guidance present and counted in the Track Z overhead fixture.

### 3.4 L3: `search_codebase`

- Problem: the one tool that can use the index is experimental, asks permission, promises semantic search even where LanceDB cannot load, and ranks nothing.
- Design as in `codebase-index.md` 3.1, with two additions from reading the code: (a) fusion function extracted from `RerankerRetrievalPipeline`/`NoRerankerRetrievalPipeline` (both already reference the experimental tool flag) so chat and tool share it; (b) the result states which layers answered (`text`, `symbol`, `semantic`) so the model knows when semantic was unavailable. Registration rule: indexing enabled and at least one artifact present. Read-only policy, allowed in every mode.
- Alternatives rejected: enabling the existing `codebase` tool by default (its contract is semantic-only); MCP-only exposure (the agent would see it only when a server is configured).
- Risks: a second search tool the model never calls; this is the main reason L4 and the turn text exist. Token budget must be enforced in the tool, not left to the model.
- Test plan: unit tests of rank fusion with fixed lists; a retrieval test over a fixture repository (there are none today, per `codebase-index.md` 1.1); the L4 scenario with the tool on and off.
- Size: M. Depends on L0, L1. Acceptance: the tool is present with no experimental flag when an index exists, absent otherwise; output includes path, lines, layer; the pipelines share one fusion function; the allowlist in `repoMapRequest.ts` is removed behind a config flag.

### 3.5 L4 and L11: measure before building more

- Design: one scenario group in `bench/` on a pinned public repository of 2,000 to 5,000 files, 20 to 40 "find where X is handled" tasks, checks `tool-used` and `files-located`, arms grep-only, plus `code_navigation`, plus `search_codebase` (FTS and symbol), plus embeddings with MiniLM and Qwen3-Embedding-0.6B (EXP-1), and the guidance on/off split (EXP-4). Local model on the lab machine (Ollama) so no API spend; three runs per cell (the lab's own variance warnings apply, `Later` below).
- Risks: model policy noise dominates (the point of EXP-4); a repository that the model memorised proves nothing; choose a smaller recent project or a vendored slim copy.
- Size: L4 M, L11 M. Acceptance: a table in `codebase-index.md` with files-located per arm and tool calls per task; a stated decision for L13.

### 3.6 L12: the vector store spike

- Question: does one SQLite file with sqlite-vec replace LanceDB? Facts: LanceDB is the legacy `vectordb` 0.21.2 package, native, already the known failure on older Linux CPUs (the `codebase` tool silently runs FTS-only there); sqlite-vec is pre-v1 per its README, with the Windows and old-CPU install story unstated on the page read.
- Design of the spike: same corpus, top-10 latency, index size, install success in Windows Sandbox, Linux without AVX2, macOS arm64 (EXP-3). Alternative that needs no new dependency: brute-force cosine over a Float32 blob in SQLite for repositories under about 50,000 chunks (a few hundred thousand multiplications per query on 384 to 1,024 dimensions is a few milliseconds in JavaScript with typed arrays; this is an estimate, not a measurement).
- Recommendation: run the spike including the brute-force arm; if brute force is fast enough, drop LanceDB without adding sqlite-vec. Size S plus install checks.

### 4.2 O4: modes for subagents (and the Claude format)

- Problem: a delegated task cannot be told to plan only, or to run read-only, except through the tool list.
- Design: accept `permissionMode` (map `plan` to our Plan mode, `default` to the parent's; refuse `bypassPermissions`/`auto` equivalents unless the parent is already there). Adopt Claude's rule as the invariant: the child is never more permissive than its parent, and a parent in plan mode forces plan (https://code.claude.com/docs/en/sub-agents). Accept `background` and `isolation` as parsed-but-warned until O3 and O8 exist, so a shared `.claude/agents` file does not error. A plan subagent returns a plan file, as in interop M1. Unknown fields stay ignored (current behaviour, the same as Claude).
- Alternatives rejected: honouring `permissionMode: bypassPermissions` from a repository file (a repository-controlled path to dropping approvals; folder trust already gates hooks, same reasoning).
- Dependencies: S2, F4 as in the row. Size S for parse and the child-not-looser test; M with the plan file. Acceptance: test that a child cannot exceed its parent's mode; a file with Claude-only fields loads with warnings, not errors.
