# Forking a session and selective compaction, priced against the prompt cache

Status: research, 2026-11-13. Docs only: no code, no ROADMAP edit, no model call. Provider facts were fetched on 2026-11-13 unless a row says otherwise. Codebase references are to `main` at `1227dda`. Companion to [`caching-context-cost.md`](./caching-context-cost.md) (provider table, 2026-11-11), [`../cache-safeguards.md`](../cache-safeguards.md) (the notices that exist) and [`../checkpoints.md`](../checkpoints.md) (file restore).

The owner's idea: let a person fork a conversation into a new session (from a message, with only the messages they keep, or into a subagent) and compact selectively, but only where that is cheap with respect to the prompt cache, or with a warning beforehand that says what it costs.

## 1. Summary

1. **A fork that keeps the exact prefix is nearly free while the cache is warm.** On Anthropic and on Bedrock the cache is keyed on the exact bytes of the prefix, isolated per workspace (Anthropic) or per organization (Bedrock), and not per conversation. A second session that sends the same tools, system prompt and messages to the same model reads the entry the first one wrote. On Claude Opus 5.5 a 200k-token fork costs about $0.04 warm and about $1.00 cold (5-minute write).
2. **"Fork from here" at an earlier message is warm only if that message boundary still has a live cache entry.** Entries exist only where an earlier request put a breakpoint. Ours go on the last two user-role messages of every request (`core/llm/llms/anthropicCache.ts:117`), so every turn boundary (and in Agent mode every tool-result boundary) had one. But an entry that is no longer read expires one TTL after it was last read. The entry at a boundary from 30 minutes ago is gone on a 5-minute cache, while the system prompt and tools are still warm. The cost preview has to work this out per fork point, not assume "warm".
3. **"Fork with only what I keep" rebuilds from the first removed message onward.** That is a prefix change. Removing messages near the end costs little; removing one early message costs nearly the whole conversation. The cheap alternatives are to fork everything and append a "disregard X" instruction at the end, or to remove the messages from the tail backward.
4. **A fork into another model, another mode (system prompt and tools) or another reasoning setting is a full miss** on every provider. Our existing `ModeSwitchCacheNotice` and model-switch confirm already price this. The fork dialog should reuse them.
5. **"Fork into a subagent" is cheap only if the subagent inherits the parent's model, tools, system prompt and history** and its own instructions go at the end. Our existing subagent tool starts "a fresh conversation with its own instructions and a subset of your tools" (`core/tools/definitions/subagent.ts:29`), which has its own cache by design. Claude Code documents both kinds and says the forked kind "reuses the parent's prompt cache".
6. **We already have most of the parts.** The pieces are a cache state per session with the last request's time, size and lifetime, the cost formula and wording, a per-message checksum in the cache key that finds the first changed message, a CLI cache pin for fork points, a CLI `--fork <sessionId>`, and a compaction path that reads the warm cache. What is missing is a fork action in the GUI, a per-boundary estimate of tokens and warmth, and a fork that carries the session's state beyond `history`.
7. **The CLI fork drops everything but the history.** `startNewSession(history)` (`extensions/cli/src/session.ts:702`) creates a session with no mode, model, task plan, loop state or cache record. That is safe but loses the cache record, so a fork there cannot say whether it will be warm.

Facts that shape the design, with their limits:

- **Model scope.** Anthropic's invalidation table lists tools, system, messages, thinking and effort, speed, `tool_choice` and images, but not the model, and no page read says an entry can be read by another model. Anthropic's model-migration and caching guidance (read through the `claude-api` reference, not re-fetched as a URL) says caches are model-scoped, and our code already treats a model change as a full miss (`switchKeepsCache`, `gui/src/util/cacheSafeguards.ts:128`). Treat a fork to another model as a full miss.
- **What a read refreshes.** The page says a request "reads them from the cache and refreshes their lifetime" for blocks marked on an earlier turn. It does not say whether reading a longer prefix also refreshes entries written at earlier boundaries. Until measured, assume it does not: an entry at an old boundary expires one TTL after the last request that read it at that boundary. This is the conservative choice for a cost warning (it may over-warn, never under-warn).
- **Concurrency.** "A cache entry only becomes available after the first response starts" (Anthropic; AWS says the same). A fork into a subagent sent while the parent's request is still being prefilled writes its own copy.
- **Thinking blocks.** Pass them back unchanged. Removing or editing an assistant turn's thinking in the fork is a history edit: a cache miss from that point, and on Claude Opus 5.5, Sonnet 5.5 and the Fable 5.1 and 5.2 family, later thinking blocks are invalidated too (Anthropic's preserved-thinking guidance, read through the `claude-api` reference; not re-fetched as a URL). A fork copies history verbatim, so this only matters for "fork with only what I keep" and selective compaction.

## 3. What a fork costs

Write `T` for the tokens of the fork's prefix, `P` for the model's prices from `findModelPricing` (`core/llm/utils/calculateRequestCost.ts:213`). The extra cost of a miss is what `missExtraUsd` already computes (`cacheSafeguards.ts:64`): `T x (write - read)`.

| Fork                                                              | First request of the fork pays                                                                                    | Example: Opus 5.5 ($4 in, $5 write 5m, $8 write 1h, $0.20 read), T = 200k |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Whole conversation, same model, mode and settings, within the TTL | Read T, write the new message                                                                                     | about $0.04                                                               |
| From an earlier message whose boundary entry is still warm        | Read up to the last warm entry at or before the fork point (at least the tools and system prompt), write the rest | between $0.04 and $1.00 depending on how much is warm                     |
| From an earlier message, entry expired                            | Read tools and system (refreshed by every request), write the messages up to the fork point                       | close to $1.00 for a long history                                         |
| With messages removed or edited                                   | Read up to the first changed message, write everything after it                                                   | from about $0.04 (last message dropped) to $1.00 (first message dropped)  |
| Into another model, mode, tool set, reasoning or effort setting   | Write T                                                                                                           | $1.00 (or $1.60 on the 1-hour lifetime)                                   |
| Any fork after the TTL                                            | Write T                                                                                                           | $1.00                                                                     |
| Caching off                                                       | T at the input price, and again on every later message                                                            | $0.80 per message                                                         |

Two consequences:

- **Both branches keep paying.** After the fork, the parent and the fork each build their own tail. If both stay active, each pays its own writes for new turns, which is no more than it would pay alone. The shared prefix is read by both and stays warm as long as either reads it.
- **The fork point boundary.** Forking right after an assistant reply keeps the prefix up to the user message before that reply (where the request that produced the reply wrote its entry). The reply itself was cached only by the next request, whose entry also covers the next user message, which the fork drops. So the fork writes the reply plus its own new message. That is small for a text reply and can be large for a reply that carried long tool output in an Agent turn.

## 5. What we have (file:line, `main` at `1227dda`)

### Sessions and history

- `Session` (`core/index.d.ts:352`) holds `history`, `mode`, `chatModelTitle`, `usage`, `promptCache` (`SessionPromptCache`, `core/index.d.ts:338`: last request time, its input tokens and lifetime, request count, Auto escalation), `checkpoints`, `taskPlan`, `planFile`, `queuedMessages`, `loop` and `loopRequested`.
- `HistoryManager.save` (`core/util/history.ts:356`) writes every one of those fields. A fork that builds a `Session` and saves it gets persistence and the sessions list for free.
- `ChatHistoryItem` (`core/index.d.ts:1418`) carries `contextItems` (attachments), `toolCallStates`, `reasoning`, `conversationSummary` and a request-time `cachePin` (`core/index.d.ts:1436`), documented as "a fork point ... so a retry, a branch or a subagent that starts from the same context reads the cached prefix instead of writing it again".
- `newSession` (`gui/src/redux/slices/sessionSlice.ts:925`) loads a session. At line 965 it restores the saved cache record (`lastRequestAt`, `lastInputTokens`, `lastTtl`, `requests`, `escalated`), so a fork saved with the parent's record would correctly show as warm or cold. A brand-new session starts with an empty record.
- In-place edits that already act like a destructive fork: editing an earlier user message re-sends from that index (`gui/src/redux/thunks/streamResponse.ts:26`), `truncateHistoryToMessage` (`sessionSlice.ts:513`) and `deleteMessage` (`sessionSlice.ts:538`). None of them warns about the cache.
- Session tabs: `TabBar` (`gui/src/components/TabBar/TabBar.tsx:130`) saves the current session and loads another by ID (lines 162 to 193), so a fork can open in a new tab with existing calls.
- Tool policies are global UI state (`gui/src/redux/slices/uiSlice.ts:40`), not per session, so a fork inherits them and with them the same tool list.

### Cache state and safeguards

- `PromptCacheSessionState` (`gui/src/util/promptCache.ts:55`) adds in-memory fields: `lastKey`, the miss count, and the `ledger`.
- `promptCacheKey` (`gui/src/util/cacheSafeguards.ts:289`) hashes the model and route, tools, system prompt, reasoning, tool choice and images, plus one checksum per message (`messageChecksum`, line 272). `firstChangedMessage` (line 360) and `keyChanges` (line 371) already find where two prompts diverge, which is exactly the "first changed message" a selective fork needs.
- `warmCacheLoss` (line 152), `coldResume` (line 229) and `isSignificantLoss` (line 139) with `NOTICE_MIN_EXTRA_USD = 0.25` (line 39) decide whether a notice is worth showing. `formatRereadCost` (`gui/src/util/cacheNotices.ts:40`) words it ("366k tokens at full price (about $1.10 more)"); `perMessageCost` (line 71) gives warm and cold costs per message.
- `ModeSwitchCacheNotice` (`gui/src/components/ModeSelect/ModeSwitchCacheNotice.tsx:13`) is the model to copy: one line, only while warm, reusing `warmCacheLoss` and `formatRereadCost`. `switchCost` and `formatSwitchCost` (`promptCache.ts:471`, `491`) do the same for the model switch.
- The ledger (`gui/src/util/cacheLedger.ts:20`) records per request its start time, model, mode, lifetime and the read, write and uncached token counts, up to `LEDGER_MAX = 200` (line 50). It is in memory only. For a fork point inside the ledger's window, the request that wrote at that boundary gives both its size (read + write + uncached) and its start time, which together decide whether the entry is warm. For older points or a reloaded session there is no record; the preview must say "estimate".
- Prices come from `findModelPricing` (`core/llm/utils/calculateRequestCost.ts:213`) and `costOf` (`core/util/costOf.ts:91`), the same as the cost display.
- Breakpoint placement on the Anthropic path: tools, system and the last two user-role messages (`resolveCacheParts`, `core/llm/llms/anthropicCache.ts:56`; `markCacheBreakpoints`, line 117).

### Compaction

The same rule applies to a fork from an earlier message.
- Core: `compactConversation` (`core/util/conversationCompaction.ts:48`) stores the summary on the target item; `constructMessages` (`gui/src/redux/util/constructMessages.ts:56`) then sends only what follows the latest summary.
- `useCompactionCacheNote` (`gui/src/hooks/useCompactionCacheNote.ts:15`) already tells the person that compacting drops the cached conversation. It is shown on the Compact actions in `ResponseActions` (`gui/src/components/StepContainer/ResponseActions.tsx:73`) and in the context popover (`gui/src/components/mainInput/ContextStatus.tsx:134`).
- CLI: `compactChatHistory` and auto-compaction (`extensions/cli/src/compaction.ts:56`, `319`).

### Forks, pins, subagents and rewind

- CLI `--fork <sessionId>` (`extensions/cli/src/index.ts:175`) and `/fork`, which only prints `continuous --fork <id>` and copies it to the clipboard (`extensions/cli/src/slashCommands.ts:73`). The fork itself is `initializeChatHistory` (`extensions/cli/src/commands/chat.ts:66`) calling `startNewSession(history)` (`extensions/cli/src/session.ts:702`), which copies only the history.

## 6. Design

### 6.1 Actions and where they live

| Action                      | Where                                                                                                                   | What it does                                                                                                                                       |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fork conversation           | Context popover (`ContextStatus`), the session tab's menu, and `/fork` in the CLI made real (today it prints a command) | Copies the whole session into a new one and opens it in a new tab; the original is unchanged                                                       |
| Fork from here              | Message menu in `ResponseActions`, next to Compact and Restore                                                          | Copies history up to and including this assistant turn                                                                                             |
| Fork with only what I keep  | "Select messages..." from the same menu; checkboxes on turns; a footer with the live cost line and Fork                 | Copies the kept turns; the dropped ones are gone in the fork                                                                                       |
| Fork into a subagent        | Message menu and the context popover: "Hand off to a background run"                                                    | Starts a background run with the parent's model, tools, system prompt and history, plus one appended instruction; returns its report to the parent |
| Compact selected            | From the selection view: "Summarize selected"                                                                           | Replaces a range with one summary item, in place or in a fork                                                                                      |
| Fork after the rewind (CLI) | The PR #797 picker: "Fork from here" next to "Restore conversation"                                                     | Same as Fork from here, without truncating the original                                                                                            |

Rewind (truncate in place) stays what it is. A fork never changes the original.

### 6.2 The cost line

One line in the menu item's tooltip and in the selection footer, never a dialog, following the rules in `cache-safeguards.md` ("Say nothing on the fast path"; name tokens and dollars; offer the cheaper way). A dialog only for a fork that also changes model, as the model switch already does.

- Warm, prefix kept: "Fork reads 200k tokens from the prompt cache (about $0.04)." Shown only when the person hovers, since it is the fast path.
- Partly warm: "Fork re-reads 140k of 200k tokens at full price (about $0.70 more); the cache for this point expired 9 min ago. Forking at the latest message keeps it."
- Selective: "Dropping turn 3 re-reads everything after it: 180k tokens (about $0.90 more). Dropping only the last 2 turns would cost about $0.05."
- Model or mode change: reuse `formatSwitchCost`.
- Unpriced model: tokens only, as `isSignificantLoss` already does with `NOTICE_MIN_TOKENS_UNPRICED`. Local server: time, as `formatRereadCost` already does.

Computation, all in a new pure function next to `warmCacheLoss` (say `forkCost(model, setting, state, history, forkIndex, keep?, now)`):

1. Tokens to the fork point: from the ledger entry of the request that wrote at that boundary (read + write + uncached). Otherwise estimate the messages with the existing local count and mark the line "about".
2. Warm part: the longest boundary at or before the fork point (and before the first dropped message) whose last read started less than its TTL ago; tools and system count as warm whenever the session is.
3. Extra cost = `missExtraUsd(pricing, tokens after the warm part, ttl)`, with the TTL the fork would write (Auto's choice for a new session).
4. Same model, route, tools, system and reasoning as the parent: compare with `promptCacheKey`; any difference makes it a full miss and names the cause, as `keyChanges` does.

| `checkpoints`                                                                                             | No                                                                                                | They describe the workspace, which both sessions share; a restore in one would undo the other's edits. Claude Code and the Agent SDK fork the conversation, "not the filesystem" |
| Tool and permission policies                                                                              | Nothing to copy                                                                                   | They are global (`uiSlice.ts:40`). Claude Code does not carry session grants into a fork; we have none per session                                                               |

### 6.4 Keeping the cache warm

- **Fork now, not later.** The preview shows the time left (`promptCacheCountdown.ts` exists). A fork that is created but not sent within the TTL pays the full write; the line says so.
- **Same model, tools, system prompt, reasoning and effort.** Offer the switch in the fork only as a second step with its own cost line.
- **Instructions for the fork go at the end.** "You are a fork; do X" belongs in a new user message (or a mid-conversation system message on the models that take one), never in the system prompt. This is what Claude Code does for `/fork`.
- **Nothing volatile before the fork point.** The prompt-segment manifest already orders segments by stability and rejects a per-request segment outside the tail (`plans/prompt-segments.md`); a fork must not add a "forked at" line, a timestamp or the new session ID to the system prompt or to any message before the fork point.
- **Pin the fork point.** The GUI can mark the fork point the way the CLI's `cachePin` does, so the parent's next requests keep that boundary's entry fresh while the person decides. It costs one of the four breakpoints and only helps a fork made within a TTL of the parent's last request; measure before shipping.
- **Subagent fan-out.** Send the first forked run, wait for its first streamed token, then start the others, since an entry is readable only after the first response starts.

### 6.5 Selective compaction

Compaction always replaces the history after the summarized range, so it is a miss from the first summarized message onward. What can be chosen is where that starts:

- **Summarize up to here (prefix)** rebuilds the whole conversation once, then every later message is smaller. It pays off when the conversation goes on long enough; `cache-safeguards.md` finding 6 measured that compacting at a cold resume beats continuing in 90 to 100% of cases.
- **Summarize from here (tail)** keeps everything before the range cached and rebuilds only the tail. Cheap when the noisy part is recent (a failed attempt).
- **Summarize a middle range** pays like the prefix case from the start of the range. It is the worst of both and should carry the strongest line.
- The summary request itself should keep using `compactionPrefix`, which reads the warm cache; a middle-range summary cannot (its prefix does not end at a breakpoint) unless the range ends at the last message.
- Tool-result ageing (`core/util/contextAgeing.ts`) and Anthropic's context editing are the same kind of prefix edit and need the same minimum-saving rule (`cache-safeguards.md`, Not built).
