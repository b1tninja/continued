# Research: end-to-end user journeys and failure recovery

Status: research, 2026-11-12. Documents only: no product code, no change to `plans/ROADMAP.md` (proposed rows are in section 16). Read against `origin/main` at 63e6e122d; main moved to c05057f0b while this was written, and the only difference is one new research file. The 2.14.0 tag is `v2.14.0-vscode`. Nothing was run: no `npm install`, no product start, no Windows Sandbox. Screenshots are from the harness output in `D:\temp\fable-ui-shots\before` (outside the repository).

The roadmap and the research notes were reviewed track by track on 2026-11-11, and a design review looked at single screens. This report takes the lens they did not: a person moving through the product from install to uninstall, and what happens to them when something breaks.

## 1. Method and limits

- Ten journeys (J1 to J10) were traced through the code. Each has a step table (intent, what the product does, evidence), then friction, dead ends, risks and missing recovery.
- Severity: **S1** data loss or a safety property silently lost; **S2** a dead end (the person cannot go on without outside help); **S3** friction or a surprise; **S4** wording.
- Evidence is `file:line` at 63e6e122d. Three groups of journeys (J2; J3, J4 and J6; J5) were traced by delegated read-only passes. I re-read the lines behind every S1 finding and behind the items in the top 20 that are marked "checked" in section 12; the other citations in those journeys were read once, by the delegated pass, and are marked "(d)" in the tables. J1 and J7 to J10 were traced directly.
- Not verified, because nothing was run: what a person literally sees at each step (timing, wrapping, whether the terminal echoes a typed key), JetBrains, and every runtime claim in J1, which rests on the sandbox matrix results recorded in [`area-isolation-sandbox-gate.md`](./area-isolation-sandbox-gate.md). Section 18 lists what to verify by running.
- Vocabulary follows the table at the end of `plans/ROADMAP.md` (Locks, Protections, Rules: Never, Ask, Always; levels Manual to IDGAF).

Friction and gaps:

- **S2. The published install path is not the tested one.** The sandbox matrix installs the tarball through `npm` and the VSIX directly; `install.ps1`, upgrade from the previous VSIX and uninstall have no case (proposed there as SB15). A person who follows the docs is on an untested path.

- **S4. The troubleshooting table has no row for "no Node", "npm prefix not on PATH" or "PowerShell refuses to run the script".** Not verified whether the last happens on a default Windows 11 policy.

Findings:

- **S2. `cn` first run is a dead end for everyone who is not an Anthropic customer**, and it interrupts people who already configured the extension. The only exits are `--config` and an environment variable that does nothing.
- **S1 (safety). The terminal agent stores a key in plain text in `config.yaml`**, with no `chmod` on Windows, and silently persists a key that was only in the environment. PL23 covers a secret backend; it does not cover the silent write.

- **S3. Local tab: no "not running" state, an all-or-nothing three-model gate, and LM Studio and llama.cpp users are on the wrong tab by default.**
- **S3. No validation on Save and no route from the 401 dialog back to the key field.**

Findings:

- **S1. "Always allow" in the terminal can erase the rest of `permissions.yaml`.** `loadPermissionsYaml` returns `null` when the file does not parse, when it has a top-level key outside the known list, or when `allow`, `ask` or `exclude` is not a list (`permissionsYamlLoader.ts:40-70`). The writer then starts from `{}` (`policyWriter.ts:38`) and writes a file that holds only the new rule: `floor:`, `exclude:`, the levels and the `builtin:` switches are gone. When the file does parse, `YAML.stringify` still drops every comment, and the write is a plain `writeFile` (`:61`), not temp and rename. A hand-edited file with one typo loses the person's Locks on the next "always allow".
- **S1. "Always allow" drops the session's `--allow`, `--ask` and `--exclude` flags.** `reloadPermissions()` rebuilds from the files and defaults only (`extensions/cli/src/services/ToolPermissionService.ts:391-407`), so a session started with `--exclude Bash` offers Bash again after one unrelated "always allow".
- **S2. A rule written from the terminal has no undo path** (the row above). B8a and B20 cover part.
- **S2. A refusal does not say what to do next.** The terminal clips the reason; neither surface names the command that explains it (`continuous permissions test`, `continuous audit show`).
- **S3. Headless hides Edit and Write without a line saying so**, and ends at the refusal cap with nothing on stderr.
- **S3. The extension's "Always allow" gives no feedback** (B9 mentions a diff and undo before saving).
- **S4. The approval prompt and the file header still say "Continue"** (PV10).

Findings:

- **S1. A stale window can switch a Protection back off.** The webview loads the settings once and its next save writes its whole remembered state, including `builtin: off` for a Protection another window or the terminal turned back on (`settingsFile.ts:183-188`, `:216`; plain `writeFileSync`, read-modify-write, no lock) (d).
- **S1. Remembered levels can outlive the file.** `policyLevels` is persisted in the webview and replaced only when the load succeeds (`gui/src/redux/store.ts:58-59`, `policySettings.ts:27-46`) (d). If the load fails, the remembered levels, IDGAF included, stay in force with a console line. Mechanism read; end to end inferred.
- **S2. The "why" exists but is not where the person is.** For Locks, protected paths and the safety check the extension's refusal text sent to the model is `This command has been disabled by security policy:` with the reason discarded (`gui/src/redux/thunks/evaluateToolPolicies.ts:425-429`, read), the person sees `Blocked by safety check`, and the Recently blocked hint points at `config.yaml` even for a Lock that no setting changes and for a rule that lives in `permissions.yaml`.
- **S3. No confirmation on IDGAF anywhere, and the way back is to Careful, not to "what I had".**
- **S3. Notices from the policy file are invisible**: `permissions.yaml could not be read ..., so the defaults apply.` reaches only the log, and a failed save reverts with no message (`policySettings.ts:89-91`) (d).
- **S4. Vocabulary drift in reason strings.** `floor` is user-facing in `core/tools/permissions/evaluate.ts:534` and `PolicyCard.tsx:198`; `permissions list` prints DENY, ASK, ALLOW while `add` takes never, ask, always; the model is told "security policy"; `Every rule is ignored.` (`policy.ts:320`) contradicts "block these calls at every level, IDGAF included" (`PolicyCard.tsx:199`). UX7, UX12 and B24 cover the page, not the strings sent to chat, model and audit (d).

Findings:

- **S2. A finished or stopped loop tells the person almost nothing.** No list of changed files, no recap of failed and skipped items, no cost line unless a budget was set, no pointer to a diff or an undo. A person who was away for two hours has a tick and a number. Y1 to Y3 write notes for the next item, not for the person; RF9 mentions a summary.
- **S1. A stopped loop's partial edits cannot be told from the person's own**, and checkpoints are in the extension only and miss terminal edits and subagent writes (`plans/loop-mode.md:518`). In the terminal agent there is no checkpoint at all (section 8).
- **S1 (trust). "Plan edits: Automatic" promises a reviewer that is not built.** The description shown is `In Loop, a reviewer model judges each plan and waits if unsure.` (`policy.ts:332-333`); the code comment says `A reviewer model for plans is not built, so Automatic goes on without a cap` (`:625-628`). Automatic is therefore looser than Permissive, which has a cap.
- **S2. Supervised and Auto wait forever on a question, with no notification.** A person who walked away comes back to a loop that did nothing.
- **S3. A re-plan has no "no".** The card offers `Continue the loop`; rejecting means editing a file or stopping everything.
- **S3. The extension saves loop state only at stream end**, so a reload can lose a check result, a skip or a budget edit, and an item that reported done is run again.
- **S3. Resume after a rounds stop runs into the same limit** unless the person raises it first; nothing says so. `Close` on a finished loop discards the record without asking.
- **S3. No lock or warning for two loops on one workspace**; the terminal's checkbox sync writes the plan file with a plain `writeFileSync` (`extensions/cli/src/plans/planStore.ts:161-163`).
- **S4. "The window reloaded" in a terminal**, and `docs/ide-extensions/agent/leave-and-resume-loop.mdx:32` says the terminal agent has no mode picker.

## 13. Cross-journey patterns

1. **Errors say what failed, not what to do.** `Error: <message>` in the terminal, `Blocked by safety check`, `Could not save the rule.`, `Compaction failed:`. The exception, the extension's stream-error dialog, shows the house can do it.
2. **The reason exists and is thrown away on the last metre.** Reasons are computed by the engine and then clipped to 100 characters, put in a tooltip, sent to a log, or replaced by a generic sentence (J3, J4, J6).
3. **Notices go to a log nobody is pointed at.** Six S1 or S2 conditions in this report are reported only by `logger.warn` or `console.warn`.
4. **Fail-open on unreadable input.** An unreadable `permissions.yaml` means defaults; an unreadable hooks file means no hooks; an unreadable session means an empty one. Each is the convenient choice and each silently removes something the person set up to protect themselves.
5. **Two write disciplines.** Sessions, `config.yaml` rules, trust and pin files use temp file and rename. `permissions.yaml` (two writers), the terminal's file tools and the plan file do not. The helper exists three times (`core/util/history.ts:30`, `core/util/paths.ts:575`, `hookTrust.ts:239`) and is not shared.
6. **State in many places, no map and no reset.** Rules live in `config.yaml` and in `permissions.yaml`, each with its own editor that refuses the other's file; trust lives in three files and two commands; levels live in a file and in webview storage.
7. **No single answer to "what is my configuration right now".** Which config file, which levels, which rules from where, which hooks are running or held, which servers are trusted: five commands and two pages.
8. **The terminal agent trails the extension on recovery**: no checkpoints, no retry dialog, no key storage, no folder-trust prompt, onboarding for one provider.
9. **Words promise more than the code does**: "a reviewer model judges each plan", "✓ Using AWS Bedrock", "Every rule is ignored", "existing settings keep working", "should not be edited manually. Use the TUI".
10. **Silent network or process starts**: catalogue fetches on mount, `npx -y mcp-remote`, a key copied from the environment into a file.
11. **Leaving a risky state is lossy**: IDGAF returns to Careful, `Close` discards a loop record, the crash page's `Continue` clears stored state.

### 14.2 Recovery features

- **One atomic write helper**, shared: temp file in the same folder, fsync, rename, the Windows EPERM and EBUSY fallback that `core/util/paths.ts:582-599` already has, and "compare before replace" (fail if the file changed since it was read). Used by both `permissions.yaml` writers, the terminal's file tools and the plan file.
- **Edit the YAML document, never the parsed object.** The terminal's allow-list writer changes one sequence in the parsed document (the `yaml` package's `Document` API keeps comments and unknown keys) and refuses to write when the file did not load: `Not saved: permissions.yaml could not be read, and writing now would replace it.`
- **Fail closed on unreadable protection input** (permissions, hooks), with the sentence above, and a way out (`--safe`).
- **Quarantine, do not overwrite.** A session, loop, trust or pin file that does not parse is renamed to `<name>.damaged-<date>` and reported once.
- **Checkpoints in the terminal agent**: a snapshot of each file before the agent's first write to it in a turn, kept with the session, `/undo` (last turn) and `/rewind` (pick a turn). Claude Code and Cline do this; section 15 has their limits, which should be stated the same way (shell changes are not tracked).
- **A loop record that survives**: per item, the files it changed (from the same snapshots), the check's last lines, tokens and cost; a summary card at the end; `Undo this item` and `Undo this loop`; `Close` keeps the record in the session.
- **Safe start**: `continuous --safe` (and a VS Code command "Continuous: Start in safe mode") ignores project config, hooks and MCP servers, uses the user `config.yaml` only, starts at Careful, and prints what it skipped. `--no-hooks` and `--no-mcp` are the narrow forms.
- **Config validation with pointed errors**: `continuous config check [file]` prints file, line, key, the problem and the fix; the same text is used at start-up and in the extension's "View errors".
- **`continuous doctor` sections**: `config` (which files were loaded, in order, and each error), `models` (each model: key present or missing, last test result, retirement), `permissions` (file state, levels, counts of Locks, Never, Ask, Always per file, Protections switched off), `hooks` (running, held, failed to load), `mcp` (state, last error, pin state), `trust` (every grant with its file), `state` (the table in section 10 with sizes), `network` (today's). `continuous doctor` alone prints one line per section with `ok`, `note` or `fix`, and `--copy` writes a bundle of names and counts with no contents (J7 on the roadmap describes that bundle).
- **A reset command**: `continuous reset` is a dry run that lists what each scope holds; `--sessions`, `--trust`, `--permissions`, `--onboarding`, `--index`, `--all` choose; `--yes` applies; a backup folder is written first and its path printed. The extension gets "Continuous: Reset stored panel state" for the webview storage the terminal cannot reach.
- **An upgrade notice**: the last-seen version is stored; on the first start of a newer one, a single dismissible line names only the changes that touch this person's settings, for example `2.18.0: with --auto, file edits can now write outside the workspace. Details: <release note>`. Rules are data in the release-notes file (a condition and a sentence), so the release checklist (CI5) can require one for each "Behaviour changes" entry.
- **Explain at the point of refusal**: `/why` in the terminal and "Why?" on the chip run the existing `permissions test` on the last refused call and print the decision steps.

## 15. External research

All pages read on 2026-11-12.

- Microsoft, "Error Messages" (Windows UX guidelines), <https://learn.microsoft.com/en-us/windows/win32/uxguide/mess-error> (page dated 2022-01-11, updated 2025-07-24): a good message has "A problem. States that a problem occurred. A cause. Explains why the problem occurred. A solution. Provides a solution so that users can fix the problem."; "Often the best error message is no error message"; and "Good error messages aren't just a UI problem, they are a software design problem." The last one is pattern 2 above: the reason has to survive to the surface.
- Nielsen Norman Group, "Error-Message Guidelines" (Neusesser and Sunwall, 2023-05-14), <https://www.nngroup.com/articles/error-message-guidelines/>: "Display the error message close to the error's source"; "Merely stating the problem is also not enough; offer some potential remedies"; "Preserve the user's input"; "Take a positive tone and don't blame the user".
- GOV.UK Design System, "Error message", <https://design-system.service.gov.uk/components/error-message/>: "Describe what has happened and tell them how to fix it"; avoid "valid" and "invalid", "sorry", "please" and "humourous, informal language like 'oops'"; "Different errors need different messages."
- VS Code UX guidelines, "Notifications", <https://code.visualstudio.com/api/ux-guidelines/notifications>: "Respect the user's attention by only sending notifications when absolutely necessary"; "Show one notification at a time"; do not "Send repeated notifications"; for progress, "Show a link to see more details (like logs)". This bounds the upgrade notice and the loop-waiting notification to one each.
- Claude Code, "Checkpointing", <https://code.claude.com/docs/en/checkpointing>: a checkpoint per prompt, snapshots kept with the conversation ("you can still run `/rewind` after you resume a session"), restore code, conversation or both; stated limits: "A file that only Bash commands changed isn't tracked", subagent edits are usually not captured, symlinked and hard-linked paths are skipped with a warning, and it is "Not a replacement for version control".
- Cline, "Checkpoints", <https://docs.cline.bot/features/checkpoints>: a shadow Git repository ("Your main Git repository stays untouched"), a checkpoint after each tool use including commands, three restore choices (files, task, both); cost: on large repositories it "may use significant storage and slow down Cline".
- Aider, "Git integration", <https://aider.chat/docs/git.html>: "Whenever aider edits a file, it commits those changes"; "Aider will first commit any preexisting changes"; "`/undo` will undo and discard the last change"; commits carry "(aider)" in the author or committer name. The second point is the one this product lacks most: separating the person's uncommitted work from the agent's before the agent writes.
- npm `write-file-atomic`, <https://github.com/npm/write-file-atomic>: temp name from the target plus a hash of pid and an invocation counter, fsync by default, rename last, unlink on error, and writes to one file "put into a queue and serialized". The in-process queue is what `mcp-tool-pins.json` has; none of this covers two processes, which is why "compare before replace" is in 14.2.

Read across: peers differ on where snapshots live (session files, a shadow repository, the real repository) and agree on three things this product's terminal agent lacks: a snapshot before the first write, an undo the person can name, and a written statement of what is not covered.

## 17. Owner questions

Each has a default marked "recommended, pending owner".

1. **Where do people report a problem?** Issues and Discussions are both off. Options: enable Discussions only; enable Issues with a template; keep both off and say so. Recommended, pending owner: enable Discussions (lower triage duty than Issues), point every link there, and have `doctor --copy` produce what to paste.
2. **Fail closed when `permissions.yaml` cannot be read?** It is safer and it will stop some people's sessions on a typo. Recommended, pending owner: yes, with the sentence in 14.1 and `--safe` as the way out.
3. **Remove the `mcp-remote` fallback before `mcp login` exists?** Recommended, pending owner: yes; a sentence that says "sign-in needed" is better than an unpinned package run without asking. Keep an opt-in setting for one release.
4. **"Plan edits: Automatic" until a reviewer exists**: reword and cap like Permissive, or hide the level for Plan edits? Recommended, pending owner: reword and cap; hiding changes stored settings.
5. **Does IDGAF get a confirmation?** It contradicts the name. Recommended, pending owner: one sentence per session, no question, because the outside-workspace reach is new in this release and `--auto` reaches it.
6. **Terminal checkpoints: session-file snapshots (Claude Code) or a shadow repository (Cline)?** Recommended, pending owner: session-file snapshots of the files the agent writes; smaller, no git dependency, and the limits are easy to state.
7. **Is JSON on stderr the contract for `-p` errors?** (Open in `area-isolation-sandbox-gate.md` section 9, question 1.) Recommended, pending owner: a plain sentence on stderr by default and JSON only with `--format json`.
8. **Should `continuous reset --all` touch `~/.continue`?** Recommended, pending owner: never; it belongs to another product. Say so in the output.
9. **Upgrade notice: per behaviour change that matches the person's settings, or one line with a link?** Recommended, pending owner: matched lines, at most three, then a link.
10. **Safe mode's name**: `--safe` reads like a permission level. Recommended, pending owner: `--safe` on the command line with help text "start without project config, hooks and MCP servers", and "safe mode" in the docs.
