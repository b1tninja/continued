# Shell awareness: which interpreter reads a command, and what follows from it

Research and decision report, 2026-11-12. Code read on `origin/main` at `ecb8c6dcc` and on the draft `fable-security-refinements` (#744). `plans/ROADMAP.md` is not edited: section 9 holds the exact row text. Releases use even minors: 2.16.0 is being cut, so "2.18.0 candidate" means the release after it.

Convention: "verified by test" means a test was written and run. "Verified by reading" names the file and line. "Measured" means run on the review machine (Windows 11, Windows PowerShell 5.1.26100, cmd.exe, Git for Windows bash 5.3.9, WSL with an Arch Linux distribution; no `pwsh`, no zsh, no fish). "Unverified" means from memory or a secondary source.

## 1. Summary

1. **A command means what its interpreter makes of it, and we have been naming the interpreter from the wrong machine in one case and not at all in another.** In a remote VS Code window the terminal tool types the command into the editor's terminal on the other machine, while the policy, the Auto reviewer and the command lint were given this machine's shell (`core/core.ts:773` and `:2098`, `resolveShell().kind`). On a Windows laptop with a Linux remote that is PowerShell rules for a command bash reads. Fixed in #758.
2. **Where we start the shell ourselves, we know it exactly.** `core/util/shell.ts` `resolveShell()` is the one place: `powershell.exe -NoLogo -ExecutionPolicy Bypass -Command <command>` on Windows (always Windows PowerShell 5.1, never `pwsh`), `$SHELL -l -c <command>` elsewhere, `wsl.exe -- bash -lc` and `docker|podman run` when the person asked for them. The IDE tool in a local window, the CLI tool, loop checks and background jobs all go through it (section 2).
3. **Where we do not start it, we cannot tell, and the code now says so.** A remote window's terminal, a JetBrains terminal widget and anything the person types themselves are read by a shell we never see. `executionShell()` answers `unknown` there, and unknown is treated as: deny and ask rules read every grammar, nothing is vouched read-only, no allow rule applies.
4. **The command line can change the interpreter under us.** `bash -c`, `cmd /c`, `powershell -EncodedCommand`, `wsl`, `ssh host`, `docker exec`, `python -c`, `./deploy.sh`. The deny and ask side already reads inside almost all of these (`candidates.ts` tries every suffix of a command as a command, in every plausible grammar). Three forms were opaque to it; the cheapest one (`-EncodedCommand`) is fixed in #758; script files and `Start-Process -ArgumentList` remain (section 4).
5. **Nothing told the person.** The approval card now says "Runs through: bash -lc in WSL" when a command hands its text to another interpreter (#757), from a new pure module that names the interpreter, how it was determined and how sure that is (#756).
6. **The word `bash` on Windows does not name a shell.** Measured: from a plain PowerShell, `where bash` gives `C:\Windows\System32\bash.exe`, the WSL launcher; the same word inside a Git Bash session runs Git's bash (`uname` printed `MINGW64_NT`). The text cannot say which; only PATH can. The classifier reports such a launcher at medium confidence.

## 6. The decision: a shell context for every command

For every terminal command about to be decided, two things are determined, each with how it is known.

**The outer shell** (who is handed the command):

| Source   | Meaning                                                                                                                       | Treated as                                                      |
| -------- | ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| spawned  | This process starts the shell (`executionShell` with a local window, the CLI, a loop check, WSL or a container by preference) | A fact. Its grammar is the dialect for rules, vouching and lint |
| terminal | The command is typed into a terminal this process cannot see                                                                  | Unknown                                                         |
| (none)   | The shell is not one the product parses (fish, nushell, ksh, tcsh)                                                            | Unknown                                                         |

**The interpreters inside the command** (who is handed its text next), from `classifyInterpreter`: family, `via` (outer, wrapper, script, shebang, unknown), confidence (high, medium, low), and whether what runs is opaque.

Rules:

1. **Unknown never auto-allows.** With an unknown outer shell no allow rule applies and nothing is vouched read-only; deny and ask rules read every grammar. Built (#758).
2. **The dialect follows the interpreter.** An inner script is read with its interpreter's grammar, not the outer shell's (`candidates.ts` already does this for deny and ask; `interpretersOfCommand` does it for description).
3. **A mismatch asks.** Text that reads as another dialect than its interpreter's is not vouched (`classifyReadOnly` already takes the most restrictive reading; `mismatchedShell` already feeds the lint). Nothing new is needed on the vouching side; on the allow side see rule 5.
4. **The card names a non-default interpreter.** Built for interpreters the command launches (#757). Not built: the outer shell on the card when it is not the platform's default (WSL or a container by preference, a remote terminal). The webview does not know the outer shell today; SH4 carries it in the policy result.
5. **A wrapper is never covered by an allow rule written for its inner command, and an allow rule written for the wrapper is the person's own choice.** `runTerminalCommand(echo *)` does not cover `bash -c 'echo hi'` today (the rule is matched against the command as written), and that stays. `runTerminalCommand(wsl *)` or `(ssh host *)` allows whatever follows; the Permissions page should say so when such a rule is added (SH7), not refuse it.
6. **Shebang scripts.** Decided: read the first line only when the path is literal (no variable, glob or `~`), inside the workspace, and the file is small; treat the result as a description (the card says `./deploy.sh (#! node)`), not as a licence. The script's body is what runs, so a script is always opaque: it is never vouched read-only and the card says "What that runs is not all written in this command." Reading the whole body into the rules was rejected for now: a body can source other files, and it can change between approval and run, which is DS7's problem (bind the approval to what was judged) and is solved there by hashing the file at decision time and refusing at run time on a mismatch (SH5 names the hash).
7. **Wrapper chains are peeled with a cap.** Eight launchers in a row in one simple command, four levels of nested script. Past either, the answer is unknown and opaque, and deny and ask fail closed as they already do for a truncated expansion.
8. **Nested shells and re-quoting.** Each level's inner text is taken as the outer level's quote removal leaves it (POSIX rules for a POSIX outer; quotes only, backslashes kept, for PowerShell and cmd; one outer pair of quotes removed for `cmd /c`). This is an approximation of four different re-quoting rules, so a nested level is description and deny/ask input, never a basis for allow or vouching.
9. **Windows.** The dialect is the spawned shell's: PowerShell 5.1 unless the person chose WSL or a container. Git Bash is never the outer shell of a command this product starts (we never spawn it); it appears only as `bash -c` inside a command, where the word is PATH-dependent (medium confidence, and the WSL launcher if System32 comes first). A WSL window in VS Code is a remote window: unknown until SH2.

Rejected:

- **Guessing the outer shell from the command text** (`detectCommandShell`) as a source of truth. It stays what it is: evidence for the lint and for reading a second grammar. A guess that is right 95% of the time is a bypass the other 5%.
- **Asking the shell** (`$PSVersionTable`, `$0`, `echo $SHELL`) before each command. It costs a process per call, the profile can lie, and where we spawn the shell we already know. One probe per session to learn the PowerShell version or the remote terminal's shell is reasonable (SH2), not one per command.
- **Refusing wrappers outright.** `docker exec`, `wsl` and `ssh` are everyday commands; they already never auto-run without a rule or a level that says so.
- **Parsing fish, nushell or ksh.** No demand evidence; unknown-asks is the honest position.
- **Switching Windows to `pwsh` when present.** It would make `&&` work, and it would change every Windows user's dialect under their existing allow rules. An owner decision (SH8), not a default to flip in a refinement.

## 10. Open questions for the owner

1. **Remote windows ask for every terminal command until SH2.** Recommended, pending owner: accept; the alternative is judging a remote bash by a local PowerShell.
2. **fish, nushell and ksh users lose allow rules for terminal commands.** Recommended, pending owner: accept (DS9); document it in the permissions page.
3. **An undecodable `-EncodedCommand` matches every deny and ask rule** (fail closed, as a truncated expansion does). Recommended, pending owner: keep.
4. **The card line's name.** Recommended, pending owner: "Runs through". Alternatives: "Interpreter", "Read by".
5. **`npm test`, `make`, `python x.py` get no card line.** Recommended, pending owner: keep them quiet; they are true and already plain, and a line on every test run would teach people to stop reading it.
6. **Shebang reading (SH5).** Recommended, pending owner: first line only, inside the workspace, literal path, 64 KB cap; description, never a licence.
7. **`pwsh` on Windows (SH8).** Recommended, pending owner: stay on 5.1 for 2.18.0; revisit with a migration note for rules.
8. **The profile (SH8).** Recommended, pending owner: keep it; record on the Permissions page that the profile runs first.
9. **A dedicated terminal for remote commands (SH2).** Recommended, pending owner: yes, named "Continuous", created once per window.
