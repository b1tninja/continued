## 0. Summary

Top findings, in order of consequence:

With 20 or more ready pull requests the gate alone can occupy every slot and nothing else would ever run (priority inversion). 2. **One code push starts 33 jobs** (26 in `PR Checks`, 4 in `CLI PR Checks`, 1 gate, 2 supply-chain). Under a 20-slot cap, and with every job queued separately, the number of jobs, not the minutes, is the cost. Public-repo runner minutes are free; concurrency is the budget.

### 3.2 Why jobs stay queued

1. Concurrency cap. GitHub documents 20 concurrent jobs on Free, 40 Pro, 60 Team, 500 Enterprise, and 5 concurrent macOS jobs on all but Enterprise; support can raise limits by ticket (https://docs.github.com/en/actions/reference/limits, fetched 2026-11-12). Standard runners in public repositories are free and do not use the included compute allowance (https://docs.github.com/en/billing/concepts/product-billing/github-actions, fetched 2026-11-12). So minutes are not the constraint; the cap is. Whether the owner's account is on Free is unverified.
2. Pollers consume the cap. `merge-gate` has `timeout-minutes: 240` and polls every 30 s for up to 200 min. Every ready PR holds one slot for the whole time its checks wait. With 14 pollers the effective capacity for real work is 6 slots; with 20 ready PRs it is zero until pollers time out (a timeout fails the gate, which then needs a rerun, which polls again).
3. Job count. Each of 33 jobs queues separately; the median wait does not shrink for a 1-minute job.
4. Churn. `cancel-in-progress: true` per PR is right, but a push cancels and re-queues the whole suite at the back; agents that push several times in an hour keep a PR permanently at the back.
5. Other consumers on `main` pushes: `Main Branch Build`, `Submit Gradle Dependency Graph` (a Java build on every push; the JetBrains plugin is not shipped), `Deploy Docs`, `Post-merge check` (4 jobs). Dependabot's own "Dependabot Updates" and "Dependency Graph" workflows also run as Actions workflows. Roughly six or more extra jobs per merge.
6. The stuck batch: 100 runs from 2026-11-11 20:2x with no jobs. Whether they count toward any limit is unverified (the documented limit on queued runs is 500 per 10 seconds, which they do not approach); cancelling them is free and removes the doubt.

### 3.3 Design

**T1. Make the gate event-free: one workflow, `needs`, no polling (M, highest value).** Replace the poller with a plain aggregate job.

- Add `workflow_call:` to `pr-checks.yaml` and `cli-pr-checks.yml`. In `merge-gate.yml`: job `changes` (a `git diff --name-only` of the PR files, the same list the gate uses today), jobs `pr-checks` and `cli-pr-checks` (`uses: ./.github/workflows/...`, `if: needs.changes.outputs.code == 'true'`), and `merge-gate` with `needs: [changes, pr-checks, cli-pr-checks]`, `if: always()`, using the existing `re-actors/alls-green` (already pinned by SHA) with `allowed-skips`.
- Remove `paths-ignore` from the triggers of the two workflows (they become called workflows; the filter lives in `changes`). Docs-only PRs then cost two 10-second jobs and the required check always reports, so the "path filter leaves a required check Pending forever" trap goes away by construction.
- `merge_group` now tests something: the aggregate runs the real jobs in the queue. This removes the reason `docs/ci-merge-gate.md` says a queue "adds no safety".
- Keep the check name `merge-gate` so the owner's recipe and the app id pin (15368) stay unchanged.
- Draft handling: skip the heavy jobs on drafts (as now) but make `merge-gate` itself pass on a draft with a notice. GitHub refuses to merge a draft, so a green gate on a draft cannot merge one, and the stale red gates after "mark ready" (CI28; a rerun reuses the old `draft: true` payload) disappear. If a gate must read draft state, read it from the API, not the event payload.
- Risks: reusable-workflow job names change in the checks list (`merge-gate / pr-checks / core-checks`); the `track-rerun` action reads run attempts and may need a look; the nightly `schedule` triggers stay on the original workflows. Pin nothing new.
- Test plan: a docs-only PR (expect green in under a minute, no real jobs), a code PR (real jobs run, gate waits on `needs`, no `gh api` loop), a draft (gate green, no heavy jobs), a failing core test (gate red), `workflow_dispatch`.
- Acceptance: no workflow contains a `sleep` poll on check runs; peak running `merge-gate` jobs is 0 while real jobs queue; a docs-only PR reports `merge-gate` in under 2 minutes; after marking a draft ready the gate waits on the real jobs without a new commit.

**T2. Queue discipline now, no code (XS).** Until T1 ships: owner cancels the 100 stuck runs (`gh run cancel` on each id from `gh api "repos/b1tninja/continuous/actions/runs?status=queued"`); keep at most four PRs non-draft; keep the others draft (a draft costs one 10-second gate job, which fails on purpose); batch pushes. Dependabot PRs wait (T6).

**T3. Fewer, longer jobs (M).** While the cap binds, wall time is `wait + run` per job, and wait is paid per job. Collapse the 26 jobs of `PR Checks` into about six: `static` (prettier, tsc and lint for core, gui, binary, vscode), `unit` (core, gui, binary vitest and the six package suites sequentially), `vscode-package` (build the VSIX), `e2e` (one job per command, `e2e:ci:run` and `e2e:ci:run-yaml`, running the five test files in sequence: 2 jobs instead of 10, saving about 8 checkout-and-download setups), `jetbrains` (conditional, T4). Costs: slower when the queue is empty (the longest job grows from about 8 to about 15 minutes); a failure shows as one failed step rather than one failed job. Measure first with step timings (PR #650 already gathered them for four runs). Keep per-job logs readable with `::group::`.

**T4. Conditional jobs (S).** `jetbrains-tests` (8.5 min, the JetBrains plugin is not released by this fork; `jetbrains-release.yaml` still carries upstream secrets that do not exist here) runs only when `extensions/intellij/**`, `binary/**`, `core/protocol/**` or the Kotlin twins change, and nightly. The 10 e2e jobs run when `extensions/vscode/**`, `gui/**`, `core/**` or `packages/**` change. `docs/` build runs when docs change (CI29). Inside `changes`, output booleans per area; skipped jobs are accepted by the aggregate (`allowed-skips`). Risk: a missed path hides a regression until the nightly run, so the nightly and the release gate (section 5) must run everything.

**T5. Main-branch consumers (S).** Run `Submit Gradle Dependency Graph` weekly and on dispatch, not on every push (Dependabot needs it only for Gradle alerts; the JetBrains plugin is not shipped). Extend `post-merge-check.yml` with the CLI tests and `bench/lab` tests (CI24) and keep `cancel-in-progress` there. Consider whether `Main Branch Build` still serves a purpose now that releases come from dispatch (it republishes a PR artifact; its value after a merge is unverified).

**T6. Dependabot (S, config only).** Current `dependabot.yml`: npm in 14 directories weekly Monday, `open-pull-requests-limit: 10`, one group `npm-minor-patch`, majors individual; github-actions, cargo, gradle weekly; docker and pip monthly. Today 7 Dependabot PRs are open (ai 7, `@ai-sdk/xai` 5, gradle wrapper, protobuf 4, guava, pandas, the grouped npm PR spanning 8 directories). Proposal:

- Provider SDK family: add a group `ai-sdk` with `patterns: ["ai", "@ai-sdk/*"]` and no `update-types` restriction, so `ai` 7 and `@ai-sdk/xai` 5 move together in one PR, or add both to `ignore` for majors until a person migrates `openai-adapters` (recommended: ignore majors for the `ai` family in `/packages/openai-adapters` and migrate by hand, as the file already does for `@opentelemetry/*`). Dependabot's own rule: a dependency in more than one group goes to the first matching group (documented, 2026-11-12).
- `open-pull-requests-limit: 3` for npm (the limit's default is 5; setting 0 disables version updates for that ecosystem and does not affect security updates, which have a fixed separate limit of 10).
- Version-update ecosystems that ship nothing: gradle (`/extensions/intellij`), pip and docker (`/manual-testing-sandbox`): set `open-pull-requests-limit: 0` (security updates continue) or drop them. The JetBrains plugin and the sandbox are not release artefacts.
- Cadence: npm and cargo `monthly` (first Monday), github-actions weekly (it is one grouped PR and pins by SHA). Add `cooldown` explicitly. The documentation states a 3-day cooldown already applies to version updates when none is configured, so the claim in `plans/research/interop-memory-ux-release.md` section 5.3 ("no cooldown, so a release is proposed the day it appears") is out of date; set `default-days: 7` and `semver-major-days: 30` (security updates are not delayed).
- Lockfile drift on `extensions/vscode`: root cause not established here (the failing job logs were not read). The CI `npm ci` step reports drift; a `dependabot rebase` or a manual `npm install --package-lock-only` on the branch fixes a PR. Open an issue with the first failing log before changing config.
- Dependabot PRs trigger the full suite (33 jobs) each. With T1 and T4 the cost for a lockfile-only bump drops to the jobs that depend on that package; until then the limit is the control.

**T7. Cache hygiene (S).** Land #650 (reviewed separately). It reports 13.8 GB against 10 GB, so the 10 GB limit evicts `main`'s caches in favour of per-PR copies of a 712 MB `vscode-storage`.

**T8. Capacity (decision).** Options: (a) do nothing beyond T1 to T7; (b) ask GitHub Support to raise the concurrent-job limit (the limits page says support can; whether a Free-plan owner can obtain it is **unverified**); (c) move the repository into an organisation (Team plan gives 60; section 4.3); (d) a self-hosted runner for post-merge and nightly runs only. Do not put a self-hosted runner behind `pull_request` on a public repository: a fork PR would execute on the owner's machine. Recommended, pending owner: (a) now, (c) when the repository moves for the merge queue.

**Budget for a public repository.** Minutes: not metered for standard runners in public repositories. Concurrency: 20 jobs (Free, to confirm). Target after T1, T3, T4: 6 to 8 jobs and about 25 runner-minutes per code push, 2 jobs for a docs-only push, so 20 slots serve about 10 simultaneous pushes without a queue.

### 3.4 e2e cost

### 4.2 Branch protection

Three combinations of individually green PRs have broken `main` in two days (#553 with #557, #587 with #588, and #643 to #647 on 2026-11-12), so the case for `strict: true` is real. Recommended sequence, pending owner:

1. Land T1 (gate no longer polls) and cancel the stuck runs.
2. Apply the recipe in `docs/ci-merge-gate.md` section 4 exactly (required check `merge-gate`, app id 15368, squash only, `enforce_admins: false`). Also set `delete_branch_on_merge: true` and `allow_update_branch: true` (shows the Update branch button; it does not update anything by itself, per the GitHub documentation quoted in `docs/ci-merge-gate.md` section 6).
3. `strict: true` with a merge cadence: merge one PR, `gh pr update-branch <n> --repo b1tninja/continuous` the next, wait for the gate. With 15 to 20 minutes of wall time per PR after T3 this is about three to four merges an hour. If that is too slow, the fallback is `strict: false` plus the extended post-merge check (CI24) plus `merge-ready --trial --run` locally; it finds a bad combination minutes after it lands rather than preventing it.
4. A step that updates branches automatically would need a token that triggers workflows (pushes made with `GITHUB_TOKEN` do not start workflow runs; this is documented GitHub behaviour, not re-fetched today, **unverified**), so an auto-update bot needs a PAT or a GitHub App. Not recommended for a one-person repository.

## 5. Release process

### 5.1 Current steps, verified from the workflows and the 2.14.0 runs

`.github/workflows/main.yaml` ("Publish Extension"), triggers `release: [released]` and `workflow_dispatch` (inputs `publish_build`, `darwin_runner`, `release_tag`, `republish_run_id`).

1. Write `.github/release-notes/<tag>.md` (a staging note lives in `UNRELEASED.md`). The `release` job fails with "Missing ..." if absent, and checks the tag equals `v<version>-vscode` for `extensions/vscode/package.json`.
2. Set the version in `extensions/vscode/package.json`. `check-version` runs `versionCheck.js` and fails on an odd minor (section 5.4).
3. Merge the release PR. Merging publishes nothing.
4. Dispatch `Publish Extension` on `main` with `publish_build=true`. Jobs: `check-version`, `check_release_name`, `build` (six VSIX targets: win32 x64 and arm64 on Windows runners, linux x64 and arm64 and darwin x64 and arm64 on Ubuntu), `cli` (builds, packs, runs `check-artefact-licences.mjs` on the tarball, installs it in a scratch prefix and runs `continuous --version`), `publish-marketplace` (OIDC trusted publishing, `vsce@4.1.0 publish --oidc --skip-duplicate` per VSIX, `environment: marketplace`, `needs: build` only), `publish-openvsx` (skips every step unless the secret `VSX_REGISTRY_TOKEN` exists; it reports success in about a minute when skipped), `release` (only when the ref is a tag or `release_tag` is set).
5. Create the GitHub release. Observed for 2.14.0: the run of 10:27Z (dispatch, `release` job skipped because no tag) published to the Marketplace; the release was created by hand (`created_at` 10:22Z, `published_at` 10:43Z, author b1tninja, target `a5f42332`), and publishing it fired the `release` event, a second full run (10:43Z to 10:52Z: all six builds again, the CLI, the `release` job which attached 14 assets, and a second `publish-marketplace` that skipped duplicates). The same two-run pattern appears for 2.10.0 (dispatch 15:51Z, release event 16:10Z). The `release_tag` input exists to avoid it: `gh workflow run main.yaml -f publish_build=true -f release_tag=v2.16.0-vscode` builds once, creates the tag at `github.sha`, attaches the VSIX files, the agents VSIX files, the CLI tarball and `SHA256SUMS.txt` (generated with `sha256sum`), and publishes. A release created by the workflow with `GITHUB_TOKEN` does not start another workflow (documented GitHub behaviour, not re-fetched today).
6. Previous releases in `releases`: 14 assets each (6 VSIX, 6 agents VSIX, 1 tarball, 1 `SHA256SUMS.txt`).

Problems in the current process:

- `publish-marketplace` needs only `build`: if `cli` or the `release` job fails, the Marketplace still publishes.
- Marketplace publish and the GitHub release are independent; a failed release job leaves a published version with no release.
- The manual `gh release create` doubles the build time and the runner use.
- `CONTRIBUTING.md` lines 177 to 183 still describe upstream's pre-release flow (`preview.yaml`, `releaseflow.org`); the `release` job in `main.yaml` no longer targets upstream, so CI28's first sentence is stale. `preview.yaml`, `vscode-prerelease.yml`, `jetbrains-release.yaml` and `docs-screenshots.yml` are upstream workflows with upstream secrets (JetBrains signing, Apple certificates); they are dead weight and attack surface.
- `environment: marketplace` has a branch policy (`main` and tags `v*-vscode`) but no required reviewer.
- No attestation, no SBOM, no recorded sandbox-matrix result.

## 6. Privacy, egress, licensing and identity decisions

### 6.1 Distribution: Open VSX, verified publisher

- Reference channel: GitHub Releases (VSIX, CLI tarball, `SHA256SUMS.txt`, attestation). Marketplace: published by trusted publishing, no stored token. Record both as decided (the ROADMAP recommends it).
- Open VSX (https://github.com/EclipseFdn/open-vsx.org/wiki/Publishing-Extensions, fetched 2026-11-12) requires: an Eclipse account with the same GitHub username used to log in to open-vsx.org, a signed Eclipse Publisher Agreement, a namespace matching `publisher` (`b1tninja`) created before publishing, an access token (one per environment is advised), and a separate request for verified ownership of the namespace (creating a namespace does not verify you; without it extensions show a warning). Open VSX has no trusted publishing. Recommended default: do not publish until the agreement is signed and the namespace is claimed; after that, add the token as an environment secret and publish the same artefacts. Reason: the audience that uses Open VSX (VSCodium and other forks) overlaps with people who dislike unsigned side-loading, but a registry entry under a name close to the upstream product invites confusion, and the agreement has legal terms the owner must accept personally. Reversibility: easy to add later.

The fork has no domain; defer (the ROADMAP row agrees). The publisher display name must not change afterwards.

### 6.2 Telemetry posture

Default (already implemented, state it as policy in `PRIVACY.md`): no usage data, no crash reports, no machine id, no update check; OpenTelemetry metrics only with `CONTINUOUS_OTEL=1` and an exporter the person configured. ### 6.3 Third-party fetch: the ask-once pattern

Cases today: model lists from `openrouter.ai` and `ollama.com` when provider setup opens (PRIVACY.md "tracked for a later release"; PR #690 "ask once, keep a dated local copy" is open), the Chromium download, GitHub API for docs entries. Pattern, recommended pending owner:

- One consent record per (host, purpose) in `~/.continuous/egress-consent.json`: host, purpose, what is sent ("GET, no body, no identifiers"), grant time, scope (this machine). A first use shows a prompt that names the host and what leaves the machine; "Always allow this host for this purpose" and "Not now" are the only choices. No default grant.
- Headless runs (`serve`, a non-interactive CLI, the sandbox): deny without a prompt unless the record exists or the person set `CONTINUOUS_EGRESS=allow:<host>`. The notice that something was skipped names the setting.
- A bundled dated snapshot is the offline answer (what #690 does for OpenRouter prices), so a refusal costs freshness, not function.
- Revocation: `continuous privacy` lists and removes records; a setting `privacy.thirdPartyFetch: off` refuses all.
- Allowlist classes: `configured` (a host the person typed), `consent` (needs a record), `fixed` (documented, e.g. `github.com` for an explicit docs URL). The vitest adds one assertion: every `consent` host's call site is behind the consent check (a source test that finds the helper call, not a network capture).
- Size: M, one PR for the helper and the allowlist classes, one for #690's callers.

**Merge queue on a user-owned repository.** Unchanged in substance, better sourced. ### 13.2 Release runbook amendment: even minor versions only

Verified from the code: `extensions/vscode/scripts/versionCheck.js` reads `package.json`, takes `parseInt(version.split(".")[1])` and throws "Do not publish odd-numbered version to main VS Code release!" when it is odd. `check-version` is a `needs` of `build` and `cli` in `main.yaml`, so an odd minor stops the whole run within seconds, before any build, for both the dispatch and the `release` event. Written into the runbook:

1. **The minor version of every release is even.** 2.14.0 is followed by **2.16.0**, then 2.18.0. 2.15.x and 2.17.x are never released (2.13 was skipped the same way). A patch release keeps the minor: 2.16.1 is fine.
2. `scripts/release/prepare.mjs <version>` refuses an odd minor before it edits anything; `release-check.mjs` repeats the check; the proposed PR-time guard (CI40) fails a pull request that sets an odd minor in `extensions/vscode/package.json`, so the mistake shows at review and not at dispatch.
3. The release PR template has a line "minor version is even".
4. `preview.yaml` and `vscode-prerelease.yml` (upstream's odd-minor pre-release channel) are not part of this process; they are removal candidates in CI32 and must not be used to bump a version.
5. A version dispatched by mistake does not burn a number: `check-version` fails first, so nothing is published and nothing needs rolling back.

Ordering with the sandbox release gate (#711, section 5 of `area-isolation-sandbox-gate.md`, and its open addendum #721): the gate runs on the candidate before anything is published, which conflicts with the single dispatch of section 5.2 (`publish_build=true` and `release_tag` in one run). Reconciled as a two-phase flow: dispatch 1 builds with `publish_build=false` (the workflow already uploads every VSIX and `cli-tgz`); the person runs the gate on those artefacts and commits `release-gates/<tag>.json`; dispatch 2 publishes. For dispatch 2 not to rebuild, `republish_run_id` must also create the draft release and attach the assets (today it skips the `release` job because of `inputs.republish_run_id == ''`); #721 states the same requirement. CI31 and the `gate-verify` job should therefore be one pull request that changes `main.yaml` once.
