# RQ8: chat templates still unread

Desk research, no model call. Fetched 2026-11-11 with `curl` and read in full (raw bytes, not a summary), from the model repositories on Hugging Face and the vendor code or docs named in each row. Each fixture below is **built from template, not recorded from a model**: the assistant turn that carries `tool_calls` was rendered with Jinja2 (3.1.6, a sandboxed environment with Hugging Face's `tojson`) from the published template, or, where the vendor publishes code instead of a template, written by hand from that code. The fixtures are `synthesised` in the corpus (`core/llm/toolDialects/corpus/fixtures/`) and carry that sentence in `provenance.note`.

What a template shows is the form the model sees in history, so it is the form it was trained to emit. It does not show how often the model keeps to it.

## Findings

1. **No new dialect is needed.** Every call form read maps onto a dialect we already have. The one family with no form at all is the Nemotron-H 4B, 8B and 47B set, whose templates cannot render a tool; it needs a prompted path (the `codeblock` style in `core/tools/systemMessageTools`, untested on it) rather than a parser.
2. **A real gap, recorded.** Qwen3.5 and Nemotron 3 Ultra render a boolean argument as the Python word `True` (Jinja `string` of a Python bool); Qwen3.6 writes `true`. `QwenXmlRecovery` accepts only JSON literals, so a Qwen3.5 reply whose call has a boolean argument stays text. The fixture `qwen35-two-calls-python-bool` is policy `should` and listed in `KNOWN_SHOULD_GAPS` in `qwenXml.corpus.vitest.ts`; the test fails when the gap is fixed, so the entry is removed then. The Ultra fixture has no top-level boolean (its object value is `tojson`, so its `false` is JSON) and passes; a top-level boolean on Ultra has the same `True` problem, from the same template line.
3. **Prose before a call.** The Qwen3.5, Qwen3.6 and Ultra templates tell the model it may reason in prose before the call and render `prose\n\n<tool_call>`. The strict whole-reply `QwenXmlRecovery` leaves such a reply as text (corpus fixture `qwen3-coder-prose-then-call`). That is a pinned design choice, not new, but it means the template's own trained shape is one the parser refuses.
4. **Gemma 4 puts assistant text after the calls**, the opposite of the others. A reply with prose before `<|tool_call>` is not the trained shape.
5. **Nano v2's instruction example has doubled braces.** The template writes `{{"name": "tool_name1", ...}}` literally (the doubling is inside a Jinja string, not an escape), so the prompt the model reads shows `{{`; history renders single braces. A parser should not expect doubled braces from the model; the fixture uses single.
6. **Mistral: Tekken is the tokenizer, not a call format.** `TokenizerVersion` in `base.py` says v3 "adds improved function calling", v7 "improved system prompt and function calling", v11 "improved function calling", v13 "removes call id tokenization". In `instruct.py` V7 inherits V3's tool-call encoder unchanged (the array form), V11 writes `[TOOL_CALLS]NAME[CALL_ID]ID[ARGS]{json}` per call, V13 and V15 drop the `[CALL_ID]`. So there are three layouts: array (v3, v7), `[ARGS]` with id (v11), `[ARGS]` without id (v13, v15). The `mistral` dialect handles all three; the corpus had v3 and v11 and now has v7. Not read: which released model uses which tokenizer version (that needs each model's tokenizer file, which is binary).
7. **Nemotron 3 Ultra needs `force_nonempty_content`.** The card says that with `tools`, `chat_template_kwargs` must carry `{"enable_thinking": true, "force_nonempty_content": true}` for the reasoning and tool-call parsers to agree. Our request builders do not send it. Not tested here. Re-read 2026-11-11 in the card: SGLang tool calls must send both kwargs; for vLLM the card only advises `force_nonempty_content` for coding agents, so "required" holds for SGLang only. It is a template variable passed through the engines' `chat_template_kwargs` field, not an engine parameter, so no request option was added (a model can set it with `extraBodyProperties`).

## Not done, and why

- Hy4, LFM3 and Qwen3.7 (named in the ROADMAP row as still unread) are outside this task's list and were not fetched.
- The Kimi K3 fixture is hand-built from `encoding_k3.py`; the downloaded script was not executed. The fixture text stops before `<|end_of_msg|>`, like the existing K3 fixtures.
- Only the assistant `tool_calls` branch of each template was rendered, with no images, no thinking and no tool responses.
- The two corpus tests `qwenXml` and the other dialect tests pass; `textFilters.corpus.vitest.ts` does not load in a fresh checkout because `@continuedev/llm-info` is not built there (a build step, unrelated to the fixtures).
