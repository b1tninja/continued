Status: DRAFT research note. Docs only: no product code changed, no model called, nothing run in Windows Sandbox. Code read at `origin/main` 62277ea. Web pages fetched on 2026-11-13; a claim not confirmed on the vendor's own page is marked **unverified**. `plans/ROADMAP.md` is not touched; this note proposes rows in section 11 and does not apply them.

Builds on, and does not repeat: [`isolation.md`](../isolation.md) (executor model, backends, decisions D1 to D5), [`jail-network.md`](../jail-network.md) (threat model, egress proxy, probes), [`area-isolation-sandbox-gate.md`](./area-isolation-sandbox-gate.md) (state of every W row on 2026-11-12, the release gate) and the custom-policy review of PR #818 (`plans/research/custom-policy-concept-review.md`, open), whose section 5.1 says which guards are "best-effort until W8". This note answers one question for the terminal tool: what OS sandbox to put around agent commands on each platform, how it meets the policy guards, and what the smallest honest first step is.

## 1. Summary

1. **The seam exists, but the terminal tools step around it.** `CommandExecutor` (`core/util/commandExecutor.ts:34-54`) has a `spawn()`, yet five of the six places that start an agent command call `child_process.spawn` themselves with the executor's `invocation()` argv: the IDE tool three times (`core/tools/implementations/runTerminalCommand.ts:222, 492-496, 634-641`), the CLI tool (`extensions/cli/src/tools/runTerminalCommand.ts:237-242`) and CLI background jobs (`extensions/cli/src/services/BackgroundJobService.ts:68-71`). Only loop checks use `executor.spawn` (`extensions/cli/src/loop/loopChecks.ts:128`). Both OS-sandbox libraries worth using are **async** (`wrapWithSandbox` in sandbox-runtime, `spawn(request)` in MXC), and `invocation()` is synchronous. So the first piece of work is to make every agent command go through one async `executor.spawn(command, { cwd, env, stdio, detached })`. That is a refactor with no new claim, and it is the smallest honest first step (section 9, phase 0).
2. **A bug found on the way, to verify first:** the container executor builds its `docker run` argv from `process.cwd()` (`commandExecutor.ts:142, 147`), and `containerArgs` mounts that folder read-write (`core/util/containerArgs.ts:76-77`). The IDE tool passes the workspace as `cwd` to `spawn` (`runTerminalCommand.ts:132-136`), but the argv was already built from the extension host's own working directory, which is not the workspace in a VS Code or JetBrains host (what it is on each OS is **unverified**). If confirmed, the IDE container mode mounts the wrong folder. The executor's `invocation` must take `cwd`.
3. **Windows changed since W-D2.** Microsoft's MXC (Microsoft eXecution Containers, MIT, [github.com/microsoft/mxc](https://github.com/microsoft/mxc)) is public, and its `processcontainer` backend runs a command in a BaseContainer (AppContainer-based) with per-container WFP egress filters and **no UAC prompt per launch** ([networking.md](https://github.com/microsoft/mxc/blob/main/docs/backends/process-container/networking.md)), on Windows 11 24H2/25H2 from build x.9278 and 26H2 from 26300.9550 ([os-version-support.md](https://github.com/microsoft/mxc/blob/main/docs/backends/process-container/os-version-support.md)). Codex's preferred Windows sandbox is now MXC ([Codex Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox)), and VS Code's agent sandbox uses BaseContainer on Windows, as Experimental ([VS Code agent sandboxing](https://code.visualstudio.com/docs/agents/run/agent-sandboxing)). The owner's machine is 26300.9974 (26H2, read from the registry for this note), above that floor. Two costs: MXC sends Required diagnostic data on Windows that "does not require user consent" and cannot be switched off by request or policy ([telemetry.md](https://github.com/microsoft/mxc/blob/main/docs/telemetry.md)), and its Node SDK needs Node 24 or later and pulls native modules (`koffi`, `node-pty`; npm registry, `@microsoft/mxc-sdk@1.0.1`). The SDK ships `wxc-exec.exe`, which takes a JSON request, so we can drive it from Node with `child_process` and no native addon in our process. **Recommendation: replace W-D2's "no native Windows" with "spike MXC processcontainer behind our interface, as opt-in, after the owner rules on the telemetry" (decision O7).**
4. **Linux, WSL2 and macOS stay on sandbox-runtime (srt)**, as W-D2 decided. Nothing found today argues otherwise: Claude Code, Codex, VS Code and Cursor all use Seatbelt on macOS, and bubblewrap (or Landlock) on Linux. srt's latest is 0.0.83 (npm registry, published 2026-11-13); we pin 0.0.82 (`core/util/srtStatus.ts:25`).
5. **IDGAF and the sandbox are on separate axes.** The sandbox is a property of where a command runs, not a check that asks or refuses. Plain IDGAF runs with no sandbox unless the person opted in, as the owner set. When the person opted in, IDGAF keeps it on, never widens it, and never auto-approves a retry outside it (section 7).
6. **What the sandbox makes honest, from #818's table 5.1:** no writes outside the workspace, the policy-file lock and secret-file reads for terminal commands, and "network only to listed hosts" for commands whose traffic goes through the proxy. It does not make a command denylist honest. It bounds what a bad command can reach; it does not recognise the command. File tools, hooks and MCP servers stay outside, as they do in Claude Code.

What is already in front of every command and must stay in front of the sandbox:

- **The scrubbed environment (2.12.0).** `terminalEnvironment()` removes secret-looking names by default (`core/util/terminalEnvironment.ts:16, 161-171`), and the executor's own `spawn` uses it unless the caller passes `env` (`commandExecutor.ts:89-97`). The CLI builds the same from `shellChildEnv()` (`extensions/cli/src/tools/runTerminalCommand.ts:239`). srt and MXC do not scrub the environment: the scrub stays ours, and runs first.
- **The non-interactive executor changes (#790).** `COMMAND_STDIO` gives the child no open standard input (`core/util/commandSpawn.ts:24-28`), `realExitInvocation` adds the real-exit-code tail for PowerShell (`:40-47`) and `commandEnvironment` adds pager defaults and `WSLENV` names (`:57-67`). All three are about the command line and its streams, so a sandbox executor wraps the result of these, not the bare command. That order also keeps what is shown, approved, linted and audited equal to the command the model wrote, which `commandSpawn.ts:36-38` already promises.
- **The gates before spawn.** `commandBlocked` returns `executor.unavailable`, the lint or the missing-binary gate before anything runs (`core/tools/implementations/runTerminalCommand.ts:151-158`; CLI `extensions/cli/src/tools/runTerminalCommand.ts:113-120`). A sandbox that was asked for and cannot start is an `unavailable` executor: the command is not run, and it never falls back to the host (the rule `commandExecutor.ts:47-53` already states).

Pure code that is built and waits for this executor: the policy-to-sandbox compiler `compileSandboxConfig` (`core/util/sandboxPolicy.ts:569`, platforms `linux | wsl2 | macos`, `core/util/sandboxPolicyTypes.ts:10`), the prompt-skip `sandboxAutoApproval`, gated on a `verified` flag nothing sets yet (`core/util/sandboxApproval.ts:13-31, 108`), the srt status probe that never says "contained" (`srtStatus.ts:620-645`; the CLI prints "no result here means contained", `extensions/cli/src/commands/sandbox.ts:103`), the egress proxy (`core/util/egressProxy.ts:152`), the 22 escape probes (`core/util/escapeProbes.ts:89`, bash only, `:59`) and the reserved `sandbox` key in `permissions.yaml` (`core/tools/permissions/settingsFile.ts:48-56`).

What the field agrees on, and what we take:

- **Separate "what can happen" from "who approves".** Codex says it outright ("The sandbox defines what Codex can technically do, and the approval policy defines when it must stop and ask"), and VS Code's sandbox "continues to restrict terminal commands with **Allow all** and **Autopilot**". Our levels and IDGAF are the approval axis; the sandbox is the other one.
- **Writes: workspace plus temp, minus config that runs later.** Every product protects `.git/hooks` and `.git/config` or all of `.git`. Our compiler already narrows `.git` to `hooks` and `config` so `git commit` works (`isolation.md`, W8a mapping item 2).
- **Reads: everyone except Cursor reads broadly by default.** Secrets are a deny list. Our `readPolicy` default stays `open` (owner decision S9-X3, ROADMAP B76).
- **Network: split.** Claude Code, Codex, Cursor and srt deny by default; VS Code allows by default; Gemini's default profile is open. Ours: `none` by default when the sandbox is on, with a one-click registries preset (decision O6).
- **The retry outside the sandbox is the weak point.** Claude Code, VS Code and Cursor all have one, and each puts it behind approval or a classifier. In an unattended or IDGAF run there is nobody to approve, so ours must be off there (section 7).
- **Silent fallback is the default in Claude Code**, and its docs offer `failIfUnavailable` for people who treat the sandbox as a gate. Ours fails closed when the person asked for it; that is already the executor rule.

## 4. Platform mechanisms

### 4.1 Linux and WSL2

- **bubblewrap** builds a mount, PID and network namespace with an unprivileged user namespace; srt and VS Code use it, and so does Codex together with seccomp. Known blockers: Ubuntu 24.04+ AppArmor restricts unprivileged user namespaces ("Disable the restriction with: `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`", [srt](https://github.com/anthropics/sandbox-runtime)); nested namespaces are blocked, so Chromium and rootless Podman fail inside; Docker is "incompatible with the sandbox" ([Claude Code](https://code.claude.com/docs/en/sandboxing)). Our `srtStatus` already checks user namespaces and seccomp (`srtStatus.ts:341, 376`).
- **Landlock** lets "any process, including unprivileged ones" restrict itself; filesystem since ABI 1 (Linux 5.13), TCP bind and connect by port since ABI 4, UDP since ABI 10. It cannot restrict chdir, stat, chmod, chown and some others, and network rules are by port, not host ([kernel docs](https://docs.kernel.org/userspace-api/landlock.html)). Cursor uses it with seccomp and needs kernel 6.2+. For us it is a fallback idea for hosts where user namespaces are blocked, not the first backend: a host allowlist needs a proxy either way, and srt already brings one.
- **seccomp** blocks system calls (srt uses it to block unix sockets, which closes the Docker socket and ssh-agent).
- **Network namespaces** with no interface except a relay to the host proxy are what make "only through the proxy" hold for programs that ignore `HTTPS_PROXY`: they simply cannot connect.
- **WSL2**: the same as Linux inside the distribution; WSL1 is unsupported everywhere. From a Windows host, `/mnt/c` and Windows interop (`powershell.exe` from bash) are outside a bubblewrap jail unless masked; Claude Code notes Windows binaries reached from WSL2 go through the unix-socket rule and need the seccomp filter ([sandboxing](https://code.claude.com/docs/en/sandboxing)). The W4b spike already measured `/mnt/c` readable (ROADMAP W4c).

### 4.2 macOS

Seatbelt through `sandbox-exec` with a generated profile is what srt, Claude Code, Codex, Cursor, Gemini and MXC all use. The `sandbox-exec` man page has said "DEPRECATED" for years (quoted secondhand, for example [jmmv.dev, 2019](https://jmmv.dev/2019/11/macos-sandbox-exec.html); Apple publishes no first-party page for it), and Apple offers no supported replacement for sandboxing an arbitrary child process. Risk accepted with the whole field: if Apple removes it, every peer breaks the same day, and our status probe must turn `unavailable`, never "contained". Known breakage under Seatbelt: Go CLIs (`gh`, `gcloud`, `terraform`) fail TLS verification, `git` over SSH fails, Apple Events are blocked ([Claude Code](https://code.claude.com/docs/en/sandboxing)).

### 4.3 Windows (in depth)

The owner develops on Windows 11 Pro, build 26300.9974 (26H2). Every native Windows mechanism below therefore needs code outside Node's standard library: a native addon loaded into our process, or a helper executable we spawn. ## 5. What the sandbox enforces (the profile)

One profile, compiled from the policy by `compileSandboxConfig` (W8a, built), the same input on every backend. Backends differ in what they can express; what one cannot express goes into `notEnforced` (`core/util/sandboxPolicyData.ts:136`), never silently dropped.

**Keeping commands working.** The breakage list from the peers is long and predictable, so plan for it rather than discover it:

- **Package managers** need their registry hosts (`egressPresets.ts` has npm, PyPI, crates and others) and a writable cache outside the workspace. VS Code grants "shared build caches" read-write by default (`allowDevToolAccess`). Ours: a `toolchain caches` preset (npm, pnpm, yarn, pip, uv, cargo, Go, Gradle and Maven caches) that the person turns on, shown as a loosening, because a writable cache is a place to plant code that a later host build runs. Install scripts still run inside the jail, which is the point.
- **git**: commits, branches and fetches over HTTPS work with `.git` writable except `hooks` and `config`. `git` over SSH fails (plain `ssh` ignores proxy variables), so the failure message says "use HTTPS or run outside the sandbox". Worktrees: the main repository's shared `.git` must be writable, as Claude Code does.
- **Compilers and test runners** work if their install dir is readable (default `open`). Watchers that use daemons (`watchman`) and anything that needs Docker do not.
- **Windows-specific**: under srt's Windows backend, Schannel clients fail HTTPS. Under MXC, unknown until the spike.
- **Long-running servers** (`npm run dev` in the background) need the sandbox to allow children to outlive the foreground and need a port: `allowLocalBinding` is false in our compiled config (`isolation.md`, W8a), so a dev server in the sandbox is unreachable from the host browser. Say so in the failure; a per-session "allow local listening" setting is a later decision.

Two engine rules follow:

1. **The sandbox never loosens a check.** It already does not: `sandboxAutoApproval` refuses to skip a floor, a deny or ask rule, a protected or locked path (`sandboxApproval.ts:13-31`), and levels never change the compiled config (W8a). The prompt-skip (W8c) stays gated on the path analyser (B28) and the confused-deputy work (W8d).
2. **A workspace file may tighten the sandbox, never loosen it.** `allowWrite`, extra readable dirs, `allowedDomains`, toolchain caches, `readPolicy: open` and any unsandboxed-retry switch go into the untrusted loosening list next to `toolPermissions.allow` (`core/tools/permissions/trust.ts:16-27`).

## 7. Opt-in, IDGAF, escape hatches and failures

**Opt-in.** Off by default on every platform, for interactive use and for unattended runs, until probes on that platform are green in CI (Linux, macOS) or in the harness (Windows) for one release. Turning it on is a setting (`sandbox: on` in `permissions.yaml`, the reserved key) and a per-session toggle, as VS Code does.

**IDGAF.** The owner's rule holds: plain IDGAF runs with no sandbox unless the person opted in. If the person opted in:

- IDGAF keeps the sandbox on and never widens it. IDGAF is about who approves; the sandbox is about what can happen (Codex's two axes). Claude Code lets `bypassPermissions` reach hosts outside the allowlist without a prompt ([sandboxing](https://code.claude.com/docs/en/sandboxing)); we do not, because then "sandbox on" would mean something different at each level, and the badge would lie at exactly the level where nobody watches.
- A sandbox denial is not an IDGAF refusal. The policy engine approved the call; the OS returned an error inside the command. "IDGAF never denies" (#818 section 1) is about the engine, and stays true. The result says what was denied (W25), so the model does not retry blindly.
- **The retry outside the sandbox is not available under IDGAF** (nor in any unattended run) unless the person turned on a separate, named setting, "allow unsandboxed retries without asking". A retry that IDGAF auto-approves is a sandbox switch the model controls.
- The chip shows both axes: "IDGAF · sandbox on (verified)" or "IDGAF · no sandbox".

**Escape hatches, in order of preference.**

1. **Ask to run outside, once.** When a command fails and the sandbox recorded a violation, the tool result names it; the model may ask to rerun outside; the person approves with the denial shown. Never in a run nobody watches (the unattended `ask` rule of #818 section 3.3 makes it a refusal). Audited.
2. **Turn the sandbox off for the session.** Explicit, audited, the chip changes.
3. **No `excludedCommands` in the first version.** It is a command-name list that grants full access, the exact shape #818 calls bypassable (`sh -c`, a path, an alias). If people need it for `docker`, add it later with the same matching as the deny rules and a warning that it is full access, as Claude Code's docs do.

**Failures, and how they surface.**

| Situation                                   | What happens                                                                                                                                                                           |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sandbox asked for, backend missing          | `executor.unavailable`: "Command not run: the sandbox is on but bubblewrap is not installed. Install: ..."; never runs on the host (`commandExecutor.ts:47-53`)                        |
| Backend present, initialise fails           | same; never a weaker sandbox without saying so (compiler rule 7, `isolation.md`)                                                                                                       |
| Command hit a denial                        | normal exit code and output, plus "denied by the sandbox: write to C:\Users\me\.ssh\config" from the violation log (srt `annotateStderrWithSandboxFailures`; MXC audit **unverified**) |
| Probes stale (new srt version, config hash) | status `unverified`; labels go back to best-effort; the sandbox still runs                                                                                                             |

**Performance.** Not measured here. To measure in phase 1 and the spike: bubblewrap start per command (srt), Seatbelt per command, `wsl.exe` round trip (measured in W1 work), one `wxc-exec.exe` launch, and `npm install` and `tsc` wall time inside versus outside. A budget to test against: under 100 ms per command on Linux (`area-isolation-sandbox-gate.md` 4.3); Windows Sandbox at 2.2 to 4.0 s a cycle is only for whole runs.

Design rules for the executor change (phase 0):

- `invocation(command, cwd)` takes the cwd; `spawn` becomes async and is the only way any tool starts an agent command. A unit test lists every `child_process.spawn` in the tool paths and fails on a new one outside the executor.
- The sandbox wraps the final command line from `realExitInvocation`, with the environment from `commandEnvironment(terminalEnvironment(...))`, so what is approved and audited is unchanged.
- The wrapped command must run in the process that prepared it (srt's proxies live there). In the IDE that is the extension host or the JetBrains binary; in the CLI the `cn` process.
- `describe()` returns the backend and the verified properties from the probe table, never from the library's own getters (`srtStatus.ts:5-21` already insists on this).

## 12. Risks

1. **Words outrun evidence.** A label flips to "enforced" before the probe table says so. Guard: labels read only the probe table (W7h), and a test fails on any UI string "contained" without it.
2. **Breakage drives people to turn it off.** The peers' breakage lists are long (section 5). Mitigation: presets, a denial message that says what to do, and opt-in until data exists.
3. **The retry becomes the hole.** Any automatic unsandboxed retry defeats the jail; section 7 forbids it where nobody approves.
4. **Confused deputy.** A jailed command plants a link or a hook that a host tool later follows. W8d and W14 stay before any prompt-skip.
5. **Windows build fragmentation.** MXC needs specific builds; managed machines may block parts. Status must say which and why, as `srtStatus` does.
6. **Third-party telemetry and native code.** MXC's Required telemetry and its native modules (if the SDK were used) cut against this fork's privacy stance; O7 and O8.
7. **Beta libraries.** srt is a "research preview" whose "APIs and configuration formats may evolve"; MXC has experimental backends and versioned contracts. Exact pins, our own interface, and a CI job that fails on a new version until the probes pass.
8. **Background processes.** A sandbox that kills children when the foreground exits breaks `waitForCompletion: false` (`runTerminalCommand.ts:634-641`) and CLI background jobs.

## 13. Do not claim

- "Sandboxed", "contained" or "isolated" for any command until our probes passed on this machine for this backend version and config hash. "Configured" is the most a status may say before that.
- That the sandbox covers file tools, hooks, MCP servers, LSP servers, the person's `!` commands, VS Code remote windows or JetBrains over SSH.
- "Network only to listed hosts" without the caveats: DNS and tunnels through an allowed host, every port of an allowed host when no port is given.
- That a command denylist is enforced because a sandbox is on.
- Any Windows sandbox before the MXC spike; and never that WSL distributions are a VM boundary from each other (they share one VM, `area-isolation-sandbox-gate.md` 4.4).
- That `sandbox-exec` is supported by Apple. It works, and it is deprecated.
- That IDGAF is "safe" because a sandbox is on. The chip shows both axes; the sandbox bounds what a command reaches, not what the model decides.
