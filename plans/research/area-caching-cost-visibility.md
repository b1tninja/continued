Section 5 proposes one sequence-level cache golden that ties them together, so a prefix move is accepted on a number and not on a belief.
3. **The cost of the tool list is small per request and large per rewrite.** The measured lists are 2.0k to 4.0k tokens built in and 100 to 125 tokens per MCP tool (Z0). On Claude 5.5-generation models a cache read costs 0.05 of base input (Opus 5.5, Sonnet 5.5) or 0.025 (Fable and Mythos 5.1, 5.2), so a cached 9k-token list costs 450 or less token-equivalents a request, while one activation that rewrites the prefix at 40k tokens costs about 48k. Deferral through our client-side `search_tools` therefore pays back only when it happens early or when the model is uncached (section 6.3). That makes **Z2 (shorten `multi_edit`, about 580 tokens of description) and Z6 (a CI budget) the only unconditional Z wins**, and Z3 (a stable `call_tool` indirection) the only way to make deferral safe late in a session.
4. **A real defect in the CLI tool search, from reading the code (not run):** the CLI keeps the activated tool names in module state (`extensions/cli/src/tools/searchTools.ts`, `activated`), the IDE derives them from the history (`activatedFromResults`). On a resumed CLI session the activated tools are gone from the list while the history still calls them, and nothing outside tests calls `resetToolSearchState`. It is off by default, so no user is hit today, but it must be fixed before Z4 (section 6.3, Z8).
5. **Track J is entirely unbuilt, and most of it is blocked on one function.** `contextBreakdown` (J0) has no code on main. A first slice that needs no UI (a `/context` table in the CLI and `/state.context`) is an M and unlocks J1, J2, J5, J6, TR6 and the measurement in Z4. After #690 and #696 the cost side is better placed: `calculateRequestCost` already prices OpenRouter from the downloaded list, so J-row cost lines should call it and not add a second price path.
6. **Anthropic's invalidation table (fetched today) matches what #630 now models,** with one gap: a `fast` speed setting and a web-search or citations toggle invalidate the tools cache and the miss detector does not carry them (C81, S, section 4.1).
7. **Recommended 2.16.0 set** (section 8): C65+C74 (one S, cap and reorder the environment block), C70 (S), Z2 (S), Z6 (S), C81 (S), J8 (S), C73 (S, offline), the sequence cache golden (S to M), J0 (M, CLI and serve only), Z8 (S, the CLI activation fix) and C55's decision. ### 4.2 Tool-definition cost and mitigations

Techniques, in the order of how safe they are for the prefix:

1. **Trim text** (no mechanism): shorten the few dominating descriptions. Anthropic's only authoring guidance is to put the keywords users use in descriptions (tool search page), so trimming must keep names, argument names and discriminating words. No controlled study of description length against accuracy was found (prior and `plans/tool-overhead.md` section 4 agree).
2. **Per-role subsets** (Track TR): Plan mode drops edit tools; already built for the CLI role table and Plan MCP filtering (#646). Each subset is a different prefix, so a mode switch rebuilds the cache (`prompt-segments.md`); the owner has deferred the one-list design to C69.
3. **Provider-native deferral**: Anthropic `defer_loading` and the tool search tool (not Converse), OpenAI `tool_search` (documentation reached only through mirrors in `tool-overhead.md`; unverified here). Cache-safe by construction.
4. **Client-side deferral** (`search_tools`, built): saves tokens, but an activation rewrites the prefix. Safe only early or uncached.
5. **Indirection** (`call_tool`, Z3): never changes the list; costs a hop and the model loses native argument validation and our per-tool permission display unless the dispatcher maps the call back to the real tool name. The permission engine must see the real name (TR rule, `tool-overhead.md` section 5, point 5).
6. **Tools as skills or CLIs**: Claude Code's own advice (costs page) is to prefer `gh`, `aws` and similar CLIs over MCP servers, which cost no per-tool listing, and to move workflow instructions from CLAUDE.md into skills. For us this is documentation, not code.

Claude Code freezes the tool list at the first request (prior, from its prompt-caching page, not refetched), which is C80.

### 4.3 Context and cost UI patterns

- **Claude Code**: `/context` category table, `/usage` Session block with a priced estimate and the cache line, a status-line script API, spinner output-token count, ranked recommendations with an apply key (costs page, today). The recommendation rows are what a person acts on; the table is what they audit.
- **Cline**: a progress bar of input and output tokens against the model's maximum, auto-compact near the limit with LLM summaries for some models only; the bar stays at 0 percent when a provider returns no usage (a user report). Sources: [Cline blog](https://cline.bot/blog/understanding-the-new-context-window-progress-bar-in-cline), [auto-compact docs](https://docs.cline.bot/features/auto-compact), search summaries only, unverified in detail. I found no per-task dollar figure in Cline.
- **Cursor**: a user thread says the context-fill circle was removed in the 2.x line and later moved into a tooltip on the chat title ([forum](https://forum.cursor.com/t/where-did-context-window-fill-indicator-go/156687)); a user report, not documentation. Lesson only: people notice and ask for a fill indicator, and a missing usage object makes any indicator lie.
- **Lesson for the fork**: the two failure modes seen elsewhere are an indicator that depends on a provider field that is sometimes absent (our `estimated` marker and "unknown, never zero" rule already cover it) and recommendations that cannot be applied. J2 should only list warnings that have an action.

**Proposal (task C82): a sequence cache golden.** One test, `core/llm/cacheSequence.vitest.ts` plus a golden `cacheSequenceGolden.json`, runs scripted sessions through the real request builders and the cache simulator and records numbers, not hashes:

- Scenario spec: the existing `CliScenarioSpec` (`extensions/cli/src/stream/segmentScenarios.ts`) gains an `events` list per turn: `mode-switch`, `mcp-connect`, `rule-match`, `agents-md-edit`, `taskitem-appears`, `resume-after <seconds>`, `compaction`, `model-switch`, `effort-change`. Each turn builds the real request with `buildChatRequestBody` (CLI) or `buildChatRequest` (IDE) and applies the event to the inputs.
- Simulation: extend `replayHistory` to take a request as `{ tools, system, messages }` rather than messages only, tokenise the three regions separately (the repo's `countTokens`, the same estimator as the segment manifests), and run the Anthropic breakpoint rules from `anthropicCache.ts` (after tools, after system, last two user messages) to decide where a prefix ends. A request reads the cache when the bytes before its last breakpoint equal an earlier request's and the gap is inside the lifetime (the simulator's existing assumption).
- Recorded per scenario: simulated read share of input tokens, write tokens, rebuild count, the first changed segment per rebuild (from the manifest), and a cost index at 5m and 1h (multiples of base input; for 5.5-generation reads use 0.05 as a second column because the read ratio differs by model, section 6.3).
- Gate: a PR that changes a builder must either keep the golden or regenerate it with `WRITE_GOLDEN=1` and say why; the PR description pastes the before and after of the rows it moved. A negative control (a timestamp in the system text) must fail the gate, as the existing prefix tests already do for single cases.
- Token savings use the same record: a `toolOverheadGolden.json` (Z6) of tokens per tool and per list, so a description trim shows as a number and is never claimed from character counts.
- Limits, stated so nobody over-reads it: the simulator ignores output tokens and assumes every request is fully cacheable; cache hit rates on a provider also depend on routing (Bedrock cross-region, OpenAI key routing), concurrency (entries exist only after the first response starts) and the 20-block lookback. The golden proves the prefix is byte-stable and prices the sequence; it does not predict a bill. Each moved row therefore also needs one live Bedrock or Anthropic run read from the ledger (C13 data) before the claim "N percent fewer rebuilds" is written into the roadmap.

### 6.1 Prefix hygiene: C65, C74, C66, C70, C67, C68, C55, C80, C69, C71

**Problem in user terms.** A coding session pays for its prefix on every request. Anything that changes the first part of the request (tools, system, the first user message) rebuilds the whole cache: the first request after it pays 1.25x (or 2x) on everything, and the person sees a slow, expensive turn with no explanation. Measured sources of change in the CLI today: a long `git status` pasted into the first user message; the `TaskList` tool appearing when the first plan item is saved; skills and subagents named inside tool descriptions; mode switches; MCP servers connecting late; an `AGENTS.md` edit mid-session.

**C65 + C74 (one change, S).** The environment block (`environmentContext.ts`) holds the date and the `git status --porcelain` text; the working directory and platform sit in the preamble of the system message (`preamble` segment, 113 tokens in the CLI scenario).

- Design: cap the git status in `getGitStatus` at N lines (recommended 40) and N characters (4,000), appending `... and K more changed files` when cut; keep the saved block on resume until compaction (today a resume rebuilds the block from the new run, so a resumed session's first request has a different first user message than the saved one, which is a rebuild of the entire history). C74 (move working directory and platform out of the preamble into the block, order only) goes in the same PR only if the golden shows no loss; otherwise separate.
- Config: none. A cap is a fixed constant with a one-line mention in the docs; `CONTINUE_ENV_STATUS_LINES` is not worth a key.
- Rejected: dropping git status entirely (the model uses it, and the C62 plan wants the block, not its absence); computing it lazily per request (that is the bug the block was built to avoid).
- Risk: the model loses the tail of a very large status; the marker line says how many were cut and `git status` is one tool call away.
- Test: a fixture repository with 300 changed files gives a block under the cap; two consecutive requests are byte-identical; a resume reuses the saved block (new `prefixStability`-style case); `requestGolden` for the CLI scenarios is unchanged for the small-status case.
- Acceptance: block bytes bounded; resume keeps the first message identical; golden unchanged for a clean tree.

**C70 (S).** `getAllAvailableTools` removes `TaskList` until `getSessionTaskPlan()?.items.length` is nonzero or a loop item runs. The first plan item therefore changes the tool list mid-session (`tool-list-event` offender in the manifests). The roadmap row says the break-even is "an event probability over about 8 percent": a tool of about 450 tokens (the IDE agent-with-task-list set is 3,156 against 2,701, so about 455 tokens, Z0) read at 0.1 costs about 45 token-equivalents a request, while the event rewrites the prefix at (1.25 - 0.1) times S. Equal when the per-session event probability times 1.15 S equals 45 times the remaining requests; for S = 30,000 and 20 requests that is a 2.6 percent event probability, so offering it always wins above roughly 3 percent. Recommend: offer `TaskList` from the first agent request in Agent mode (Plan mode keeps it out, per the existing research that a model offered both resent the list). Keep the loop item swap, which is a different list anyway.

- Rejected: a deferred `TaskList` (a deferred tool in a client list is a rewrite when it activates).
- Test: update the BASELINE `tool-list-event` assertion in the CLI manifest test; the sequence golden shows a rebuild fewer in the `taskitem-appears` scenario.
- Risk: models that over-call `TaskList` when it is visible (Q-track and "task_list resent up to 107 times" findings, J plan section 1); the repeat guard exists. Measure with the Nova and Qwen scenarios before shipping on by default; ship behind `CONTINUE_TASKLIST_ALWAYS` for one release if the bench has not been run.
- Acceptance: no tool-list change at the first plan item; plan-mode tool list unchanged; bench tool-call counts not worse on the three recorded scenarios.

**C66 (S).** Freeze the registry text. The `Skills` tool description lists every skill; the `Subagent` tool description lists the agents (`subagent.ts`, `skills.ts`). A skill added or a model-service change rewrites tools, the first region. Design: build both descriptions once per process at first request and reuse (like the environment block), and move the lists to the first user message when TR17 lands (`TR17`, K18 slice 2). Test: a registry change mid-session leaves the request bytes equal; the segment dump shows `registry-in-tool-description` stable. Risk: a newly added skill is invisible until restart; say so in the `/skills` output. Size S.

**C67 and C68 (M each, defer one release).** C67 puts the IDE compaction summary at the head of the history instead of the system message; C68 appends a newly matched file-scoped rule to the next user message once instead of editing the system message. Both change the bytes every user's model reads and need an adherence measurement (RQ34 harness, per the row). They gain only in sessions that compact or match scoped rules; the frequency is unmeasured until C73. Recommend: do C73 first; schedule C67 and C68 on its result. Test plan: cache golden scenarios `rule-match` and `compaction`; RQ34 for the rule-adherence side.

**C55 (decision, then S).** Rules and `AGENTS.md` read once per session and rebuilt on `/reload`, plus the date fixed at process start with a "date changed" reminder appended to the next user message after midnight. The default in Open decisions is already "read once, rebuild on `/reload`" (recommended there). Cost of the alternative: an agent that edits its own instructions file rebuilds the prefix on the next request, which is correct behaviour for the model and expensive for the person. Design: the fingerprint in `SystemMessageService` is kept for detecting a change; on a change, do not rebuild, post a one-line notice ("`AGENTS.md` changed; applies after `/reload` or a new session") and record it in the audit trail. A `/reload` command rebuilds and notes the cache cost. Date: append `Date changed to YYYY-MM-DD.` as a tail line. Size S after the decision.

**C80 (S to M, owner decision).** Freeze the CLI tool list at the first request. Design: `getAllAvailableTools` computes the list once per conversation (keyed by mode, loop-item state and the role filter, since those are intentional list changes) and keeps it; MCP servers that connect later, or tools a server adds, are not added. A late server is announced in the transcript ("server X connected; its tools are available after `/reload` or deferred through SearchTools"). Interaction with Z8: with tool search on, late tools go into the deferred index without touching the list. Rejected: refreshing per request (the status quo). Risk: a person adds a server and the model cannot call it until reload, which is surprising; the notice must be loud. The Open decisions recommendation is "yes". Size M because the mode-keyed freeze has several event sources.

**C69 (M, measure first).** One tool list and one system text across Plan and Act, the mode as an append-only message. Downside: Plan mode currently withholds edit tools by not offering them; with a single list a plan-mode model could call an edit tool and the role gate (`roleGate.ts`) must refuse it, so plan-mode violations are measured first. Run the C62 manifests with a `shared-list` arm and the RQ34-style adherence harness. Do not ship without a measurement. Rejected: shipping behind a flag unmeasured. Size M, 2.17+.

**C71 (M, defer).** Batch pruning in `compileChatMessages`: drop old messages in steps, with the cold-cache clock (VA3). The IDE already has ageing (VA1 and VA2, off by default); C71 is only valuable once VA3 gives the clock. Defer with VA3.

### 6.2 Cache controls and per-request lifetimes: C29, C46, C51, C72, C8, C44

**Subagent and compaction lifetime (C29 rest, C46; S plus a decision).** Claude Code splits lifetime into main and everything else (`promptCacheTtl`, `subagentPromptCacheTtl`, from the prior note's reading of its prompt-caching page). Ours: the title request is excluded (#264), compaction deliberately reads the conversation's cache (C25), subagents have their own adapter and their own Auto counter. Design: a `cacheBehavior.subagentTtl` key (`5m | 1h | auto | inherit`, recommended default `5m`), read where the subagent builds its adapter; subagents that run longer than 5 minutes between requests are rare, and a 1-hour write costs 2x for entries that are read a few times. Test: a subagent request after four conversation requests (the Auto threshold) does not send `1h`. Owner decision: default `5m` (recommended, pending owner). Size S.

**Fan-out hold (C51, C72; M).** Anthropic and AWS both say an entry is usable only after the first response starts, so N parallel requests on one prefix are N writes. Design: a small `PrefixGate` in the Loop driver and the subagent runner (core, because the IDE spawns subagents too): the first request with a given prefix hash (the segment manifest's static and session hashes) is sent alone; the gate opens when the first stream emits its first token or after 5 seconds, whichever is first (Claude Code's value per prior, unverified here), then the rest are released. State is in memory, keyed by prefix hash, expiring with the cache lifetime. Measurement: the cache golden gets a `fan-out 4` scenario whose simulated cost shows writes 4x without the gate and 1x with; one live run on Bedrock with four parallel subagents reads the ledger (C35's method). Risk: adds up to 5 seconds latency to the second to Nth worker; the gate is skipped when the cache is cold for all (first request of a conversation) or off. Rejected: sleeping a fixed delay; a global lock (serialises distinct prefixes). Dependency: C50 (pinned fork point, built). Size M; schedule after the sequence golden so the benefit is measured. Not for 2.16.0 unless Loop parallel waves (Track N) ship in that release (they are 2.6-era design, state unverified here).

**C8, C44, C26 (L, blocked).** Appending a `system` message so a mode switch does not edit the cached prefix works on the newest Anthropic models; Converse accepts it only before an assistant turn (live, 2026-11-04). Anthropic's table (today) says mid-conversation system messages leave system and message caches intact on supported models. The unanswered question is whether a Converse request with `system` in the middle keeps the prefix alive and where it may sit. Design of the check, not the feature: one script (`bench/probes`) with three requests on Sonnet 5.5 or Haiku 5.5 over Converse, placement before and after an assistant turn, reading `cacheReadInputTokens`. Cost: well under a dollar at 512-token minimums. Result decides C8, C44 and C69. Size S for the probe; the feature is L and stays blocked.

### 6.3 The cost of the tool list: Z2, Z3, Z4, Z5, Z6, Z8

**Cost model (numbers, with their sources).** Let T be the tool-list tokens, S the tokens after the tools at the moment of activation, a the activations per session, n the requests after an activation, r the read ratio, w the write ratio.

- Carrying a cached list costs T x r per request. Deferral to a core list C saves (T - C - k) x r per request, k the tokens of activated tools.
- One activation rewrites everything after the tools: S + C + k tokens re-written, extra cost (S + C + k) x (w - r).
- Break-even requests after an activation: n* = (S + C + k) x (w - r) / ((T - C - k) x r).

Using the repo's Z0 numbers (T = 8,842 agent with 60 MCP tools, C = 2,701 built in, k = 250) and Anthropic's ratios today (w = 1.25):

| Model class                                 | r                                       | S = 4,000 (early)                              | S = 40,000 (late)                     |
| ------------------------------------------- | --------------------------------------- | ---------------------------------------------- | ------------------------------------- |
| Most Claude (Sonnet 5, Opus 4.x, Haiku 4.5) | 0.1                                     | (6,951 x 1.15) / (5,891 x 0.1) = 13.6 requests | (42,951 x 1.15) / 589 = 83.9 requests |
| Opus 5.5, Sonnet 5.5                        | 0.05                                    | (6,951 x 1.2) / (5,891 x 0.05) = 28.3 requests | (42,951 x 1.2) / 295 = 175 requests   |
| Fable and Mythos 5.1 and 5.2                | 0.025                                   | about 57 requests                              | about 350 requests                    |
| No cache (local servers)                    | n/a: T is paid on every request in time | deferral wins from the first request           | deferral wins from the first request  |

(Arithmetic on repo measurements and the vendor ratios; reasoning costs and output tokens are ignored; not a live run. The first row reproduces prior's 14 and 84.) Two consequences. First, **the cheaper reads get, the worse late client-side deferral looks**, so on the 5.5 generation the default `toolSearch` budget of 4,000 tokens (2 percent of 200K) is too eager for cached models and about right for uncached ones. Second, deferral also buys selection accuracy, which this table does not price; Z4 is where that is measured.

**Z2 (S): shorter `multi_edit`.** The description is about 580 tokens of 776 for the tool (Z0); the other built-ins average near 190. Design: cut to the facts the model cannot guess: parameter meanings, "edits apply in order and atomically", "old_string must match exactly", "read the file first", and drop the repeated warnings. A target near 150 tokens is a quarter of today's text. Rejected: removing the tool (it is the edit tool several families are tuned to); a per-family profile (Q6) as the mechanism (a profile is how to ship a family-specific text later, not how to remove duplicated sentences). Risk: edit-failure rate rises. Test: the tool-token golden (Z6) records before and after; the edit scenarios of the bench (I-track) on two families, `n` of at least 3, compare invalid-call and edit-failure counts; the description is a byte change, so every user's prefix rebuilds once at the upgrade, which should be noted in the release notes. Acceptance: tool tokens drop by at least 400 in both the IDE and CLI lists (the CLI `MultiEdit` is 846), bench not worse. Do the same to `code_navigation` (388) and `AskQuestion` (330) in a second pass only if the first holds.

**Z3 (M): `call_tool`.** A stable list: built-ins plus `SearchTools` plus one `CallTool({name, arguments})`. ### 6.6 Track J

**Principle.** One pure function (`contextBreakdown`) in core, no I/O, safe for the webview (the same constraint #696 put on `catalogPricing.ts`), consumed by three surfaces. Everything else is a view of its output.

**J0 (M): `contextBreakdown`, `/context`, `/state.context`.**

- Module: `core/llm/contextBreakdown.ts`, next to `promptSegments.ts`. It does not recompute segmentation: it takes the segment manifest (`describeCliRequest` and the IDE `describeChatRequest` already produce `PromptSegment[]` with id, region, stability, tokens, hash, `exposedTo`) plus the compiled message array and the tool list, and adds what the manifest lacks: tools by group and by MCP server with per-tool tokens, messages by role and by tool (largest results), calls per tool this session, and the cache section.
- Data shape (versioned, names and numbers only):

  ```ts
  interface ContextBreakdown {
    version: 1;
    model: { provider: string; model: string; windowTokens?: number };
    sections: Array<{
      id: "system" | "tools" | "environment" | "history" | "tail";
      tokens: number;
      parts: Array<{
        id: string;
        label: string;
        tokens: number;
        callsThisSession?: number;
      }>;
    }>;
    largest: Array<{ id: string; tokens: number }>; // top five
    cache: {
      prefixTokens: number; // same as previous request
      changedTokens: number;
      firstChanged?: string; // segment id
      cause?: string; // from keyChanges / the CLI equivalent
      warm?: boolean;
      lifetime?: "5m" | "1h";
    };
    totals: {
      input: number;
      output: number;
      cacheRead: number;
      cacheWrite: number;
      processedInput: number;
    };
    estimated: boolean; // true when any token count is a local estimate
    cost?: {
      usd: number;
      source: "list" | "openrouter catalogue" | "user price";
      estimated: boolean;
    };
  }
  ```

  The cost block calls `calculateRequestCost` (and with #696 its `estimate` marker) and never a new price path; "unknown" stays unknown.

- Token counts: the repo's `countTokens` unless J9 supplies an exact count; the `estimated` flag says which. Apply the per-family factor for Claude 4.7+ (prior M7: about 30 percent more tokens) only inside the estimate and say so in the output.
- CLI: `/context` prints the table (sections, five largest, the cache line) with names only, never content; `/state.context` returns the object (the serve allow-list rule: names and counts, no values, canary test as for the agents map). IDE panel is J1.

- Alternatives rejected: computing the breakdown in the webview from redux state (diverges from the CLI and misses what `buildChatRequest` adds); a provider `count_tokens` call per section (J9, a network call per refresh, owner decision).
- Test: sections sum to totals (property test over the existing segment scenarios); each manifest scenario of `promptSegments.test.ts` and `describeChatRequest.test.ts` yields a breakdown; `/context` rendering snapshot; `/state.context` shape and a canary-string test that no message text appears.

## 7. Risks and cross-cutting dependencies

- **Token estimates:** every local count is an estimate, worse on Claude 4.7+; the golden's absolute numbers are conservative proxies. State this wherever a number is shown.
- **Read-price drift:** the break-even moves with each model generation (0.1, 0.05, 0.025). The tool-search budget should be a function of the model's read ratio from `PROMPT_CACHE_RULES`, not a constant (recommend adding `readRatio` to the table; S, part of Z1's follow-up).

- **Bedrock Converse limits dominate** the fork's Claude path: no `defer_loading`, no top-level automatic caching surface used, system-in-the-middle only before an assistant turn. Anything that depends on those is Anthropic-direct only.
