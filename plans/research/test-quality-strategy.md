# Research: test and quality strategy across the product

Date of reading: 2026-11-12 (local; GitHub timestamps are 2026-11-13 UTC). Scope: every test suite, harness and check in the repository, what CI runs of it, on which operating system, and what a release is gated on. Method: a fresh clone of `b1tninja/continuous` at `origin/main` 63e6e122 (re-checked at c05057f0); every file under `.github/workflows/` and `.github/actions/`; every `package.json` script and test-runner config; the tests and product code named in the ledger; GitHub REST for `b1tninja/continuous` (read-only: runs, jobs, job logs, secret names; nothing was cancelled or re-run). No test suite was run for this note. Two facts were probed with one-line `node -e` calls on a Windows 11 dev machine (Node 25.9.0) and are marked **probed**. Statements marked **probable** were reached by reading and not by running. No API key was used.

This note does not repeat the CI throughput design (`area-ci-privacy-release.md` section 3, draft PR #751) or the sandbox gate design (`area-isolation-sandbox-gate.md` section 5). It builds on both and says where it depends on them.

## 0. Summary

Findings, in order of consequence:

1. **A nightly Windows and macOS run exists, has been red for two nights, and nobody is told.** `CLI PR Checks` runs the CLI suite on `ubuntu`, `windows` and `macos` with Node 22 and 24 every night. The runs of 2026-11-11 and 2026-11-12 failed on both Windows legs, and the 2026-11-12 run also failed on both macOS legs. 4 of the last 10 nightly CLI runs and 6 of the last 10 nightly `PR Checks` runs failed. The failing tests are the ones the dev machines report (`projectEnv`, `loopDriver`) plus four the dev machines do not see. There is no report job, Issues are off, and no agent brief reads the nightly result. Section 3.
2. **The repository has no Actions secrets, so no key-gated test has run in CI.** `GET actions/secrets` returns an empty list (the token could list them; whether an environment-level secret exists was not checked). `ANTHROPIC_API_KEY` is empty in the `smoke-api` job log, which runs four test files, skips all four and reports green. The nightly run also sets `IGNORE_API_KEY_TESTS=true` on purpose, because `check-llm-changes` treats "no base branch" as "nothing changed". The AI SDK break (#389, fixed by #741) sat on `main` for about 3.2 days (2026-11-09 21:03Z to 2026-11-13 00:58Z) for that reason. Section 4.3.
3. **`core`, `gui`, `packages/*` and the VS Code tests have never run on Windows or macOS in CI.** Only the CLI suite does, and only at night. `core/tools/permissions/corpus/powershellOracle.vitest.ts` says "Windows CI is the home of it"; there is no Windows CI for `core`, so the differential test of the PowerShell command scanner, a security control, runs only on a developer's machine. Section 4.2.
4. **Windows CI and a Windows dev machine fail different tests.** The hosted runner's temp directory is `C:\Users\RUNNER~1\...` (an 8.3 short name) and the runner is elevated. A dev machine has a long temp path and no symlink privilege. Three nightly failures come from the short name; one dev-machine failure comes from the missing privilege. Neither environment reproduces the other's failures. Section 3.
5. **Formatting is the largest single cause of a red PR run.** Of the last 100 completed `PR Checks` runs, 23 failed, and `prettier-check` failed in 12 of those 23. The cause is that formatter output depends on what happens to be installed. Section 3, F13.
6. **Seven groups of tests run in no workflow**: `binary/test` (3 files), `bench/tier0` (6), `bench/lab` (8 of 9), `bench/research` (3), `bench/screenshots/test` (3), three `scripts/ci` tests, and the axe run. The 2.14.0 release notes call the axe run "an axe-core gate"; it gates nothing. Section 2.4.
7. **The release workflow runs no test.** `main.yaml` goes `check-version` to `build` and `cli` to `release` and the publish jobs. Nothing requires a green suite on the release commit, and the sandbox gate (SB1) is a rule that no job reads.
8. **The JetBrains message list has drifted from the TypeScript one and no test compares them.** 20 webview-to-core message types exist in `core/protocol/passThrough.ts` and not in `MessageTypes.kt` (all of `policy/*`, `audit/*`, `models/*`), and 7 exist only in Kotlin. Section 4.4.
9. **There is no property test, no mutation test, no coverage figure and no saved-state fixture from an earlier release.** `fast-check` and Stryker are in no `package.json`. Coverage tooling exists in `gui` and `core` scripts and is collected by no job.
10. `TESTING.md` is a checklist for an old upstream pull request ("PR #2 Testing Checklist"). There is no guide to running the suites.

Do first, in this order (all small): fix the six tests that make the nightly red (QA2), make the nightly report (QA1), stop `npm test` from calling a paid API on a machine that has a key (QA4), then add the Windows leg (QA6).

### 2.5 Coverage, mutation and property tooling

- Coverage: `gui` has `@vitest/coverage-v8` and a `test:coverage` script; `core` has `jest --coverage` (jest files only) with `collectCoverage` commented out; the CLI config names coverage reporters. No job collects coverage and no figure is recorded anywhere.
- Mutation testing: none.
- Property-based testing: none. `fast-check` is in no `package.json`. Three test files mention fuzzing (`streamDiff`, `recoverMatch`, `FileIndexService`); none uses a generator library.
- Retries: only `vitest.smoke-api.config.ts` sets `retry: 2`. No other suite retries. No completed run among the last 100 of either workflow had `run_attempt > 1`, so reruns are not masking failures today.
- Timeouts: `core` vitest and `gui` use the vitest default of 5 s per test; `packages/fetch` sets `timeout: 10000`, which is not a vitest option name (the others use `testTimeout`), so its tests also run at 5 s (**probable**; the config reference lists `testTimeout`).
- `packages/openai-adapters` runs `vitest` without `run`: a watch in a local terminal, a single pass only where vitest detects CI.

### 5.2 Flaky-test policy

This refines CO23 (`product-review-controls-and-roadmap.md` section 4.8: `scripts/ci/flaky.json`, expiry 14 days, at most 3 entries, nothing under `core/tools/permissions/`) and keeps its numbers.

- **Definition.** A test is flaky when it failed and passed on the same commit, on the same platform, without a change to its inputs. A test that fails every time on one platform (F1 to F10) is broken, not flaky, and is fixed or platform-skipped with a ledger entry; it does not go to quarantine.
- **Mark.** One vitest tag, `quarantine` (vitest 4.1 and later have declared tags with per-tag options, section 9; the repository is on 5.x). The tag sets `retry: 2`. For the jest files and the e2e legs the list in `flaky.json` is the mark.
- **Record.** `scripts/ci/flaky.json`: test id, file, first seen (run URL), platform, owner (a ROADMAP row id), expiry (first seen plus 14 days), last three outcomes. A check fails the static job when an entry is past expiry, when there are more than 3 entries, when an entry is under `core/tools/permissions/`, `core/util/secretScan/` or `packages/terminal-security/`, or when a test carries the tag without an entry.
- **Gating.** T1 runs with `--tags-filter` excluding `quarantine`. T3 runs the quarantined tests alone, 20 times each, and writes pass counts into the job summary: that is the evidence for removing an entry (20 of 20 on two consecutive nights) or for the diagnosis.
- **Retry rules.** No blanket retry in any suite. Retries exist in three places only: quarantined tests (2), live tests against a real API (2, with a delay; a rate limit is not a product failure), and the e2e legs (1 for the whole leg, recorded). A whole-job rerun is not a fix: the `track-rerun` action already notices `run_attempt > 1`; it gains one line that appends to the metrics file (section 5.8).
- **Timing assertions.** A wall-clock assertion is not allowed in T1. Tag it `perf`; it runs in T3 where a failure is a data point (F11).
- **Owner and SLA.** The owner of a quarantined test is the row that created the entry. Seven days to a diagnosis written in the entry, 14 to a fix or a deletion with the reason. When the list is full, the next flaky test blocks merges until an entry leaves: the cap is the forcing function.
- **External practice.** Fowler: put a non-deterministic test in quarantine, fix it quickly, cap the quarantine by count ("e.g. only allow 8") or by time ("no longer than a week"). Google: tests begin to lose value as flakiness approaches 1%. Both in section 9. Three entries and 14 days are stricter on count and looser on time, which suits a repository where agents do most of the fixing.

### 5.3 Golden-file governance

1. **One command.** `node scripts/ci/goldens.mjs --check` runs the tests that guard every golden in `scripts/ci/goldens.json` (the table in section 2.4 as data: file, package, test, whether machine facts are involved). `--write` regenerates all of them in a fixed order and prints a per-segment diff (`preamble`, `tools.builtin@agent`, `turn.act@full`, ...) from the segment manifests, not just hashes. `WRITE_GOLDEN` stops being read from the ambient environment: the script sets a variable that includes the commit, and the tests ignore anything else.
2. **One bot check, in the static job.** When a pull request's diff touches a golden, the check requires a line `Golden-Change: <segment>[, <segment>]` in the PR description (or `all`), recomputes which segments changed between the base and the head from the two golden files, and fails when the sets differ. A change to prompt text that moves `tools.builtin@agent` cannot ride along in a PR that declared only `preamble`. A PR that touches prompt-building code and no golden passes only because the golden tests pass.
3. **Portable goldens.** A golden may contain no machine fact after normalisation. The check is the nightly matrix: the same hashes on three operating systems (F9 is the first failure of this rule).
4. **Serial merges.** The four request and segment goldens join the hot-file list of CI3; `merge-ready.mjs --combine` already detects two open PRs touching the same file.
5. **Baselines shrink only.** `axe-baseline.json` may lose entries or lower counts in any PR; a PR that raises a count needs `Golden-Change: axe` and a reason.

### 5.5 Nightly key-gated run

- **Workflow.** `live-nightly.yml`, `schedule` and `workflow_dispatch` only. Never `pull_request`: fork and Dependabot runs get no secrets by design (section 9), and a PR must not be able to spend the owner's money.
- **Secrets.** In a GitHub environment `live-keys`, not at repository level, so only this workflow's job reads them and the environment can require the owner's approval for a dispatch. Minimum set: one Anthropic key and one OpenAI-compatible key, each created for CI with the lowest spend limit the provider allows. Bedrock through OIDC to a role limited to `InvokeModel` on two model ids, if the owner wants Bedrock covered (question 3).
- **What runs.** `core/llm/llm.test.ts` with `IGNORE_API_KEY_TESTS=false` for the providers that have a key; `openai-adapters` `main.test.ts`, `vercel-sdk.test.ts`, `cli-tools.test.ts`; the CLI `smoke-api` suite (with a current, cheap model id passed in `SMOKE_MODEL`); one cached-prefix scenario from `anthropic-caching.live.test.ts`. Not the evaluation suites: they measure quality, cost more and belong to the bench.
- **Budget.** `fileParallelism: false`, `retry: { count: 2, delay: 5000 }`, the smallest model of each provider, `max_tokens` capped. A pre-flight step estimates the request count from the test list and stops above a fixed number. Expected cost is cents per night; the provider-side limit is the real cap.
- **All-skipped is a failure.** The job reads the vitest JSON report and fails when fewer tests ran than `scripts/ci/live-expected.json` says for the keys that are present. This is the rule the `smoke-api` job lacks.

### 5.6 Release-gate composition
