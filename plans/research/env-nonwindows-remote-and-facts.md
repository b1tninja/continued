# What we tell the agent about its environment: macOS, Linux, other shells, remote and non-local targets, and the cheap facts

Research report, 2026-11-12. Code read on `origin/main` at `ee644eb` (merge of #759). `plans/ROADMAP.md` is not edited: section 9 holds the exact row text. Releases use even minors: 2.16.0 is being cut, so "2.18.0 candidate" means the release after it. Scope: the non-Windows and non-local environments and the other environment facts. The Windows and WSL window is another report; the shell decision for permissions is `plans/research/shell-awareness.md` (SH1 to SH10) and is not repeated here.

Convention: "read" means read in this repository (file and line). "Measured" means run on the review machine (Windows 11; WSL 2 with an Arch Linux distribution: `/bin/sh` is a symlink to bash, GNU sed 4.9, `LANG=en_US.UTF-8`, kernel `6.6.87.2-microsoft-standard-WSL2`; no macOS, no Alpine, no fish, no `pwsh`). "Cited" means a primary page read on 2026-11-12 with its URL. "Unverified" means from memory or a secondary source and is marked so; nothing marked unverified should carry a decision until it is checked on the real platform.

## 1. Summary: the ten findings

1. **The agent is told four environment facts today, and two of them can be wrong in a remote window.** The CLI system message states the working directory, whether it is a git repository and `process.platform` (`extensions/cli/src/systemMessage.ts:45-50`). The IDE terminal tool description says "Choose terminal commands and scripts optimized for ${os.platform()} and ${os.arch()} and shell ${getPreferredShell()}" (`core/tools/definitions/runTerminalCommand.ts:26`), computed once in the core process from `os.platform()` and `process.env.SHELL`. Core runs in the extension host of the editor (`extensions/vscode/src/extension/VsCodeExtension.ts:270-286`, in-process messenger), and the extension declares `"extensionKind": ["ui", "workspace"]` (`extensions/vscode/package.json:10-13`). VS Code documents that UI extensions "always run on the user's local machine" and that a workspace extension runs where the workspace lives; for an extension that can be either it says VS Code "will attempt to choose the optimal one" (cited, section 7). So in a Remote-SSH window it is **unverified which host core runs on**, and when it is the local one the tool description names the laptop's OS and shell for a command that is typed into the remote's terminal. This is the single largest "wrong claim is worse than silence" risk in this area.
2. **The IDE has no shell or platform statement outside that tool description, and the date and git state are CLI-only.** The CLI puts the date and `git status --porcelain` in a `<context name="environment">` block in the first user message, once per process (`extensions/cli/src/environmentContext.ts:42-66`). The IDE path has no equivalent in `core/llm` (grep for "Platform", "Operating system" found only the Auto reviewer's `Operating system:` line, `core/tools/permissions/auto/prompt.ts:175`, and the `@os` context provider, `core/context/providers/OSContextProvider.ts`).
3. **`resolveShell()` already names every shell family, and handles non-POSIX login shells by accident of flags.** Elsewhere than Windows it runs `$SHELL -l -c <command>` (`core/util/shell.ts:196-206`, ends at the `executable = env.SHELL || "/bin/bash"` branch). fish, nushell, xonsh and ksh accept `-l -c` (unverified except by documentation of each shell); `pwsh` does not take `-l`/`-c` in that order on every version (unverified: the `about_pwsh` page read for the shell-awareness report lists `-Command` and `-File` but this round did not find `-Login`; EV47). `shellKindOf` returns `unknown` for all of them (`core/util/shell.ts:38-58`), which is the right answer for permissions and means the model is told "Runs in fish as a login shell on linux" (`extensions/cli/src/tools/runTerminalCommand.ts:96-106`) with no dialect hint.
4. **On macOS and Linux a command is read by whatever `$SHELL` is, but a non-interactive `sh` is something else.** Hooks run `/bin/sh -c` (`extensions/cli/src/hooks/hookRunner.ts:118-123`, from the shell-awareness report). On Debian and Ubuntu `/bin/sh` is dash, on macOS it is bash 3.2 in POSIX mode (unverified; Apple's documentation is the source to check), on the review machine's Arch it is bash (measured). A hook written with `[[ ]]` works on one and fails on the others, and nothing tells the person.
5. **The BSD-versus-GNU userland differences are the most common avoidable failures on macOS, and no text in the product mentions them.** `sed -i ''` against `sed -i`, `readlink -f`, `grep -P`, `xargs -r`, `date -d`, `stat -c`: section 3 lists them with their status. A one-line "this is macOS: the userland is BSD, not GNU" in the tool description costs about 15 tokens and is static per session.
6. **Containers are the case where we know the most and say the least.** `containerArgs` starts every command with `--network none`, `--read-only`, a 256 MB `/tmp` tmpfs, `--cap-drop ALL`, `HOME=/tmp`, 2 GB and 512 processes (`core/util/containerArgs.ts:38-75`), and `describeShell` says only "use bash syntax and Linux paths; the command starts in the workspace folder and cannot see anything else" (`extensions/cli/src/tools/runTerminalCommand.ts:86-88`). A model that does not know there is no network will run `npm install` and `pip install` and lose the call. Three words fix that.
7. **Remote windows are unknown by construction.** `getIdeInfo` returns `remoteName: vscode.env.remoteName || "local"` (`extensions/vscode/src/VsCodeIde.ts:214`); JetBrains guesses `ssh` from the `SSH_CLIENT` or `SSH_TTY` variables of the IDE process (`IntelliJIde.kt:150-153`), which is true for an IDE started from an SSH session and says nothing about JetBrains Gateway. The terminal tool types into the active terminal (`VsCodeIde.ts:344-364`) with no output capture, so even whether a command ran is unknown (shell-awareness report, SH2). What the editor does expose: `vscode.env.remoteName` (`undefined` locally; examples `wsl` and `ssh-remote`), `vscode.env.shell` ("the detected default shell for the extension host") and `uiKind` (cited, section 7). `vscode.env.shell` answers for the extension host, not necessarily for the remote terminal, so it is only a hint until we know where core runs (finding 1).
8. **Most "environment facts" a model wants are cheap to state and only a few are volatile.** Static for the session: platform, architecture, shell family, working directory, workspace roots, locale, whether a TTY is attached, the output cap and timeout. Volatile: the date, the git state, which tools are installed (changes when the agent installs one), network reachability. Only the volatile ones belong after the cache checkpoint, where `environmentContextBlock()` already puts the date and git status (`environmentContext.ts:42-66`). Section 6 gives the table.
9. **Permission mode is told to the model only through results.** The turn text "names the turn, never the mode that launched it or the surface" (`core/llm/prompts/turns.ts:3-5`) and the refusal text says "The result says who stopped it and what to do next". The levels (manual, idgaf and the rest, `core/tools/permissions/approval.ts:20-27`) are never in the prompt. Codex, by contrast, reports its approval policy and sandbox to the model (section 7, a secondary source, unverified). Recommended: keep the mode out of the prompt (it changes mid-session and it is the person's setting), but state the _consequence that is static_: "commands run without network" in a container, "you are in a read-only sandbox" when one is on.
10. **Detection is cheap where it reads the process and expensive where it asks a tool.** `os`, `process.env`, `/proc/version` and a PATH search cost microseconds; `git status` and `git rev-parse` cost a process (the CLI runs two, synchronously, on first use, `environmentContext.ts:12-34`, with no timeout and no size cap on a huge repository: `git status --porcelain` output is put into the prompt whole); version probes (`node --version`, `python3 --version`, `rg --version`) cost a process each and 20 to 200 ms apiece on a cold machine (unverified, a typical figure, to be measured by EV55). The existing PATH search (`core/tools/permissions/missingBinaryGate.ts`, `onPath`) answers "is this program present" without starting anything and is already cached for 60 seconds.

## 3. macOS

Everything in this section is **unverified on a Mac** (none was available); each item names the primary source to check. Sources: Apple's `man` pages for the BSD tools (<https://ss64.com/mac/> is a secondary index; the authoritative pages are the macOS `man` pages), the Homebrew documentation (<https://docs.brew.sh/Installation>), and Apple's "Use zsh as the default shell" support note.

**Shell.** zsh has been the default login shell for new accounts since macOS Catalina (10.15); accounts created earlier keep bash. `/bin/bash` is bash 3.2 (GPLv2, never upgraded) and `/bin/sh` is a bash-compatible shell. `$SHELL` is therefore usually `/bin/zsh`; a Homebrew bash is `/opt/homebrew/bin/bash` on Apple silicon and `/usr/local/bin/bash` on Intel. The code already handles this: `shellKindOf("/bin/zsh")` is `zsh`, and the default is `/bin/zsh` for the tool description's `getPreferredShell()` (`core/tools/definitions/runTerminalCommand.ts:19-21`) but `/bin/bash` for `resolveShell()` when `$SHELL` is unset (`core/util/shell.ts:196`): the two disagree on macOS with no `$SHELL`, a GUI-launched editor on some setups. Harmless today (the tool text is advisory) and a one-line fix (EV48).

**BSD versus GNU.** The user-visible differences an agent trips over:

| Command                                                                                                                                | GNU (Linux)                   | BSD (macOS)                                                                                       | Failure                                                            | Status                                                 |
| -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------ |
| `sed -i`                                                                                                                               | `sed -i 's/a/b/' f`           | `sed -i '' 's/a/b/' f` (the suffix argument is required)                                          | `sed: 1: "f": invalid command code f` or a backup file named `f-e` | Unverified (well known); check with `man sed` on a Mac |
| `readlink -f`                                                                                                                          | resolves symlinks recursively | not supported by the system `readlink` before macOS 12.3; `realpath` exists since 13 (unverified) | `readlink: illegal option -- f`                                    | Unverified                                             |
| `grep -P`                                                                                                                              | Perl regex                    | not in the system `grep` (BSD grep has `-E` and `-e` only)                                        | `grep: invalid option -- P`                                        | Unverified                                             |
| `xargs -r`                                                                                                                             | do not run on empty input     | BSD `xargs` skips on empty input by default and rejects `-r` in older versions                    | `xargs: illegal option -- r`                                       | Unverified                                             |
| `date -d '1 day ago'`                                                                                                                  | GNU date parses free text     | `date -v-1d`; `-d` sets the kernel's DST flag, not a date                                         | `date: illegal option` or a wrong date                             | Unverified                                             |
| `stat -c %s f`                                                                                                                         | format with `-c`              | `stat -f %z f`                                                                                    | `stat: illegal option -- c`                                        | Unverified                                             |
| `find -printf`, `-regextype`, `ls --color`, `cp --parents`, `mktemp -d` without a template, `head -n -1`, `sort -V`, `tar --wildcards` | GNU extensions                | absent or different                                                                               | `illegal option`                                                   | Unverified                                             |
| `echo -e`, `echo -n` in `sh`                                                                                                           | bash builtin accepts both     | `/bin/sh` `echo` prints the `-e`                                                                  | A literal `-e` in output                                           | Unverified                                             |

Mitigation costs: a Homebrew `coreutils`/`gnu-sed` install puts GNU tools under `gnubin` paths only when the person adds them, so we cannot assume them. The cheap, true statement is the **userland family** (`bsd` on darwin, `gnu` on glibc Linux, `busybox` on Alpine) and the advice to prefer portable forms. Detection: `darwin` is the whole answer (`process.platform === "darwin"`); a Linux machine is GNU unless `/etc/alpine-release` exists or `sed --version` mentions BusyBox (unverified; busybox `sed` prints usage to stderr rather than a version, so test the presence of `/bin/busybox` as the symlink target of `/bin/sed`, `readlink` is the portable check).

**Homebrew and architecture.** On Apple silicon Homebrew lives in `/opt/homebrew` (`/opt/homebrew/bin` on PATH only if the profile adds it; a GUI-launched editor on macOS does not read the shell profile, so PATH lacks it: the reason `getEnvPathFromUserShell` sources `~/.zprofile ~/.zshrc ~/.bash_profile ~/.bashrc` in a login shell, `core/util/shellPath.ts:15-28`). On Intel it is `/usr/local`. Rosetta: a Node binary running under Rosetta reports `process.arch === "x64"` on Apple silicon hardware (unverified in this repo; Apple documents the translated-process sysctl `sysctl.proc_translated`). The claim to avoid is "this is an Intel Mac" from `arch` alone. The state to give is `arch` as reported and nothing about the hardware.

**Privacy prompts.** TCC (Transparency, Consent and Control) prompts appear when a process first reads Desktop, Documents, Downloads, removable volumes or "Full Disk Access" locations; a prompt blocks the command until answered, so a `cat ~/Documents/x` from the agent can hang until the timeout (unverified; Apple support documents the settings). Detection is impossible without trying. The honest advice to the model is nothing; the honest advice to the product is that the 2-minute tool timeout (`DEFAULT_TOOL_TIMEOUT_MS = 120_000`, `core/tools/implementations/runTerminalCommand.ts:7`) is what bounds the damage, and the timeout message should say "a macOS permission prompt may be waiting" on darwin (EV51).

**Sandbox.** macOS has `sandbox-exec` (Seatbelt), deprecated in its man page but what `@anthropic-ai/sandbox-runtime` uses on macOS (unverified; the repo's `core/util/srtStatus.ts` has `SrtHostKind` `macos`). The product probes it as a status only (`srtStatus.ts:1-40`).

**WSL as a Linux.** `isRunningInWsl()` (`extensions/cli/src/tools/runTerminalCommand.ts:41-57`) uses `WSL_DISTRO_NAME` then `/proc/version` containing `microsoft` or `wsl`; the measured `/proc/version` on the review machine contains `microsoft-standard-WSL2`. **Containers without systemd.** `systemctl` and `journalctl` fail with "System has not been booted with systemd as init system" in a container whose PID 1 is not systemd (unverified, the exact text). A model told "this is a container" stops proposing `systemctl restart`. Detection of "inside a container" is covered in section 5.

**Landlock and bubblewrap.** `srtStatus` already probes `bwrap --version`, `socat -V`, `rg --version` and the kernel's user-namespace policy (`core/util/srtStatus.ts:1-40`) and never claims containment (`containment` is the literal "not-verified"). Landlock is a Linux 5.13+ LSM (unverified; kernel documentation `Documentation/userspace-api/landlock.rst`); no code in this repository probes it. Not needed until a jail row uses it (`plans/isolation.md`).

## 5. Shells people actually use, and how the product decides

**How the shell is chosen today.** `resolveShell()` (`core/util/shell.ts:164-215`): a container preference wins (bash inside the image), then WSL on Windows, then Windows PowerShell 5.1, then `$SHELL` with `-l -c`, else `/bin/bash`. The editor's own terminal profile is not consulted when the product spawns the command (only when the command is typed into a remote terminal, where it is unknown). `getPreferredShell()` in the tool definition is a second, separate implementation of the same question with a different macOS fallback. The `SHELL` variable is the user's login shell as recorded in the account database, not the shell of the current terminal: `$SHELL` stays `/bin/zsh` while a person has typed `bash` or `fish` into a terminal, and in CI or a container it is often unset (hence the `/bin/bash` default; Alpine has no bash, so a container image without bash fails to start the command: the container path always passes `bash`, `core/util/containerArgs.ts`, so only host Alpine is affected).

For `pwsh` the owner's remark ("uncommon but possible") is right: it is `unknown`-safe (never vouched read-only wrongly) only because `shellKindOf` maps `pwsh` to `powershell` and the policy then reads PowerShell grammar, which for 7 is correct. The tool description, though, says "Runs in pwsh as a login shell on linux" with no hint that `&&` and POSIX syntax are wrong there. EV46 proposes one sentence per family.

**What the model should be told per shell family**, each at most 25 tokens, static per session: `posix` (nothing, the default assumption), `zsh` ("zsh: quote globs that may not match"), `fish` ("fish: no `$(...)` before 3.4, use `(...)`; set variables with `set -x`"), `nushell` ("nushell: not POSIX; pipelines carry tables; use `^cmd` for external commands"), `pwsh` ("PowerShell 7: use cmdlets and `$env:NAME`; `&&` works"), `unknown` ("Shell not recognised: write portable `sh` and avoid shell-specific syntax"). The last is the safe default and is what a wrong detection degrades to.

**VS Code terminal profile.** `terminal.integrated.defaultProfile.<platform>` decides the editor terminal's shell and overrides `env.shell` (cited, section 7). The product does not read it: the IDE tool spawns `$SHELL` itself for a local window and does not use the person's terminal profile. This is deliberate (a profile could be `cmd` or a custom wrapper) and worth keeping.

**Dev Container and Codespaces detection.** Cited: Codespaces sets `CODESPACES=true` and `CODESPACE_NAME` (GitHub documentation, <https://docs.github.com/en/codespaces/developing-in-a-codespace/default-environment-variables-for-your-codespace>, read 2026-11-12). The Dev Container specification page read (<https://containers.dev/implementors/json_reference/>, 2026-11-12) names `containerEnv` and `remoteEnv` and **no runtime marker variable**; `REMOTE_CONTAINERS=true` (set by the VS Code Dev Containers extension) is from memory and unverified. The portable container marker is not VS Code's: Docker creates `/.dockerenv` and Podman `/run/.containerenv` (unverified, from the respective projects' behaviour), and `/proc/1/cgroup` containing `docker`, `kubepods` or `containerd` is the older heuristic that cgroup v2 weakened (unverified). Every one of these is a hint; none proves a container, and none says the container is a _jail_ (a Dev Container is a user-written environment, as `core/util/devcontainer.ts:5-9` already states).

**What to do about the unknown.** Where the host of core and the remote differ, the product has three honest choices: say nothing about OS and shell (silence), say what is known with its source ("this editor window is remote (ssh-remote); the shell on the remote machine is not known"), or run its own probe in the remote terminal once (SH2 in the shell-awareness report, with its own risks: a probe typed into the person's terminal). Recommended, pending owner: the second, behind a detector that returns a `confidence` and a `source`, and the first when the confidence is `unknown`.

## 10. Open questions for the owner

1. **Wrong claim or silence in a remote window until EV41 is answered.** Recommended, pending owner: ship EV42 first (drop the OS and shell sentence when `remoteName` is not `local`); a missing sentence costs nothing, a wrong one costs a failed call per command.
2. **A static environment sentence in the system message (EV44).** Recommended, pending owner: yes, about 40 tokens in total, built only from `known` or `likely` facts; it is in the cached prefix and does not change between sessions on one machine.
3. **The person's local date and zone (EV49) instead of UTC.** Recommended, pending owner: yes; the cache is unaffected, the block is already per process.
4. **Cap the git status (EV50).** Recommended, pending owner: 2,000 characters and a 2-second timeout.
5. **Permission mode in the prompt (EV59).** Recommended, pending owner: not by name.
6. **`PAGER=cat` and `GIT_PAGER=cat` in the command environment (EV58).** Recommended, pending owner: yes; it changes no command's meaning and stops a pager from hanging a non-TTY run.
7. **Do we guess the Linux distribution?** Recommended, pending owner: yes from `/etc/os-release`, labelled as such, used for install hints only (EV57).
8. **Shells outside bash and zsh.** Recommended, pending owner: tell the model the family and one dialect sentence (EV46); do not parse them (decided in DS9).
