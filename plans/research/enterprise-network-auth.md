# Enterprise network, authentication and the fork plan: research

Status: complete first version, 2026-11-11. Docs only; no code was changed and no experiment was run. Protocol claims are read through the rfclib tools (RFC numbers and sections cited inline); vendor and spec-site claims cite a URL with the fetch date 2026-11-11.

## 1. Where the fork plan stands

`plans/fork-plan.md` (written 2026-10-27) named three gaps: OAuth tokens only attached to `sse` servers, the sign-in button shown only on a literal 401 string, and no OS trust store. The roadmap's Shipped table records all three as done (remote MCP OAuth #7 and #14, enterprise TLS #5 and #8, Bedrock and Mantle, `modeModels`). This document audits the code behind those rows against the specs and lists what is still open.

## 3. MCP authorization: what the spec requires

Read 2026-11-11 from https://modelcontextprotocol.io/specification/latest/basic/authorization (the page identifies version 2026-07-28) and its sub-pages `.../authorization/client-registration.md` and `.../authorization/authorization-server-discovery.md`. RFC text was read through rfclib (all documents `current`).

**The flow.** (1) Unauthenticated request, 401 with `WWW-Authenticate: Bearer resource_metadata="..."` (RFC 9728 section 5.1). (2) Fetch protected resource metadata; its `resource` MUST equal the URL the client used, else the data MUST NOT be used (RFC 9728 section 3.3). Without the header, try `/.well-known/oauth-protected-resource/<path>`, then the root form. (3) Fetch authorization server metadata: RFC 8414 path insertion, then OIDC path insertion, then OIDC path appending; `issuer` MUST equal the issuer used to build the URL (MCP discovery page; RFC 8414 section 3.1). (4) Obtain a client id: pre-registered, then Client ID Metadata Document (CIMD, `client_id_metadata_document_supported`), then Dynamic Client Registration (RFC 7591), then ask the user. DCR is marked deprecated in 2026-07-28 and a DCR client MUST send `application_type` (`native` for desktop and CLI). (5) Authorization request with PKCE S256 (RFC 9700 section 2.1.1: public clients MUST use PKCE; S256 is the only method that does not expose the verifier), the `resource` parameter (RFC 8707 section 2; MUST be sent in both the authorization and token requests, and even if the server does not advertise support), and the scope chosen from the challenge `scope` or `scopes_supported`. (6) The client MUST record the issuer first and validate `iss` (RFC 9207) before sending the code anywhere; an absent `iss` is rejected when the server advertises `authorization_response_iss_parameter_supported`. (7) Token request, then bearer on every request, never in the query string. (8) A 403 with `error="insufficient_scope"` starts step-up with the union of old and new scopes and a retry limit. (9) Credentials are keyed by the authorization server's issuer, and refresh tokens are kept confidential in storage.

**Native-app rules.** RFC 8252 section 7.3: loopback redirect URIs use the `http` scheme and the IP literal with whatever port the client holds, and the server MUST allow any port. Section 8.3: open the port only for the request and close it after, listen on loopback only, and `localhost` is NOT RECOMMENDED. RFC 9700 section 2.1: exact string match on redirect URIs except the loopback port; PKCE (or `state`) must prevent CSRF; `iss` defends against mix-up when more than one authorization server is in play. RFC 9700 section 4.14.2: for public clients the server must detect refresh replay by rotation or sender constraint, so a client MUST persist the newest refresh token from every refresh response. RFC 8628 section 3.5 (device flow): poll no faster than `interval` (5 s default), `slow_down` adds 5 s, any other error stops polling, back off on timeouts.

Two lessons for us. First, the static-client path is not optional: GitHub has no DCR, Claude Code and Cursor both grew `clientId` and fixed-port options for that reason, and Datadog requires the redirect URL to be allow-listed by an admin, which a random port would break. ## 6. Design: MCP OAuth v2

Keep the SDK provider (it already does refresh and rotation) and extend around it.

1. **Config.** `oauth: { clientId, clientSecret?: ${{ secrets.X }}, scopes, authServerMetadataUrl, callbackPort, redirectHost: "localhost" | "127.0.0.1" }`. A static `clientId` skips DCR and CIMD, matching the registration priority in section 3.
2. **Order.** Pre-registered, then CIMD when the metadata advertises it and a metadata URL is configured, then DCR with `application_type: "native"`, then a prompt that names where to register and which redirect URI to give the admin (Datadog needs it allow-listed).
3. **Callback.** Bind loopback only, accept `code`, `state`, `iss`, `error`; send our own `state` (a nonce bound to the pending record, one-time); validate `iss` against the issuer recorded before the redirect; close the port after the first valid callback. Remove `?state=` from `redirect_uris`. In VS Code keep `getExternalUri`; add a `vscode://` URI handler as the fallback for remote and web hosts, but only for servers whose registration allows a custom scheme.
4. **Step-up and 403.** Treat 403 `insufficient_scope` as "needs sign-in with more scope"; merge scopes; at most two attempts per tool call.
5. **Store.** Key by (scope, issuer, resource URL, account label). Record `issuer` and `resource` in the record and refuse to reuse a client id whose recorded issuer differs. Allow more than one account per server by adding an `account` label to the key; the UI shows the label.
6. **Where tokens live.** IDE: keep the `readSecrets` path (VS Code `SecretStorage`, the wrapper already works around its stale-read problem, comment in `SecretStorage.ts`). CLI: no keychain dependency exists in the repo; options are `@napi-rs/keyring` or `keytar` (native modules; the VS Code stub says keytar "cannot be used in vscode extensions without majorly complicating the build"), or an AES-GCM file with a key the OS protects (DPAPI on Windows, Keychain on macOS through `security`, Secret Service through `secret-tool`), falling back to a mode 0600 file with a printed warning. Recommend: shell out to the OS tools behind one `SecretBackend` interface, no native module; owner decision.
7. **Sign out.** Call the revocation endpoint when the metadata lists one, for the refresh token first, then delete locally; report whether revocation succeeded.
8. **Headless.** `cn mcp login <name>`: if the authorization server metadata lists `device_authorization_endpoint` use RFC 8628 (print `verification_uri` and `user_code`, poll per section 3.5); otherwise print the authorization URL and accept the pasted redirect URL (Claude Code's approach), with `--no-browser`. CLI `serve` and loops never start a flow; they report "needs sign-in" with the exact command.
9. **Logs.** Registration responses, token responses, `Authorization` and `Cookie` headers and URL query values named `code`, `state`, `access_token`, `refresh_token`, `client_secret` are masked by the existing masker (X9 shared rule set) before any log, audit or error write; add the OAuth shapes to its test corpus.
10. **CLI parity.** Move the CLI's `mcpTransports.ts` onto the core provider and `createWebFetch`, deleting the `mcp-remote` fallback once tests pass.

**Consequences for us.**

- `tls.getCACertificates("system")` exists from Node 22.15 and 23.10; on older runtimes `CertsCache.systemCa` returns an empty list and says so only under `VERBOSE_FETCH`. A user on an older runtime who sets `useSystemCa: true` gets nothing and no message. Fix: report it in `doctor` and as a one-time warning.
- `defaultUseSystemCa()` is false on Linux. With `--use-system-ca` semantics Linux reads the same OpenSSL directory Node would use anyway, so "off by default on Linux" mostly changes whether `/etc/ssl/certs` additions reach us; corporate roots installed with `update-ca-certificates` land there. Recommend: default on everywhere when `getCACertificates` exists (cost: one directory read, cached).
- `NODE_EXTRA_CA_CERTS` is applied by us in `CertsCache.fixedCa` by reading the file ourselves, which fixes the "read once at start" limit for our own agents, but the setuid and file-capability ignore rule is not reproduced and a malformed file is silent.
- Proxy variable precedence differs between tools. Ours: `requestOptions.proxy`, then `HTTPS_PROXY` / `https_proxy`, then falls back to `HTTP_PROXY` for https URLs (`util.ts:8-21`); no `ALL_PROXY`; `NO_PROXY` split on commas only. Whether curl, Go, Python requests and Node's `--use-env-proxy` each fall back from https to `HTTP_PROXY`, honour lower-case first, accept `*.corp`, leading dots, CIDR and ports, differs; the doc table must be built from each tool's manual (experiment E4) before we claim parity. Our fallback to `HTTP_PROXY` for https is a defect candidate if the user set only `HTTP_PROXY` for plain HTTP traffic.
- PAC files: neither `packages/fetch` nor the CLI evaluates PAC. VS Code core does through Chromium, extensions do not (page text above). Options: a `pac-proxy-agent` based resolver behind `requestOptions.proxy: pac+https://...` (effort M), or shelling out to `Get-ItemProperty` on the Windows Internet Settings key and `scutil --proxy` on macOS to read the system proxy (effort S, read-only, no secrets). NTLM and Kerberos (Negotiate) proxy auth: the Node agents we use do Basic only (URL credentials); `tlsErrors.ts` hints at `http://user:pass@proxy`, which puts a password in config and is a secret-handling smell. Practical answer: for NTLM or Kerberos proxies, tell users to run a local forwarding proxy (CNTLM or px) and point `requestOptions.proxy` at it; evaluate `proxy-agent` with an NTLM plugin only if demand appears (owner decision).
- Certificate pinning clashes: a TLS-inspecting proxy re-signs every origin, so pinned clients (any client with a baked-in pin) fail; we do not pin, but `rejectUnauthorized` stays on and the hint text must say that pinned vendors (some SSO, update, and telemetry endpoints) need a bypass rule on the proxy, not a weaker client.
- Electron or webview: GUI network calls (`SafeImg.tsx`) use Chromium and follow the OS; model calls run in core in Node and follow `packages/fetch`.

### 7.1 Gaps found (from section 2.2)

1. CLI MCP transports ignore proxy, CA bundle and `useSystemCa` (file `mcpTransports.ts`): a sign-in that works in the IDE fails in `cn` behind the same proxy.
2. Bedrock credential providers (SSO, STS, web identity) build their own HTTP handler: under TLS inspection `aws sso login` may succeed (a separate process) while our token refresh fails. Pass `clientConfig` with the same `NodeHttpHandler` to `fromNodeProviderChain` (it accepts one in the credential-providers package; to confirm in a spike, E5).
3. Docs crawler, model list fetches, favicon, CLI sync and hook URL calls use the runtime's global `fetch`. Route them through `fetchwithRequestOptions` or set `NODE_USE_SYSTEM_CA` and `NODE_USE_ENV_PROXY` for the CLI process at startup (S, with a runtime version check).
4. `useSystemCa: true` on a runtime without `getCACertificates` is silent.
5. HTTPS fallback to `HTTP_PROXY` (above).

### 7.2 `continuous doctor network` (design)

One command, also a button in the Test connection result (PL3). Inputs: the configured model endpoints, MCP server URLs, Bedrock regional endpoints (runtime, control plane, Mantle, `oidc.<region>.amazonaws.com` and `portal.sso.<region>.amazonaws.com` for SSO profiles), and any `--url`. Per host, with the same agent the product uses: DNS result (addresses only), proxy chosen and why (`requestOptions.proxy`, env var name, NO_PROXY rule that matched), TCP and CONNECT status (407 reported as such), TLS handshake outcome, negotiated protocol, and a certificate chain summary: subject CN, issuer CN, SHA-256 fingerprint, notBefore/notAfter and whether each issuer came from `bundled`, `system`, `extra` or `caBundlePath` (so "signed by CorpInspection Root, found in system store" is visible). Header summary: status and `WWW-Authenticate` scheme and `resource_metadata` presence for MCP hosts. Never print request bodies, `Authorization`, `Cookie`, query strings, client certificate key paths' contents, or proxy credentials (mask `user:pass@`). Runtime block: Node version, whether `getCACertificates` exists, count of CAs per source, which of `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `NODE_USE_SYSTEM_CA`, `HTTPS_PROXY`, `NO_PROXY` are set (names and whether set, not values for URLs with credentials). Output human and `--json`; exit code 0, 1 (a host failed), 2 (config problem). Each failure maps to the existing `getTlsErrorHint` text plus a fix.

## 8. Bedrock for enterprises

Read 2026-11-11 from AWS documentation.

- **API keys** (https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys.html): short-term keys last up to 12 hours or the session, inherit the creating principal's permissions, only work in the Region they were generated in, and are recommended for production; long-term keys create an IAM user and a service-specific credential and are "recommended only for exploration". `AWS_BEARER_TOKEN_BEDROCK` is the environment variable. Calls are logged in CloudTrail while the key is not. IAM actions `bedrock:CallWithBearerToken` and `bedrock-mantle:CallWithBearerToken` (with `bearerTokenType` of `SHORT_TERM` or `LONG_TERM`) let an organisation deny or limit keys; a short-term key is killed by invalidating the session or a deny policy. Our code accepts a key from config or the env var (`Bedrock.ts` `_resolveApiKey`); it has no expiry awareness. For short-term keys the doc recommends calling the token generator (`@aws/bedrock-token-generator`) before each request; we should offer a `bedrockKeyProvider` that does that from the SSO or IAM credentials, so no key ever lands in config (M, owner decision on the new dependency).
- **SSO and Identity Center.** Our chain is `fromNodeProviderChain({profile, ignoreCache: true})`, which includes SSO; the AWS docs say the SDK refreshes the session automatically with the `sso-session` configuration and that the legacy non-refreshable setup does not (https://docs.aws.amazon.com/sdkref/latest/guide/feature-sso-credentials.html, search result). A reported refresh bug existed in older v3 releases (github-redirect.dependabot.com/aws/aws-sdk-js/issues/4441). We resolve credentials when a client is built and pass static keys, so a long stream that outlives temporary credentials is not re-signed; each request builds a client, which bounds the problem but costs a chain walk per call (`ignoreCache: true`). Recommend passing the provider function itself with caching, plus the handler fix in section 7.1.
- **VPC endpoints** (https://docs.aws.amazon.com/bedrock/latest/userguide/vpc-interface-endpoints.html): service names `bedrock`, `bedrock-runtime`, `bedrock-mantle`, `bedrock-agent`, `bedrock-agent-runtime`, plus FIPS variants for `bedrock` and `bedrock-runtime` in six Regions; with private DNS enabled the normal regional names resolve to the endpoint, otherwise the endpoint URL must be given (our `apiBase` handles that). Endpoint policies list `bedrock:InvokeModel` and `bedrock-mantle:CreateInference`; a policy that omits `bedrock:InvokeModelWithResponseStream` or the Converse actions breaks streaming silently, so Test connection should call a streaming path too.
- **Mantle.** `bedrock-mantle.<region>.api.aws` serves the OpenAI-compatible Responses and Chat Completions APIs and the Anthropic Messages API; accepts a Bedrock API key or SigV4; support is per model (a gateway document reports GPT-5.x on Responses only; not confirmed from AWS in this pass). Our `bedrock-mantle` provider is key-only (`BedrockMantle.ts:51`); SigV4 would let SSO users in. Region list not read.
- **CloudTrail and logging.** The key is not logged, the call is; with SSO the principal in CloudTrail is the assumed-role session, so per-user attribution works only with identity-centre profiles, not with shared long-term keys. Model invocation logging (prompt text in S3 or CloudWatch) is an account setting; users on managed accounts should be told that prompts may be retained there (a note in the Bedrock setup wizard; S).
- **Cross-account roles and inference profiles.** `source_profile` and `role_arn` chains are resolved by the same chain (so the STS handler gap applies). Inference profile IDs and quotas are already handled by K3 and C34; applied-0 TPM accounts are the reason for the open "Bedrock quotas" row.

## 9. Per-mode models: prior art against ours

Cline: a setting "Use different models for Plan and Act"; each mode keeps its own selection and switching modes switches the model (https://docs.cline.bot/features/plan-and-act, fetched 2026-11-11). Roo Code's per-mode model behaviour was not verified (the documentation URL redirected and was not read). Ours (ROADMAP Shipped, A1 to A5, M0, K8, K13): `modeModels` per Chat, Plan and Agent with a list of models per mode, reasoning effort, prompt and tail per use, the mode menu naming the model, CLI parity from M0, subagent and reviewer entries open (K13). Ours is the richer design; the gap is the enterprise side: a mode's model should be able to differ in provider and credentials (Bedrock SSO profile for plan, Mantle key for act), which already works because each model carries its own `requestOptions` and `profile`, but the doctor and Test connection must run per mode model.
