# Enterprise network, authentication and the fork plan: research (DRAFT)

Status: draft, 2026-11-11. Sections marked PENDING are still being researched. Docs only; no code was changed and no experiment was run. Protocol claims are read through the rfclib tools (RFC numbers and sections cited inline); vendor and spec-site claims cite a URL with the fetch date 2026-11-11.

## 1. Where the fork plan stands

`plans/fork-plan.md` (written 2026-10-27) named three gaps: OAuth tokens only attached to `sse` servers, the sign-in button shown only on a literal 401 string, and no OS trust store. The roadmap's Shipped table records all three as done (remote MCP OAuth #7 and #14, enterprise TLS #5 and #8, Bedrock and Mantle, `modeModels`). This document audits the code behind those rows against the specs and lists what is still open.

### 2.2 Outbound HTTP clients and whether each honours system CA and proxy

`useSystemCa` defaults on for Windows and macOS only (`packages/fetch/src/certs.ts` `defaultUseSystemCa`); it merges `tls.getCACertificates("system")` (Node 22.15+/23.9+, else empty) with `tls.rootCertificates`, `NODE_EXTRA_CA_CERTS` and `caBundlePath`. Proxy comes from `requestOptions.proxy`, then `HTTPS_PROXY`/`https_proxy`, falling back to `HTTP_PROXY`/`http_proxy` for https URLs; `NO_PROXY`/`no_proxy` plus `noProxy`, with CIDR, `*.` and port matching (`packages/fetch/src/util.ts`). HTTPS through a proxy uses `HttpsProxyAgentWithTls` so the origin handshake gets the CA list (`agent.ts`).

## 3. Specs: MCP authorization (PENDING detail; key reads done)

Read on 2026-11-11 from https://modelcontextprotocol.io/specification/latest/basic/authorization (page text identifies version 2026-07-28), with its sub-pages `.../authorization/client-registration.md` and `.../authorization-server-discovery.md`:

- Discovery: clients MUST use the `resource_metadata` URL from `WWW-Authenticate` when present, otherwise try `/.well-known/oauth-protected-resource/<path>` then the root form. Authorization server metadata: RFC 8414 path insertion, then OIDC with path insertion, then OIDC path appending; the `issuer` in the document MUST equal the issuer used to build the URL.
- Registration priority: pre-registered client, then Client ID Metadata Documents (`client_id_metadata_document_supported`), then Dynamic Client Registration, then prompt the user. DCR is marked deprecated in this version. DCR clients MUST send `application_type` (native for desktop and CLI).
- `resource` (RFC 8707) MUST be in both the authorization and token requests and MUST be sent whether or not the server supports it.
- Clients MUST record the issuer and validate `iss` (RFC 9207) before sending the code to a token endpoint; absent `iss` is rejected when the server advertises `authorization_response_iss_parameter_supported`.
- Step-up: a 403 with `error="insufficient_scope"` and `scope` triggers re-authorization with the union of old and new scopes, with a retry limit.
- Credentials MUST be keyed by authorization server issuer; refresh tokens MUST be kept confidential in storage.

RFC points (rfclib, all `current`): RFC 9728 section 3.3 (the `resource` value MUST match the request URL or the data MUST NOT be used) and 5.1 (`resource_metadata`); RFC 8414 section 3.1 (path insertion); RFC 8707 section 2 (absolute URI, no fragment, `invalid_target`); RFC 9700 section 2.1 (exact-string redirect match except loopback port; PKCE or `state` for CSRF; `iss` against mix-up), 2.1.1 (public clients MUST use PKCE; S256) and 4.14.2 (refresh token rotation or sender constraint for public clients); RFC 8252 sections 7.3 and 8.3 (loopback redirect should use the IP literal; `localhost` NOT RECOMMENDED; open the port only for the request); RFC 8628 section 3.5 (poll at `interval`, `slow_down` adds 5 s).
