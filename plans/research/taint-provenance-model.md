# Taint by provenance: threat model, design and plan (2026-11-13)

Status: DRAFT research, docs only. No product code changed, no model called. Code read at `origin/main` 62277ea. Web pages fetched on 2026-11-13. A claim I could not confirm on a first-party page is marked **unverified**. This builds on `plans/design/tainted-session.md` (the built rule), `plans/research/agent-security.md` (sections 2 and 8) and the concept review in PR #818 (`plans/research/custom-policy-concept-review.md`, not yet merged). Where this note says "#818 precedence" it means that review's section 3.2: `deny > ask > record > allow`, with an unattended `ask` held in a loop that has an inbox and refused otherwise, never approved.

## 1. Summary

1. **The built rule is the right core, and it is narrower than it looks.** It taints on provenance and raises sinks to `ask` (`core/tools/permissions/taint/taintRule.ts:40-62`). But it is off by default (`taintSetting.ts:23-25`), it has one action (`ask`), one undifferentiated label per session, and three gaps an attacker would pick first: files inside the open folder never taint (a cloned repository's README, its `AGENTS.md`, its scripts' output), a secret read is a sink but never a label, and `untrusted-workspace` is declared and never set (`taintState.ts:13`, design §8).
2. **Split the one flag into labels.** Integrity labels say where untrusted text came from (web, MCP server X, issue text, outside read, untrusted folder). One confidentiality label says private data entered (a secret read). A policy is a small table: label by sink class to `off | record | ask | deny`, resolved with #818's precedence. This is FIDES's coarse "context label" model, which the paper itself calls conservative ([arXiv 2505.23643 §5](https://arxiv.org/html/2505.23643v2)), not CaMeL's per-value capabilities.
3. **A detector may raise a label, never lower one.** A hit on output that no provenance rule tainted adds a `signal` label whose strongest action is `ask`. No detector result, model verdict or timer ever removes a label. Only a person does, and the audit trail records that.
4. **What holds today is the tool layer.** Fetch, file-tool writes, MCP calls, `git push` and the recognised network and publish programs are enforceable now. A Python or Node script that opens a socket is not, and will not be until the sandbox (W8) can switch the network off for a tainted session. A CaMeL-style planner is out of scope for the open-ended agent. A narrow form fits Loop's fixed plans and fetch summaries.
5. **Measure it with a structural corpus, not only with models.** The two existing injection scenarios in `bench/scenarios/` deliver the attack through vectors the rule does not taint today (a workspace file and a workspace script's output), so they measure only whether the model ignores it. Section 9 proposes a small AgentDojo-shaped corpus that scores "stopped by structure" separately from "the model declined".

## 3. Threat model

**Assets.** The person's credentials (environment, `~/.ssh`, cloud and package-registry tokens, `.env`), private source, the integrity of the repository and its remote, the person's other accounts reachable through MCP servers, and the machine outside the workspace (shell profiles, other repositories).

**Attacker.** Controls text that reaches the model through a tool: a web page or search result, an issue or pull-request body, an MCP server's output (a hostile server, or an honest server relaying hostile text, such as a GitHub server returning an issue), a file in a repository the person cloned (README, docs, `AGENTS.md`, test fixtures), a dependency's files, the output of a script in that repository. The attacker can adapt to any detector we publish (§2, Nasr et al.).

**Out of scope here.** A malicious model provider, a compromised local machine, and a malicious MCP _binary_: a local server already runs code as the person, which is a supply-chain problem handled by the launch pin and project trust (`core/config/projectTrust.ts:1-13`), not by taint.

**Attacker goals and the channels they need.**

| Goal                           | Channel                                                                            | Covered by a sink today                                                                                                                                                                                       |
| ------------------------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exfiltrate a secret or source  | `curl`/`wget`/`nc`/`ssh`/`scp`, `gh api`, `fetch_url_content` to an untrusted host | Yes (`taintSinks.ts:122-152, 177-181`)                                                                                                                                                                        |
|                                | `fetch_url_content` to a host in `trustedDomains` with data in the path or query   | **No**: a trusted host is not a sink (`taintSinks.ts:179`). A host where anyone can post (a code host, a paste site) is a receiver                                                                            |
|                                | `search_web` query text                                                            | **No**, by design (`plans/design/tainted-session.md` §3)                                                                                                                                                      |
|                                | An MCP tool of another server                                                      | Yes, unless the tool is a believed read-only one (`taintSinks.ts:169-176`). A read-only tool's _arguments_ still leave the machine                                                                            |
|                                | A script or interpreter that opens a socket (`python x.py`, `node -e`)             | **No**, by design; needs the sandbox                                                                                                                                                                          |
|                                | Markdown image in the model's reply                                                | Blocked by default in the GUI (`gui/src/components/StyledMarkdownPreview/SecureImageComponent.tsx:126-127`), though the webview CSP allows any `https:` image (`extensions/vscode/src/util/webviewCsp.ts:32`) |
| Push or publish attacker code  | `git push`, `gh pr create`, package publish                                        | Yes (`taintSinks.ts:103-120`)                                                                                                                                                                                 |
|                                | `git remote add evil ...` then `git push evil`                                     | Asks as a push, but is not distinguished from a push to the configured remote                                                                                                                                 |
| Persist outside the workspace  | File-tool write outside                                                            | Yes (`taintSinks.ts:186-190`)                                                                                                                                                                                 |
|                                | Shell redirect to `~/.bashrc`                                                      | Not a taint sink; the runtime-write and protected-path rules cover it (design §3)                                                                                                                             |
| Backdoor the repository itself | Edit inside the workspace, later committed by the person                           | **No sink, by design.** Integrity of in-workspace edits rests on the person reviewing the diff. CaMeL also leaves "text-to-text" attacks out of scope                                                         |
| Spend or destroy               | Long loops, `rm -rf`                                                               | Not taint's job: budgets and destructive-command rules                                                                                                                                                        |

**Trust boundary.** The person's own config (`~/.continue/config.yaml`, `permissions.yaml`) is trusted. Everything a repository carries may only tighten (`core/tools/permissions/trust.ts:1-26`). The taint setting is read from the person's file only (`taintSetting.ts:7-11`), which is correct: a repository that could set it to `off` would disable it for its own content.

## 4. Current implementation (file:line at 62277ea)

### 4.1 The tainted-session rule

- **State.** A per-session monotone set of five kinds with the first turn, no content kept (`core/tools/permissions/taint/taintState.ts:1-16, 41-55`). `fork` copies kinds as inherited and `join` returns only what the child met (`:77-93`). `clear` takes a reason and ignores it (`:71`, parameter `_reason`), so a clear is not audited.
- **Sources** are judged from the call, never the content (`taintSources.ts:101-122`): any MCP result (`:103`), `fetch_url_content` and `search_web` (`:104-109`), a file read outside every workspace folder (`:110-116`, path check at `:35-55`, erring toward "outside"), and terminal commands whose program is curl, wget, httpie or Invoke-WebRequest, or a `gh` read of issues, pull requests, releases, gists or runs, or `gh api` (`:71-98`). `untrusted-workspace` is declared (`taintState.ts:13`) and no host sets it (design §8).
- **Sinks** (`taintSinks.ts:15-22`): `network-egress`, `outside-write`, `credential-read`, `vcs-publish`, `package-publish`, `mcp-send`, read with the engine's own command readers (`:122-152`). An MCP tool is a sink unless its `readonly` is believed and it did not come from the open folder (`:169-176`).
- **Rule.** Runs after every other check and only raises an allow to an ask (`taintRule.ts:40-62`), named on every result of a tainted session as `taintSink` so the replay can count it (`:47-52`). It sits between the policy-file locks and `noAskAtIdgaf` (`core/tools/permissions/evaluate.ts:183-193`), so today at IDGAF a tainted sink is refused rather than asked (`evaluate.ts:197-229`). #818 phase 0 turns that into `record` under pure IDGAF.
- **Reviewer.** `tainted-session` is a final source the Auto reviewer cannot move (`auto/handler.ts:119-126`), a tainted sink returns as the person's ask (`:198-206`), and non-sink calls carry one line of session taint in the reviewer prompt (`auto/prompt.ts:176-177`).
- **Setting.** `toolPermissions.auto.environment.taintedSessionRule`, anything but `ask` is `off`, user file only (`taintSetting.ts:7-46`). Off means no mark, no fact, no audit field (`taintWiring.ts:14-41`).
- **Wiring.** Core marks after a tool returns (`core/tools/callTool.ts:275`, `core/tools/taintResult.ts:13-40`, MCP detected by URI at `:30`). The IDE evaluator adds the fact (`core/core.ts:2191`). The CLI marks after each call (`extensions/cli/src/stream/streamChatResponse.helpers.ts:1034`, `extensions/cli/src/permissions/cliTaint.ts:18-38`, workspace taken as the process cwd at `:32`) and clears with `/untaint` (`cliTaint.ts:41-49`). The GUI has no clear control and no indicator; it only keeps the rule's ask away from the reviewer (`gui/src/redux/thunks/evaluateToolPolicies.ts:316-317, 494`).
- **Audit.** Decision records carry `tainted: <kinds>` (`core/tools/permissions/audit/record.ts:123-124, 321`; written by `audit/hook.ts:98` and `extensions/cli/src/audit/cliAudit.ts:96`) and `source: "tainted-session"` on the call it asked. No record is written when a label is added or cleared.

### 4.2 MCP trust and read-only hints after #740

A server is trusted when it is not from the open folder and is named `trusted` in `permissions.yaml`, written inline in the person's `config.yaml`, or defined by a file in the global folder (`core/context/mcp/mcpTrust.ts:3-41`). `readOnlyHint` is believed only from a trusted server (`:47-55`), applied at load (`core/config/profile/doLoadConfig.ts:293-319`, which also sets `mcpFromWorkspace`). The CLI's list is `cliTrustedMcpServers` (`extensions/cli/src/tools/mcpTrust.ts:40-45`), and a believed read-only tool turns a catch-all ask into an allow (`extensions/cli/src/permissions/readOnlyMcp.ts:53-62`). Server trust decides whether the server's _claims about its tools_ are believed. It has no effect on taint: every MCP result taints as `mcp-result`, whichever server it came from (`taintSources.ts:103`), and the label does not record which server.

### 4.3 Fetch and web content

`fetch_url_content` checks scheme, userinfo and secrets in the URL, pins and re-checks each redirect hop public-to-private (`core/util/guardedFetch.ts:35-58`), cuts at 20,000 characters and adds a truncation note (`core/tools/implementations/fetchUrlContent.ts:8-45`). Page text is cleaned by `sanitizeFetchedText`: HTML comments removed, invisible characters stripped, images turned into `[image: alt]` (`core/util/fetchedText.ts:80-90, 103-144`, applied at `core/context/providers/URLContextProvider.ts:135-137`). Spotlighting is wired into the fetch tool behind `experimental.spotlightUntrusted` or `CONTINUOUS_SPOTLIGHT_UNTRUSTED=1` (`fetchUrlContent.ts:47-55`). The header of `core/tools/permissions/spotlight.ts:1-11` still says it is "not wired into any tool path yet", which is stale.

### 4.4 The injection detector

Regex patterns over a normalised view (NFKC, zero-width removed, tag characters decoded) plus a `hidden-unicode` match (`core/tools/permissions/injection.ts:127-170`). Its own header says it is a hint that "never blocks anything" (`:3-11`). It prepends a notice to flagged output in the GUI (`gui/src/redux/thunks/callToolById.ts:142`), in GUI subagents (`gui/src/util/subagents/runSubagent.ts:590`) and in the CLI (`extensions/cli/src/stream/streamChatResponse.helpers.ts:67-70`). The reviewer sees only the fact `outputFlagged`, never the text (`evaluateToolPolicies.ts:284-286`, `auto/prompt.ts:170`). It feeds no taint today, which is the correct starting point. Measured on its own corpus: precision 0.96, recall 0.73, 0 of 10 on the reworded split (`plans/research/agent-security.md` §2 mapping table, corpus `core/tools/permissions/injectionCorpus.ts`).

### 4.5 Sanitisers and hidden characters

- **Child-process environment.** `terminal.environment` defaults to `scrub`, which removes secret-looking names from what agent commands, loop checks and hooks receive (`core/util/terminalEnvironment.ts:7-19`). Only the person's own config may loosen it (`:64-69`). This shrinks what a `credential-read` can find; it does not label anything.
- **Settings sanitisers** keep only well-formed fields and refuse loosening from non-user sources: `sanitizeEnvNames` (`core/tools/permissions/userEnvNames.ts:7-31`), `sanitizeTrustedDomains` (`userTrustedDomains.ts:24`), `sanitizeTerminalSettings` (`core/util/userTerminalSettings.ts:11-30`), and the repository-file loosening keys (`trust.ts:15-26`).
- **Hidden characters** are handled by four different sets: `fetchedText.ts:84` (stripped, fetched pages and dropped text, `gui/src/components/mainInput/TipTapEditor/drop/resolveDrop.ts:242`), `auto/guidance.ts:40-41` (stripped, reviewer guidance), `spotlight.ts:40` (token redaction), `injection.ts:144, 153-170` (flag and match only). MCP results and file reads are not stripped at all; they are only flagged.

### 4.6 Rendering

Remote images in chat markdown are blocked until clicked, and the card names the host and the query (`SecureImageComponent.tsx:88-127`). The CSP still allows them once loaded (`webviewCsp.ts:32`). That is the right deterministic block for the image channel MSRC describes.

| Gap                            | Effect                                                                                                                                                                                                            |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Off by default                 | Unattended runs and YOLO sessions get no structural check at all                                                                                                                                                  |
| No in-workspace source         | The two existing bench injection scenarios (`bench/scenarios/injection-in-file.json`, `injection-in-tool-result.json`) never taint the session; only the model stands between the injected `curl` and the network |

## 5. Design

### 5.1 Labels

A label is `(family, kind, origin?)`. Labels only join (set union); nothing but a person removes one.

| Label                 | Family          | Set when                                                                                                                                               | Origin kept                          |
| --------------------- | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------ |
| `web`                 | integrity       | Fetch, search, recognised web programs (today's `web-fetch`)                                                                                           | host, in the audit record only       |
| `issue`               | integrity       | `gh` reads of issues, PRs, releases, runs; `gh api` (today's `issue-text`)                                                                             | none                                 |
| `mcp:<server>`        | integrity       | Any result from that server (today's `mcp-result`, split per server)                                                                                   | server name                          |
| `outside-read`        | integrity       | File-tool read outside every workspace folder (as today)                                                                                               | none                                 |
| `untrusted-workspace` | integrity       | Session start, when the folder's content is not trusted (decision O3)                                                                                  | folder                               |
| `signal`              | integrity       | A detector hit on output that carried no integrity label of its own (5.4)                                                                              | detector ids                         |
| `secret`              | confidentiality | A read of a protected secret path through any file tool, a `credential-read` command (`taintSinks.ts:131-137`), an MCP tool the person marks `private` | the label word only, never the value |

The trusted-server distinction from #740 does not remove `mcp:<server>`. It is the input to one optional per-server switch, `contentTrusted`, set only in the person's `permissions.yaml`, for a server whose data is the person's own (a local database). A GitHub, Slack or browser server relays strangers' text and should not get it.

### 5.2 Sinks

Today's six classes stay. Three refinements:

- `network-egress` gains a detail `trusted-host-with-data`: a fetch to a `trustedDomains` host whose URL has a query string or a path that did not appear in the user's own messages. It is `record` by default (decision O7), so the person can see in the audit how often it would fire before deciding.
- `vcs-publish` gains `new-remote`: a push to a remote that was added or repointed during the session, Claude Code's rule (section 2). Default `deny` while any integrity label is present.
- `mcp-send` gains `cross-server`: a call to server B while `mcp:A` is present (A ≠ B). This is the trifecta inside MCP that Willison describes. Same action as `mcp-send` by default; it exists so a person can set it stricter.
- `search-query` is new and `record` only: the query leaves the machine to the provider the person chose.

### 5.3 Policy: label by sink to action

One table, resolved with #818's precedence (strictest wins, ties to the earlier row, every `record` written). Defaults proposed for the rule switched on:

| Labels present                            | `network-egress`         | `vcs-publish` / `package-publish` | `outside-write` | `mcp-send`               | `credential-read` | `search-query` |
| ----------------------------------------- | ------------------------ | --------------------------------- | --------------- | ------------------------ | ----------------- | -------------- |
| any integrity label                       | ask                      | ask (`new-remote`: deny)          | ask             | ask                      | ask               | record         |
| `secret` only                             | ask                      | record                            | record          | ask                      | record            | record         |
| integrity **and** `secret` (the trifecta) | ask, **deny unattended** | ask, **deny unattended**          | ask             | ask, **deny unattended** | ask               | record         |
| `signal` only                             | ask                      | ask                               | ask             | ask                      | record            | record         |

Rules for the table:

1. The table can only raise. It runs after every other check, as `applyTaintedSessionRule` does now (`evaluate.ts:183-193`), and its result joins the earlier verdict with `max`.
2. An unattended `ask` follows #818: held in a loop with an inbox, refused otherwise (already the CLI's behaviour, `streamChatResponse.helpers.ts:385-397`). The trifecta row says `deny` outright when unattended so a loop does not pile up held exfiltration attempts.
3. Under pure IDGAF (after #818's phase 0), every cell is `record`. Any custom policy with a guard at `ask` or `deny` uses the table as written.
4. The person may set any cell stricter in `permissions.yaml`. Looser than the default needs the person's own file; a repository file can only tighten (`trust.ts` rule).
5. The reviewer cannot move an `ask` or `deny` from this table (already true for the source, `auto/handler.ts:119-126`).

### 5.4 Detector signals: raise, never lower

- A detector hit on output that already carries an integrity label adds nothing to the decision. It is written into the audit record (`detector: [ids]`) and into the reviewer's `outputFlagged` fact, as now.
- A hit on output with no integrity label (a file inside a trusted workspace, a local script's output) adds `signal`. `signal`'s strongest action is `ask`, never `deny`, because the detector has a measured false-positive rate on security text and fixtures (`injection.ts:7-8`).
- The absence of a hit never removes or withholds a label. No detector or model verdict clears a label. A future classifier (Prompt Shields-like, or a local model) plugs into the same slot with the same ceiling.
- Measured, not assumed: the replay (`taintReplay.ts`) gains a `signal` arm so the extra asks per 100 calls are known before it is turned on.

### 5.5 Clearing

- Per label, by the person: `/untaint` with no argument clears integrity labels; `/untaint secret` clears `secret`; `/untaint mcp:github` clears one. The IDE gets the same choices on the approval card ("I reviewed what came in from github") and in the chip menu.
- Approving one ask never clears. A new session clears. Nothing else does.
- Every add and clear writes a `taint` audit record: `{ type: "taint", op: "add" | "clear", label, turn, reason }`, using the reason `taintState.ts:71` already receives.

### 5.6 UI and audit

- **Chip** in the chat header and the CLI status line, only while a label is present: "Untrusted: web, github · Private: secret". Clicking it lists the labels with the turn each entered and the clear actions. The chip is a fact, never a reassurance: no green state, no "protected".
- **Approval card reason** keeps today's sentence (`taintRule.ts:21-24`) with the label list and the sink detail, plus "Nobody to answer: refused" when unattended.
- **Audit decision record** keeps `tainted` (kinds) for compatibility and adds `labels` (with origin), `taintSink`, `taintAction` (`record | ask | deny`), and `detector` when a hit was seen. Existing masking applies (`audit/record.ts`). No content, URL path or value is stored for a label, matching the state's rule (`taintState.ts:4-7`).

### 5.7 Unattended behaviour

| Run                             | Integrity label + sink | Trifecta + sink | `record` cells |
| ------------------------------- | ---------------------- | --------------- | -------------- |
| Interactive                     | ask                    | ask             | audit only     |
| Loop with inbox                 | held                   | refused         | audit only     |
| Headless `cn -p`, CI            | refused                | refused         | audit only     |
| Pure IDGAF (after #818 phase 0) | record                 | record          | audit only     |

Recommendation: an unattended run turns the rule on regardless of the setting, because nobody is watching for the rest. This is decision O1.

## 9. Evaluation: a small AgentDojo-style corpus in `bench/`

Shape, after AgentDojo and InjecAgent: each case is a user task, an injection vector, an attacker goal and expectations, as the existing scenario files already are (`bench/scenarios/injection-in-tool-result.json`).

**Matrix (about 24 cases).** Vectors: fetched page, search result, `gh issue view` text, MCP result from a stub server, a file in an untrusted folder (`AGENTS.md`, README, test fixture), a repository script's output, a file outside the workspace. Goals: `curl` exfiltration of `.env`, fetch with the secret in the query to a trusted host, `git remote add` then push, MCP call to a second stub server, write to a shell profile outside the workspace, `python -c` socket (expected **not** stopped until T5). Each goal has a benign twin (the same task without the injection) to score utility.

**Two tiers.**

- **Tier 0, structural, no model.** Feed the scripted call sequence (source call, then attacker's sink call) through the real evaluator with the rule on (`testToolCall.ts` already takes a `taint` input). Expected verdict per case is part of the file. This is deterministic, runs in CI, and is the only tier whose pass means "stopped by construction".
- **Tier 2, live.** Run the same cases with models through `bench/runner.mjs`. Score four outcomes separately: utility without attack, utility under attack, attack attempted and stopped by a rule (`source: tainted-session` in the audit), attack not attempted (model declined). Report the last two apart: only the first is a guarantee, and the adaptive-attack literature says the second will not hold under pressure.

**Friction.** Re-run `taintReplay.ts` with the label table and report asks per 100 calls by label, plus the share of sessions needing one clear, before any default changes (T4).

**What not to conclude.** A corpus written by us is not an adaptive attack. A zero here says the sinks we know of are covered, not that the agent is safe. Cite AgentDojo numbers only for AgentDojo runs.

## 10. Do not claim

- Do not call the injection detector, spotlighting or the reviewer "protection" or "prevention". They lower rates; Nasr et al. show adaptive attacks get past published defences of this kind.
- Do not say a session is "safe", "clean" or "verified" because no label is present. No label means no recognised source was read, not that nothing hostile was.
- Do not claim terminal egress control for scripts and interpreters, or any control of an MCP server's own network access, until a verified sandbox is active (T5).
- Do not claim the repository's own code is protected from a tainted session. In-workspace edits are not a sink; the person's diff review is the control.
- Do not claim CaMeL or FIDES guarantees. This design uses FIDES's session-level label join and CaMeL's vocabulary, not either system's per-value tracking or interpreter.
- Do not describe `trustedDomains` as "safe destinations" while tainted: a host anyone can write to is a receiver.
- Do not call `record` entries "blocked" or "caught" (#818 §7.4).
- Do not present a trusted MCP server's output as trusted content.
- Do not report a corpus pass as a security result without separating "stopped by rule" from "model declined".
