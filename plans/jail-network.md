# Jail, network policy and escape tests: design for Track W rows W5 to W8

Status: research and design, 2026-11-10. Built so far as pure code, wired into nothing: W6a and the decision half of W6b (`core/util/egressPolicy.ts`, `core/util/egressPresets.ts`) and W7a (`core/util/escapeProbes.ts`, `core/util/escapeProbeRunner.ts`). The proxy listener, the model gateway, executor wiring and every backend's probe run are not built.

Research of 2026-11-10 against `origin/main` of b1tninja/continuous (fetched that day). Read-only: no repo edits. "Verified" means read on the cited page on 2026-11-10; "unverified" means inferred, reported second-hand, or not checked, and is collected in section 9.

## 1. What the code does today (the seams)

- `core/util/commandExecutor.ts`: three executors (local, wsl, container). The container executor is one `docker run --rm` per command (`containerArgs.ts`: `--network none`, `--cap-drop ALL`, `no-new-privileges`, `--read-only`, tmpfs `/tmp`, pids and memory limits, host uid, one rw bind mount of the workspace, no env passed). There is no long-lived container, no proxy, no way to reach anything from inside. That is right for W2 and wrong for W5, which needs a process that lives for a loop.
- The local executor spawns with `process.env` spread in (`runTerminalCommand.ts` line 126), so any host secret reaches commands that are not in a container. A whole-process jail must build its environment from nothing, not scrub the host's.
- `core/tools/permissions/destinations.ts` already normalises hosts (octal, hex, decimal, IPv4-mapped IPv6) and has `hostInNetSet(host, "metadata" | "local" | "private")`. The egress proxy should reuse exactly this for its resolved-address denial. `unresolved` destinations (built from a variable) are "unsure" today; in a `none` jail they stop mattering.
- `extensions/cli/src/commands/serve.ts` listens on `host:port` (loopback default), with `installServeGuards` (Host and Origin checks, bearer token). A `--network none` container cannot publish a port, so the IDE-to-jailed-serve link needs a different transport (row W5c).
- Keys: `${{ secrets.NAME }}` resolves in `LocalPlatformClient` from IDE secure storage, then `~/.continuous/.env`, `<workspace>/.continuous/.env`, `<workspace>/.env`, then the process environment. Anthropic and OpenAI-compatible adapters take `apiBase` and `apiKey`. Bedrock (`packages/openai-adapters/src/apis/Bedrock.ts`) takes a bearer token (`authSchemePreference: ["httpBearerAuth"]`) or IAM credentials (static keys, a named profile, or `fromNodeProviderChain`). Mantle is an OpenAI-compatible adapter on `bedrock-mantle.<region>.api.aws` with a bearer key. `packages/fetch/src/agent.ts` already handles proxies, custom CA and `NO_PROXY`.
- The owner works behind a TLS-inspecting enterprise proxy (`plans/fork-plan.md`). That constrains section 4.

## 2. Threat model for an unattended loop

Attacker: text the model reads (repository files, issue text, web pages, MCP results, dependency install scripts) that steers it. Nobody is watching, so every "ask" becomes a stop or an auto-deny. Goals, in the order a jail must answer them:

1. **Steal secrets**: the model API key, cloud credentials, `~/.ssh`, `.env` files, environment variables, the IDE's secure storage.
2. **Exfiltrate**: over HTTP to an attacker host, over DNS, through an allowed host that accepts uploads (a git push to any GitHub repository, a gist, a storage bucket), or through the model provider itself.
3. **Persist on the host**: files the host later executes. Git hooks, `.git/config` (`core.fsmonitor`, `hooksPath`), `.vscode/tasks.json`, shell rc files, `.continuous/` config, `package.json` scripts, `.envrc`. CVE-2026-25725 is this class in Claude Code's bubblewrap sandbox: with `.claude/settings.json` absent at startup the parent stayed writable, so the sandbox could plant hooks that ran with host privileges at next start (fixed in 2.1.2; [NVD-derived page](https://www.tenable.com/cve/CVE-2026-25725), 2026-11-10; severity scores differ by source).
4. **Reach neighbours**: host loopback services (including the IDE's own `cn serve`), the LAN, cloud metadata, the Docker socket.
5. **Damage and spend**: delete the workspace, burn tokens, fill a disk. A jail does not stop damage inside the writable mount; checkpoints do (`plans/checkpoints.md`). The claim must say so.
6. **Escape the boundary**: kernel and runtime bugs. Out of scope as a guarantee (`isolation.md`), but versions are reported.

Two framing facts from vendors. Claude Code's own docs say effective sandboxing needs both filesystem and network isolation, and that the per-command sandbox "is not sufficient for fully unattended runs"; whole-process boundaries (dev container, sandbox runtime, VM) are what they recommend ([sandbox-environments](https://code.claude.com/docs/en/sandbox-environments.md)). Their dev-container page warns that with permission checks skipped a container "do[es] not prevent a malicious project from exfiltrating anything accessible inside the container" ([devcontainer](https://code.claude.com/docs/en/devcontainer)). So the property that matters is what is inside, which is why the key must not be.

## 3. Host-proxy architecture for model calls (W5)

### Pattern and precedents

Everyone converges on one pattern: a proxy outside the boundary injects the credential, the agent holds a placeholder. Anthropic's secure-deployment guide: "run a proxy outside the agent's environment that injects the key into requests", with `ANTHROPIC_BASE_URL` for sampling and a Unix-socket mount into a `--network none` container ([secure-deployment](https://code.claude.com/docs/en/agent-sdk/secure-deployment.md)). Claude Code cloud sessions keep git credentials in a proxy and give the sandbox a scoped credential that the proxy checks per operation ([engineering post](https://www.anthropic.com/engineering/claude-code-sandboxing)). Docker Sandboxes inject auth headers at a host-side forward proxy; "credential values are never stored inside the VM" ([isolation docs](https://docs.docker.com/ai/sandboxes/security/isolation.md)); only the forward proxy injects, the transparent one does not. sandbox-runtime offers `credentials: mask` (sentinel in the sandbox, proxy substitutes on egress to `injectHosts`) but it needs experimental `tlsTerminate` ([README](https://github.com/anthropic-experimental/sandbox-runtime)).

### Decision: reverse proxy ("gateway") for model hosts, not CONNECT plus MITM

The jailed `cn` is configured with `apiBase = http://127.0.0.1:<relay>/<provider>` and `apiKey = <per-run token>`. The model proxy terminates plain HTTP on loopback, authenticates the token, rewrites the request and opens its own TLS connection upstream. Advantages: no CA in the jail for model traffic; the proxy sees the body, so it can enforce a path allowlist; streaming passes through; the host's system CA and corporate proxy (`packages/fetch` agent) are used upstream, so the jail never needs the enterprise root for model calls.

Routes (all other paths 403, and client-supplied `Authorization`, `x-api-key`, `x-amz-*` are stripped before injection):

| Provider                                                   | Upstream                                 | Allowed                                                                                                                                       | Injection                                                  |
| ---------------------------------------------------------- | ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Anthropic                                                  | `api.anthropic.com`                      | `POST /v1/messages`, `/v1/messages/count_tokens`, `GET /v1/models`                                                                            | `x-api-key`, keep `anthropic-version` and `anthropic-beta` |
| OpenAI-compatible (OpenAI, OpenRouter, local, Azure shape) | the configured `apiBase` host, pinned    | `/v1/chat/completions`, `/v1/responses`, `/v1/models`, `/v1/embeddings`                                                                       | `Authorization: Bearer`                                    |
| Bedrock Converse with bearer key                           | `bedrock-runtime.<region>.amazonaws.com` | `POST /model/{id}/converse`, `/converse-stream`, `/invoke`, `/invoke-with-response-stream`; model id optionally pinned to the configured list | `Authorization: Bearer <real key>`                         |
| Bedrock with IAM (SigV4)                                   | same host                                | same                                                                                                                                          | proxy signs                                                |
| Mantle                                                     | `bedrock-mantle.<region>.api.aws`        | the model's path prefix (`/v1` or `/openai/v1`)                                                                                               | bearer                                                     |

The path allowlist matters: the injected key is the user's, so without it the jail could call file, batch or admin endpoints as the user.

### Bedrock: one client path for both auth types

Make the in-jail Bedrock client always use the bearer scheme with a sentinel token (the code path at `Bedrock.ts` lines 312-323 exists). The host proxy then either swaps in the real bearer token or **signs** the request itself with host credentials (`@smithy/signature-v4` plus `fromNodeProviderChain`, which covers SSO, profiles and assumed roles). SigV4 covers the host header, date and payload hash, so the proxy must sign the request it actually sends: buffer the (JSON, small) request body, hash, sign, forward; stream the response untouched. Envoy's AWS request signing filter works the same way (credentials live on the proxy host) but is documented experimental and has buffer limits ([Envoy docs](https://www.envoyproxy.io/docs/envoy/latest/_sources/configuration/http/http_filters/aws_request_signing_filter.rst.txt)); a small Node implementation reusing the adapter's own credential chain is the lower-risk choice. For long-term bearer keys, the proxy can mint short-term keys from its credentials with `@aws/bedrock-token-generator` (up to 12 hours, same-region only, [AWS docs](https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys.html)), but because the proxy holds the real credential anyway, minting only helps if the real credential is itself longer-lived than you want in memory. Bearer tokens are controlled by the IAM actions `bedrock:CallWithBearerToken` and `bedrock-mantle:CallWithBearerToken`; which Bedrock APIs reject bearer tokens is unverified.

### The per-run token

A random 256-bit value generated by the host per jail start, valid for that jail's run, bound to the listener, revoked at jail stop or loop end. It is not the provider key and is useless elsewhere. On a Unix socket mounted only into one jail it is defence in depth; on a TCP loopback listener (Windows) it is essential, with the Host check from `installServeGuards` to resist DNS rebinding against the proxy itself. Add per-run limits: request count, token budget (feeds `loop-budgets.md`), body size, and a request log kept on the host.

### What else is in the jail

- **Environment**: build from empty. Pass only a short allowlist (`PATH`, `LANG`, `HOME` pointing at a tmpfs, the proxy variables, the CA bundle variables). Never mount `~/.ssh`, `~/.aws`, `~/.continuous`, browser profiles, or the Docker socket.
- **Secrets resolved in the jail**: none. `${{ secrets.* }}` is resolved on the host; for the jail the config writer substitutes the sentinel or the proxy route. Workspace `.env` files are in the workspace and therefore readable: the jail cannot hide them, so `protect-secrets` stays on for workspace files.
- **MCP servers inside the jail**: stdio servers needing secrets are unsupported in v1 (say so). Remote HTTP servers with auth are fronted as reverse routes (`/mcp/<name>`) with header injection, which also keeps OAuth tokens out (the fork's OAuth work stores them on the host). Later slice.
- **Workspace and persistence**: a bind-mounted rw workspace is a delayed-escape channel (threat 3). Default for loops: run on a worktree or clone (Tracks N and O already have worktree code), mount `.git/hooks` and `.git/config` read-only (Codex keeps `.git` read-only even in `workspace-write`, [OpenAI docs](https://learn.chatgpt.com/docs/agent-approvals-security.md); sandbox-runtime denies `.git/hooks` and `.git/config` and `.mcp.json`, but on Linux builds its deny list once at launch, so nothing created later is covered, per sandbox-environments, verified), and apply the result as a reviewed patch. Docker's `--clone` mode (host repo mounted read-only, agent on a private clone) is the same idea.
- **Trust bundle**: behind a TLS-inspecting proxy, an opaque CONNECT tunnel carries the enterprise-signed certificate to the in-jail client, so npm, pip, cargo and git inside the jail need the enterprise root. Export the host's trust store (`tls.getCACertificates("system")` on Node 22.15 or later, per [Claude Code network docs](https://code.claude.com/docs/en/network-config.md)) to a PEM mounted read-only, and set `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `CARGO_HTTP_CAINFO`, `GIT_SSL_CAINFO`. Public data, not a secret. The egress proxy chains to the corporate proxy upstream.
- **The jail still talks to the model**: the model provider is an exfiltration channel (prompts leave the machine anyway). The proxy cannot fix that; the claim must not say "nothing leaves".

## 4. Network policy model and registry presets (W6)

### Modes

`none` (no route; the model proxy still works), `allowlist` (the model proxy plus named hosts through one egress proxy), `open` (no proxy; the UI says "open"). Direct sockets are blocked by the backend, never by convention: no network namespace or `--network none` or internal network or WFP filter, and the proxy variables are conveniences for tools that honour them. Claude Code's docs note UDP, HTTP/3 and ICMP cannot leave, and tools ignoring proxy variables (plain `ssh`, most database drivers) fail even to allowed hosts ([sandboxing](https://code.claude.com/docs/en/sandboxing.md)); expect the same.

### Proxy rules (what to build, and why)

1. **Name resolution happens only in the proxy.** The jail has no resolver. This closes DNS exfiltration: CVE-2025-55284 was `ping`/`nslookup`/`dig`/`host` auto-approved, leaking `.env` into a subdomain ([write-up](https://embracethered.com/blog/posts/2025/claude-code-exfiltration-via-dns-requests), fixed by un-allowlisting them), and Anthropic's own devcontainer firewall leaves UDP 53 open to any server (verified by reading `init-firewall.sh`), which is a tunnel. Proxy-based exfiltration of split secrets still works through allowed hosts; per-run byte budgets and request logging are the only mitigation.
2. **Resolve, check every address, connect to the pinned address.** Deny the whole answer if any record is loopback, link-local, metadata, private or the host's own interfaces (reuse `hostInNetSet`), as sandbox-runtime does ("resolves and drops addresses in a denied set", verified) and Codex does (loopback and private blocked by default, `allow_local_binding = false`, verified). Re-check on every connection (DNS rebinding: a name that was public at check time flips later; [practitioner analysis](https://sbf-pages.pages.dev/writing/dns-rebinding-in-2026), secondary source). An allowed hostname that resolves to `169.254.169.254` must fail.
3. **IP literals** (any spelling) are denied unless listed; normalise with `normalizeHost` first.
4. **CONNECT only to 443** (and listed ports), plain-HTTP forward only to listed hosts. Deny wins over allow; wildcards match subdomains only unless written with the apex.
5. **Domain fronting** is the known gap of a non-inspecting proxy; Anthropic says so explicitly and recommends a TLS-terminating custom proxy for stronger guarantees ([sandboxing limits](https://code.claude.com/docs/en/sandboxing.md#security-limitations)). Cheap partial mitigation: read the ClientHello SNI and require it to equal the CONNECT host (defeated by Encrypted ClientHello, so also refuse tunnels that offer ECH; unverified feasibility). Say in the claim that allowed hosts on a shared CDN edge are only as separated as the CDN makes them.
6. **Broad hosts are exfiltration holes.** `github.com` accepts pushes to any repository; `storage.googleapis.com` accepts any bucket. Warn in the preset; the real fix (filter `git-receive-pack`, restrict by path) needs TLS termination, a later slice (W6e).
7. **Denials name themselves**: the proxy returns a body and logs "host X not on the allowlist (preset npm?)", and the agent's tool result carries it, so the agent and the person know it was the jail.

## 5. Escape tests per backend (W7)

### Method

A probe bundle (one static script plus a small Node driver) runs through any `CommandExecutor`, with **canaries** prepared by the harness: a fake `~/.ssh/id_probe`, `~/.aws/credentials`, `<parent>/.env`, `~/.continuous/.env` holding a fake API key, an environment variable `PROBE_SECRET`, a host loopback listener, a listener on the LAN address, and a UDP/DNS capture. Each probe prints `{id, property, verdict: pass|fail|skip|unsupported, evidence}`. Probes are behavioural, not kernel exploits: the claim is "these probes found no way through", never "cannot be escaped". Results carry backend, runtime versions, platform, config hash and time.

### Common probes (all backends)

| Property                    | Probes                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| Host-executed files         | write `.git/hooks/*`, `.git/config` (`core.hooksPath`, `fsmonitor`), `.vscode/tasks.json`, `.continuous/*`, `.mcp.json`, `package.json` scripts, `.envrc`; run `git init` and `git clone` inside, then write the new repo's hooks (the Linux deny-list-built-at-launch gap). Result is reported per path, not pass or fail overall                                                                                                                                            |

### Backend-specific probes

- **Container (docker, podman)**: runtime version against the fixed runc releases for the three November 2025 flaws (masked paths, `/dev/console`, procfs write redirects; fixed in runc 1.2.8, 1.3.3, 1.4.0-rc.3, [Sysdig](https://sysdig.com/blog/runc-container-escape-vulnerabilities), [BleepingComputer](https://bleepingcomputer.com/news/security/dangerous-runc-flaws-could-allow-hackers-to-escape-docker-containers); report a "runtime patched" property by version, do not exploit); rootless or rootful; `--privileged`, `--pid host`, `--net host`, Docker socket and devcontainer `runArgs` detection (W3); on Docker Desktop, state that the boundary is the VM, not Windows; bind-mount of an NTFS workspace: symlink and case-folding behaviour (unverified).
- **bubblewrap or sandbox-runtime (Linux, WSL2)**: user namespaces available or fail closed (Ubuntu 24.04 can need `kernel.apparmor_restrict_unprivileged_userns=0`, verified); `allowNestedUserNamespaces` false (when true "code ... can end up running outside the sandbox"); seccomp active, because without it Unix sockets are unrestricted and only a warning is shown (verified); TIOCSTI/new-session terminal injection (unverified for current builds); the config-injection class above.
- **Seatbelt (macOS)**: `/tmp` versus `/private/tmp` symlink resolution, Mach and XPC lookups (`allowMachLookup`), Apple Events and `open`/`osascript` (removes code-execution isolation if allowed), `security` keychain access, pasteboard, the `trustd` network path (`enableWeakerNetworkIsolation`). `sandbox-exec` is deprecated but works (verified earlier in `isolation.md`); record the macOS version.
- **WSL2**: write to `/mnt/c` and `/mnt/d` (automount); run `cmd.exe` and `powershell.exe` (interop); Windows `PATH` appended; Docker Desktop socket in the distro; Windows-side reach to `\\wsl$` (reverse direction); reach to the Windows host through the NAT gateway and, in mirrored networking mode, through loopback (unverified); `/mnt/wsl` shared across distros (unverified); all WSL2 distros share one VM. A default distro is not a jail: the W9 route is a dedicated imported distro with `[automount] enabled=false`, `[interop] enabled=false`, `appendWindowsPath=false` in `wsl.conf` ([MS reference](https://learn.microsoft.com/windows/wsl/wsl-config); community use of these keys as hardening only, nothing authoritative says they form a boundary), plus bubblewrap inside. The probe run decides what the claim says.
- **Windows Sandbox**: mapped folders rw or ro, clipboard, audio, vGPU and networking toggles in the `.wsb`, network all-or-nothing, results only through a shared folder (`wsb exec` returns no output, per `isolation.md`).

### Where it runs

Linux container and bwrap probes run in CI on a Linux runner. macOS needs a macOS runner. Windows and WSL probes run in the existing Windows Sandbox recipe or a developer machine and are pinned as recorded results, not CI gates (hosted Windows runners with WSL2: unverified). The probe bundle versions with the claim generator; the runtime result is also produced on the user's machine on demand ("Verify this jail", a few seconds with canaries) because claims about a backend depend on the machine.

## 6. W8: how decisions read the properties, and what the UI may claim

### The data

`IsolationProperties` (produced by W7, never hand-written):

```
backend, scope: "command" | "process", platform, runtime versions, configHash, verifiedAt, evidence: probeId -> verdict
writes: "workspace" | "workspace+tmp" | "host"        hostExecutedFilesWritable: paths[]
reads: "workspace" | "allowlist" | "host"               secretsInside: string[]   (canary names found)
network: "none" | { allowlist: hosts[] } | "open"       reachesHostLoopback, reachesLan: boolean
processes: "own" | "host-visible"   dockerSocket: boolean   kernelBoundary: "shared" | "vm"
persistence: "disposable" | "workspace" | "host"
```

### How `policy-areas.md` levels use it

Order is unchanged: floor and deny and ask rules first, then the level. The jail only turns "the rules left it open" into a quieter answer where the property that matters holds, and never touches the floor, the reviewer, `access` questions or protected paths.

- **Tool use, command writes**: today a command "can still write files"; with `writes = workspace` verified, the write-target check plus the jail covers it, so the note on the File edits control changes to "commands write only inside the workspace".
- **Tool use, network commands**: with `network = none`, `curl` and friends are harmless and `unresolved` destinations stop being "unsure"; with an allowlist, `host:` and `net:` rules still run as a cheap early check and the jail enforces; with `open`, nothing changes from today.
- **File edits**: an in-workspace write is allowed where it would have asked only because the command could not be bounded. `hostExecutedFilesWritable` non-empty keeps the ask for those paths, or the mount makes the attempt fail visibly.
- **Context use**: `reads = workspace` plus passed canary probes let reads of `~/.ssh`-style paths drop out of the "ask", since they cannot succeed; workspace `.env` stays protected.
- **Loop preset "Unattended, in a jail"**: refuses to start unless `writes = workspace`, no model key in `secretsInside`, `network != open` (or explicit consent with the exfiltration warning), the claim is fresh for this machine, runtime versions and config hash, and the model proxy is healthy. A mid-run backend or proxy loss stops the loop; nothing falls back to the host.
- **Settings**: a `sandbox` key in `POLICY_FILE_KEYS`, shape `{ backend, scope, network: none|allowlist|open, allow: ["preset:npm", "host:..."], requireFor: ["unattended"] }`. It is honoured only from user or machine settings; a workspace file may tighten it but never loosen it or choose a backend (Anthropic applies the same rule to its riskiest sandbox keys: project settings "cannot enable `allowAppleEvents`", and the CVE above shows what a repository-controlled path costs). `sandbox` never changes what a level means (existing rule).

### What the UI may honestly say

Three states per property: **verified** (probe passed on this machine on this date with these versions), **configured, not verified**, **not isolated**. The word "Contained" (D4) appears only when every probe in the contract set passes now. Never "safe" or "secure". Every badge also lists the limits that always hold: the workspace is writable (damage possible, checkpoints exist), the model provider receives what the agent sends, allowed hosts can receive data, a shared kernel (container, bubblewrap) versus a VM. Examples: "Docker, verified 2026-11-10: writes to the workspace only, no network except the model, no host secrets; shared kernel; runc 1.3.3". And: "WSL: not isolated: `/mnt/c` is writable and Windows programs can be started". A claim goes stale when a runtime version, the config hash, or the platform changes (and after a TTL, 7 days proposed), and a regression flips the badge because the text is generated from `evidence`; pin the claim strings with snapshot tests.

## 8. Risks

- Sidecar and relay reachability on Docker Desktop are the most likely place for the design to need rework; test W6c on Windows first.
- A host proxy is a new network-facing component holding the key; it must listen on a Unix socket or an authenticated loopback port only, and be as small as possible. A bug there is worse than a missing jail.
- Domain fronting, shared CDNs and broad hosts mean `allowlist` is not exfiltration-proof; the claim says "limits where data can go", not "prevents leaks".
- `sandbox-runtime` is a beta research preview with a changing configuration format; Windows backend is alpha. Pin versions; use it for W4, not as the only W5 path.
- Delayed escapes through workspace files are likely the most realistic attack; worktree plus read-only hooks plus patch review matters more than network detail.
- Probes can pass on a backend and still miss a class: the claim must be conditional on the probe version.
- Tools that ignore proxy variables will fail confusingly; the denial message must say "no direct network in the jail".
- Behind the corporate proxy, installs inside the jail depend on the exported trust bundle; a stale bundle fails TLS, not safely-but-silently.
