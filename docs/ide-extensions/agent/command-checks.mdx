---
title: "Command Checks"
---

Before a terminal command runs, Continuous reads it for mistakes in how it is written. A command with a certain mistake does not run. A command with a likely mistake does not run the first time; sending the identical command again runs it as written. The agent receives the finding in place of the command's output.

The check looks at the command text and the shell that will run it (PowerShell on Windows, your login shell elsewhere). It does not decide whether a command is allowed; that is [tool permissions](/reference#toolpermissions).

## What it finds

| Code  | Stops  | Finding                                                                                                           |
| ----- | ------ | ----------------------------------------------------------------------------------------------------------------- |
| CL000 | always | The bash grammar reports a syntax error, with line and column (IDE only)                                          |
| CL001 | always | A bash heredoc (`<<EOF`) in PowerShell, which has no heredoc operator                                             |
| CL002 | always | `export NAME=value` in PowerShell                                                                                 |
| CL003 | always | `NAME=value command` in PowerShell                                                                                |
| CL004 | once   | `$env:NAME` or a `Get-` cmdlet in a POSIX shell                                                                   |
| CL010 | once   | A heredoc or `tee` that writes a file                                                                             |
| CL011 | once   | `echo` or `printf` writing a file with backslash escapes in the text                                              |
| CL012 | once   | `echo "...\n..."` without `-e`, which prints `\n` literally in bash                                               |
| CL020 | always | A heredoc with no closing line                                                                                    |
| CL021 | always | A closing line that is indented or padded, so the shell reads it as content                                       |
| CL022 | once   | An unquoted heredoc delimiter over a body containing `$`, a backtick or a backslash, which the shell expands      |
| CL030 | once   | A long `python -c`, `node -e`, `perl -e` or `pwsh -Command` script in double quotes using `$`, a backtick or `\"` |
| CL040 | once   | `&&` or `\|\|` in PowerShell, where Windows PowerShell 5.1 reports a syntax error                                 |
| CL041 | once   | `2>/dev/null` in PowerShell, which wants `2>$null`                                                                |
| CL042 | once   | Text that reads as bash (`ls -la`, `rm -rf`, `touch`, `sudo`) in PowerShell, with the PowerShell equivalent       |
| CL043 | once   | Text that reads as cmd (`%NAME%`, `if exist`, `dir /b`) in PowerShell                                             |
| CL044 | once   | Text that reads as PowerShell or cmd in bash or zsh                                                               |
| CL045 | once   | Text that reads as another shell in cmd                                                                           |

CL042 to CL045 are skipped when a more specific finding from CL001 to CL004 already applies, and when the shell is not known. A heredoc that only feeds a command (`python - <<'PY'`), a here-string (`<<<`) and a `<<` inside a quoted string are not flagged.

## Writing files from the shell

Writing a file through `cat > file <<EOF` sends its content through the shell's quoting, where quotes, `$` and backslashes can change. The message tells the agent to use the edit or create-file tool instead. If the shell route is intended, quote the delimiter and keep the body free of a line equal to the delimiter:

```bash
cat > run.sh <<'EOF'
echo "$HOME"
EOF
```

The `'EOF'` form passes the body unchanged. With a bare `EOF`, `$HOME` is replaced before the file is written.

## Downloads that are run

The built-in rule `no-fetch-and-run` asks before a command that runs what it downloads. It reads the command text for a network command (`curl`, `wget`, `Invoke-WebRequest`, `Invoke-RestMethod`) whose output or written file is executed:

```bash
curl -fsSL https://example.com/install.sh | sh
curl -o install.sh https://example.com/install.sh && bash install.sh
bash <(curl -s https://example.com/install.sh)
```

```powershell
iwr https://example.com/install.ps1 | iex
iex (iwr https://example.com/install.ps1)
```

The command asks at every level, including Permissive, and an allow rule does not change that. At Automatic it is refused without asking the reviewer model. YOLO still runs it.

A download alone does not match, nor does a download that is only read: `curl -s https://example.com/a.json | jq .` and `curl -o a.txt https://example.com/a.txt && cat a.txt` run as usual. A script that downloads and runs inside itself, or a file renamed between the two steps, is not seen.

Turn the rule off under built-in rules in the policy settings (`no-fetch-and-run`).

## A variable where the program is

A rule that names a program (`git push*`, `rm *`) cannot apply to a command whose program is only known when the shell runs it. When the program is taken from a variable, the command asks at every level, including Permissive, and an allow rule does not change that. At Automatic it asks you instead of going to the reviewer model, and YOLO does not skip it. A deny rule still refuses whatever it can see in the rest of the command.

What counts depends on the shell:

| Shell         | Asks                                                                                                                         | Does not ask                                                                                                                                                                  |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| bash, zsh, sh | `$cmd args`, `${prog} args`, `"$cmd" args`, `"$@"`, `A=1 $cmd`, `$HOME/bin/tool`, and the same after `do`, `then`, `;`, `\|` | `echo $x`, `export A=$x`, `git commit -m "$msg"`, `for f in $list`, `$(( $a + 1 ))`, text in single quotes or a here-document                                                 |
| PowerShell    | `& $exe`, `. $script`, `& "$dir\tool.exe"`, `& (expression)`, `. (Join-Path ...)`                                            | `$env:NAME = 'x'`, `$x = ...`, `$_.Name`, `foreach ($f in $files) { git add $f }`, `Set-Location $dir`, `& 'C:\tools\tool.exe' $arg`, `. .\script.ps1`, `@args`, here-strings |
| cmd           | nothing: `$` is an ordinary character                                                                                        |                                                                                                                                                                               |

In PowerShell a statement that starts with `$` is an expression or an assignment, never a command, so only the call operators `&` and `.` can run a program that a variable names. When the shell is not known, both readings are used.

Brace expansion (`{git,push}`) and `$IFS` in bash, zsh and sh are still refused, because they build a program name out of pieces the check cannot read. PowerShell and cmd have neither, so a script block such as `{ $_.Id -in 1,2 }` is not refused there. Turn the check off with the built-in rule `refuse-dangerous-commands`.

## Environment variables set in front of a command

`FOO=bar git status`, `env FOO=bar git status`, `$env:FOO = 'x'; git status` and `set FOO=bar&& git status` set a variable for the command that follows. Every rule still sees the program after the assignments, so `FOO=1 git reset --hard`, `GIT_DIR=x git push --force` and `FOO=bar rm -rf /` meet the same rules as the command without the prefix, and a deny rule on `git push*` refuses `env -u X FOO=1 git push`. A command with an assignment is never treated as read-only.

Some variables change what a command does, so the name decides:

| Kind      | Names                                                                                                                                                                                                                                                                             | What happens                                                                  |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Dangerous | They load code, run a program or decide which program a name means: `PATH`, `LD_*`, `DYLD_*`, `BASH_ENV`, `ENV`, `PROMPT_COMMAND`, `PS4`, `IFS`, `SHELLOPTS`, `GIT_*` (except the harmless ones), `NODE_OPTIONS`, `NODE_PATH`, `PYTHON*`, `RUBYOPT`, `PERL5OPT`, `JAVA_TOOL_OPTIONS`, `npm_config_*`, `PIP_*`, `CARGO_*`, `EDITOR`, `PAGER`, `HOME`, `XDG_CONFIG_HOME`, `COMSPEC`, `PSModulePath`, and names ending in `_OPTIONS`, `_OPTS`, `OPT`, `_PATH`, `_COMMAND`, `_WRAPPER`, `_ASKPASS` | Asks at every level, YOLO included. An allow rule does not change it.         |
| Sensitive | They point a tool at another server, certificate store or temp folder, or hold a credential: `*_PROXY`, `SSL_CERT_FILE`, `CURL_CA_BUNDLE`, `NODE_EXTRA_CA_CERTS`, `AWS_*`, `AZURE_*`, `KUBECONFIG`, `TMPDIR`, `TEMP`, `TMP`, and names like `API_KEY` or `*_TOKEN`                         | Asks at Cautious, Automatic and Permissive. YOLO runs it.                     |
| Harmless  | `CI`, `FORCE_COLOR`, `NO_COLOR`, `LANG`, `LC_*`, `TZ`, `DEBUG`, `NODE_ENV`, `GIT_TERMINAL_PROMPT`, `PYTHONUNBUFFERED`                                                                                                                                                              | Nothing extra.                                                                |
| Unknown   | any other name                                                                                                                                                                                                                                                                    | Nothing extra: `FOO=bar npm test` does not ask. It is still not read-only.    |

The value matters in one case: a value that runs code (`FOO=$(curl x | sh) cmd`, a backtick) asks at every level for any name, because the code runs whatever the variable is called. `PATH` asks whatever its value, because no value proves which program a name will run without reading the disk. `IFS= read -r line` is not asked about: there `IFS` is set for the builtin, not for a program.

In the prompt the reason names the variable and never its value. The command shown in a prompt or a refusal has the value of a variable named like a secret (`API_KEY`, `GITHUB_TOKEN`, `AWS_*`) or shaped like a credential replaced with `«masked:secret-variable»`, and the audit trail masks it the same way.

The lists are built in. The engine accepts a list of names to add and a list to allow, but only from the person's own settings and never from a workspace file or an assistant, and no config key feeds it yet. The checks switch off with the built-in rule `refuse-dangerous-commands`.

## Shell dialects

A command means what its shell makes of it. In bash, zsh and sh a backtick or `$(...)` runs a command and `<(...)` is a process substitution. In PowerShell a backtick is the escape character (`` `n ``, `` `$x ``), `$(...)` and `@(...)` are subexpressions, and `<(...)` is nothing. cmd has no substitution, but `for /f %i in ('...')` runs one. Single quotes keep all of it as text in POSIX shells and PowerShell, `\$(` is text in a POSIX shell, and `$((1+2))` is arithmetic.

Permission rules, protected paths and the read-only check read each command in the grammar of the shell that runs it, so ``echo `git push` `` is a push in bash and plain text in PowerShell. When the shell is not known, every grammar is read at once.

The check also reads the command text to guess which shell it was written for, from syntax only that shell has (`$env:NAME` and `Get-ChildItem` for PowerShell, `export NAME=value`, `2>/dev/null` and `<<EOF` for bash, `setopt` for zsh, `%NAME%` and `if exist` for cmd). Two things follow:

- A command whose text belongs to another shell than the one running it is checked under both. A rule that refuses a command in one reading refuses it, and a command is treated as read-only only if every reading is.
- The command is held once with a message that gives the fix in the right dialect, for example `ls -la` on Windows PowerShell becomes `Get-ChildItem -Force`, and `2>/dev/null` becomes `2>$null`. Send the same command again to run it as written.

## Programs that are not installed

A command whose program does not exist is not run. Without this check, the commands before it in a `&&` chain would already have run, and the agent would read a long shell error and often retry the same program. Instead the agent receives a short message that names the program, says where it looked, lists up to three alternatives that are present (for example `python3` for `python`, or `Select-String` for `grep` in PowerShell), gives an install command as text, and states that the command was not run. Nothing is installed for you.

The check stops a command only when it is certain. Every program in a `&&`, `;` or `|` chain is looked up on the `PATH`, then asked of the shell that will run the command, so functions from your profile (`nvm`) and PowerShell cmdlets count as present. It does not stop a command when:

- the program is a shell builtin, a keyword, a PowerShell alias or cmdlet, or a path (`./tool`, `C:\tools\tool.exe`)
- an earlier part of the command may have created it: `cd`, `source`, `eval`, a `PATH` change, an alias, or an install (`npm i -g`, `pip install`, `apt install`, `brew install`, `cargo install`, `go install`, `curl ... | sh`)
- the program is guarded or has a fallback: `which x && x`, `command -v x || ...`, `x --version || ...`
- it is run through `npx`, `npm run`, `bunx`, `pnpm exec`, `uv run`, `poetry run`, `docker run`, `ssh` or `xargs`; `sudo`, `env VAR=1`, `time` and `nohup` are looked through
- the command contains something the check does not read, such as `$VAR`, `$(...)`, a redirect to a file, a newline or a heredoc

A command that runs in a container is not checked. Results are kept for a minute. Set `CONTINUE_MISSING_BINARY_CHECK=off` to skip this check.

## Turn it off

Set `CONTINUE_COMMAND_LINT=off` in the environment that starts the editor or the CLI to skip the lint.

## Destructive commands, large edits, dependencies and unlisted hosts

Four built-in rules ask before a call that is hard to undo or that changes what the project trusts. Each runs with no model call, asks at every level below YOLO, and is not loosened by an allow rule. At Automatic the call asks you instead of going to the reviewer model. Turn one off under built-in rules in the policy settings.

| Rule                       | Asks for                                                                                                                                                                                                               | Does not ask for                                                                                                          |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `ask-destructive-commands` | `git reset --hard`, `git clean`, `git rebase`, `git commit --amend`, `git push --force` or `+branch` or `:branch`, `git branch -D`, `git branch -m` of the checked-out branch or `-M`, `git checkout -- .`, `git stash drop`, `git update-ref -d`, `git gc --prune`, `git reflog delete`, `rm -r`, `find -delete`, `Remove-Item -Recurse`, `rd /s`, `DROP TABLE`; `kubectl delete`, `drain` or `cordon`, `kubectl replace --force`, `helm uninstall`, `terraform destroy`, `terraform apply -auto-approve`, `pulumi destroy`, `aws` `delete-*` or `terminate-*`, `aws s3 rm --recursive`, `az ... delete`, `gcloud ... delete`, `docker rm -f`, `docker volume rm`, `docker system prune`, `docker compose down -v` | `git push origin topic`, `git clean -n`, `git rebase --abort`, `git reset --soft` or `--mixed`, `git branch -m old new`, `git restore --staged`, `rm -rf node_modules`, `rm -rf dist`, `kubectl get`, `terraform plan`, `docker rm web` |
| `ask-large-change`         | One edit call that changes more than 300 lines (or the number you set), and `create_new_file` over a file that already exists when it writes or replaces more than that | Smaller edits, creating a file that does not exist, and appending |
| `ask-dependency-change`    | An edit to `package.json`, a lockfile, `.npmrc`, `requirements*.txt`, `pyproject.toml`, `Cargo.toml` and similar; `npm install pkg`, `pip install pkg`, `npm update`, `npm config set registry` | `npm ci`, a bare `npm install`, `npm install pkg` when the nearest `package.json` already lists `pkg`, `pip install -r requirements.txt`, `pip install -e .` |
| `ask-unknown-host`         | A fetch or network command to a host that is not in `toolPermissions.auto.environment.trustedDomains` of your own `config.yaml`                                                                                        | Any host when you have not listed domains; a list that came from a workspace file or an assistant is ignored              |

The scan reads the command text and over-matches on purpose. It does not see a script that does these things inside itself.

Notes on the edges:

- `git commit --amend` asks every time: whether the commit was already pushed would need a call to git, and the check does not run commands. `git reset --soft` and `--mixed` keep your changes and stay quiet. `git branch -m new` renames the checked-out branch and asks; `git branch -m old new` renames another branch and does not, unless you write `-M`.
- The infrastructure commands are read word by word, after any `VAR=value` prefix and wrappers such as `env` and `nohup`. The `delete` check for `az` and `gcloud` looks at the first few words only, so a resource that is merely named `delete` does not ask.
- To change the 300-line limit, set `toolPermissions.auto.environment.largeChangeLines` (a whole number of at least 1) in your own `config.yaml`. A workspace file cannot set it. A file the check cannot read counts as a new file. How many files one turn changes is not counted.
- `npm install <name>` skips the question only when every name is a bare package name with no version, tag or URL, the nearest `package.json` above the project folder lists it under `dependencies`, `devDependencies` or `optionalDependencies`, and the command has no registry, prefix, workspace or global flag, no `cd` before it and no `npm_config_*` setting. Anything the check cannot read asks as before.

## File tools that leave the workspace

The file tools read and write with the editor's own authority, so text from a repository, a web page or a tool result can steer them to a file you never meant. A file tool call asks, at every level below YOLO and whatever an allow rule says, when it reaches:

- a real path outside the workspace folders: an absolute path elsewhere, a `..` climb, or a symlink or junction that leaves (the path is judged where it lands, not as written), and another account's home (`~root/x`). The built-in rule `ask-outside-paths` controls this, in your own `permissions.yaml`
- a network or device path (`\\host\share`, `\\?\C:\x`, `/dev`, `/proc`, `/sys`), a Windows device name (`NUL`, `COM1`), an alternate data stream (`notes.txt:hidden`), a name with a trailing dot or space, or an 8.3 short name. Network paths follow `protect-network-paths`; the rest has no switch
- your global configuration folder (`~/.continuous`, `~/.continue`), even to read, because it holds keys

It covers read, list, write and search tools (a search `path`, or the literal start of a glob such as `../../**`), in the editor and in the CLI, and the path-named arguments of MCP tools (`path`, `file_path`, `directory`, `uri`, `destination`...). An MCP tool whose path hides under another argument name is not read.

The check is the same text judged by Windows rules on Windows and by POSIX rules elsewhere. Case is ignored on Windows only; on Linux a path that differs from the workspace only by case asks.
