---
title: "Text Tool-Call Recovery"
---

Some models on Bedrock write a tool call as plain text in their reply instead of making the call, so the agent shows the text and does nothing. Recovery reads such a reply and turns the text into the call. It is experimental and off by default.

```bash
CONTINUE_RECOVER_TEXT_TOOL_CALLS=qwen-xml
```

Set the variable in the environment that starts the editor or the CLI. It takes one name or a comma-separated list:

| Value                | Recovers                                                              | Only for model ids containing |
| -------------------- | --------------------------------------------------------------------- | ----------------------------- |
| `qwen-xml`           | Qwen3-Coder's markup: `<tool_call><function=NAME><parameter=KEY>...`  | `qwen`                        |
| `pythonic`           | Python call syntax, as Nova 2 Lite writes it: `present_plan(title="...")`; also Llama 4's list `[get_weather(city="Paris"), get_time(tz="UTC")]` and Llama 3.x's `<\|python_tag\|>NAME.call(...)` | `nova`                    |
| `llama-json`         | Llama's JSON call as text: `{"type": "function", "name": "read_file", "parameters": {...}}`, or an array of such objects or of JSON strings of them | `llama` |
| `hermes-json`        | Hermes-style JSON in tags: `<tool_call>{"name": "...", "arguments": {...}}</tool_call>` | `qwen`, `hermes`            |
| `glm-xml`            | GLM's tags: `<tool_call>NAME<arg_key>K</arg_key><arg_value>V</arg_value></tool_call>` | `glm`                         |
| `kimi-tokens`        | Kimi K2's section tokens, with ids `functions.NAME:IDX` (forms below) | `kimi`, `moonshot`            |
| `kimi-xtml`          | Kimi K3's XTML tags: `tools`, `call` and `argument` parts (forms below) | `kimi`, `moonshot`          |
| `minimax-xml`        | MiniMax-M2's XML: `<minimax:tool_call><invoke name="NAME"><parameter name="K">V</parameter></invoke></minimax:tool_call>` | `minimax` |
| `minimax-ns-xml`     | MiniMax-M3's namespaced tags, each behind the token `]<]minimax[>[` (forms below) | `minimax`                |
| `toolcall-json`      | NVIDIA's JSON array in tags: `<TOOLCALL>[{"name": "...", "arguments": {...}}]</TOOLCALL>` | `nemotron`                  |
| `harmony`            | gpt-oss's Harmony call: `<\|channel\|>commentary to=functions.NAME <\|constrain\|>json<\|message\|>{...}<\|call\|>` | `gpt-oss` |
| `mistral`            | Mistral's `[TOOL_CALLS]` forms: `[TOOL_CALLS] [{"name": "...", "arguments": {...}}]` and `[TOOL_CALLS]NAME[ARGS]{...}` | `mistral`, `mixtral`, `devstral`, `magistral` |
| `dsml`               | DeepSeek V3.2 and V4 DSML: `<｜DSML｜function_calls>` (V4: `<｜DSML｜tool_calls>`) with `<｜DSML｜invoke name="...">` and `<｜DSML｜parameter name="..." string="true\|false">` | `deepseek` |
| `deepseek-v31`       | DeepSeek V3.1's tokens: `<｜tool▁calls▁begin｜><｜tool▁call▁begin｜>NAME<｜tool▁sep｜>{...}<｜tool▁call▁end｜><｜tool▁calls▁end｜>` | `deepseek` |
| `deepseek-r1`        | The fenced layout of DeepSeek R1 and V3-0324: `<｜tool▁calls▁begin｜><｜tool▁call▁begin｜>function<｜tool▁sep｜>NAME`, a `json` code fence holding the arguments, then `<｜tool▁call▁end｜><｜tool▁calls▁end｜>` | `deepseek` |
| `granite-tokens` | IBM Granite 3.x: `<|tool_call|>[{"name": "...", "arguments": {...}}]` | `granite` |
| `lfm-tokens` | Liquid LFM2: `<|tool_call_start|>[name(arg=...)]<|tool_call_end|>` | `lfm`, `liquid` |
| `hy3-tags` | Tencent Hy3: `<tool_calls:opensource><tool_call:opensource>NAME<tool_sep:opensource>` and suffixed `<arg_key>` / `<arg_value>` tags | `hy3` |
| `solar-tokens` | Upstage Solar Open: `<|tool_call:begin|>ID<|tool_call:name|>NAME<|tool_call:args|>{...}<|tool_call:end|>` | `solar` |
| `longcat-json` | Meituan LongCat: `<longcat_tool_call>{"name": "...", "arguments": {...}}</longcat_tool_call>` | `longcat` |
| `olmo-function-calls` | AI2 Olmo 3: `<function_calls>name(arg=...)</function_calls>` | `olmo` |
| `seed-xml` | ByteDance Seed-OSS: `<seed:tool_call><function=NAME><parameter=KEY>...</parameter></function></seed:tool_call>` | `seed` |
| `cohere-action` | Cohere Command: `<|START_ACTION|>[{"tool_name": "...", "parameters": {...}}]<|END_ACTION|>` | `command`, `cohere` |
| `qwen-xml,pythonic`  | Both                                                                  | each by its own match         |

The same setting can be given per model as `x_continue_recover_text_tool_calls` in `requestOptions.extraBodyProperties`; it takes the same values. Recovery applies to Amazon Bedrock models only, and a model whose id does not match gets no recovery whatever the setting says.

## When recovery is off

Recovery is not needed for the agent to notice. On every provider, a reply that is a tool call written as text, such as `<function=Write>...</function>`, a `<tool_call>` block, a JSON object naming a tool or a call like `present_plan(title="...")`, no longer ends the turn silently. The agent counts it as a stopped turn and sends the model one message saying that nothing was run and asking it to call the tool in the API's own tool-call format. Nothing is parsed from the text and nothing in it is run. The nudge is sent once per turn, so a model that cannot comply is not asked again, and it applies only to a tool that was offered in that request. A tool call quoted in a code block or in inline code is an example, not a call, and is left alone. In the CLI it applies to headless runs (`cn -p`); in the extension, to agent turns outside a Loop run, which has its own nudge for a run that ends without its report.

## Per-model setting

A model entry in `config.yaml` can turn recovery on without environment variables:

```yaml
models:
  - name: Qwen3-Coder
    provider: bedrock
    model: qwen.qwen3-coder-30b-a3b-v1:0
    toolDialect: qwen-xml
```

| `toolDialect` | Effect                                                                                  |
| ------------- | --------------------------------------------------------------------------------------- |
| `auto`        | The default. Nothing changes.                                                           |
| `native`      | The model's calls arrive structured. Recovery is off for this model.                    |
| `off`         | Recovery is off for this model.                                                         |
| `qwen-xml`    | Recover Qwen markup for this model, whatever its id is.                                 |
| `pythonic`    | Recover Python call syntax for this model, whatever its id is.                          |
| `llama-json`  | Recover Llama JSON calls for this model, whatever its id is.                            |
| `hermes-json` | Recover Hermes-style JSON calls for this model, whatever its id is.                     |
| `glm-xml`     | Recover GLM tag calls for this model, whatever its id is.                               |
| `kimi-tokens` | Recover Kimi K2 section-token calls for this model, whatever its id is.                 |
| `kimi-xtml`   | Recover Kimi K3 tag calls for this model, whatever its id is.                           |
| `minimax-xml` | Recover MiniMax-M2 XML calls for this model, whatever its id is.                        |
| `minimax-ns-xml` | Recover MiniMax-M3 namespaced calls for this model, whatever its id is.              |
| `toolcall-json` | Recover `<TOOLCALL>` JSON calls (Nemotron-H, Llama-Nemotron) for this model, whatever its id is. |
| `harmony`     | Recover gpt-oss Harmony calls for this model, whatever its id is.                       |
| `mistral`     | Recover Mistral `[TOOL_CALLS]` calls for this model, whatever its id is.                |
| `dsml`        | Recover DeepSeek V3.2 and V4 DSML calls for this model, whatever its id is.             |
| `deepseek-v31` | Recover DeepSeek V3.1 token calls for this model, whatever its id is.                  |
| `deepseek-r1` | Recover DeepSeek R1 and V3-0324 fenced token calls for this model, whatever its id is. |
| `granite-tokens` | Recover Granite 3.x `<|tool_call|>` JSON-list calls for this model, whatever its id is. |
| `lfm-tokens` | Recover LFM2 token-wrapped Python-list calls for this model, whatever its id is. |
| `hy3-tags` | Recover Hy3 tag calls for this model, whatever its id is. |
| `solar-tokens` | Recover Solar Open token calls for this model, whatever its id is. |
| `longcat-json` | Recover LongCat JSON calls for this model, whatever its id is. |
| `olmo-function-calls` | Recover Olmo 3 `<function_calls>` calls for this model, whatever its id is. |
| `seed-xml` | Recover Seed-OSS tag calls for this model, whatever its id is. |
| `cohere-action` | Recover Cohere Command action calls for this model, whatever its id is. |

Any other value is rejected when the config loads. When `CONTINUE_RECOVER_TEXT_TOOL_CALLS` is set, it wins over `toolDialect`. The same switch decides whether Llama 3.x models are offered tools at all (they are off by default, because they write calls as text): setting `llama-json` in either place turns them on. The setting applies to Bedrock models in the IDE and in the CLI (`cn`); the rules below apply unchanged.

## Test connection

In the Bedrock add-model form, **Test connection** also sends one request with a made-up tool at temperature 0 and shows one line: `Tool calls: native`, `Tool calls: written as text (qwen-xml)`, `Tool calls: not supported` or `Tool calls: unknown`. The request costs a few hundred tokens, the tool is never run, and the check is never sent anywhere else. A result of `written as text` tells you which `toolDialect` to set. Timeouts and errors show `unknown`, not `not supported`.

## Ollama models with a server-side parser

Many Ollama models (for example `qwen3.6`) are served through a renderer and parser: `/api/show` reports `parser: qwen3.5` and a template of just `{{ .Prompt }}`, so there is no tool markup in the template to read. The model-metadata lookup reads the `parser` name first (then the template, then the model name) and maps the parser names it has verified in Ollama's source to a dialect. Because Ollama itself turns the call into a structured one for these models, the hint is marked `serverParses`: the live notice and the recovery suggestion are not shown for that endpoint, and Test connection leaves out the preset line. A parser name that is not in the verified table maps to nothing and falls back to the model name.

## Live notice

When a Bedrock model writes a recoverable tool call as text in a reply (not inside a code fence) and `toolDialect` is not set, the IDE shows one dismissible notice per model per session: "This model wrote a tool call as text (looks like qwen-xml). Turn on recovery for this model?" **Turn on recovery** sets `toolDialect` for that model in `config.yaml`. Nothing is turned on until you click it. The CLI prints a one-line hint once per session instead, naming the key to set.

## Rules

Recovery is strict, because text that looks like a call is sometimes an example. A call is recovered only when all of these hold:

- The model made no tool call of its own in that reply.
- The whole reply is calls, with at most one `<think>` block before them. Prose before the calls ("I'll read it now." and then a call) or after them leaves the reply as text and nothing is recovered, in every dialect and whether the reply streams or arrives whole. The text may be a description or an example of a call, and a call run on a guess is worse than one the model is asked to make again. The reply is not lost: it shows as written, and the nudge above still counts it as a call written as text, so the turn asks the model once to call the tool in the API's own format instead of ending silently. A reply that starts like a call is still held until it ends and then judged as a whole.
- The call names a tool that is in the request, and every argument is one the tool's schema declares, with a value of the type the schema asks for. Every required argument is present.
- A string that is the exact literal of the type the schema declares is read as that value, in every dialect: `"10"` for an integer, `"true"` for a boolean, JSON text for an array or object. Only the plain spelling counts (`10`, not `10abc`, `1e3`, `010` or an empty string), a parameter that may be a string keeps its text, and the recovered call records the repair. This runs only when recovery is on.
- For `qwen-xml`, the reply is nothing but calls and whitespace, and a marker inside a code fence or right after a backtick does not start a call.
- For `pythonic`, each call starts a line at column 0 outside a code fence, uses keyword arguments only, and the reply is nothing but such calls. Values are read as Python literals (strings, numbers, `True`, `False`, `None`, lists, tuples, dicts with string keys) by a small parser. Nothing is evaluated.
- For `llama-json`, the reply is nothing but one call object or an array of them, with exactly the keys `name` and `parameters` (and an optional `type` of `function`).
- For `hermes-json` and `glm-xml`, the reply is nothing but calls (an opening `<think>` block is kept as text), and for `glm-xml` a value is a string unless the schema declares another type, in which case it must be JSON of that type. Both were built from the model chat templates and checked on synthesised fixtures; no live leak of either was captured, so treat them as untested against real replies.
- For `kimi-tokens`, the reply is nothing but one section of calls (an opening `<think>` block is kept as text). Each id must be `functions.NAME:IDX` with `NAME` a tool in the request and ids not repeated, and the arguments must be one JSON object. The form is from the Kimi-K2-Thinking chat template and the vendor's tool-calling guide. The wire form is `<|tool_calls_section_begin|><|tool_call_begin|>functions.NAME:0<|tool_call_argument_begin|>{...}<|tool_call_end|><|tool_calls_section_end|>`. The markers are special tokens: a server that strips special tokens from content leaves `functions.NAME:0{...}`, which cannot be told from prose, so only a reply that still carries the markers is recovered.
- For `kimi-xtml`, the reply is, in order, an optional think part and an optional empty response part (both kept as text; a response part with text is prose, so the reply stays text), one `tools` part and nothing else but the closing `message` tag. The wire form is `<|open|>tools<|sep|><|open|>call tool="NAME" index="1"<|sep|><|open|>argument key="K" type="string"<|sep|>V<|close|>argument<|sep|><|close|>call<|sep|><|close|>tools<|sep|>`. The grammar is derived from the vendor's `encoding_k3.py`: `<|open|>`, `<|sep|>` and `<|close|>` are not special tokens, so a server does not strip them. `index` counts 1, 2, ... in order, each argument's `type` must agree with its text (`string` for text, JSON of that type otherwise), and the arguments the encoder writes as a raw `<json>` block are not recovered. This is the form the model is rendered in, not one captured from a reply.
- For `minimax-xml`, the reply is nothing but `<minimax:tool_call>` blocks of `<invoke name="NAME">` with `<parameter name="KEY">` values (an opening `<think>` block is kept as text). A value is a string unless the schema declares another type, in which case it must be JSON of that type. M2's generation prompt ends inside `<think>`, so a reply that begins with reasoning and a bare `</think>` does not start with a marker and is left as text.
- For `minimax-ns-xml`, the reply is nothing but one `]<]minimax[>[<tool_call>` block of invokes (a leading `<mm:think>` block, or the bare `</mm:think>` the template writes for a turn without thinking, is kept as text). The wire form is `]<]minimax[>[<tool_call>`, then `]<]minimax[>[<invoke name="NAME">`, then `]<]minimax[>[<K>V]<]minimax[>[</K>` per argument, `]<]minimax[>[</invoke>` and `]<]minimax[>[</tool_call>`. Nested objects are tags per key, arrays are `<item>` tags, and each nested value is typed by the schema's `properties` and `items`. `]<]minimax[>[` is not a special token in the tokenizer, so it reaches the client; a stream with it removed is left as text.

The Kimi and MiniMax parsers are for self-hosted servers (vLLM, SGLang, llama.cpp, reached through an OpenAI-compatible provider) that do not run the model's tool-call parser. On Bedrock, Kimi and MiniMax models return structured calls through Converse, so these settings change nothing there. All four were built from the vendor files named in their source headers and checked on synthesised fixtures; no live leak of any was captured, so treat them as untested against real replies.

- For `toolcall-json`, the reply is nothing but one or more `<TOOLCALL>` blocks (an opening `<think>` block is kept as text). A block is a non-empty JSON array of objects with exactly the keys `name` and `arguments`; `arguments` is an object, or a string holding one. Several calls in one array, or several blocks, are all recovered. Unlike NVIDIA's own vLLM parser, which keeps only the first block and silently drops a call that has no `arguments`, one bad call (no `arguments`, `parameters` instead, a bare object that is not in an array, an unknown tool, an argument the schema refuses) makes the whole reply stay text, and it is counted as held and released as text in the recovery counts. The form comes from the model's chat template; no live reply was captured, so treat it as untested against real replies.

- For `pythonic`, besides one call per line, a reply can be Llama 4's bracketed list, `[get_weather(city="Paris"), get_time(tz="UTC")]` (every element must be a valid call and a trailing comma is refused), or Llama 3.x's `<|python_tag|>NAME.call(k="v")`. Llama 4's own prompt forbids prose around the list, and as for every dialect prose before or after the calls leaves the reply as text.
- For `harmony`, the reply is nothing but Harmony messages. A call has the commentary channel, the recipient `functions.NAME` (in the role or the channel part of the header), an optional `<|constrain|>json` (or a bare `json`), one JSON object as the body, and ends with `<|call|>`. An analysis message (the model's reasoning) before it is dropped, and a commentary message with no recipient (a preamble) is prose, so the reply stays text. A `final` message, another recipient such as `browser.search` or `python`, another constrain type, a body that is not a JSON object, or a missing `<|call|>` leaves the reply as text.
- For `mistral`, the reply is nothing but one layout: `[TOOL_CALLS]` followed by a JSON array of objects with exactly `name`, `arguments` (an object) and an optional string `id` (Mistral 7B v0.3 and similar), or one or more `[TOOL_CALLS]NAME[ARGS]{...}` calls, with an optional `[CALL_ID]id` after the name (Mistral Small, Devstral, Magistral). Mixing the layouts, prose around the calls, or any bad call leaves the reply as text.
- For `dsml`, the reply is nothing but one `<｜DSML｜function_calls>` (V3.2) or `<｜DSML｜tool_calls>` (V4) block of invokes laid out as DeepSeek's reference parser requires, with the closing tag of the same name. A `string="true"` parameter is the text as written; a `string="false"` parameter must be JSON. A repeated or undeclared parameter, a missing close tag, or prose before the block leaves the reply as text (DeepSeek's reference parser tolerates prose before the block; this one does not, so that a quoted example is never run). DeepSeek V3.2 on Bedrock leaves an unclosed `<｜DSML｜function_calls` at the end of its text before a structured call; that fragment is never a call and is dropped from the visible text, as before.
- For `deepseek-v31`, the reply is nothing but one `<｜tool▁calls▁begin｜>` block of `<｜tool▁call▁begin｜>NAME<｜tool▁sep｜>{JSON}<｜tool▁call▁end｜>` calls and the end token. R1 and V3-0324 write a different layout, recovered by `deepseek-r1`.
- For `deepseek-r1`, the reply is nothing but one `<｜tool▁calls▁begin｜>` block of `<｜tool▁call▁begin｜>function<｜tool▁sep｜>NAME`, a newline, a `json` code fence holding one JSON object, a newline and the closing fence, then `<｜tool▁call▁end｜>`, ending with `<｜tool▁calls▁end｜>` (an end-of-sentence token after it is allowed). This is the layout the R1 and V3-0324 chat templates write for a call in the history and that vLLM's `tool_chat_template_deepseekr1.jinja` asks R1 to write; the original R1 was not trained for tools, so a model that writes something else is simply left alone.
- The `harmony`, `mistral`, `dsml` and `deepseek-v31` parsers were built from the vendors' chat templates, encoders and reference tokenizer code (named in each source file), and checked on synthesised fixtures; only the DeepSeek V3.2 fragment above was seen live. gpt-oss, Mistral and DeepSeek V3.2 return structured calls on Bedrock Converse today, so these parsers matter for a self-hosted server (vLLM, llama.cpp, Ollama, LM Studio) that returns the raw tokens in the reply. Recovery stays off unless you ask for it.

Anything else stays text, exactly as the model wrote it. While a reply streams, text that might be the start of a call is held back until the reply ends, so a recovered call never shows as text first; with recovery on, replies from a matching model can appear later than without it.
- For the families below, the reply is nothing but calls in the family's own markers (an opening think block in the family's own tags is kept as text). They share one reader, so what they refuse is the same: prose before or after the calls, a fenced example, a tool that was not offered, a body that is not exactly the family's grammar, a missing close marker. When a value contains the close marker itself, the reader tries each later close marker until the call and the rest of the reply both parse. Every form was built from the model's own chat template, the vendor's documentation or the vendor's own parser, read on 2026-11-10; no live reply of any of them was captured, so treat them all as untested against real replies.
  - `granite-tokens`: `<|tool_call|>` and then a JSON array of objects with exactly the keys `name` and `arguments` (an object).
  - `lfm-tokens`: `<|tool_call_start|>`, a non-empty Python list of calls with keyword arguments, `<|tool_call_end|>`. Values are Python literals, as for `pythonic`. LFM's optional JSON mode is not recovered.
  - `hy3-tags`: one `<tool_calls:opensource>` block of one or more `<tool_call:opensource>NAME<tool_sep:opensource>` calls whose arguments are `<arg_key:opensource>` / `<arg_value:opensource>` pairs. A value is a string unless the schema declares another type, in which case it must be JSON of that type, as for `glm-xml`.
  - `solar-tokens`: one or more `<|tool_call:begin|>ID<|tool_call:name|>NAME<|tool_call:args|>{JSON object}<|tool_call:end|>` blocks, the ID being ten lowercase letters or digits, with an optional `<|tool_calls|>` before and `<|calls|>` after.
  - `longcat-json`: one or more `<longcat_tool_call>` blocks, each one JSON object with exactly `name` and `arguments` (an object, not a string).
  - `olmo-function-calls`: one `<function_calls>` block of calls with keyword arguments, one per line or separated by whitespace. Values are JSON or Python literals.
  - `seed-xml`: one or more `<seed:tool_call>` blocks, each exactly one `<function=NAME><parameter=KEY>value</parameter></function>`, read as for `qwen-xml`.
  - `cohere-action`: one `<|START_ACTION|>` block holding a non-empty JSON array of objects with `tool_name`, `parameters` (an object) and optionally a string `tool_call_id`. Cohere's Hub repositories are gated, so this form comes from Cohere's public documentation (`docs.cohere.com/docs/command-a-hf`). Command R and R+ of 2024 write a different, fenced form and are not covered.

Anything else stays text, exactly as the model wrote it. While a reply streams, text that might be the start of a call is held back until the reply ends, so a recovered call never shows as text first; with recovery on, replies from a matching model can appear later than without it. While a reply is held, the chat shows "Reading the model's reply" where it would show "Generating", and the CLI spinner says "Reading the model's reply..."; the line goes away as soon as the held text has been shown or turned into a call. Nothing changes when recovery is off.

A recovered call goes through the same tool permissions as any other call.

## Model presets

Picking a model does not need `toolDialect` set by hand. A table of model families (`core/util/toolDialectPresets.ts`) records, for each, whether tools work on Bedrock, what the family writes when nothing parses its calls, which `toolDialect` recovers it, and the vLLM parser to use when you self-host it (only where one was verified). The preset does three things and no more:

- It switches tools on for Bedrock families a live run showed to return structured calls: Kimi, GLM, MiniMax and Nemotron 3 (Devstral and Mistral were already on).
- It switches tools on for Llama 3.x only when the model's `toolDialect` is `llama-json`. Llama 3.3 returned its calls as JSON text on every prompt, so tools without recovery would print raw JSON into the chat.
- It adds a line under the tool-call result of the add-model Test connection, such as `GLM-4.7: text dialect glm-xml (recoverable with toolDialect: glm-xml)`.

The preset never turns recovery on. To recover a family's text calls, set `toolDialect` as above; an explicit value always beats the preset.

Nemotron 3 (Super, Nano) writes the same markup as Qwen3-Coder, and NVIDIA's model cards use vLLM's `qwen3_coder` parser for it. Nemotron-H and Llama-Nemotron write `<TOOLCALL>[{"name": ..., "arguments": ...}]</TOOLCALL>` instead; set `toolDialect: toolcall-json` to recover it (the preset does not set it for you).

Phi-4-mini and Falcon-H1 have no recovery. Phi-4-mini's card and template do not say what its calls look like (the tokens `<|tool_call|>` and `<|/tool_call|>` exist, and vLLM's parser reads a different form for a different template), and Falcon-H1's template shows a single-quoted dictionary whose real output is not documented.
