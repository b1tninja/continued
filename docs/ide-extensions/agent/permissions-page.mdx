---
title: "Permissions page"
---

**Settings, Permissions** shows every permission rule in effect, where it came from, whether it is being obeyed, and lets you try a call against them. It answers "why did this ask?" and "which rule refused that?" without reading the config files. You can also add, change and remove your own rules here, and adopt a rule that came from elsewhere.

## Words used here

One word for each idea, in the page, the toolbar, `/policy` in the terminal agent and these docs. No stored key changed: the files keep the names on the right.

| Word           | It means                                                                                                                                                                                     | Stored as                                              |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| Area           | One of the five things the agent can do: Context use, Tool use, File edits, Plan edits, Questions                                                                                            | `context`, `tools`, `edits`, `plan`, `questions`       |
| Level          | How far one area is trusted, from Manual (you decide everything) through Cautious, Automatic and Permissive to YOLO (nothing asks; IDGAF on Plan edits and Questions). Each area has its own | `levels.<area>`                                        |
| Preset         | A named bundle that sets all five levels at once: Careful, Accept edits, Hands off, Reviewer, YOLO. Custom is any set of levels that matches no preset                                       | the five levels; the preset is worked out, never saved |
| Rule           | A line `toolName(pattern)` that gives a call one decision. Yours live in `config.yaml`; others come from elsewhere                                                                           | `toolPermissions`                                      |
| Never          | A rule that refuses the call                                                                                                                                                                 | `deny`                                                 |
| Ask            | A rule that stops and asks you                                                                                                                                                               | `ask`                                                  |
| Always         | A rule that lets the call run without asking                                                                                                                                                 | `allow`                                                |
| Built-in rule  | A protection that ships with the product, listed per area with its on or off state. It cannot be edited here                                                                                 | `builtin`                                              |
| Always-on rule | A Never rule in `permissions.yaml` that binds at every level, YOLO included. Locked on this page                                                                                             | `floor`                                                |
| Lock           | Something no rule can change: always-on rules, protected paths, your policy files                                                                                                            |                                                        |

Each level and each preset has a glyph and a tone on the toolbar chips and in the overview card. Levels: Manual a raised hand, Cautious a shield, Automatic sparkles, Permissive an open lock, YOLO a bolt, tinted green, green, blue, amber and red. Presets: Careful a shield, Accept edits a check badge, Hands off a fast-forward, Reviewer sparkles, YOLO a bolt, Custom sliders. A preset takes the tone of its loosest level other than Context use; Custom is neutral unless an area is at YOLO. The glyph and the colour never carry the meaning alone: every chip has its text.

A level and a preset are different ideas: "Cautious" is a level, "Careful" is a preset. The Careful preset is the default set: Permissive for Context use, Manual for File edits and Cautious for the other three.

## Five areas

The page has one tab for each policy area. Each tab shows the area's level (change it in **Settings, Tools** or the toolbar), the built-in protections that apply to it, and its rules.

| Tab         | Rules that appear here                                                                                                 |
| ----------- | ---------------------------------------------------------------------------------------------------------------------- |
| Context use | `readFile`, `listDirectory`, `grepSearch`, `globSearch`                                                                |
| Tool use    | `runTerminalCommand`, `fetchUrl`, `searchWeb`, every `mcp__server__tool`, and any tool name this version does not know |
| File edits  | `writeFile`                                                                                                            |
| Plan edits  | none: a level, the number of new to-dos a re-plan may add, and the check-keeping switch                                |
| Questions   | none: a level and the two lists of question types you or the agent decide                                              |

The tool name in a rule decides the tab. A terminal command rule is listed under Tool use, but a command the parser can show only reads is Context use for that one call, so the page says the area is decided per command. Rules for tools that only touch the session (the task list, Loop's tools) and rules that cannot be read are listed at the bottom under "Rules with no area".

Rules are shown grouped as Never, Ask and Always (the files keep the names `deny`, `ask` and `allow`). The order does not matter, and there is no way to reorder them: a call is weighed by decision (always-on rules, then Never rules, then protected paths, then Ask rules, then Always rules, then the level), never by where a rule sits in a list.

## Where a rule came from

| Badge     | Source                                                                                                                                                                                        |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| You       | the `toolPermissions` of your own `config.yaml`                                                                                                                                               |
| CLI file  | the `allow`, `ask` and `exclude` lists in `permissions.yaml`, written in the CLI's dialect (`Bash(npm test)`). The CLI weighs them first, and the page shows the config.yaml form beside them |
| Always on | the `floor:` rules in `permissions.yaml`. They bind at every level, YOLO included, and are locked here                                                                                        |
| Assistant | a hub or assistant configuration                                                                                                                                                              |
| Workspace | a file that came with the folder you opened                                                                                                                                                   |
| Built-in  | a built-in rule that ships with the product, listed per area with its on or off state                                                                                                         |

A rule that is **Ignored** is struck through with the reason: an `allow` rule that came with the workspace is ignored (a repository can add deny and ask rules, not allow rules), allow rules are not consulted while an area is Manual (file edits excepted), and every rule but the always-on rules is ignored while an area is at YOLO. A rule the page can warn about says so: a pattern after an MCP tool name never matches, and an allow rule written with `host:`, `net:` or `effect:` never allows anything.

## Edit your rules

Each area with rules has **Add a rule**, and your own rules have **Change** and **Remove**. Rules are saved to the `toolPermissions` of your own `config.yaml`, with its comments kept. Only that dialect is written: rules in the CLI's `Bash(...)` form in `permissions.yaml` are still read and shown, never written, and say so.

Every change is checked by the same code before anything is written, and the form shows the result as you type:

- the rule must be readable (`toolName(pattern)` or a bare tool name, no control or invisible characters)
- warnings: a rule you already have, an Always rule that a Never or Ask rule covers (it can never take effect, because Never beats Ask beats Always whatever the order), a more specific Never that takes a part out of an Always, a new Never that makes an Always of yours dead
- what a sample call gets now and with the rule (type your own under **Try a call**, or one is made from the pattern)
- the lines of `config.yaml` that would change

Nothing is written until you press **Save**. A change that loosens (a new Always rule, a removed Never or Ask rule, a rule moved to a looser list, an undo that restores less) also waits for your editor's own confirmation dialog, described below. If the file cannot be written, or was changed by someone else since the page read it, you are told and nothing changes. After a save, **Undo last change** puts the file back as it was, as long as it is unchanged since; if you edited it in between, it is left alone and you are told.

If `config.yaml` cannot be read (a syntax error, or `toolPermissions` of the wrong shape) the page shows the reason, says your rules cannot be shown, and turns editing off. It never shows a broken file as "no rules".

### Friction

An Always rule that matches everything or a broad wildcard needs a typed confirmation: you type `allow everything` before Save turns on, and the form says plainly what the rule would allow. That covers a bare tool name (`runTerminalCommand`), a pattern of only `*`, a command rule whose first word is a wildcard or an interpreter that runs whatever follows (`bash*`, `sudo*`, `python*`), an MCP rule for every server, a fetch rule for every host, and a path rule that covers `/`, your home folder or a credentials folder such as `~/.ssh`. The typed phrase is checked before the editor's dialog opens.

### Confirmation in your editor

A change that loosens is confirmed in a dialog the editor opens itself (a modal warning in VS Code, a notification with an Allow action in other IDEs), not by a checkbox in the page, because text in the page can be made to send a click. The page says "Your editor will ask you to confirm before it is saved" and then "Waiting for your answer in the window your editor opened". If you decline, close the dialog, it times out, or the host has no dialog, nothing is written. In IntelliJ the notification has no modal form and an unanswered one after 15 seconds counts as no. A change that only tightens, and every preview, never asks. The **Always allow** button on an approval prompt goes through the same path, and the audit record says the change was confirmed natively.

### Refusals

An Always rule is refused, and nothing is written, when an always-on rule or a built-in rule already holds everything it would allow, or when its own sample call would still be held by a protected path, an always-on rule or a built-in rule. The result shows the verdict that held the call.

### The rule as a command

The form shows the rule as `continuous permissions add always '<rule>'` with a **Copy** button. Copy does not run it. Pasting that command, or a `NEVER  rule` line from `continuous audit suggest`, into the Rule field sets the list and the rule, and the change goes through the same preview, confirmation and audit record. Flags in pasted text are refused.

What no rule can change is shown under **Locks**: always-on rules, protected paths (credentials always ask), and your policy files (`config.yaml`, `permissions.yaml` and the files that change what runs later), which the agent cannot write without asking you. The page's write is a message from the page to the app, not a tool, so the model cannot reach it.

### Rules from elsewhere: Adopt

Only your own `config.yaml` can add an Always rule. An Always rule that came with the workspace or an assistant is shown as ignored, with **Adopt**. Adopt first shows what the rule changes (a sample call, now and after), then copies the rule into your own `config.yaml`; that is the only way such a rule takes effect.

### The audit trail

Every add, change, remove, adopt and undo is written to the audit trail as a `policy` record: where it came from (`permissions-page` or `cli`), what it did, the rule with its arguments masked like a command's, whether it loosens anything, how it was confirmed, and a hash of the file before and after. Secrets are masked and the file's text is never stored.

## Try a call

Each of Context use, Tool use and File edits has a **Try a call** box. Choose what to try (a command, a file, a URL, an MCP tool), type it, pick a mode (Agent, Plan or Chat) and press **Test**. The result shows:

- the decision: runs, asks or refused, and the sentence the agent would be given, naming the file the matching rule came from
- every rule that matches, with its source, and the one that decided
- a step-by-step explanation: the command check, the built-in rule check, always-on rules, Never rules, protected paths, Ask rules, Always rules, the area's level, and whether the reviewer would be consulted
- command-check findings, and whether a tool result with the text you give would be marked by the injection notice

The test runs the same check the agent uses. Nothing is run, written or sent, and no model is asked: when the call would reach the reviewer model, the result says "would ask the reviewer".

## While it loads, and when it fails

The page shows grey placeholders while it reads your rules. If that takes more than eight seconds it says so and offers **Try again**. If the read fails, it says the rules could not be read, names `config.yaml` and `permissions.yaml`, and offers **Retry**; it never shows a failed read as "no rules". An area with no rules says to press **Add a rule**.

## First-run notices

The first time you open the page, a short card explains the five areas, the five levels and the presets, using the same glyph and colour as the toolbar chips. Press **Got it** and it does not come back: the choice is saved as `permissionsIntroDismissed` in your own settings.

An empty chat shows the same tip as one dismissible line: "New here? Each area has a level and a preset sets them all; Always on rules apply first. Open Permissions". It shares `permissionsIntroDismissed` with the card, so dismissing either hides both.

The interactive terminal agent shows one line in its header, once per user: "Permissions: Careful preset. Change it with /policy (presets, or area=level). Shown once." It names "a custom mix" when the levels match no preset. It never shows with `-p`, in `serve` or without a terminal, and its flag (`cliFirstRunBannerShown`) lives in the global context file, separate from the editor's.

## From the terminal agent

```text
continuous permissions list [--area context|tools|edits|plan|questions] [--json]
continuous permissions test <tool> <arg...> [--mode agent|plan|chat] [--level tools=permissive] [--json]
continuous permissions add <never|ask|always> '<rule>' [--yes-allow-everything] [--dry-run] [--probe <call>]
continuous permissions remove '<rule>' [--decision never|ask|always] [--yes]
continuous permissions adopt '<rule>' --from <file> [--yes-allow-everything] [--dry-run]
```

`list` prints the same data as the page. `test` takes a tool (`runTerminalCommand` or `Bash`, `readFile`, `writeFile`, `listDirectory`, `fetchUrl`, `grepSearch`, `searchWeb`, or `mcp__server__tool`) and the call's argument, for example `continuous permissions test Bash git push origin main`. `--level area=level` tries another level for one area and may be repeated. The command reads your `config.yaml` and `permissions.yaml` and does not load an assistant, so rules that come from an assistant are not listed by the terminal command.

`add`, `remove` and `adopt` change your own `config.yaml` with the same checks and friction as the page, and write the same audit record (source `cli`). They exit 0 when the change was made (or previewed with `--dry-run`), 2 when a confirmation is missing and 1 on any refusal: a rule that cannot be read, an Always rule that is already held (see Refusals), a file that cannot be read or written, or a rule that is not there. A change that loosens needs `--yes` (removing a Never or Ask rule, or adding an Always rule); a broad Always rule needs `--yes-allow-everything`. There is no editor dialog in the terminal: the flag is the confirmation. `adopt` reads the rule from the workspace or assistant file you name with `--from`, shows what it changes, and copies it.
