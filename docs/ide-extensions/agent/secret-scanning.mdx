---
title: "Secret Scanning"
---

Continuous ships one rule set for finding secrets in text, and a command that runs it over files. It exists so API keys do not end up in captures, fixtures, datasets and result files, and later so they do not leave in a prompt. Today the file scanner, the scan of the product's own stores and scrub-on-write for files the product writes are wired in; nothing is scanned or changed in a chat session yet.

```bash
continuous secrets scan captures/ --profile at-rest
```

Output names the rule, file, line, column and a short fingerprint. It never prints the secret or the line it is on. Exit code 0 means clean, 3 means findings, 2 means a usage error.

## Profiles

One rule set, two profiles.

| Profile | For | Runs |
| --- | --- | --- |
| `at-rest` (default) | captures, fixtures, datasets, result files, logs | every rule, including `NAME=value`, URL passwords, bearer headers and entropy checks. Recall first: over-reporting a local file costs a review |
| `outbound` | prompts and tool results on their way to a provider (not wired yet) | only high-confidence provider key shapes, private key blocks, passwords in URLs and known values. No entropy rule. Precision first: a false alarm teaches people to switch the feature off |

## Rules

Each rule has an id, a description and a confidence (`high`, `medium`, `low`). The provider rules cover AWS access key ids and secret keys, GitHub tokens, Anthropic, OpenAI and OpenRouter keys, Google API keys, Slack tokens and webhooks, Stripe, npm, PyPI, Hugging Face, GitLab, DigitalOcean, Shopify, SendGrid and Twilio keys, PEM private keys and JSON Web Tokens. The `url-credential` rule finds `scheme://user:password@host` for database, cache, queue, mail, SSH and HTTP schemes when the password passes shape checks (below). The contextual rules cover short passwords in any URL, bearer tokens, `NAME=value` assignments with a secret-like name, and quoted high-entropy strings next to such a name.

Most provider patterns are ported from the default rules of [gitleaks](https://github.com/gitleaks/gitleaks) (MIT licence); the licence is in `NOTICE`. A few rules are our own, and a few ported ones are loosened for recall. The `origin` field on each rule says which.

**Known values.** The strongest detector is one a general tool cannot have: it knows this machine's own secrets. The scan matches, by exact value, the environment variables whose names `scrubEnvironment` treats as secret, and the secrets in `~/.aws/credentials`, `~/.npmrc`, `~/.netrc`, `~/.git-credentials`, `~/.docker/config.json`, `~/.config/gh/hosts.yml`, `~/.continue/.env` and the private keys in `~/.ssh`. Values are held as hashes in memory, never logged, stored or printed. Turn it off with `--no-known`.

## Checking a value's shape

A `NAME=value` rule guesses from the name, so the value must also look generated. `env-secret-assignment` rejects a value that is:

- code or markup: it contains `( ) [ ] { } < > \ | ;` or a backtick, as in `x = foo(bar)`
- a reference to another variable: `$VAR`, `${VAR}`, `$(cmd)`, `%VAR%`, with or without a backslash before it
- grep or stack-trace output (`file.ts:99:`), a dotted identifier (`config.secrets.name`, `a?.b`), a camelCase or snake_case word, a slug, a version (`2.14.0-rc1`) or a UUID
- a path (has a file extension, starts with `/`, `./`, `~` or a drive letter, or is slash-separated words of one case, such as `vendor/model:v2`) or a URL (credentials in a URL belong to `url-credential`)
- a digest of 32, 40, 64 or 128 hex digits next to a name such as `cache`, `checksum`, `sha`, `commit` or `integrity`
- short or plain: next to `password`, `secret` or `token` it needs 8 characters and entropy 3, and either 16 characters or three kinds of character (lower case, upper case, digit, other). Next to any other name (`key`, `credential`, `auth`) it needs 16 characters and entropy 3.5

The value ends at an `&`, so `?token=abc...&format=json` reports only the token. In files under `test/`, `tests/`, `__tests__/`, `fixtures/`, `mocks/`, `examples/` and `samples/`, in `*.test.*`, `*.spec.*` and `*.example` files, the `NAME=value` and quoted-string rules do not run; every provider rule, `url-credential` and known values still do. These tests are also applied to `bearer-token` and `generic-secret` (no paths).

`url-credential` needs a password of 8 or more characters that is not a placeholder word (`password`, `changeme`, `your...`), a variable reference, a format template (`%s`), or a run of one character, with at least two kinds of character; a host such as `host`, `server`, `example` or `your-...` is skipped.

## Actions: redact and warn

Each finding carries an `action`. `redact` means the value may be replaced by its placeholder; `warn` means report it and leave the text unchanged. Under the `outbound` profile `gcp-api-key` is `warn`: Google browser, Maps and Firebase keys are public by design, and most of the values found in a real corpus were test data. `redact()` leaves warn findings in the text. Under `at-rest` every finding is `redact`.

## Private keys and certificates

`private-key` is high confidence and needs the words `PRIVATE KEY` in the header (`PRIVATE KEY`, `RSA`, `EC`, `OPENSSH`, `ENCRYPTED` and so on) and a base64 body. Public keys, certificates, certificate requests and the bare header sentence are not secrets and are not reported; a test in the suite pins this.

## Allowing a value

- Example and placeholder values are skipped: `AKIAIOSFODNN7EXAMPLE`, `xxxx`, `${VAR}`, `{{ var }}`, `<token>`, `your-api-key`.
- A line containing `secretscan:allow` is skipped.
- `--allow <fingerprint>` skips one value. Give `--salt` too, so fingerprints are the same from run to run.

## False-positive policy

- Warn first. A finding names the kind and where it is, never the value.
- Redact only when opted in. A redacted value becomes a stable placeholder such as `[REDACTED:aws-access-key:1a2b]`; the same value always gets the same placeholder, so a model can refer to it.
- Outbound never uses an entropy rule, a model or a remote service.
- Measured on this repository's own tracked files (939,000 lines), the at-rest scan went from 88 findings (49 distinct values) to 10 (9 values), none of them in `env-secret-assignment`; the rest are test fixtures. Over real transcripts, 71 percent of distinct `env-secret-assignment` values had been false.
- The budget is measured by the test suite: zero outbound findings on benign text and on this repository's own source and docs, and at most 2 at-rest findings per 1000 lines.

## Secrets already on disk

```bash
continuous secrets scan --history
```

`--history` scans the product's own stores under the global folder (`sessions`, `dev_data` and `logs`) with the `at-rest` profile, at most 64 MB per file, and ends with a summary of findings by rule and guidance: a finding means a credential was written to a file on this disk, so rotate it at the issuer and then delete the file. Add `--include-claude-code` to also read `~/.claude/projects` transcripts; those files are opened read-only and never changed. Files readable by other users are listed (on POSIX; a Windows run reports none).

## Scrub on write

Files the product writes are scrubbed with the `at-rest` rules before they reach the disk, so a value the rule set knows is replaced by `[REDACTED:<kind>:xxxx]`: the `dev_data` event files, the core log (`core.log`), the terminal agent's log, and request dumps from `CONTINUE_DUMP_REQUESTS`. JSON lines stay valid. It is best effort: a credential in a shape no rule knows passes through, a secret split across two writes is not seen, and it is not applied to a file that must read back exactly, such as a session needed for resume. Existing files are not rewritten; use `continuous secrets scan --history` to find them.

## Clean the stores

```bash
continuous clean [--older-than <age>] [--yes] [--json]
```

Deletes the product's own persisted files older than an age, and is a dry run unless you pass `--yes`. It touches only `sessions`, `dev_data` and `logs` under the global folder, prints counts, sizes and paths and never contents, and never runs by itself. Without `--older-than` each store has its own age: sessions 30 days, logs 14, `dev_data` 90 (inside kept files, old lines are dropped). `--older-than` takes `30d`, `12h` or `2w` and replaces all three. `input_history.json` and `file://` data destinations are not touched. Deleting is not secure erasure: SSDs, journals, snapshots and backups can keep the bytes, so rotate a credential that was in a file you removed. Exit code 0 means done or previewed, 1 means some deletions failed and 2 a bad age.

## Using it from a pre-commit hook

In another repository, point a hook at a checkout of this one:

```bash
#!/bin/sh
# .git/hooks/pre-commit
CONTINUOUS=/path/to/continuous
cd "$CONTINUOUS/extensions/cli" && \
  npx tsx --tsconfig scripts/tsconfig.json scripts/secretScan.ts \
  --profile at-rest --salt my-repo --staged
```

Or, with the CLI installed: `continuous secrets scan --staged`. In CI, run `continuous secrets scan . --profile at-rest` and let exit code 3 fail the job. This repository does not run it in its own hooks or CI yet.
