```bash
cd my-project
continuous
```

`continuous` with no arguments starts an interactive session in the current folder. `cn` is the same command. This page walks through the first one: the model, a message, an approval, and how to come back to a session later.

## Before the first message: a model

The terminal agent reads the same `~/.continuous/config.yaml` as the VS Code extension. If the extension is already set up, its models are there.

The first interactive start asks for an Anthropic API key:

```text
To get started, enter your Anthropic API key.
```

- A key that starts with `sk-ant-` is written to `~/.continuous/config.yaml` as the `apiKey` of two Anthropic chat models, in plain text. No request is sent to check it.
- Anything else ends the program with `API key must start with "sk-ant-"`, and the next start asks again.
- The question is asked until a key has been entered once, even when `config.yaml` already has working models from another provider.

To use another provider, or to keep the key out of `config.yaml`, write the config yourself and pass it with `--config`. The question is skipped whenever `--config` is given:

```bash
continuous --config ~/.continuous/config.yaml
```

[Model setup](/customize/model-setup) covers providers and where keys are kept. To check an endpoint before starting a session:

```bash
continuous test-connection --provider ollama
```

It lists the models the endpoint offers; with `--model <id>` it also sends one tool-call probe to that model.

When input is not a terminal (a pipe, a CI job) nothing is asked. If `ANTHROPIC_API_KEY` is set in that case, the key is written into `config.yaml` and the run says `Using ANTHROPIC_API_KEY from environment`.

## Send a message

Type a request and press Enter. The input line takes three prefixes:

| Prefix | What it does                                                                |
| ------ | --------------------------------------------------------------------------- |
| `@`    | Search for a file and attach it as context                                  |
| `/`    | Run a [slash command](/cli/slash-commands)                                  |
| `!`    | Run the rest of the line as a shell command yourself, without asking the model |

`/help` prints the keys. The ones worth knowing on day one:

| Key         | What it does                                      |
| ----------- | ------------------------------------------------- |
| Enter       | Send the message                                  |
| Shift+Enter | New line (or end a line with `\`)                 |
| Up, Down    | Move through suggestions or your input history    |
| Tab         | Complete the selected command or file             |
| Esc         | Cancel the reply in progress, or close suggestions |
| Shift+Tab   | Cycle the mode: normal, plan, loop, auto          |
| Ctrl+C      | Clear the input                                   |
| Ctrl+D      | Exit                                              |

## Approve a tool call

In an interactive session the terminal agent reads, lists and searches files without asking. An edit (`Edit`, `MultiEdit`, `Write`), a shell command (`Bash`) and any MCP tool stop and ask first. The prompt has three choices:

- **Continue** runs this one call. `y` does the same.
- **Continue + always allow** runs it and saves a rule to the `allow:` list in `~/.continuous/permissions.yaml`. For a shell command the rule is that exact command; for any other tool it is the tool's name, so "always allow" on one edit covers every later edit.
- **No, and tell Continue what to do differently** refuses the call and stops the reply so you can redirect. `n` does the same.

`/policy` shows how far each area is trusted. `/policy <preset>` changes it for this session and saves it for the next one, except IDGAF, which is never saved. The levels and presets are the ones on the [Permissions page](/ide-extensions/agent/permissions-page); the file is described in the [`permissions.yaml` reference](/reference/permissions-yaml).

## Modes

Shift+Tab moves through four entries. The mode indicator shows the current one.

| Entry  | What it is                                                                                                                                            | Flag at start |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| normal | The default: reads run, edits and commands ask                                                                                                        |               |
| plan   | Read-only. The edit tools are not offered; shell commands and MCP tools ask. The agent writes a plan file and offers **Build**, **Build in a loop** or **Keep planning** | `--readonly`  |
| loop   | Plan mode for the first message, then the plan is built in a loop without the Build question. See [Loop mode](/ide-extensions/agent/loop-mode)        |               |
| auto   | Everything runs without asking. This is the IDGAF level on Context use, Tool use and File edits                                                       | `--auto`      |

`--readonly` and `--auto` cannot be combined.

## One-shot runs

`-p` (`--print`) sends one prompt, prints the answer and exits. This is a headless run: there is no interface and nobody to ask.

```bash
continuous -p "Summarise what changed in the last commit"
git diff | continuous -p "Review this diff for mistakes"
```

Piped input is placed before the prompt. `--format json` prints JSON instead of text, and `--silent` strips `<think>` blocks and extra whitespace; both work only with `-p`.

Because nobody can answer a question, a headless run uses different defaults: shell commands and MCP tools are allowed, where an interactive session would ask. Read [what a headless run allows](/reference#toolpermissions) before running one on a machine that matters, and give it [run limits](/cli/run-limits).

## Come back to a session

Sessions are saved as you go, under `~/.continuous/sessions`.

| Command                      | What it does                                             |
| ---------------------------- | -------------------------------------------------------- |
| `continuous --resume`        | Continue the most recent session                         |
| `continuous ls`              | List recent sessions and pick one to resume              |
| `/resume`                    | The same list, from inside a session                     |
| `continuous --fork <id>`     | Start a new session from a copy of an existing one (history, mode, model, task plan) |
| `/fork`                      | Fork this session and continue in the copy; the original is unchanged |

## When something is wrong

`continuous --verbose` turns on debug logging and prints the log file's path and a `grep` line that filters this run. The log is `~/.continuous/logs/cn.log`. [Getting help](/reference/storage-and-reset#getting-help) lists the other places to look.
