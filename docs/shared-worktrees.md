# Shared worktrees: research notes and guards

Fetched 2026-11-10. Written for the incidents of the week of 2026-11-02: one agent popped another's
stash, lint-staged's backup stash polluted the shared list and led agents to skip hooks, sessions
restarted and lost uncommitted work, and PRs that were green alone broke `main` in combination.

## Findings

| Is `refs/stash` per worktree?         | No. "All pseudo refs are per-worktree and all refs starting with `refs/` are shared", except `refs/bisect`, `refs/worktree`, `refs/rewritten`. `refs/stash` is therefore shared. | Can the stash be made per worktree?   | Not through config. `extensions.worktreeConfig` only makes `config` per worktree (`git config --worktree`, file `config.worktree`); it does not move refs. Older git refuses to open such a repository.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | <https://git-scm.com/docs/git-worktree>                                                                                                                                                                                                          |
| Is there a stash hook?                | No: the 28 hooks of githooks(5) include none for stash.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | <https://git-scm.com/docs/githooks>                                                                                                                                                                                                              |

Tested here (git 2.54.0, Windows): `git stash` and `git stash store` both die with "in 'prepared' phase, update aborted by the reference-transaction hook" and the working tree is left untouched. `scripts/agents/stash-guard.sh`.                                                                                                                                                                                                                                                                                                                                                                                               | <https://git-scm.com/docs/githooks>, `scripts/agents/stash-guard.test.mjs`                                                                                                                                                                       |
| lint-staged backup                    | Default: a backup stash is created before the tasks (`git stash create` + `git stash store`; the worktree is left as is) and dropped only after every step succeeded; on failure it is restored from it. `--no-stash` disables it and "leaves all modifications in the index when aborting"; it implies `--no-hide-partially-staged`. `--diff` implies `--no-stash`. `--diff-filter` defaults to `ACMR`. `--no-hide-partially-staged` makes the unstaged half of partially staged files be committed. Unstaged parts are kept in `.git/lint-staged_unstaged.patch`. The README does not discuss worktrees. Installed version here is 15.5.2 (`bin/lint-staged.js` shows `--no-stash` implies `hidePartiallyStaged: false`, but an explicit `--hide-partially-staged` wins: tested). | <https://github.com/lint-staged/lint-staged> (README), `node_modules/lint-staged/bin/lint-staged.js`                                                                                                                                             |
| husky v9 and worktrees                | The husky docs do not mention worktrees. By reading `husky/index.js` (9.1.7): `husky` runs `git config core.hooksPath .husky/_` (relative, in the shared config) and writes stubs into the git-ignored `.husky/_` for 14 hook names (not `reference-transaction`). Consequence: every worktree resolves `.husky/_` against its own top level, so a new worktree has no hooks until `husky` runs in it, and the guard must be copied in per worktree. `HUSKY=0` skips install and run.                                                                                                                                                                                                                                                                                               | <https://typicode.github.io/husky/how-to.html>, `node_modules/husky/index.js`                                                                                                                                                                    |
| `git merge-tree --write-tree`         | Git 2.38+. Merges two commits without commits, working tree or index; exit 0 clean, 1 conflicts, other = failure. `--name-only` lists conflicted paths, `--no-messages` drops prose, `--quiet` only the status. Do not infer cleanliness from an empty file list: check the exit status. Used by `scripts/ci/combine.mjs`.                                                                                                                                                                                                                                                                                                                                                                                                                                                          | <https://git-scm.com/docs/git-merge-tree>                                                                                                                                                                                                        |
| Merge queue                           | Organisation-owned repositories only (public ones, or any plan on Enterprise Cloud); not for user-owned repositories. GitHub's own docs page fetched here does not state this; web sources dated 2023 to 2024 do, and `docs/ci-merge-gate.md` records `gh api repos/b1tninja/continuous` owner type `User`. Needs the `merge_group` trigger in CI and a branch protection rule without wildcards.                                                                                                                                                                                                                                                                                                                                                                                   | <https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue>, <https://github.blog/news-insights/product-news/github-merge-queue-is-generally-available/> |

The page ties rulesets to the Team and Enterprise plans for organisations and does not say whether user-owned repositories have them; `gh api repos/b1tninja/continuous/rulesets` returned an empty list (readable).                                                                                                                                                                                                                                                                                                                             | <https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets>                                                                                                                    |

## Agent status convention

An agent that works longer than a few minutes calls `scripts/agents/checkpoint.sh` after each
meaningful step and before anything risky (a rebase, a branch switch, a large generated change).
The branch on `origin` is then the status: `git log origin/<branch>` shows the last checkpoint and
a restarted agent resumes with `git fetch && git status` in its worktree, or re-creates the worktree
from `origin/<branch>`. Branch names say what the work is; the PR is opened early as a draft so
`merge-ready.mjs` can see it.

## Known limits

- `--no-stash` means no automatic rollback after a failed task. The index is only updated after all
  tasks succeed, so the cost is a working tree that prettier has already rewritten.
- lint-staged keeps `.git/lint-staged_unstaged.patch` in the shared git directory; two worktrees
  committing partially staged files at the same instant could collide on it. Not observed.
- The guard hook costs one process per ref update, including fetches and commits.
- `--combine` checks textual merges only. Semantic breakage (a test against a changed wrapper) still
  needs CI on the combination, which is what "Update branch" and `merge-gate` are for.
